Part 01

Computer Science: The Fan-Out Theorem & Storage Alignment

Why do foundational databases like PostgreSQL, MySQL (InnoDB), and SQLite rely on multi-way trees (specifically B-Trees and B+ Trees) rather than Red-Black or AVL trees?

The reason is hardware reality: The Memory Hierarchy and the Fan-Out Theorem. In computing systems, memory is not transferred in single bytes; hardware controllers transfer data in fixed-size blocks (typically a 64-byte CPU cache line, or a 4KB to 16KB virtual memory page / storage block).

The Fan-Out Theorem: Binary Trees (Fan-Out = 2) vs. Multi-Way B-Trees (Fan-Out = 100)

Evaluating pointer-dereference depth and cache-line efficiency across 10,000,000 records

1. Binary Tree (AVL / Red-Black) Fan-Out B = 2
Tree Height for 10M records:
h ≈ ⌈log₂ (10,000,000)⌉ = 24 pointer hops!

Every single node holds only 1 key and 2 child pointers (taking ~32 bytes). When loaded from memory or disk, it uses less than 1% of a 4KB memory page, wasting 99% of transferred bandwidth on empty padding. Traversal forces 24 disjoint random memory address dereferences!

2. Multi-Way B-Tree (Storage Aligned) Fan-Out B = 100
Tree Height for 10M records:
h ≈ ⌈log₁₀₀ (10,000,000)⌉ = 4 pointer hops!

Each node holds up to 99 sorted keys and 100 child pointers, packed contiguously into a single 4KB block. Finding an element takes only 3 to 4 node fetches. Once a node is brought into CPU cache, all 99 keys are searched using instantaneous binary search in L1 cache!

The Core Storage Principle:

By increasing the branching factor $B$, tree height shrinks drastically from $O(\log_2 n)$ to $O(\log_B n)$. In high-performance data systems, CPU computation inside a localized contiguous memory block is thousands of times cheaper than chasing pointers across disjoint random memory addresses.

Part 02

Under the Hood: B-Tree Invariants & The B+ Tree Extension

Invented by Rudolf Bayer and Edward M. McCreight at Boeing Labs in 1970, a B-Tree of Minimum Degree $t \ge 2$ satisfies the following strict mathematical invariants:

1. Node Key Bounds

Every node except the root contains at least $t - 1$ keys and at most $2t - 1$ keys. The root contains at least 1 key (unless the tree is empty).

2. Child Branching

If an internal node contains $k$ keys, it must have exactly $k + 1$ children. The keys act as partition separators between the subtrees.

3. Strict Leaf Balance

All leaf nodes reside at the exact same depth. A B-Tree grows upward from the root upon splitting, never downward at arbitrary branches.

Architectural Duality: Standard B-Tree vs. B+ Tree with Leaf Chaining
Standard B-Tree

Every node (internal nodes and leaves) stores both keys and data values.

Internal Node: [Key 50 + Data Payload 50]
Leaf: [20 + Data 20]
Leaf: [75 + Data 75]
  • Advantage: Point queries for keys located near the top return immediately without reaching leaves.
  • Disadvantage: Data payloads consume space inside internal nodes, reducing fan-out. Range queries require in-order traversal jumping up and down the tree.
B+ Tree (Database Standard)

Internal nodes store keys only (routing guide). All data values reside exclusively in leaves, linked in a chain!

Router Node (Keys Only): [ 50 ]
Leaf: [20:Data, 35:Data]
⇔
Leaf: [50:Data, 80:Data]
  • Advantage (Maximized Fan-Out): Internal nodes hold hundreds of keys, keeping tree height extremely flat ($h \le 3$).
  • Advantage (Linear Range Scans): Range queries ($v_1 \le x \le v_2$) binary search to the starting leaf once, then simply follow the leaf's horizontal next pointer without touching the tree!
Part 03

Algorithmic Mechanics: Proactive Top-Down Node Splitting

In classical tree algorithms, insertion descends to a leaf, adds the key, and if the leaf overflows, triggers a cascading sequence of parent splits propagating back up the tree.

In production systems, this bottom-up splitting introduces complex locking contention in multi-threaded databases. The standard production algorithm (formalized in Cormen, Leiserson, Rivest, and Stein • CLRS) is Proactive Top-Down Splitting:

The CLRS Single-Pass Invariant

Proactive Median Promotion ($t=2$ Example)

As the insertion algorithm descends the tree from the root, whenever it encounters a full node (holding $2t - 1$ keys), it splits that node immediately before descending into it!

// Splitting a full child node [10, 20, 30] with degree t = 2 (max keys = 3):
1. Identify the median key at index $t - 1 = 1$ → Key 20.
2. Promote median Key 20 up into the parent node.
3. Left keys [10] remain in the original child.
4. Right keys [30] are allocated into a new sibling child node.
5. Because the parent was guaranteed non-full during descent, the promotion never triggers an upstream cascade!

This guarantees that insertion completes in a single top-down pass without backtracking or recursive stack propagation. If the root is full, the root splits: a new root is created with 1 key, and the tree grows in height by 1 from the top!

Part 04

MemForge Milestone 09: In-Memory Multi-Way B-Tree Index Implementation

We now assemble Milestone 09 of MemForge. We implement src/memforge/index/btree.py: an in-memory Multi-Way B-Tree Secondary Range Index.

The B-Tree Index features:

  • Configurable minimum degree $t$ (e.g. $t=2$ for a 2-3-4 tree, or $t=3$ for max 5 keys per node).
  • Proactive Top-Down Node Splitting: Splits full nodes ($2t - 1$ keys) during descent, eliminating parent recursion cascades.
  • Multi-Value Duplicate Mapping: Each key maps to an array of associated record_ids.
  • Pruned Range Scans: Recursively prunes subtrees outside query boundaries to execute $[v_{\min}, v_{\max}]$ scans in $O(\log_t n + k)$ time.
  • In-order generator traversal yielding all indexed records in strictly ascending order.

1. Production B-Tree Engine: src/memforge/index/btree.py Multi-Way Storage Tree Implementation 
# ==============================================================================
# MemForge Index Engine - Multi-Way B-Tree Storage Range Index (Milestone 09)
# ==============================================================================

from bisect import bisect_left
from typing import Any, Iterator, List, Optional, Tuple


class BTreeNode:
    """Discrete B-Tree node storing up to (2t - 1) keys and (2t) child pointers."""
    def __init__(self, is_leaf: bool = True):
        self.is_leaf: bool = is_leaf
        # Contiguous list of sorted keys
        self.keys: List[Any] = []
        # Parallel list of record ID arrays (handles duplicate indexed keys)
        self.values: List[List[int]] = []
        # List of child node pointers (len(children) == len(keys) + 1 if not leaf)
        self.children: List["BTreeNode"] = []


class MemBTreeIndex:
    """
    PRODUCTION MULTI-WAY B-TREE SECONDARY INDEX:
    Implements CLRS proactive top-down node splitting with degree t >= 2.
    Guarantees strict O(log_t n) search and sub-millisecond range scanning.
    """
    def __init__(self, degree: int = 3):
        if degree < 2:
            raise ValueError("B-Tree minimum degree t must be >= 2.")
        self._t: int = degree  # Minimum degree
        self._root: BTreeNode = BTreeNode(is_leaf=True)
        self._total_entries: int = 0

    def __len__(self) -> int:
        """Returns total active record ID pointers indexed across all keys."""
        return self._total_entries

    def search(self, key: Any) -> List[int]:
        """Point lookup returning matching record IDs in O(log_t n) time."""
        return self._search_node(self._root, key)

    def _search_node(self, node: BTreeNode, key: Any) -> List[int]:
        # Use binary search inside the node's sorted key array
        i = bisect_left(node.keys, key)
        if i < len(node.keys) and node.keys[i] == key:
            return node.values[i].copy()

        if node.is_leaf:
            return []

        return self._search_node(node.children[i], key)

    def insert(self, key: Any, record_id: int) -> None:
        """
        PROACTIVE TOP-DOWN INSERTION:
        Splits full nodes during descent, eliminating upward cascading splits.
        """
        root = self._root
        # If root is completely full (2t - 1 keys), tree must grow in height by 1
        if len(root.keys) == (2 * self._t - 1):
            new_root = BTreeNode(is_leaf=False)
            new_root.children.append(root)
            self._split_child(new_root, 0, root)
            self._root = new_root
            self._insert_non_full(new_root, key, record_id)
        else:
            self._insert_non_full(root, key, record_id)

        self._total_entries += 1

    def _insert_non_full(self, node: BTreeNode, key: Any, record_id: int) -> None:
        i = bisect_left(node.keys, key)

        # Case 1: Key already exists in this node → append record_id
        if i < len(node.keys) and node.keys[i] == key:
            node.values[i].append(record_id)
            return

        # Case 2: Node is a leaf → insert key and value in-place
        if node.is_leaf:
            node.keys.insert(i, key)
            node.values.insert(i, [record_id])
            return

        # Case 3: Internal node → descend into child
        child = node.children[i]
        # Proactive Split Check: Split child if full before descending!
        if len(child.keys) == (2 * self._t - 1):
            self._split_child(node, i, child)
            # If key is greater than promoted median, descend into right sibling
            if key == node.keys[i]:
                node.values[i].append(record_id)
                return
            elif key > node.keys[i]:
                i += 1

        self._insert_non_full(node.children[i], key, record_id)

    def _split_child(self, parent: BTreeNode, index: int, child: BTreeNode) -> None:
        """
        Splits a full child node around its median key at index (t - 1).
        Promotes the median key up into parent node.
        """
        t = self._t
        median_idx = t - 1
        median_key = child.keys[median_idx]
        median_val = child.values[median_idx]

        # Allocate new right sibling node
        sibling = BTreeNode(is_leaf=child.is_leaf)

        # Transfer upper (t - 1) keys and values to sibling
        sibling.keys = child.keys[median_idx + 1 :]
        sibling.values = child.values[median_idx + 1 :]

        # Transfer upper t children to sibling if not leaf
        if not child.is_leaf:
            sibling.children = child.children[t:]
            child.children = child.children[:t]

        # Shrink original child to lower (t - 1) keys
        child.keys = child.keys[:median_idx]
        child.values = child.values[:median_idx]

        # Insert median key and sibling child into parent node
        parent.children.insert(index + 1, sibling)
        parent.keys.insert(index, median_key)
        parent.values.insert(index, median_val)

    def inorder_traversal(self) -> Iterator[Tuple[Any, List[int]]]:
        """Yields (key, record_ids) tuples in strictly ascending sorted order."""
        yield from self._inorder_recursive(self._root)

    def _inorder_recursive(self, node: BTreeNode) -> Iterator[Tuple[Any, List[int]]]:
        for i in range(len(node.keys)):
            if not node.is_leaf:
                yield from self._inorder_recursive(node.children[i])
            yield (node.keys[i], node.values[i])

        if not node.is_leaf:
            yield from self._inorder_recursive(node.children[len(node.keys)])

    def range_scan(self, min_val: Any, max_val: Any) -> List[int]:
        """
        PRUNED B-TREE RANGE SCAN [min_val, max_val]:
        Selectively descends only subtrees intersecting the interval.
        Complexity: O(log_t n + k) where k is matching records.
        """
        results: List[int] = []
        self._range_recursive(self._root, min_val, max_val, results)
        return results

    def _range_recursive(self, node: BTreeNode, min_val: Any, max_val: Any, out: List[int]) -> None:
        for i in range(len(node.keys)):
            key = node.keys[i]
            # Descend left child if min_val could reside in that subtree
            if not node.is_leaf and min_val <= key:
                self._range_recursive(node.children[i], min_val, max_val, out)

            # Capture matches within interval
            if min_val <= key <= max_val:
                out.extend(node.values[i])

            # Pruning: Stop searching this node if key exceeds max_val
            if key > max_val:
                return

        # Descend final right child if applicable
        if not node.is_leaf and node.keys[-1] <= max_val:
            self._range_recursive(node.children[len(node.keys)], min_val, max_val, out)

import pytest
from memforge.index.btree import MemBTreeIndex

class TestMemBTreeIndex:
    """Unit tests asserting B-Tree proactive splits, sorted invariants, and range scans."""

    def test_root_split_grows_tree_upward(self):
        # Minimum degree t = 2 (max keys = 2t - 1 = 3 keys per node)
        btree = MemBTreeIndex(degree=2)
        assert btree._root.is_leaf is True

        # Insert 3 keys -> fills the root node completely: [10, 20, 30]
        btree.insert(10, 1)
        btree.insert(20, 2)
        btree.insert(30, 3)
        assert btree._root.is_leaf is True
        assert btree._root.keys == [10, 20, 30]

        # 4th insert forces root split: Key 20 promotes to a NEW root!
        btree.insert(40, 4)
        assert btree._root.is_leaf is False
        assert btree._root.keys == [20]  # Median promoted
        assert len(btree._root.children) == 2
        assert btree._root.children[0].keys == [10]
        assert btree._root.children[1].keys == [30, 40]

    def test_adversarial_sorted_data_ingestion(self):
        # Ingest 100 strictly ascending sequential numbers into B-Tree (t = 3)
        btree = MemBTreeIndex(degree=3)
        for i in range(1, 101):
            btree.insert(i, record_id=i * 10)

        assert len(btree) == 100

        # Point search validation across extremes and interior
        assert btree.search(1) == [10]
        assert btree.search(50) == [500]
        assert btree.search(100) == [1000]
        assert btree.search(999) == []

    def test_duplicate_key_accumulation(self):
        btree = MemBTreeIndex(degree=2)
        btree.insert(25, 101)
        btree.insert(25, 102)
        btree.insert(25, 103)

        assert len(btree) == 3
        assert btree.search(25) == [101, 102, 103]

    def test_inorder_traversal_sorting_guarantee(self):
        btree = MemBTreeIndex(degree=2)
        raw_keys = [45, 12, 89, 3, 23, 77, 91, 14, 66]
        for k in raw_keys:
            btree.insert(k, record_id=k)

        sorted_output = [k for k, _ in btree.inorder_traversal()]
        assert sorted_output == [3, 12, 14, 23, 45, 66, 77, 89, 91]

    def test_pruned_range_scan_extraction(self):
        btree = MemBTreeIndex(degree=3)
        for i in range(10, 110, 10):  # 10, 20, ..., 100
            btree.insert(i, record_id=i // 10)

        # Range scan [25, 65] -> matches 30, 40, 50, 60
        results = btree.range_scan(min_val=25, max_val=65)
        assert results == [3, 4, 5, 6]
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Setting Degree t Too Small in Memory

Defaulting to degree = 2 (a 2-3-4 tree) for millions of in-memory objects.

Why this hurts performance: If $t=2$, nodes hold only 1 to 3 keys, creating excessive node allocations and null child pointers. In memory, degree should be tuned to cache-line width (e.g. $t = 16$ to $64$), packing 31 to 127 contiguous keys per node to exploit high CPU cache locality.

❌ Linear Scans Inside Nodes

Iterating via for key in node.keys: if key == target: ....

Why this degrades throughput: If a node stores 128 keys, a linear scan requires up to 128 comparisons per node. Because the keys inside every B-Tree node are strictly sorted, you should use bisect_left(node.keys, target) to locate child branches in only 7 operations ($O(\log k)$)!

❌ Neglecting Proactive Splitting

Implementing naive bottom-up insertion splitting.

Why this complicates concurrency: If a leaf split cascades upward to its parent, grandparent, and root, an engine must lock the entire tree path to prevent concurrent race conditions. Proactive top-down splitting guarantees that when you arrive at a leaf, its parent is guaranteed non-full, bounding mutations to localized subtrees.

❌ Using B-Trees When B+ Trees Are Needed

Choosing a standard B-Tree for a workload dominated by range scans (e.g. WHERE date BETWEEN x AND y).

Why this wastes CPU: Standard B-Trees must climb up and down parent pointers via in-order traversal to collect range matches. B+ Trees link all leaf nodes in a horizontal sequence (leaf.next), executing range scans with zero parent node overhead.
