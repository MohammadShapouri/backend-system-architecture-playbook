Part 01

Computer Science: The SQLite Parity Fallacy in Financial Ledgers

A pervasive shortcut in Python test engineering is swapping PostgreSQL for an in-memory SQLite database (sqlite:///:memory:) during unit and integration runs. While in-memory SQLite is fast, it introduces severe architectural blind spots that pass in testing but cause fatal crashes when deployed to production clouds.

SQLite vs. Production PostgreSQL: The Dialect Gap

Feature In-Memory SQLite Production PostgreSQL 16 Financial Failure Impact
Row-Level Locking ✗ Coarse File Lock ✓ SELECT ... FOR UPDATE SQLite locks the entire database on writes, masking concurrency deadlocks and race conditions.
Data Type Affinity ✗ Dynamic Affinity ✓ Strict Typing (NUMERIC) SQLite permits inserting arbitrary strings into decimal fields; Postgres crashes on invalid precision.
Foreign Key Integrity • Disabled by Default ✓ Enforced Atomically Requires manual PRAGMA foreign_keys = ON; orphaned child rows pass silently in SQLite.
Check Constraints • Basic Emulation ✓ Complex SQL Expressions Complex balance constraints (balance >= 0) execute differently under edge-case nullability.

The Senior Rule: Test pure business logic in-memory with pure Python objects (Milestones 01–03). When verifying persistence, SQL expressions, and relational constraints, test against the exact database engine deployed in production using Testcontainers.

Part 02

Production Parity: Ephemeral Engines with testcontainers-python

Rather than relying on developers to manually run Docker Compose files before invoking PyTest (which leads to "works on my machine" failures and port collisions in CI), testcontainers-python programmatically controls the local Docker daemon:

The Testcontainers Lifecycle Schedule
1. Session Boot
PyTest begins collection
Pull postgres:16-alpine
→ binds port →
2. Port Randomization
Zero port 5432 collisions
localhost:32768 → 5432
→ runs migrations →
3. DDL Initialization
Runs Alembic/SQL DDL ONCE
Schema Ready in 1.2s
The Session-Scoped Rule:

Spawning a Docker container takes ~1–2 seconds. Running this per test function would make a 200-test suite take 10 minutes. We define the container as a session-scoped fixture: it boots once when PyTest starts, runs schema migrations once, serves all integration tests in milliseconds via savepoints, and terminates automatically when the test process exits.

Part 03

The 1ms Reset: The Transactional Savepoint Rollback Pattern

If multiple integration tests run against a single shared PostgreSQL container, Test 1 will insert rows that contaminate Test 2. Naive solutions wipe the database between tests by running TRUNCATE accounts CASCADE; or dropping all tables. Table truncations invalidate Postgres engine caches, flush disk buffers, and take 30–100ms per test.

The senior standard is the **Transactional Savepoint Pattern**: every test executes inside a subtransaction (SAVEPOINT). Application code issues real SQL queries and tests verify persisted rows. During fixture teardown, PyTest issues a ROLLBACK TO SAVEPOINT:

The Nested Transactional Sandbox Lifecycle
1. Outer Master Connection (Session-Scoped Engine)
BEGIN TRANSACTION; ← Physical database connection held open
2. Function Fixture Check: SAVEPOINT test_sandbox_1;
3. Test Execution Body
• repository.create_account(acc_number="ACC-99", balance=5000)
• SQL emitted over TCP: INSERT INTO accounts ...
• In-test assertion: assert loaded.balance == 5000 (✓ Validated!)
4. Fixture Teardown: ROLLBACK TO SAVEPOINT test_sandbox_1;
Master transaction stays uncommitted • Sockets remain warm • Zero tables wiped!
Performance Metrology:

Rolling back to a memory savepoint takes approximately 0.8 milliseconds in PostgreSQL. Your integration tests run at nearly the same speed as pure in-memory unit tests while executing real SQL over real network sockets against the exact production Postgres query planner.

Part 04

Sentinel Auditing: Detecting Connection Pool Socket Leaks

In high-throughput services like VaultFlow, a subtle bug where an exception handler forgets to close or release a database connection (session.close()) will cause connection pool exhaustion (QueuePool limit reached) in production.

We can write a PyTest sentinel fixture using an autouse=True hook that inspects SQLAlchemy's internal connection pool telemetry before and after every integration test:

// The Connection Pool Leak Sentinel Fixture:
@pytest_asyncio.fixture(autouse=True)
async def assert_zero_connection_leaks(async_engine):
    # 1. Record checked-out connections before test runs
    pool = async_engine.pool
    initial_checked_out = pool.checkedout()

    yield  # Execute test body

    # 2. Audit checked-out connections after test teardown
    leaked_connections = pool.checkedout() - initial_checked_out
    if leaked_connections > 0:
        pytest.fail(
            f"CRITICAL CONNECTION LEAK: Test leaked {leaked_connections} physical database socket(s)! "
            f"Check missing 'await session.close()' in repository or service exception handlers."
        )

# VaultFlow Storage - SQLAlchemy 2.0 Declarative Models (Milestone 06)
# ==============================================================================

from decimal import Decimal
from datetime import datetime, timezone
from sqlalchemy import (
    String, Numeric, DateTime, Boolean, ForeignKey, 
    CheckConstraint, Index, func
)
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase):
    pass

class AccountRecord(Base):
    __tablename__ = "accounts"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    account_number: Mapped[str] = mapped_column(String(32), unique=True, index=True, nullable=False)
    account_type: Mapped[str] = mapped_column(String(16), nullable=False)
    
    # Precise financial numeric: 14 total digits, 4 decimal places
    balance: Mapped[Decimal] = mapped_column(Numeric(14, 4), default=Decimal("0.0000"), nullable=False)
    currency: Mapped[str] = mapped_column(String(3), nullable=False)
    is_active: Mapped[bool] = mapped_column(Boolean, default=True, nullable=False)
    
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), 
        default=lambda: datetime.now(timezone.utc), 
        nullable=False
    )

    __table_args__ = (
        CheckConstraint("balance >= 0", name="ck_account_balance_non_negative"),
    )


class JournalRecord(Base):
    __tablename__ = "journal_entries"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    reference_id: Mapped[str] = mapped_column(String(64), unique=True, index=True, nullable=False)
    amount: Mapped[Decimal] = mapped_column(Numeric(14, 4), nullable=False)
    currency: Mapped[str] = mapped_column(String(3), nullable=False)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), 
        server_default=func.now(), 
        nullable=False
    )
2. Async Repository & Row-Locking: src/vaultflow/storage/repositories.py Pessimistic Concurrency Service 
# ==============================================================================
# VaultFlow Storage - Async Repository with Row-Level Locking (Milestone 06)
# ==============================================================================

from decimal import Decimal
from typing import Optional
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession
from vaultflow.core.money import FinancialDomainError
from vaultflow.storage.models import AccountRecord, JournalRecord

class AccountRepository:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def create_account(
        self, account_number: str, account_type: str, currency: str, initial_balance: Decimal
    ) -> AccountRecord:
        record = AccountRecord(
            account_number=account_number,
            account_type=account_type,
            currency=currency,
            balance=initial_balance
        )
        self.session.add(record)
        await self.session.flush()
        return record

    async def get_by_number_with_lock(self, account_number: str) -> Optional[AccountRecord]:
        """
        SELECT ... FOR UPDATE:
        Acquires an exclusive PostgreSQL row lock over TCP.
        Prevents concurrent double-spending at the database hardware layer.
        """
        stmt = (
            select(AccountRecord)
            .where(AccountRecord.account_number == account_number)
            .with_for_update()
        )
        result = await self.session.scalar(stmt)
        return result

    async def execute_transfer(
        self, source_number: str, dest_number: str, amount: Decimal, reference: str
    ) -> JournalRecord:
        # 1. Deterministic lock ordering (asc order) prevents circular deadlocks
        numbers = sorted([source_number, dest_number])
        for num in numbers:
            await self.get_by_number_with_lock(num)

        source = await self.session.scalar(select(AccountRecord).where(AccountRecord.account_number == source_number))
        dest = await self.session.scalar(select(AccountRecord).where(AccountRecord.account_number == dest_number))

        if not source or not dest:
            raise FinancialDomainError("One or more accounts not found.")
        if source.balance < amount:
            raise FinancialDomainError("Insufficient funds for transfer.")

        source.balance -= amount
        dest.balance += amount

        journal = JournalRecord(
            reference_id=reference,
            amount=amount,
            currency=source.currency
        )
        self.session.add(journal)
        await self.session.flush()
        return journal

# ------------------------------------------------------------------------------
@pytest.fixture(scope="session")
def postgres_container():
    """Spawns an ephemeral PostgreSQL 16 container on a randomized port."""
    with PostgresContainer("postgres:16-alpine") as postgres:
        yield postgres

# ------------------------------------------------------------------------------
# 2. SESSION-SCOPED ENGINE: Runs DDL migrations ONCE
# ------------------------------------------------------------------------------
@pytest_asyncio.fixture(scope="session")
async def async_engine(postgres_container):
    sync_url = postgres_container.get_connection_url()
    async_url = sync_url.replace("psycopg2", "asyncpg").replace("postgresql://", "postgresql+asyncpg://")
    
    engine = create_async_engine(async_url, pool_size=5, max_overflow=5)

    # Run DDL schema migration ONCE over session
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)

    yield engine
    await engine.dispose()

# ------------------------------------------------------------------------------
# 3. FUNCTION-SCOPED SAVEPOINT FIXTURE: 1ms Reset Sandbox per Test!
# ------------------------------------------------------------------------------
@pytest_asyncio.fixture(scope="function")
async def db_session(async_engine) -> AsyncSession:
    """
    Yields an AsyncSession wrapped inside a SAVEPOINT subtransaction.
    Rolls back automatically at teardown: leaves database pristine in 0.8ms!
    """
    connection = await async_engine.connect()
    trans = await connection.begin()  # Outer Master Transaction

    session_maker = async_sessionmaker(bind=connection, expire_on_commit=False)
    session = session_maker()

    await connection.begin_nested()  # SAVEPOINT test_sandbox

    yield session

    # Teardown: Unconditional rollback resets DB instantaneously!
    await session.close()
    await trans.rollback()
    await connection.close()

import pytest
from decimal import Decimal
from sqlalchemy.exc import IntegrityError
from vaultflow.storage.repositories import AccountRepository

@pytest.mark.integration
class TestPostgresAccountRepository:
    """Verifies real PostgreSQL constraints, transactions, and savepoint rollbacks."""

    async def test_create_and_load_account_persists_in_savepoint(self, db_session):
        repo = AccountRepository(db_session)
        acc = await repo.create_account(
            account_number="ACC-CORP-900",
            account_type="ASSET",
            currency="USD",
            initial_balance=Decimal("1500000.5000")
        )

        loaded = await repo.get_by_number_with_lock("ACC-CORP-900")
        assert loaded is not None
        assert loaded.balance == Decimal("1500000.5000")

    async def test_database_level_negative_balance_check_constraint_enforced(self, db_session):
        repo = AccountRepository(db_session)
        
        # Proves real PostgreSQL check constraints fire, which SQLite frequently mishandles!
        with pytest.raises(IntegrityError, match=r"ck_account_balance_non_negative"):
            await repo.create_account(
                account_number="ACC-ILLEGAL-NEG",
                account_type="ASSET",
                currency="USD",
                initial_balance=Decimal("-50.0000")
            )

    async def test_subtransaction_isolation_leaves_database_blank(self, db_session):
        repo = AccountRepository(db_session)
        
        # Assert that accounts created in previous tests do NOT leak into this test!
        previous_acc = await repo.get_by_number_with_lock("ACC-CORP-900")
        assert previous_acc is None  # Proof that Savepoint Rollback returned DB to 0 rows!
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Committing Real Transactions Inside Tests

Calling await session.commit() inside an integration test function.

Why this destroys test suites: Calling commit() flushes the outer transaction to disk, breaking out of the outer savepoint! Your test data is now permanently committed to the database, contaminating all subsequent tests. Fix: Use await session.flush() inside tests to validate constraints while letting the fixture handle the rollback!

❌ Rebuilding Schema Per Test

Calling Base.metadata.drop_all() and create_all() before every test function.

Why this causes slow CI: Rebuilding tables, indexes, and constraints takes ~100ms per test. In a 500-test suite, schema recreation wastes 50 full seconds of CI build time. Use the Savepoint Rollback Pattern (0.8ms reset) instead.
