Part 01

Computer Science: Coroutine Execution & The Event Loop in PyTest

Unlike multithreading where the operating system kernel preemptively interrupts threads across CPU cores, Python’s asyncio relies on cooperative multitasking. A single OS thread executes a loop that manages a queue of pending tasks. Control is yielded voluntarily only when a coroutine encounters an await expression on a non-blocking socket or I/O boundary.

Standard test runners execute functions synchronously from top to bottom. If you declare a test as async def test_something(): without specialized runner instrumentation, standard Python simply returns an un-executed coroutine object—and PyTest marks the test as passed without executing a single line of assertion logic!

The Synchronous Trap in Async Tests:

If an async test invokes a blocking CPU calculation or synchronous network call (time.sleep() or standard requests.get()) instead of an awaitable non-blocking equivalent (asyncio.sleep() or httpx.AsyncClient), it freezes the entire event loop. Concurrent background tasks cannot execute, producing false-positive timeouts and invalidating concurrency assertions.

Part 02

Under the Hood: asyncio_mode & Loop Scoping

In modern test suites, managing how PyTest treats coroutines is dictated by the asyncio_mode configuration inside pyproject.toml. Choosing the wrong mode causes decorator bloat or uncontrolled fixture state contamination.

1. asyncio_mode = "strict" Enterprise Standard

Requires explicit declaration. Only test functions and fixtures explicitly marked with @pytest.mark.asyncio or declared via @pytest_asyncio.fixture are executed as coroutines: 

@pytest.mark.asyncio
async def test_settlement_dispatch():
    assert await worker.flush() == 0

Why Staff Engineers Enforce This: Prevents third-party plugin helper functions from accidentally being picked up and scheduled on an event loop. Guarantees complete clarity on which tests are asynchronous.

2. asyncio_mode = "auto" Convenience

PyTest automatically inspects all collected functions. Any test declared with async def is automatically treated as an asyncio test without needing the decorator: 

# No decorator needed; automatically wrapped
async def test_implicit_coroutine():
    assert await worker.ping()

Trade-off: Highly convenient and reduces decorator noise, but can lead to ambiguity when mixing Trio, AnyIO, or multi-threaded fixtures.

Two-Phase Asynchronous Fixtures (async def with yield)

When fixtures manage async resources (e.g., an in-memory Redis connection pool or an active settlement background queue), setup and teardown must use async def coupled with yield: 

import pytest_asyncio

@pytest_asyncio.fixture(scope="function")
async def active_settlement_worker():
    # 1. Asynchronous Setup: Start background worker task
    worker = SettlementWorker(batch_size=50)
    await worker.start()

    yield worker  # 2. Injected into calling async test function

    # 3. Asynchronous Teardown: Drain queue and cancel worker cleanly
    await worker.stop()

If an exception is raised inside the test, PyTest guarantees the post-yield async teardown code executes on the exact same event loop before the loop closes.

Part 03

Deterministic Concurrency: Eradicating "Sleep-and-Pray" with Synchronization & Virtual Clocks

The most toxic anti-pattern in asynchronous test suites is the "Sleep-and-Pray" idiom: an engineer spawns a background task, suspects it will finish in 100 milliseconds, and writes await asyncio.sleep(0.2) before asserting.

In CI environments under high CPU contention, the scheduler delays the task; 200ms expires, and the assertion fails intermittently. Conversely, when the test passes, it needlessly burns 200ms of idle wall-clock time. Across 500 tests, this adds minutes of wasted build latency.

Strategy A: asyncio.Event Synchronization

Instead of guessing how long a background worker takes, coordinate execution using an asyncio.Event. The worker sets the event the instant processing completes; the test waits with a fail-safe timeout: 

done_signal = asyncio.Event()
worker.on_batch_complete = done_signal.set

await worker.submit_batch(records)
# Wakes up immediately upon completion! (e.g. 1.2ms instead of 200ms)
await asyncio.wait_for(done_signal.wait(), timeout=1.0)
✓ Zero wasted time • Completely immune to CPU scheduling latency
Strategy B: Virtual Clock Fast-Forwarding

When testing business rules with long time delays (such as a 24-hour sliding idempotency window or a 30-minute batch flush), use time-machine to warp time forward instantaneously: 

import time_machine

async def test_idempotency_window_expiration():
    with time_machine.travel("2026-11-01 10:00:00", tick=False) as traveller:
        await worker.process_transaction(tx)
        
        # Warp time forward 25 hours in 0.0001 seconds of real time!
        traveller.shift(datetime.timedelta(hours=25))
        assert await worker.is_key_expired(tx.idempotency_key)
✓ Tests multi-day sliding expirations in sub-millisecond CPU time
Part 04

Concurrency Hazards: Race Conditions & TaskGroup Safety

In non-blocking financial systems, race conditions happen when two concurrent coroutines interleave across an await expression. Consider this classic asynchronous double-spend vulnerability:

The Asynchronous Interleaved Race Condition

Account Balance: $100.00 USD • Two Concurrent Withdrawals of $80.00 Arrive

Task A (Withdrawal #1: $80) Coroutine 1
1. Reads balance: $100 ≥ $80 (✓)
2. await db.audit_log() → YIELDS TO EVENT LOOP!
3. Resumes execution...
4. Sets balance: $100 - $80 = $20
Task B (Withdrawal #2: $80) Coroutine 2
1. Executes during Task A's yield!
2. Reads balance: $100 ≥ $80 (✓) (Stale!)
3. await db.audit_log() → YIELDS TO EVENT LOOP!
4. Sets balance: $20 - $80 = -$60 (CORRUPTED!)
Modern Defense: TaskGroup & Async Locks:

To test this, we use asyncio.gather or Python 3.11+ asyncio.TaskGroup to fire 50 concurrent transfers against a single account, asserting that internal critical sections protected by asyncio.Lock or idempotency gates strictly reject concurrent double-spends.

1. Asynchronous Settlement Pipeline: src/vaultflow/services/settlement_worker.py Non-Blocking Queue Worker 
# ==============================================================================
# VaultFlow Services - Asynchronous Settlement Pipeline (Milestone 05)
# ==============================================================================

import asyncio
from dataclasses import dataclass
from decimal import Decimal
from typing import Dict, Set, Optional
from vaultflow.core.money import Money, FinancialDomainError
from vaultflow.core.ledger import Ledger, Account, JournalEntry, Posting

class DuplicateSettlementError(FinancialDomainError):
    """Raised when an idempotency key replay is detected."""
    pass


class InsufficientSettlementFundsError(FinancialDomainError):
    """Raised when source account balance cannot satisfy settlement amount."""
    pass


@dataclass(frozen=True)
class SettlementInstruction:
    idempotency_key: str
    source_account: Account
    destination_account: Account
    amount: Money


class AsyncSettlementWorker:
    """
    HIGH-THROUGHPUT ASYNCHRONOUS SETTLEMENT PIPELINE:
    Consumes settlement instructions from an internal non-blocking queue.
    Guarantees atomic commit, idempotency deduplication, and zero race conditions.
    """
    def __init__(self, ledger: Ledger):
        self.ledger = ledger
        self.queue: asyncio.Queue[SettlementInstruction] = asyncio.Queue()
        self.processed_idempotency_keys: Set[str] = set()
        self._lock = asyncio.Lock()
        self._worker_task: Optional[asyncio.Task] = None
        self._batch_processed_event = asyncio.Event()

    async def submit(self, instruction: SettlementInstruction) -> None:
        # Fast-path idempotency check before queue ingestion
        async with self._lock:
            if instruction.idempotency_key in self.processed_idempotency_keys:
                raise DuplicateSettlementError(
                    f"Settlement key {instruction.idempotency_key} has already been cleared."
                )
        await self.queue.put(instruction)

    async def start(self) -> None:
        self._worker_task = asyncio.create_task(self._process_queue_loop())

    async def stop(self) -> None:
        if self._worker_task:
            self._worker_task.cancel()
            try:
                await self._worker_task
            except asyncio.CancelledError:
                pass

    async def _process_queue_loop(self) -> None:
        while True:
            instruction = await self.queue.get()
            try:
                async with self._lock:
                    # Deduplicate under critical section lock
                    if instruction.idempotency_key in self.processed_idempotency_keys:
                        continue

                    # Balance verification
                    if instruction.source_account.balance.amount < instruction.amount.amount:
                        raise InsufficientSettlementFundsError(
                            f"Account {instruction.source_account.account_number} has insufficient funds."
                        )

                    # Execute double-entry ledger mutation
                    entry = JournalEntry(
                        reference_id=f"SETTLE-{instruction.idempotency_key}",
                        postings=[
                            Posting(account=instruction.source_account, amount=instruction.amount, is_debit=False),
                            Posting(account=instruction.destination_account, amount=instruction.amount, is_debit=True),
                        ]
                    )
                    self.ledger.commit_entry(entry)
                    self.processed_idempotency_keys.add(instruction.idempotency_key)
                    self._batch_processed_event.set()
            finally:
                self.queue.task_done()

# VaultFlow Test Suite - Asynchronous Settlement Testing (Milestone 05)
# ==============================================================================

import asyncio
import pytest
import pytest_asyncio
from decimal import Decimal
from vaultflow.core.money import Money
from vaultflow.core.ledger import AccountType
from vaultflow.services.settlement_worker import (
    AsyncSettlementWorker,
    SettlementInstruction,
    DuplicateSettlementError,
    InsufficientSettlementFundsError
)

@pytest_asyncio.fixture
async def settlement_worker(empty_ledger):
    """Async fixture managing clean worker boot, execution, and teardown."""
    worker = AsyncSettlementWorker(ledger=empty_ledger)
    await worker.start()
    
    yield worker

    # Guaranteed async teardown: cancels worker loop and prevents task leakage
    await worker.stop()


@pytest.mark.asyncio
class TestAsyncSettlementWorker:
    """Validates non-blocking queue operations, race-conditions, and task safety."""

    async def test_concurrent_settlement_batch_execution(
        self, 
        settlement_worker: AsyncSettlementWorker, 
        account_factory
    ):
        # 1. Arrange: Create funded source and reserve destination accounts
        source = account_factory(account_type=AccountType.ASSET, balance=Decimal("10000.0000"))
        destination = account_factory(account_type=AccountType.LIABILITY, balance=Decimal("0.0000"))
        settlement_worker.ledger.register_account(source)
        settlement_worker.ledger.register_account(destination)

        # 2. Act: Fire 10 concurrent settlement instructions simultaneously using asyncio.gather
        instructions = [
            SettlementInstruction(
                idempotency_key=f"IDEMP-CONCUR-{i}",
                source_account=source,
                destination_account=destination,
                amount=Money(Decimal("100.0000"), "USD")
            )
            for i in range(10)
        ]

        await asyncio.gather(*(settlement_worker.submit(instr) for instr in instructions))
        
        # Deterministic Synchronization: wait for queue to drain cleanly without any sleep()
        await asyncio.wait_for(settlement_worker.queue.join(), timeout=2.0)

        # 3. Assert: Verify balance deductions ($10,000 - $1,000 = $9,000)
        assert source.balance.amount == Decimal("9000.0000")
        assert destination.balance.amount == Decimal("1000.0000")
        assert len(settlement_worker.ledger.journal_entries) == 10

    async def test_concurrent_idempotency_key_replay_rejected(
        self, 
        settlement_worker: AsyncSettlementWorker, 
        account_factory
    ):
        source = account_factory(balance=Decimal("500.0000"))
        dest = account_factory()
        settlement_worker.ledger.register_account(source)
        settlement_worker.ledger.register_account(dest)

        duplicate_instruction = SettlementInstruction(
            idempotency_key="REPLAY-KEY-999",
            source_account=source,
            destination_account=dest,
            amount=Money(Decimal("50.0000"), "USD")
        )

        # First submission passes
        await settlement_worker.submit(duplicate_instruction)
        await asyncio.wait_for(settlement_worker.queue.join(), timeout=1.0)

        # Replay of the identical idempotency key is rejected immediately!
        with pytest.raises(DuplicateSettlementError, match=r"already been cleared"):
            await settlement_worker.submit(duplicate_instruction)

    async def test_worker_task_cancellation_preserves_ledger_integrity(
        self, 
        empty_ledger, 
        account_factory
    ):
        # Verifies worker task cancels safely without corrupting memory
        worker = AsyncSettlementWorker(ledger=empty_ledger)
        await worker.start()

        # Stop worker while idle
        await worker.stop()

        assert worker._worker_task.cancelled() is True
        assert worker.queue.empty() is True
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The "Sleep-and-Pray" Anti-Pattern

Writing await asyncio.sleep(0.1) waiting for an async worker to finish processing.

Why this causes flaky tests: In CI containers running under heavy CPU load, a background task might take 105ms instead of 100ms. Your assertion fails intermittently, producing a "flaky" build that passes when rerun. Fix: Use event coordination (asyncio.Event) or queue synchronization (await queue.join()).

❌ The "Un-Awaited Coroutine" Illusion

Calling an async function inside a test without the await keyword: worker.submit(instr).

Why this passes tests incorrectly: In Python, calling an async def function returns a coroutine object. If you omit await, the code inside the coroutine never runs! Python logs a RuntimeWarning: coroutine was never awaited, but PyTest marks the test as passing 100% green! Fix: Enforce strict compiler warnings in pyproject.toml with filterwarnings = ["error"].
