Part 01

Computer Science: The Unit of Work & ACID Guarantees

Relational databases (PostgreSQL, SQLite, MySQL) store data in flat two-dimensional tables of rows and columns governed by relational algebra. In contrast, object-oriented Python programs represent business domains as interconnected graphs of rich class instances with methods and nested types. This fundamental dissonance is known as the Object-Relational Impedance Mismatch.

1 ACID Transaction Semantics

Every relational write must adhere to four safety guarantees:

  • Atomicity: All mutations inside a transaction succeed together or fail together. If step 2 of 3 fails, the entire transaction is rolled back.
  • Consistency: The database enforces all constraints (foreign keys, check bounds, unique indexes) before committing to disk.
  • Isolation: Concurrent transactions run independently without seeing uncommitted intermediate states from other workers.
  • Durability: Once committed, data is written to a write-ahead log (WAL) and survives power cuts or OS crashes.

2 The Unit of Work Pattern (The Session)

An ORM Session is not simply an open TCP socket. It is an implementation of Martin Fowler's Unit of Work pattern:

  • Identity Map: The Session keeps a registry of every loaded entity. If you query Note ID 1 five times in one request, SQLAlchemy executes SQL once and returns the exact same in-memory object instance.
  • Dirty Tracking: The Session watches your objects for attribute changes. When you call db.commit(), it computes the minimal SQL update changeset necessary.
The SQLAlchemy Session Unit of Work Lifecycle
1. Session Spawn Checked out from Engine Pool
→ Read/Mutate →
2. Sandbox Staging db.add(entity) / entity.title = 'X'
→ Commit/Rollback →
3. Flush & Commit Emits SQL • Closes in finally

Calling db.add() does not write to disk immediately. It stages the object in the sandbox. The SQL INSERT statement is emitted only when db.commit() or db.flush() is executed.

Part 02

SQLAlchemy 2.0: Modern Type-Safe Declarative Models

SQLAlchemy 2.0 represents a major paradigm shift. Legacy 1.x syntax relied on untyped Column(String, primary_key=True) declarations and implicit queries like db.query(Note).filter(...).

Modern 2.0 syntax leverages standard Python type hinting (Mapped[], mapped_column()) and explicit query construction using select() statements that integrate cleanly with IDE autocompletion, Pyright, and mypy.

Legacy 1.x Syntax (Deprecated / Legacy Style)
# Legacy 1.x: No IDE type validation, string lookups
class Note(Base):
    __tablename__ = "notes"
    id = Column(Integer, primary_key=True)
    title = Column(String(100), nullable=False)

# Legacy Query API:
notes = db.query(Note).filter(Note.title == "Test").all()
Modern 2.0 Syntax (Type-Safe / DeclarativeBase)
# Modern 2.0: Type-annotated, fully checked
class Note(Base):
    __tablename__ = "notes"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(100))

# Modern Select API (Standardized with Core):
stmt = select(Note).where(Note.title == "Test")
notes = db.scalars(stmt).all()

Driver Architecture Synchronous vs. Asynchronous Database Engines (psycopg2 vs. asyncpg)

A crucial decision in FastAPI architecture is selecting your database driver and session type. Python cannot perform asynchronous database I/O using traditional synchronous drivers:

Synchronous Engine (Standard)
  • PostgreSQL Driver: psycopg2 or psycopg
  • SQLite Driver: standard library sqlite3
  • FastAPI Route Type: Standard def endpoint()
  • Execution: FastAPI offloads each synchronous call to its AnyIO worker threadpool so the event loop does not freeze.
Asynchronous Engine (High Concurrency)
  • PostgreSQL Driver: asyncpg
  • SQLite Driver: aiosqlite
  • FastAPI Route Type: Non-blocking async def endpoint()
  • Execution: Queries yield control directly back to the event loop using await session.execute(...) with zero threadpool context switches.
How to Configure Async SQLAlchemy in database.py: 
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession
from typing import AsyncGenerator

# URL format uses async driver protocol: sqlite+aiosqlite or postgresql+asyncpg
ASYNC_DB_URL = "sqlite+aiosqlite:///./notevault.db"

async_engine = create_async_engine(ASYNC_DB_URL, pool_pre_ping=True)
AsyncSessionLocal = async_sessionmaker(bind=async_engine, class_=AsyncSession, expire_on_commit=False)

async def get_async_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        yield session
Part 03

Solving the DetachedInstanceError & Lazy Loading

Almost every developer working with FastAPI and SQLAlchemy eventually encounters this runtime crash: sqlalchemy.orm.exc.DetachedInstanceError: Parent instance is not bound to a Session; lazy load operation cannot proceed.

Why Does This Error Happen?

By default, SQLAlchemy uses Lazy Loading for relationships. If a User has many notes, SQLAlchemy does not query the notes table when loading the user. It waits until your code accesses user.notes in Python, and only then executes a secondary SQL query behind the scenes.

1. Route Controller executes: user = db.scalar(select(User))
2. Route Controller returns: return user
3. Dependency teardown runs: db.close() executes in the finally block! Session is closed.
4. FastAPI begins serialization to JSON: attempts to read user.notes...
5. CRASH! DetachedInstanceError: The session is already closed, so SQLAlchemy cannot run the query.

The Solution: Eager Loading via joinedload / selectinload

Never rely on lazy loading across request boundaries. Instruct SQLAlchemy to fetch related data upfront while the session is still active:

stmt = select(User).options(selectinload(User.notes))
user = db.scalar(stmt) # User and all notes fetched together; safe to serialize after session closes!

1. Database Connection Factory: app/database.py Engine & Sessionmaker Setup 
# ==============================================================================
# NoteVault Backend - Database Connection Engine (Milestone 06)
# ==============================================================================

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, DeclarativeBase
from app.config import settings

# 1. Connection URL: Read dynamically from .env
# Defaults to local SQLite, but seamlessly switches to PostgreSQL in prod:
# "postgresql+psycopg2://user:password@localhost:5432/notevault"
DATABASE_URL = getattr(settings, "DATABASE_URL", "sqlite:///./notevault.db")

# 2. Instantiate Engine (The Global Connection Pool)
# Notice: create_engine is executed ONCE at module load, NOT per request!
engine_args = {}
if DATABASE_URL.startswith("sqlite"):
    # SQLite specific: allow multi-threaded access for FastAPI async workers
    engine_args["connect_args"] = {"check_same_thread": False}
else:
    # Production PostgreSQL settings
    engine_args.update({
        "pool_size": 10,        # Persistent open connections kept in pool
        "max_overflow": 20,     # Extra connections allowed during spikes
        "pool_pre_ping": True,  # Detect and discard dead connections automatically
    })

engine = create_engine(DATABASE_URL, **engine_args)

# 3. Sessionmaker: Factory for lightweight Unit of Work sandbox instances
# autoflush=False: Prevents premature DB writes before validation completes
# autocommit=False: Enforces explicit transaction boundaries
SessionLocal = sessionmaker(
    bind=engine,
    autocommit=False,
    autoflush=False,
    expire_on_commit=False  # CRITICAL: Prevents DetachedInstanceError on attribute access!
)

# 4. Declarative Base: The foundation for all ORM models
class Base(DeclarativeBase):
    # All models inherit this base class
    pass
2. SQLAlchemy 2.0 ORM Declarations: app/models.py Physical Database Table Schemas 
# ==============================================================================
# NoteVault Backend - Relational Models (Milestone 06)
# ==============================================================================

from typing import Optional, List
from datetime import datetime, timezone
from sqlalchemy import String, Text, Integer, Boolean, DateTime, JSON, Index
from sqlalchemy.orm import Mapped, mapped_column
from app.database import Base

class NoteModel(Base):
    """
    Maps directly to the physical 'notes' table in our relational database.
    Built with modern SQLAlchemy 2.0 Mapped type annotations.
    """
    __tablename__ = "notes"

    # Primary Key with auto-increment
    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)

    # Indexed fields for high-speed queries
    title: Mapped[str] = mapped_column(String(120), nullable=False, index=True)
    content: Mapped[str] = mapped_column(Text, nullable=False)
    
    # JSON column: stores structured lists/dicts natively (JSONB in PostgreSQL)
    tags: Mapped[List[str]] = mapped_column(JSON, default=list, nullable=False)
    
    priority: Mapped[int] = mapped_column(Integer, default=1, nullable=False)
    
    # Soft Delete Pattern: Never physically destroy rows; mark them inactive
    is_archived: Mapped[bool] = mapped_column(Boolean, default=False, nullable=False, index=True)

    # Timestamps: Stored in UTC
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc),
        nullable=False
    )
    updated_at: Mapped[Optional[datetime]] = mapped_column(
        DateTime(timezone=True),
        default=None,
        nullable=True
    )

    # Composite index to optimize common queries: "Active notes ordered by date"
    __table_args__ = (
        Index("ix_notes_active_created", "is_archived", "created_at"),
    )
3. Yielding Session Dependency: app/dependencies.py Guaranteed Connection Cleanup 
# ==============================================================================
# NoteVault Backend - Database Session Dependencies (Milestone 06)
# ==============================================================================

from typing import Annotated, Generator
from fastapi import Depends
from sqlalchemy.orm import Session
from app.database import SessionLocal

def get_db() -> Generator[Session, None, None]:
    """
    Yields an isolated SQLAlchemy Session per request.
    Guarantees session teardown and returns connection to pool even on error.
    """
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()  # Always return connection to the pool

# Type alias for easy route injection
DbSession = Annotated[Session, Depends(get_db)]
4. Refactored SQL Router: app/routers/notes.py Executing Real SQL Queries 
# ==============================================================================
# NoteVault Backend - Notes API Router with SQLAlchemy (Milestone 06)
# ==============================================================================

from typing import Optional, List
from datetime import datetime, timezone
from fastapi import APIRouter, HTTPException, status, Query, Path
from sqlalchemy import select, or_
from app.schemas import NoteCreate, NoteUpdate, NoteResponse
from app.models import NoteModel
from app.dependencies import DbSession

router = APIRouter()

@router.post(
    "",
    response_model=NoteResponse,
    status_code=status.HTTP_201_CREATED,
    summary="Create a note in persistent storage"
)
def create_note(payload: NoteCreate, db: DbSession):
    # 1. Instantiate the SQLAlchemy ORM model
    new_note = NoteModel(
        title=payload.title,
        content=payload.content,
        tags=payload.tags,
        priority=payload.priority,
        is_archived=False,
        created_at=datetime.now(timezone.utc)
    )

    # 2. Add to session (sandbox) and commit to disk
    db.add(new_note)
    db.commit()

    # 3. Refresh loads generated primary key ID and defaults from database
    db.refresh(new_note)
    return new_note


@router.get(
    "",
    response_model=List[NoteResponse],
    summary="Query notes using SQLAlchemy select statements"
)
def list_notes(
    db: DbSession,
    search: Optional[str] = Query(None, min_length=2, max_length=50),
    include_archived: bool = Query(False),
    skip: int = Query(0, ge=0),
    limit: int = Query(10, ge=1, le=100)
):
    # 1. Build type-safe SQL query
    stmt = select(NoteModel)

    if not include_archived:
        stmt = stmt.where(NoteModel.is_archived == False)

    if search:
        search_pattern = f"%{search}%"
        stmt = stmt.where(
            or_(
                NoteModel.title.ilike(search_pattern),
                NoteModel.content.ilike(search_pattern)
            )
        )

    # 2. Add pagination and ordering
    stmt = stmt.order_by(NoteModel.created_at.desc()).offset(skip).limit(limit)

    # 3. Execute query: scalars() unwraps row tuples into ORM instances
    notes = db.scalars(stmt).all()
    return notes


@router.get("/{note_id}", response_model=NoteResponse)
def get_note(note_id: int = Path(..., ge=1), db: DbSession = ...):
    stmt = select(NoteModel).where(NoteModel.id == note_id)
    note = db.scalar(stmt)
    if not note:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"Note {note_id} does not exist."
        )
    return note


@router.delete("/{note_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_note(note_id: int = Path(..., ge=1), db: DbSession = ...):
    """
    Demonstrates soft deletion: preserve historical data by marking is_archived = True.
    """
    stmt = select(NoteModel).where(NoteModel.id == note_id)
    note = db.scalar(stmt)
    if not note:
        raise HTTPException(status_code=404, detail="Note not found.")
    
    note.is_archived = True
    db.commit()
    return None
Part 05

Schema Evolution: The Alembic Migration Flow & Production Rollouts

In development, some developers use Base.metadata.create_all(bind=engine) to initialize database tables. Never run create_all() in production. create_all() creates missing tables, but it cannot modify existing columns, add indexes, or rename fields on tables that already exist. Attempting schema changes by hand leads to drift and data loss.

Alembic tracks database schema changes in code, much like Git tracks source code.

The Alembic Migration Lifecycle
1. Model Mutation You edit app/models.py (e.g., add a new is_pinned boolean column)
↓
2. alembic revision --autogenerate -m "add is_pinned" Alembic inspects DB schema, diffs it against Base.metadata, and generates an upgrade/downgrade script
↓
3. alembic upgrade head Executes the SQL DDL statements, applies changes, and updates the alembic_version table

Important Step Wiring Alembic: The alembic/env.py Configuration

By default, a freshly initialized Alembic project knows nothing about your application's models. You must edit alembic/env.py to point target_metadata to your application's Declarative Base: 

# In alembic/env.py:
from app.database import Base
from app.models import NoteModel  # Must import models so Base registers table metadata!

# Point Alembic to our application's metadata registry
target_metadata = Base.metadata

⚠️ Production Reality: The Multi-Container Migration Race Condition

A catastrophic mistake in production deployment is placing alembic upgrade head directly inside your container entrypoint script (CMD or ENTRYPOINT).

1. You trigger a deployment with 4 container replicas (Pods).
2. All 4 containers start simultaneously on your cluster.
3. All 4 processes execute alembic upgrade head at the exact same millisecond!
→ Result: Database table locks, deadlocks, and corrupted alembic_version metadata table state.

The Production Architecture Standard: Migrations must run exactly once in an isolated step before the application containers receive traffic:

  • Kubernetes: Run Alembic migrations inside a one-off Job or an initContainer that completes before application Pods start.
  • Platform-as-a-Service (Render, Fly.io, Heroku): Use a dedicated Release Phase / Pre-Deploy Command (release_command: alembic upgrade head) that runs to completion before routing live traffic to the new revision.
  • Docker Compose: Use a dedicated migration service that exits cleanly before starting the web workers: command: sh -c "alembic upgrade head && exit 0"
Warning Track

Beginner Pitfalls & Anti-Patterns

❌ Committing Inside a Loop

Writing for item in items: db.add(item); db.commit().

Why this is slow: Every call to db.commit() forces the database to write to disk and wait for physical I/O confirmation (fsync). For 1,000 items, committing inside the loop executes 1,000 separate disk flushes and network round-trips. Always stage your entities with db.add_all(items) and commit once at the end.

❌ The N+1 Query Problem

Querying 50 notes, and then iterating over them in Python to access a related author object: [note.author.name for note in notes].

Why this impacts performance: SQLAlchemy runs 1 query to fetch the 50 notes, plus 50 additional queries to fetch each note's author—making 51 queries in total! Always use eager loading (options(joinedload(NoteModel.author))) to fetch all related data in a single joined SQL query.

Runbook

Running Alembic Migrations & Validating NoteVault

Ensure sqlalchemy and alembic are installed in your virtual environment. Run the migration sequence to create your database tables:

# 1. Initialize Alembic environment (run once per project):
alembic init alembic
# 2. Automatically generate the initial migration revision:
alembic revision --autogenerate -m "create notes table"
Inspect the newly created file in alembic/versions/ to review the generated table schema.
# 3. Apply the migration to the database:
alembic upgrade head
Output will show: Running upgrade ... -> create notes table
# 4. Boot the server and create a note (verify persistence across restarts):
curl -i -X POST http://127.0.0.1:8000/api/v1/notes \ -H "Content-Type: application/json" \ -d '{"title": "Persistent Database Note", "content": "Saved in SQLite!", "tags": ["db", "sql"], "priority": 3}'
