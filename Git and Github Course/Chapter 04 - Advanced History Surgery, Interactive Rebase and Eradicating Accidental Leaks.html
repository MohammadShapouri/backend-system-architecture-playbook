Part 01

Computer Science: The Interactive Rebase State Machine

When developers work on local feature branches, their natural workflow is iterative, experimental, and frequently chaotic: fixing typos, testing syntax, and making partial commits. Publishing this uncurated stream of consciousness to a team repository pollutes the DAG, breaks git bisect automation, and exhausts code reviewers.

Interactive Rebase (git rebase -i <base-commit>) is an in-memory compiler that allows you to rewrite, reorder, combine, and delete commit nodes before publishing. Git computes the series of patch deltas between the base commit and HEAD, presents them in an editable instruction script (the rebase todo list), and sequentially replays them to synthesize brand-new commit objects.

pick (p) Default Action

Retains the commit and applies its diff as is. Reordering pick lines in the instruction list physically reorders the sequence of commits in the resulting DAG.

reword (r) Message Edit

Applies the commit's code changes, but pauses execution to allow the author to edit the commit log message (e.g., standardizing a non-compliant message to Conventional Commits).

edit (e) Surgical Halt

Halts the rebase process entirely at this commit. Leaves your working tree and staging index at that exact historical moment, allowing you to add files, amend changes, or split one commit into multiple atomic units.

squash (s) Melds & Prompts

Melds the commit's diff directly into the previous commit in the list. Pauses to open an editor containing both commit messages, allowing you to synthesize a combined semantic message.

fixup (f) Silent Melt

Like squash, it merges changes into the preceding commit, but completely discards this commit's log message. Perfect for small typo corrections or formatting adjustments.

drop (d) Eradicate Node

Removes the commit entirely from the replayed history. (Alternatively, simply deleting the line from the rebase todo file achieves the exact same result).

Critical Chronology Invariant in Rebase Todo Lists:

Unlike git log (which lists the newest commit at the very top), an interactive rebase todo file is displayed in chronological execution order: the oldest commit is at the top, and the newest commit is at the bottom! The command at line 1 executes first, and line 2 squashes into line 1.

Part 02

Security Anatomy: The "Ghost Blob" Fallacy of Deleting Secrets

One of the most dangerous misconceptions in software engineering is the belief that committing a deletion of a secret remediates the leak:

❌ The Fatal Remediation Fallacy:
$ git add secrets.json && git commit -m "feat: add config" # LEAK OCCURS HERE
$ git push origin main
# Developer panics upon realizing secrets.json contains AWS Private Keys:
$ git rm secrets.json && git commit -m "fix: delete secret file"
$ git push origin main

Why this changes nothing: Git is an append-only snapshot database. While secrets.json is absent from the working tree of the latest commit, it lives permanently in the tree and blob objects of the previous commit! Anyone cloning the repository, browsing commit history on GitHub, or running git checkout HEAD~1 can extract your live production credentials in milliseconds.

Visualizing the Ghost Blob in Git's Immutable DAG
Commit A: The Leak SHA: a18f92

Root tree points directly to the secret credentials blob:

Tree: 3f88d1
• README.md → blob e69de2
• secrets.json → blob c8102a (AWS_KEY=AKIA...)
↑ THIS BLOB REMAINS IN THE DATABASE FOREVER ↑
Commit B: The "Deletion" SHA: 7b4012

Root tree omits the file, but links back to Commit A as its parent:

Parent: a18f92 (Points to Commit A!)
Tree: 9c001f
• README.md → blob e69de2
Any adversary who executes git checkout a18f92 recovers the full secret on disk!
Part 03

Cryptographic Scrubbing: Permanent Purging via git-filter-repo

To truly remediate an accidental leak, the secret blob must be physically and mathematically excised from every commit tree, tag, and reference across the entire repository DAG.

Historically, Git provided git filter-branch. Today, git filter-branch is formally deprecated by the Git Core Project because it is painfully slow, prone to corrupting commit metadata, and frequently leaves dangling references in hidden namespaces.

The modern, official standard recommended by Git and GitHub is git-filter-repo: a high-speed Python-based utility that rebuilds the entire object database from scratch in seconds:

// Installing & Executing Permanent Object Purging:
# 1. Install git-filter-repo via pip or package manager
pip install git-filter-repo

# 2. Permanently purge a secret file across ALL branches, tags, and commits
# '--invert-paths' means: KEEP everything EXCEPT the specified path!
git filter-repo --invert-paths --path secrets.json --force

# 3. Alternatively: Scrub an exact API key string anywhere it appears across ALL files:
# Create a expressions replacement file:
echo "AKIAIOSFODNN7EXAMPLE==>REDACTED_API_KEY" > replace.txt
git filter-repo --replace-text replace.txt --force
What git-filter-repo Does Under the Hood

git-filter-repo walks the entire DAG from the root commit to the tips of all branches. Whenever it encounters a tree containing secrets.json, it omits that entry from the new tree object. Because the root tree hash changes, every descendant commit receives a brand-new SHA hash. It rewrites tags, purges the local reflogs, and runs an aggressive git gc --prune=now to physically obliterate the unreferenced blobs from disk.

Part 04

Safe Remote Updating: Why --force-with-lease is Mandatory

Whenever you rebase, squash, or purge history, your local branch diverges from the upstream remote branch. Running a standard git push will be rejected by GitHub with a [rejected - non-fast-forward] error.

To publish rewritten history, engineers must force the update. However, using blind force is one of the leading causes of production code loss in software teams:

❌ git push --force Destructive Blind Overwrite

Instructs the remote server: "Overclock your branch pointer to my local SHA, regardless of what anyone else has pushed in the interim!"

1. Alice and Bob work on feature/payments
2. Bob pushes an important commit to GitHub
3. Alice rebases locally, unaware of Bob's push
4. Alice runs: git push --force
→ Bob's commit is permanently overwritten on GitHub!
✓ git push --force-with-lease Defensive Conditional Overwrite

Instructs the remote server: "Only overwrite the remote branch IF its current pointer matches my local remote-tracking branch (refs/remotes/origin/...)!"

1. Alice and Bob work on feature/payments
2. Bob pushes an important commit to GitHub
3. Alice rebases locally and pushes:
git push --force-with-lease
→ REJECTED! Remote has updated. Bob's work is saved!

├── .git/
├── src/
│ └── shipforge/
│ ├── auth.py
│ └── tokens.py # Cleanly rebased feature commit
├── tests/
│ └── test_tokens.py # Unit test suite
└── mock_aws_secret.json # Accidental leak target for surgical eradication

# ==============================================================================
# ShipForge History Surgery & Secret Sanitization Protocol
# ==============================================================================

# 1. SIMULATE DIRTY FEATURE BRANCH WITH ACCIDENTAL SECRET
git switch -c feature/token-service
echo '{"AWS_KEY": "AKIA_SHIPFORGE_SECRET_LEAK_99182"}' > mock_aws_secret.json
git add mock_aws_secret.json
git commit -m "chore: add mock credentials for local integration testing"

echo 'class TokenService: pass' > src/shipforge/tokens.py
git add src/shipforge/tokens.py
git commit -m "wip tokens"

echo 'def test_tokens(): assert True' > tests/test_tokens.py
git add tests/test_tokens.py
git commit -m "fix typo in tokens test"

# ------------------------------------------------------------------------------
# 2. INTERACTIVE REBASE: SQUASH MESSY COMMITS INTO CLEAN SEMANTIC UNITS
# ------------------------------------------------------------------------------
# Rebase the last 2 commits:
# Command: git rebase -i HEAD~2
#
# IN THE EDITOR: Change the second commit from 'pick' to 'fixup':
#   pick a1b2c3d wip tokens
#   fixup e4f5g6h fix typo in tokens test
#
# Reword the parent commit to Conventional Commits:
#   "feat(tokens): implement core token issuance and verification engine"

# ------------------------------------------------------------------------------
# 3. PERMANENT OBJECT PURGE: SCRUB mock_aws_secret.json FROM REPOSITORY DAG
# ------------------------------------------------------------------------------
# Physically excises the file across all historical trees:
git filter-repo --invert-paths --path mock_aws_secret.json --force

# ------------------------------------------------------------------------------
# 4. FORENSIC VERIFICATION: ASSERT OBJECT IS 100% GONE
# ------------------------------------------------------------------------------
# Query every object in the entire database to prove the key string does not exist:
git rev-list --objects --all | grep mock_aws_secret.json || echo "✓ SECRET COMPLETELY ERADICATED"

# ------------------------------------------------------------------------------
# 5. SAFE PUSH: GUARD UPSTREAM WITH LEASE VERIFICATION
# ------------------------------------------------------------------------------
git push --force-with-lease origin feature/token-service
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Forgetting That Git Tags Retain Secret Blobs

Running a history rewrite on branches while forgetting that release tags point to historical commits.

Why this leaves secrets exposed: Git tags are static pointers. If a tag like v1.0.0 points to an ancient commit that holds your leaked secret, that commit and all its child blobs remain reachable and cannot be garbage collected! Tools like git-filter-repo automatically rewrite tags, neutralizing this vector.

❌ Treating Git History Scrubbing as Key Revocation

Purging a secret from the Git repository and failing to immediately rotate the actual secret in your cloud infrastructure.

Security Invariant: The moment a private key or API token touches a remote repository (like GitHub), assume it is compromised immediately. Malicious bots continuously scrape the public GitHub event firehose in real-time. Rewriting history is for compliance; immediate key rotation in AWS/GCP/Vault is non-negotiable!
