Part 01

Computer Science: The Pull Request Engineering Lifecycle

A Pull Request (PR) is not a native Git command; it is an architectural collaboration mechanism popularized by GitHub. Under the hood, a pull request is a request to pull a specific commit range from a source branch (either within the same repository or from a fork) and merge it into a target base branch (such as main).

In professional engineering organizations, a Pull Request serves three distinct functions:

1. Architectural Gate Verification

Blocks unverified code from reaching production. Requires CI automated tests, static security linters, and semantic checks to pass before merging is physically permitted.

2. Peer Review Forum Mentorship

Provides a structured diff interface where senior engineers review design patterns, challenge assumptions, catch race conditions, and leave executable code suggestions.

3. Historical Audit Trail Compliance

Permanently links the business rationale, issue tracker tickets (e.g., Fixes #104), test evidence, and approval signatures directly to the merged commit.

The Power of Draft Pull Requests

Opening a PR early as a Draft PR signals to your team: "This work is in progress; do not perform formal review yet." Draft PRs provide major advantages:

  • Early CI Feedback: Automated test suites, linters, and container build checks run on your feature branch before formal review begins.
  • Accidental Merge Prevention: The GitHub UI disables the "Merge" button entirely until the author explicitly marks the PR as "Ready for review".
  • Zero Notification Spam: Teammates listed in CODEOWNERS are not pinged or requested for review while the PR remains in Draft state.
Part 02

Under the Hood: Review States & One-Click Suggestions

GitHub distinguishes between three explicit review submission outcomes:

  • Comment: Submits neutral feedback or questions without explicitly approving or blocking the pull request.
  • Approve: Formally signs off on the code diff. Counts toward the repository's minimum required approval quota.
  • Request Changes: Hard blocks the pull request from being merged. The author cannot merge until the reviewer approves the updated diff or an administrator overrides the block.
Interactive Review Technique: Executable Code Suggestions ```suggestion Markdown Block

Instead of writing a comment like: "Please add a fallback default and handle None", senior reviewers write an actionable diff using GitHub's suggestion syntax: 

```suggestion
def get_auth_token(headers: dict[str, str]) -> str:
    auth_header = headers.get("Authorization")
    if not auth_header or not auth_header.startswith("Bearer "):
        raise AuthenticationRequiredError("Missing or malformed Authorization header")
    return auth_header.removeprefix("Bearer ").strip()
```
The PR author can click "Commit suggestion" directly within GitHub's interface to apply the diff as a commit immediately!
Part 03

Branch Governance: Rulesets & Automated CODEOWNERS Routing

By default, a freshly initialized Git repository allows anyone with write permissions to run git push --force origin main, potentially obliterating the entire production commit tree.

Production repositories lock down their core branches using GitHub Branch Protection Rules or modern GitHub Rulesets:

Require a Pull Request Before Merging

Direct pushes to protected branches (main, releases/*) are rejected outright. All changes must arrive via a pull request.

Dismiss Stale Approvals on New Commits

If a reviewer approves a PR and the author subsequently pushes new commits, all existing approvals are automatically revoked. Code cannot sneak into production uninspected.

Require Status Checks to Pass (CI Gates)

Designated CI jobs (unit tests, coverage thresholds, security linters) must report a green checkmark before the merge button becomes active.

Require Linear History

Enforces that all pull requests are integrated using Squash and Merge or Rebase and Merge, blocking messy merge bubbles from entering the main branch.

Automated Reviewer Routing: .github/CODEOWNERS Ownership Definition

When a pull request touches specific files, GitHub evaluates .github/CODEOWNERS and automatically requests reviews from the assigned teams or tech leads: 

# Global default owner for everything in repository:
*                   @shipforge-core-team

# Security & Auth modules require review from Security Leads:
/src/shipforge/auth.py       @secops-lead @alice
/src/shipforge/tokens.py     @secops-lead

# CI/CD and GitHub Actions pipelines require DevOps approval:
/.github/workflows/          @devops-leads

# Database migrations require Database Architect approval:
/migrations/                 @db-architects

Merge Strategy DAG Topology Result Commit Preservation Recommended Production Use Case
Create a merge commit (merge --no-ff) Non-linear; creates a 2-parent merge commit on the target branch. Preserves 100% of individual feature commits in original form. Large enterprise releases, multi-team integration branches, compliance tracking.
Squash and merge Strictly linear; combines all PR commits into a single commit on main. Melds all commits; discards individual granular feature commits. Industry Standard for PRs: Keeps main pristine, clean, and easily bisectable.
Rebase and merge Strictly linear; replays each commit sequentially onto main without a merge commit. Preserves individual commits, but rewrites all commit SHAs. Teams with rigorous Conventional Commit discipline on every single commit.

Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The "Mega-PR" Anti-Pattern (>800 LOC)

Submitting pull requests that modify 30 files and span more than 800 lines of code across multiple unrelated subsystems.

Why this destroys code quality: Cognitive fatigue causes reviewers to glance through massive PRs and give superficial "looks good to me" approvals. Bugs inevitably slip through. Keep PRs under 300 lines of changes whenever possible!

❌ Merging with Unresolved Review Threads

Hitting the merge button while review discussions, questions, or change requests remain open and unresolved.

Why this causes technical debt: Unresolved threads represent unaddressed technical concerns or unvalidated assumptions. Configure your branch protection rules to enforce: Require conversation resolution before merging!

Runbook

Operating Pull Requests via GitHub CLI (gh)

Professional engineers don't switch to a web browser to manage PRs—they execute the review lifecycle directly from the terminal using GitHub CLI (gh):

# 1. Push branch and open an interactive Draft Pull Request from terminal:
gh pr create --draft --title "feat(tokens): add asymmetric token issuing pipeline" \ --body "Closes #104. Implements RS256 token signing and verification."
# 2. Check out a teammate's PR locally for testing and execution:
gh pr checkout 42
Automatically configures local tracking branch to the PR's remote state.
# 3. Submit formal code review and squash-merge when checks pass:
# Approve the PR:
gh pr review 42 --approve --body "Architectural patterns look clean. Test coverage verified."

# Execute a clean Squash-and-Merge:
gh pr merge 42 --squash --delete-branch
