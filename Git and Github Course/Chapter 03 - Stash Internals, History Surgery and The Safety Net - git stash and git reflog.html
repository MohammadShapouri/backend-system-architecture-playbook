Part 01

Computer Science: The Hidden Multi-Parent Architecture of git stash

Many developers conceptualize git stash as a clipboard or temporary clipboard buffer in memory. In reality, Git stores stashes directly in the permanent object store as special multi-parent commits.

When you execute git stash push, Git synthesizes two (or three, if untracked files are captured) separate commit objects and updates the reference file at .git/refs/stash:

Internal Anatomy of a Stash Reference: stash@{0}
Parent 1: HEAD Commit
The commit you were currently on when stashing.
← Parent 1 ←
stash@{0} Commit WIP on main

Snapshot of your Working Directory changes. Linked to Parent 1, Parent 2, and Parent 3.

→ Parent 2 →
Parent 2: Index Tree
Snapshot of changes that were staged in the index at stash time!
The Third Parent: git stash -u (--include-untracked)

By default, git stash ignores untracked files completely. If you add the -u flag, Git creates a third parent commit containing all untracked files before wiping them from the working tree. Always use git stash -u during context switches to avoid leaving orphan files on disk!

git stash apply Non-Destructive

Restores changes from the top stash into your working directory without removing the stash from the stack. Ideal when testing stashed changes across multiple target branches safely.

git stash pop Apply & Drop

Applies the top stash and immediately deletes it from the stack. Warning: If merge conflicts occur during the pop, Git intentionally leaves the stash on the stack so you do not lose your work!

git stash branch Conflict Insulator

Creates and switches to a brand-new branch rooted at the exact commit where the stash was created, then applies the stash cleanly. Neutralizes conflicts caused by an evolving main branch.

Part 02

History Surgery: git commit --amend & The Three Reset Modes

When you make a mistake in Git, you don't overwrite history in place—Git's object store is strictly append-only. Commands like git commit --amend and git reset generate new commits or move branch pointers across the Three Trees (Working Directory, Staging Index, and HEAD):

Reset Mode HEAD Pointer (Commit Tree) Staging Area (Index) Working Directory (Disk Files)
git reset --soft <commit> ✓ Moves to target commit ✗ UNTOUCHED (Retains staged state) ✗ UNTOUCHED (Retains local disk edits)
git reset --mixed <commit> (Default) ✓ Moves to target commit ✓ CLEARED (Matches target commit) ✗ UNTOUCHED (Local disk edits preserved!)
git reset --hard <commit> ✓ Moves to target commit ✓ CLEARED (Matches target commit) ✓ OVERWRITTEN (Destroys local uncommitted edits!)
Under the Hood: How "git commit --amend" Works

When you run git commit --amend, Git does not modify the existing commit in place. Because every commit's identity is cryptographically bound to its contents, timestamp, and parent pointer via its SHA hash, modifying anything forces Git to synthesize a brand-new commit object:

1. Original Commit [SHA: 8f31b2] ← Points to Parent [SHA: 1a9e40]
2. Developer executes: git commit --amend
3. Git writes NEW Commit [SHA: 4c92a7] pointing to the same Parent [SHA: 1a9e40]
4. Branch reference is moved to point to [SHA: 4c92a7]
→ Old commit [8f31b2] is abandoned, becoming unreachable from the branch tip!
Part 03

The Ultimate Safety Net: git reflog and Reference Logs Forensics

What happens to commits that are abandoned after a --hard reset, a rebase, or an accidental branch deletion with git branch -D? They are not deleted immediately.

Git maintains a private, local chronological journal of every movement of HEAD inside .git/logs/HEAD. This journal is called the Reference Log (Reflog):

// Anatomy of an Entry in .git/logs/HEAD Local Journal
HEAD@{0}: commit: feat(auth): implement rsa key rotation
HEAD@{1}: reset: moving to HEAD~1 ← ACCIDENTAL HARD RESET!
HEAD@{2}: commit: feat(auth): implement session validation
HEAD@{3}: checkout: moving from main to feature/auth-service
Reflog coordinates like HEAD@{1} represent points in time where HEAD rested. By running git reset --hard HEAD@{2} or referencing the raw SHA recorded in the reflog, you can rewind repository state and undo destructive mistakes instantly.
Reflog Lifecycle & Garbage Collection Constraints

Reflog entries do not last forever. They are governed by Git's automatic garbage collection daemon (git gc):

  • Reachable Commits: Kept in the reflog for a default of 90 days (gc.reflogExpire).
  • Unreachable / Dangling Commits: Kept for a default of 30 days (gc.reflogExpireUnreachable) before being permanently purged from disk.
  • Reflog is strictly local: Reflogs are never transferred across the network during git push or git fetch!

# ==============================================================================
# ShipForge Disaster Recovery Protocol & Stash Lifecycle
# ==============================================================================

# 1. SCENARIO A: Emergency Hotfix Context Switch
# Developer is working on 'feature/auth-service' with modified and untracked files
echo "uncommitted auth logic" >> src/shipforge/auth.py
echo "test payload" > tests/test_auth.py

# Stash EVERYTHING (including untracked tests) with a descriptive label
git stash push -u -m "WIP: auth token logic and test scaffold"

# Switch to main and apply emergency production patch
git switch main
git switch -c hotfix/critical-security-patch
echo "def patch_leak(): return True" > src/shipforge/hotfix.py
git add src/shipforge/hotfix.py
git commit -m "fix(security): patch token leak vulnerability"

# Merge hotfix into main
git switch main
git merge --no-ff hotfix/critical-security-patch -m "merge: resolve security hotfix"
git branch -d hotfix/critical-security-patch

# Return to feature branch and re-apply stashed work
git switch feature/auth-service
git stash pop

# ==============================================================================
# 2. SCENARIO B: Catastrophic Branch Deletion & Reflog Resurrection
# ==============================================================================
# Suppose an engineer accidentally deletes feature/auth-service with unmerged commits:
git switch main
git branch -D feature/auth-service  # Force deletes unmerged branch!

# QUERY REFLOG to find the last known commit SHA on that branch
# git reflog show HEAD
# Output: 7c4912b HEAD@{2}: commit: feat(auth): implement token authentication service

# RESURRECT BRANCH instantly from the commit hash discovered in the reflog:
git switch -c feature/auth-service 7c4912b

# ✓ Branch is fully restored with zero data loss!
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Stashing Without the -u Flag

Running a bare git stash when new files have been created in the repository.

Why this causes broken builds: Default stashing captures tracked files only. All new untracked files remain sitting in your working directory. When you switch to another branch (like a release hotfix branch), those untracked files travel with you, polluting your test runs and accidentally getting committed to the wrong branch!

❌ Assuming Reflog Protects Untracked Files

Running git reset --hard while holding uncommitted, untracked working files.

The Limits of Reflog: The Reference Log tracks movements of commits. If you wipe uncommitted changes from your disk using git reset --hard or git clean -fd without first committing or stashing with -u, those changes never entered the Git object database and are gone forever.

Runbook

Executing & Validating ShipForge Milestone 03

Follow these terminal commands to inspect raw stash commit objects, query the reference log, and practice non-destructive resets:

# 1. Create a stash and inspect its multi-parent commit object structure:
echo "temporary edit" >> README.md
git stash push -m "inspect-stash-test"
git cat-file -p stash@{0}
Notice that the commit output explicitly prints multiple "parent" lines!
# 2. View the complete reference log timeline:
git reflog --date=relative
Displays the relative time, command name, and target SHA for every HEAD transition.
# 3. Perform a soft reset to squash or recommit without losing staged state:
git reset --soft HEAD~1
git status
Your commit is unwound, but all files remain staged in the Index, ready for an immediate updated commit.
