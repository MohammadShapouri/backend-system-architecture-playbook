Part 01

Computer Science: Git as a Content-Addressable Object Store

Most developers view Git as a system that records "file deltas" or diffs over time (the model used by legacy VCS systems like CVS or SVN). Git does not store diffs. Git is fundamentally a simple content-addressable key-value datastore with a version control user interface layered on top.

When you hand content to Git, it hashes the payload using SHA-1 (or SHA-256 in newer configurations), prepends a header containing the object type and size in bytes, compresses it via Zlib, and writes it directly to disk under .git/objects/. The 40-character hexadecimal hash serves as the immutable key:

// Cryptographic Header Construction:
header = f"{object_type} {content_length_in_bytes}\0"
store_hash = sha1(header + raw_content).hexdigest()
Disk Path: .git/objects/{store_hash[0:2]}/{store_hash[2:40]}
blob Data Unit

Binary Large Object. Stores raw file contents only. A blob stores zero metadata: no filename, no directory path, and no POSIX execution permissions. Identical file contents across different folders share the exact same blob SHA.

tree Directory

Represents a directory snapshot. Maps filenames, directory modes (e.g. 100644 standard, 100755 executable), and links them to their associated blob hashes or child sub-tree hashes.

commit State Node

An immutable snapshot metadata wrapper. Holds a pointer to the root tree object, an array of parent commit SHAs (forming the DAG), author and committer timestamps, and the semantic commit log message.

tag Annotated Pin

An annotated tag object. Explicitly points directly to a specific commit SHA, storing an optional GPG signature, tagger identity, timestamp, and release notes. (Distinct from lightweight reference tags).

Part 02

Under the Hood: The Three-Tree State Lifecycle

To master Git operations without memorizing arbitrary recipes, you must visualize Git's internal state machine. Git manages content using three distinct physical and virtual staging structures called The Three Trees:

Tree Dimension Physical Location Underlying Data Representation Role in System Lifecycle
1. Working Directory Local OS Filesystem Actual files, symlinks, and directories unpackaged on disk. Where you author, modify, and test application source code. Untracked and uncommitted changes live here.
2. Staging Area (Index) .git/index (Binary file) A sorted binary cache listing file paths, permission modes, and SHA-1 hashes of staged blobs. The proposed next commit snapshot. When you run git commit, Git reads the Index to build trees, not the working disk!
3. HEAD Commit Tree .git/objects/ & .git/refs/ An immutable tree object referenced by the commit currently pointed to by the HEAD reference. The permanent historical snapshot of the branch you have checked out. The parent base of future commits.

git restore --staged <file>
Copies HEAD version of file into Index without touching disk.

git restore <file>
Overwrites working file on disk with the staged/HEAD version. Destructive!

Part 04

File Tracking Mechanics: Cache Surgery, Untracking & .gitignore

In Git's vocabulary, a file is either Tracked or Untracked:

  • Tracked: The file path is physically indexed in the Staging Area (.git/index). It was either part of the last commit snapshot or has been staged using git add.
  • Untracked: The file physically exists in the Working Directory, but is entirely absent from the Index and has never been committed.
Stopping Tracking: git rm --cached Cache Surgery

What happens when a developer accidentally commits a sensitive config file, like config/secrets.json, and wants Git to forget it without deleting the local file from their development machine?

# WRONG: Deletes file from working disk!
git rm config/secrets.json
# CORRECT: Removes from Index ONLY, preserves disk!
git rm --cached config/secrets.json
git rm -r --cached build/ # Recursive for directories

--cached strips the path from .git/index while leaving the file on the physical filesystem untouched. The file immediately transitions to Untracked status.

.gitignore Precedence & Syntax Filtering Rules

.gitignore instructs Git never to stage or display matching untracked files in git status.

# 1. Ignore all .log files anywhere:
*.log
# 2. Negation: DO NOT ignore critical.log:
!critical.log
# 3. Leading slash: Anchor to root directory only:
/dist/
# 4. Trailing slash: Match directories ONLY:
build/

Golden Rule: .gitignore operates only on Untracked files! If a file is already in the repository index, adding it to .gitignore does nothing until you untrack it with git rm --cached!

The .gitkeep Convention

Because Git tracks content via blobs and trees, Git is fundamentally incapable of tracking an empty directory. A directory only exists in Git if it contains at least one leaf blob.

To force Git to track an empty folder (such as an empty logs/ or storage/uploads/ directory), teams place an empty file named .gitkeep inside it. While .gitkeep is not a formal Git feature, it creates a blob that anchors the parent tree into the commit graph.

Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The "Ignored After Commit" Trap

Adding a secret file like .env to .gitignore *after* it has already been committed to the repository.

Why this causes data leaks: .gitignore instructs Git to ignore untracked files. If the file is already tracked in the index, Git ignores the rule and continues tracking future changes! You must explicitly execute git rm --cached .env to eject it from the index.

❌ The Blind "git add ." Blast

Routinely typing git add . or git commit -a without inspecting the staging index.

Why this causes broken builds: It accidentally sweeps temporary logs, local database sqlite files, OS metadata (.DS_Store), and half-edited debug code into the commit history. Senior engineers stage selectively using git add -p (patch mode) to audit every single chunk before staging.

Runbook

Executing & Validating ShipForge Milestone 01

Follow these terminal commands to initialize the ShipForge repository, inspect the internal object model using plumbing commands, and perform cache untracking:

# 1. Initialize ShipForge repository and examine pristine .git directory:
mkdir shipforge && cd shipforge
git init
ls -la .git/
Observe the creation of HEAD, config, description, hooks/, and empty objects/ and refs/ directories.
# 2. Author a file and inspect how Git generates raw blobs before committing:
echo "ShipForge Microservice Core" > README.md
git add README.md
# Query the Staging Index to view the generated blob SHA:
git ls-files --stage
Output displays mode 100644, a 40-character SHA-1 hash, and README.md.
# 3. Interrogate the object database directly using plumbing commands:
BLOB_SHA=$(git ls-files -s README.md | awk '{print $2}')
git cat-file -t $BLOB_SHA # Prints object type: "blob"
git cat-file -p $BLOB_SHA # Prints raw payload content!
# 4. Simulate committing a secret and performing cache surgery:
echo "API_KEY=secret_live_99" > .env
git add .env
git commit -m "chore: accidental secret addition"

# Eject from index without deleting from disk:
git rm --cached .env
echo ".env" >> .gitignore
git commit -m "chore: untrack and ignore local env"
Verifies that .env remains on your disk, but is safely purged from the active tree and ignored!
