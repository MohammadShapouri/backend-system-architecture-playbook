Part 01

Computer Science: Sub-Window Weighting & Constant Memory Scaling

When designing rate-limiting infrastructure for millions of tenants, engineers face a classic computer science dilemma: Precision vs. Resource Footprint.

As demonstrated in Chapter 01, the Sliding Window Log stores an individual timestamp for every single request. If 500,000 active clients each execute 1,000 requests per hour, your storage engine must index 500,000,000 timestamp elements in memory. Under high load, this causes out-of-memory (OOM) crashes.

To solve this, Cloudflare and major content delivery networks pioneered the Sliding Window Counter algorithm. It uses linear interpolation across rolling fixed-time blocks, estimating request volume with mathematical precision while requiring exactly two numbers per client ($O(1)$ memory):

The Sliding Window Counter Linear Interpolation Formula

Weighting Previous Window Overlap Against Current Window Volume

Standard Formula:
Count = Current_Window_Requests + (Previous_Window_Requests × Overlap_Percentage)
Overlap_Percentage = (Window_Size - Elapsed_Time_In_Current_Window) / Window_Size
Concrete Interpolation Scenario Window Size: 60s • Limit: 100 req
Previous Minute [00:00 - 01:00]:
• Total Requests Recorded = 80 requests
Stays stored in cache as static integer
Current Minute [01:00 - 02:00]:
• Current Timestamp = 01:18 (18 seconds elapsed)
• Requests in Current Window = 30 requests
// Step-by-Step Mathematical Calculation at 01:18:
1. Elapsed time in current window = 18 seconds (30% through the window)
2. Remaining overlap from previous window = (60 - 18) / 60 = 42 / 60 = 0.70 (70% overlap)
3. Weighted previous requests = 80 × 0.70 = 56 requests
4. Estimated rolling requests = 30 (current) + 56 (weighted previous) = 86 requests
→ 86 ≤ 100: REQUEST ALLOWED! Exactly 14 units of quota remaining.
Error Bound Metrology:

Cloudflare’s production benchmark analysis proves that under real-world non-uniform traffic distributions, the estimation error of the Sliding Window Counter is mathematically bounded under 0.05%. By assuming the previous window's traffic was evenly distributed, we eliminate the $2\times$ boundary burst bug of Fixed Window while reducing Redis storage requirements by over 99.8% compared to Sliding Window Log.

Part 02

Velocity vs. In-Flight Traffic: Rate Limiting vs. Concurrency Semaphores

Many backend teams suffer catastrophic server outages despite having active rate limiters because they treat Rate Limiting and Concurrency Limiting as synonymous. They govern two completely different physical constraints of a web server:

1. Velocity Rate Limiter Requests Over Time

Measures the frequency or velocity of incoming requests across a calendar or rolling window (e.g., maximum 100 requests per 1 minute).

  • Protects: API credit allocations, payment billing quotas, and overall network bandwidth.
  • Measurement Units: Requests per Second (RPS) or Requests per Minute (RPM).
  • Blind Spot: Completely unaware of request execution duration! Does not care if a request finishes in 2ms or 15 seconds.
2. Concurrency Semaphore Simultaneous In-Flight Requests

Measures the number of requests actively executing at this exact microsecond on the server (e.g., maximum 5 simultaneous requests per tenant).

  • Protects: Operating system worker threads, CPU registers, database connection pool sockets, and external AI GPU resources.
  • Measurement Units: Active in-flight connections (Lease tokens).
  • Action: Decrements available slots upon request entry, releases slots upon response completion.
The Concurrency Starvation Trap: Why Rate Limiters Alone Cannot Prevent Outages

Consider a heavy reporting endpoint: POST /api/v1/analytics/export. Each execution consumes 1 database connection socket and runs for 8 full seconds. The tenant is assigned a generous rate limit of 60 requests per minute.

T=0s: A malicious user or automated bot fires 50 requests simultaneously.
Velocity Rate Limiter Check: 50 ≤ 60 requests per minute → ALLOWED!
FastAPI / SQLAlchemy Engine: 50 worker tasks execute simultaneously...
→ SQLAlchemy QueuePool Capacity (20 connections) IS COMPLETELY SATURATED!
→ All other users across the entire company receive 500 Internal Server Errors!

✓ The Dual-Control Architecture: Pair a Velocity Rate Limiter (60 req/min) with a Concurrency Semaphore (max 3 in-flight requests per user). Request #4 is rejected immediately with HTTP 429, preserving database sockets!

Part 03

Concurrency Mechanics: Asynchronous Leases & Deadlock Prevention

Implementing a concurrency limiter in an asynchronous web framework requires managing an in-flight **lease lifecycle**. When a request arrives, the server checks out a lease; when the request finishes, the server releases the lease:

The Concurrency Semaphore Lease State Machine
1. Acquire Lease Check in-flight count < max_concurrency
→ issue lease →
2. In-Flight Execution Execute heavy route with lease active • Lease carries a safety TTL!
→ release lease →
3. Release in Finally Decrement in-flight counter even if route crashes
// The Crash Deadlock Threat: Why Leases Must Have Timeouts

What happens if an asynchronous worker container receives a SIGKILL, experiences an unhandled segmentation fault, or has its network severed mid-execution?

If your semaphore increments a counter in Redis without an expiration, the in-flight counter never decrements. Over time, leaked leases accumulate until the client is permanently locked out of their API quota! All concurrency leases must carry an automated Lease Expiration Timeout (TTL) so orphaned tokens expire naturally if the holder dies.

1. Sliding Window Counter: src/sentinelflow/core/sliding_counter.py Constant Memory O(1) 
# ==============================================================================
# SentinelFlow - Sliding Window Counter (Milestone 04)
# ==============================================================================

import time
from typing import Dict, Tuple
from sentinelflow.core.models import RateLimitResult

class SlidingWindowCounter:
    """
    SLIDING WINDOW COUNTER ALGORITHM:
    Cloudflare's hybrid approximation. Uses weighted linear interpolation across
    the current and previous discrete window blocks.
    Guarantees O(1) memory complexity (stores exactly 2 numbers per client).
    """
    def __init__(self, limit: int, window_seconds: float):
        self.limit = limit
        self.window_seconds = float(window_seconds)
        # Map: key -> (current_window_idx, current_count, prev_window_count)
        self._states: Dict[str, Tuple[int, int, int]] = {}

    def acquire(self, key: str, cost: int = 1) -> RateLimitResult:
        now_wall = time.time()
        current_window_idx = int(now_wall // self.window_seconds)
        window_start_time = current_window_idx * self.window_seconds
        time_into_current = now_wall - window_start_time

        stored_idx, current_count, prev_count = self._states.get(
            key, (current_window_idx, 0, 0)
        )

        # 1. State Rolling: Advance window blocks based on elapsed intervals
        if current_window_idx > stored_idx:
            if current_window_idx == stored_idx + 1:
                # Next contiguous window: current shifts to previous
                prev_count = current_count
            else:
                # Jumped ahead by 2 or more windows: previous expires completely
                prev_count = 0
            current_count = 0
            stored_idx = current_window_idx

        # 2. LINEAR INTERPOLATION FORMULA
        # Overlap percentage decreases as time progresses into the current window
        overlap_weight = max(0.0, (self.window_seconds - time_into_current) / self.window_seconds)
        estimated_count = current_count + (prev_count * overlap_weight)

        reset_after = max(0.0, self.window_seconds - time_into_current)
        reset_epoch = int(window_start_time + self.window_seconds)

        # 3. EVALUATION CHECK
        if estimated_count + cost <= self.limit:
            current_count += cost
            self._states[key] = (stored_idx, current_count, prev_count)
            remaining = max(0, int(self.limit - (estimated_count + cost)))
            return RateLimitResult(
                allowed=True,
                limit=self.limit,
                remaining=remaining,
                reset_after_seconds=reset_after,
                reset_epoch_seconds=reset_epoch
            )

        # Throttled
        self._states[key] = (stored_idx, current_count, prev_count)
        return RateLimitResult(
            allowed=False,
            limit=self.limit,
            remaining=0,
            reset_after_seconds=reset_after,
            reset_epoch_seconds=reset_epoch
        )
2. Asynchronous In-Flight Semaphore: src/sentinelflow/core/concurrency_limiter.py In-Flight Connection Protection 
# ==============================================================================
# SentinelFlow - Async Concurrency Semaphore with Lease TTL (Milestone 04)
# ==============================================================================

import time
import uuid
import asyncio
from dataclasses import dataclass
from typing import Dict, Optional

class ConcurrencyLimitExceeded(Exception):
    """Raised when maximum simultaneous in-flight connections are saturated."""
    pass


@dataclass(frozen=True)
class ConcurrencyLease:
    lease_id: str
    key: str
    acquired_at: float
    expires_at: float


class AsyncConcurrencyLimiter:
    """
    CONCURRENCY SEMAPHORE:
    Limits simultaneous in-flight executions per tenant/route.
    Includes automated TTL lease reclamation to defend against container crashes.
    """
    def __init__(self, max_concurrency: int, lease_timeout_seconds: float = 30.0):
        self.max_concurrency = max_concurrency
        self.lease_timeout_seconds = lease_timeout_seconds
        # Key -> Dict[lease_id, expires_at]
        self._active_leases: Dict[str, Dict[str, float]] = {}
        self._lock = asyncio.Lock()

    async def acquire_lease(self, key: str) -> ConcurrencyLease:
        now_mono = time.monotonic()
        async with self._lock:
            leases = self._active_leases.setdefault(key, {})

            # 1. DEADLOCK DEFENSE: Purge expired leases from crashed holders
            expired = [lid for lid, exp in leases.items() if exp <= now_mono]
            for lid in expired:
                del leases[lid]

            # 2. EVALUATION CHECK
            if len(leases) >= self.max_concurrency:
                raise ConcurrencyLimitExceeded(
                    f"Maximum in-flight concurrency of {self.max_concurrency} reached for key '{key}'."
                )

            # 3. ISSUE LEASE
            lease_id = str(uuid.uuid4())
            expires_at = now_mono + self.lease_timeout_seconds
            leases[lease_id] = expires_at

            return ConcurrencyLease(
                lease_id=lease_id,
                key=key,
                acquired_at=now_mono,
                expires_at=expires_at
            )

    async def release_lease(self, lease: ConcurrencyLease) -> None:
        # Releases in-flight lease token gracefully upon completion
        async with self._lock:
            leases = self._active_leases.get(lease.key)
            if leases and lease.lease_id in leases:
                del leases[lease.lease_id]
3. Composite Dual-Throttling Guard: src/sentinelflow/core/dual_guard.py Velocity + In-Flight Coordination 
# ==============================================================================
# SentinelFlow - Dual-Control Engine: Velocity + Concurrency (Milestone 04)
# ==============================================================================

from contextlib import asynccontextmanager
from sentinelflow.core.sliding_counter import SlidingWindowCounter
from sentinelflow.core.concurrency_limiter import (
    AsyncConcurrencyLimiter, ConcurrencyLimitExceeded
)
from sentinelflow.core.models import RateLimitResult

class DualControlGuard:
    """
    ORCHESTRATES DUAL-CONTROL THROTTLING:
    Enforces rolling velocity limits (requests/time) AND simultaneous in-flight limits.
    """
    def __init__(
        self,
        velocity_limit: int,
        window_seconds: float,
        max_concurrency: int,
        lease_timeout: float = 30.0
    ):
        self.rate_limiter = SlidingWindowCounter(velocity_limit, window_seconds)
        self.concurrency_limiter = AsyncConcurrencyLimiter(max_concurrency, lease_timeout)

    @asynccontextmanager
    async def throttle(self, key: str, cost: int = 1):
        # 1. Gate 1: Check Velocity Rate Limit (Sliding Window Counter)
        rate_res: RateLimitResult = self.rate_limiter.acquire(key, cost)
        if not rate_res.allowed:
            raise ConcurrencyLimitExceeded(f"Velocity limit exceeded. Reset in {rate_res.reset_after_seconds:.1f}s")

        # 2. Gate 2: Acquire In-Flight Concurrency Lease
        lease = await self.concurrency_limiter.acquire_lease(key)
        try:
            yield rate_res  # Hand control to route execution
        finally:
            # 3. Always release lease in teardown phase!
            await self.concurrency_limiter.release_lease(lease)
4. Verification Battery: tests/unit/test_sliding_counter.py Accuracy & Concurrency Tests 
import asyncio
import pytest
from sentinelflow.core.sliding_counter import SlidingWindowCounter
from sentinelflow.core.concurrency_limiter import (
    AsyncConcurrencyLimiter, ConcurrencyLimitExceeded
)

class TestSlidingCounterAndSemaphores:
    """Validates sliding window counter interpolation and async concurrency caps."""

    def test_sliding_counter_interpolates_sub_window_overlap(self, mocker):
        # Limit: 100 requests per 60 seconds
        limiter = SlidingWindowCounter(limit=100, window_seconds=60.0)

        mock_time = mocker.patch("time.time")
        
        # Step 1: Send 80 requests in Window 0 (at second 30.0)
        mock_time.return_value = 30.0
        for _ in range(80):
            assert limiter.acquire("tenant_alpha").allowed is True

        # Step 2: Jump into Window 1 at second 78.0 (18 seconds into new window)
        mock_time.return_value = 78.0
        
        # Math: Overlap is (60 - 18) / 60 = 70%. Previous weighted = 80 * 0.70 = 56.
        # Current capacity available = 100 - 56 = 44 requests.
        allowed_count = 0
        for _ in range(50):
            if limiter.acquire("tenant_alpha").allowed:
                allowed_count += 1

        # Verifies mathematical interpolation throttles at exactly 44 requests!
        assert allowed_count == 44

    @pytest.mark.asyncio
    async def test_concurrency_limiter_caps_simultaneous_in_flight_tasks(self):
        # Max 2 concurrent in-flight requests
        sem = AsyncConcurrencyLimiter(max_concurrency=2, lease_timeout_seconds=5.0)

        lease1 = await sem.acquire_lease("user_42")
        lease2 = await sem.acquire_lease("user_42")

        # 3rd concurrent attempt must be rejected immediately!
        with pytest.raises(ConcurrencyLimitExceeded):
            await sem.acquire_lease("user_42")

        # Release lease 1
        await sem.release_lease(lease1)

        # Slot becomes available immediately
        lease3 = await sem.acquire_lease("user_42")
        assert lease3.lease_id != lease1.lease_id

    @pytest.mark.asyncio
    async def test_concurrency_limiter_auto_purges_dead_leases(self, mocker):
        sem = AsyncConcurrencyLimiter(max_concurrency=1, lease_timeout_seconds=2.0)
        
        mock_mono = mocker.patch("time.monotonic")
        mock_mono.return_value = 1000.0

        # Acquire lease, then simulate container crash (never calling release_lease)
        _ = await sem.acquire_lease("crashed_worker")

        # Advance time past lease TTL (2.1s later)
        mock_mono.return_value = 1002.1

        # Deadlock Defense: Auto-purges expired lease and allows new acquisition!
        lease = await sem.acquire_lease("crashed_worker")
        assert lease is not None
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Leaseless In-Flight Counting

Writing in_flight += 1; await process(); in_flight -= 1 without timeouts or UUID tokens.

Why this causes permanent outages: If the worker process terminates abruptly, throws an unhandled exception outside the try-block, or disconnects, the in-flight counter is never decremented. The user is permanently locked out of their API limit! Always use unique lease IDs paired with automated expiration timeouts.

❌ Relying on Rate Limits for Slow Endpoints

Configuring a rate limit of 60/min on a heavy 15-second database export without setting a concurrency cap.

Why this takes down production: A client can send 30 requests concurrently. All 30 requests pass the rate limiter, immediately exhausting your database connection pool (capping out at 20 sockets). All other routes across your company fail with 500 errors! Fix: Pair velocity limiters with an in-flight concurrency semaphore!
