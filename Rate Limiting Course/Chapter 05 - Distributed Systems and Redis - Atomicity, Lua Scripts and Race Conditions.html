Part 01

Computer Science: The Multi-Instance In-Memory Splintering Trap

In a monolithic application running as a single process on a single virtual machine, in-memory rate limiting works reliably. The Python process holds a single dictionary in RAM, and all incoming requests mutate that centralized data structure.

However, modern cloud deployments run on container orchestrators (Kubernetes, AWS ECS, GCP Cloud Run) that scale applications horizontally across multiple worker pods behind a load balancer. If your rate limiter stores state in Python dictionaries, **your rate limit is multiplied by the number of pods**:

The Memory Splintering Flaw Across Replicas

Target Limit: 100 requests per minute • 10 Active Kubernetes Pods

Cloud Load Balancer (Round-Robin Ingress)
Client distributes 1,000 requests across available pods
↓ traffic dispersed ↓
Pod 1 (RAM) Counter: 100/100 Allowed: 100
Pod 2 (RAM) Counter: 100/100 Allowed: 100
... Pod 10 (RAM) Counter: 100/100 Allowed: 100
✗ Total Permitted Requests = 1,000 Requests!
Because memory is not shared across pods, the client bypassed the quota by a factor of $10\times$, taking down the backend database!
Part 02

The Read-Modify-Write Concurrency Leak

To fix memory splintering, developers move state to a centralized database: **Redis**. Redis is chosen because it operates entirely in RAM and delivers sub-millisecond key-value operations.

However, naive distributed implementations written in Python introduce a severe concurrency vulnerability known as the Read-Modify-Write Race Condition:

The Read-Modify-Write Race Condition Across Network Sockets
Pod 1 (Worker A)
T=0ms: Runs redis.get("user:42")
Receives count = 9
9 < 10 → APPROVES REQUEST!
T=3ms: Runs redis.incr("user:42")
Pod 2 (Worker B)
T=1ms: Runs redis.get("user:42")
Receives count = 9! (Before A's incr)
9 < 10 → APPROVES REQUEST!
T=4ms: Runs redis.incr("user:42")
Redis Server Key State
Initial State: count = 9
After Pod 1: count = 10
After Pod 2: count = 11!
11 > Limit of 10! LEAK OCCURRED!
⚠ Why Python-Level Logic Cannot Fix This:

Because network transit takes time (1–3ms per socket trip), multiple application servers observe the exact same stale counter simultaneously. Under concurrent traffic bursts, dozens or hundreds of requests slip past your rate limit.

Furthermore, this multi-step approach wastes 3 network round-trips per HTTP request: 1. GET count → 2. INCR count → 3. EXPIRE count 60. If each Redis round-trip takes 2ms, your rate limiter adds 6ms of pure latency to every API call!

Part 03

The Industrial Solution: Atomic Redis Lua Scripts & EVALSHA

To eliminate both race conditions and network round-trip overhead, modern infrastructure executes rate-limiting logic directly inside the Redis engine using Lua scripts.

Redis executes Lua scripts in a single-threaded atomic context. While a Lua script is executing, no other Redis command or script can run. The entire rate-limiting decision (fetching state, calculating elapsed time, incrementing counters, and setting expiration) executes as one atomic operation in a single network round-trip:

Network Round-Trip Optimization: Multi-Command vs. Atomic Lua
Naive Python Multi-Command (3 Round-Trips)
1. Client → GET user:42 → Redis → Client (2ms)
2. Client → INCR user:42 → Redis → Client (2ms)
3. Client → EXPIRE user:42 60 → Redis → Client (2ms)
✗ Total Overhead: ~6.0ms • Vulnerable to race conditions!
Atomic Redis Lua Script (1 Round-Trip)
Single Execution: Client → EVALSHA <hash> key limit cost → Redis → Client
Redis executes get, check, increment, and expire atomically in memory.
✓ Total Overhead: ~1.2ms • Mathematically immune to race conditions!
// Production Bandwidth Optimization: EVAL vs. EVALSHA

If you execute scripts using raw EVAL <script_string>, your application transmits 500–1,000 bytes of Lua source text over the network for every single HTTP request.

The production standard is SCRIPT LOAD: during application startup, your backend registers the Lua script with Redis once. Redis compiles it and returns a 40-character SHA-1 hash. During runtime, requests execute via EVALSHA <sha1_hash>, transmitting only 20 bytes over the wire!

Part 04

Production Script Engineering: Token Bucket & Sliding Counter in Lua

We now write the exact, production-hardened Lua scripts that execute inside Redis for SentinelFlow:

1. Distributed Token Bucket (Lua) Burst Handling

Tracks token accumulation and monotonic epoch time in a Redis Hash, calculating refills on the fly and setting an automated TTL: 

-- KEYS[1]: Rate limit key (e.g. "sf:tb:tenant_1:user_42")
-- ARGV[1]: Capacity (burst limit)
-- ARGV[2]: Refill rate per second
-- ARGV[3]: Cost
-- ARGV[4]: Current timestamp (seconds.microseconds)

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local now = tonumber(ARGV[4])

local data = redis.call("HMGET", key, "tokens", "last_updated")
local tokens = tonumber(data[1])
local last_updated = tonumber(data[2])

if tokens == nil then
    tokens = capacity
    last_updated = now
else
    local delta = math.max(0, now - last_updated)
    tokens = math.min(capacity, tokens + (delta * rate))
    last_updated = now
end

if tokens >= cost then
    tokens = tokens - cost
    redis.call("HMSET", key, "tokens", tokens, "last_updated", last_updated)
    local ttl = math.ceil(capacity / rate) * 2
    redis.call("EXPIRE", key, ttl)
    return {1, math.floor(tokens)} -- Allowed
else
    redis.call("HMSET", key, "tokens", tokens, "last_updated", last_updated)
    local wait_time = (cost - tokens) / rate
    return {0, math.ceil(wait_time)} -- Rejected
end
2. Sliding Window Counter (Lua) O(1) Memory

Executes Cloudflare's weighted interpolation formula atomically in Redis, managing window rollover cleanly: 

-- KEYS[1]: Base key (e.g. "sf:swc:user_42")
-- ARGV[1]: Limit
-- ARGV[2]: Window size in seconds
-- ARGV[3]: Current timestamp (seconds)
-- ARGV[4]: Cost

local base_key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])

local current_window = math.floor(now / window)
local current_key = base_key .. ":" .. current_window
local previous_key = base_key .. ":" .. (current_window - 1)

local current_count = tonumber(redis.call("GET", current_key) or 0)
local previous_count = tonumber(redis.call("GET", previous_key) or 0)

local time_into_current = now % window
local weight = (window - time_into_current) / window
local estimated = current_count + (previous_count * weight)

if estimated + cost <= limit then
    redis.call("INCRBY", current_key, cost)
    redis.call("EXPIRE", current_key, math.ceil(window * 2))
    local remaining = math.max(0, math.floor(limit - (estimated + cost)))
    return {1, remaining} -- Allowed
else
    local reset_after = math.ceil(window - time_into_current)
    return {0, reset_after} -- Rejected
end

1. Asynchronous Redis Storage Manager: src/sentinelflow/storage/redis_manager.py Connection Pool & EVALSHA Engine 
# ==============================================================================
# SentinelFlow Storage - Async Redis Storage Manager (Milestone 05)
# ==============================================================================

import time
from pathlib import Path
from typing import Optional
import redis.asyncio as aioredis
from sentinelflow.core.models import RateLimitResult

LUA_DIR = Path(__file__).parent / "lua"

class RedisRateLimiter:
    """
    DISTRIBUTED REDIS RATE LIMITER:
    Pre-compiles Lua scripts via SCRIPT LOAD and executes with EVALSHA.
    Eliminates network latency round-trips and guarantees strict atomicity.
    """
    def __init__(self, redis_url: str = "redis://localhost:6379/0"):
        self.redis_url = redis_url
        # Sized Connection Pool for async performance
        self.pool = aioredis.ConnectionPool.from_url(
            self.redis_url, 
            max_connections=50, 
            decode_responses=True
        )
        self.client = aioredis.Redis(connection_pool=self.pool)
        self._token_bucket_sha: Optional[str] = None
        self._sliding_counter_sha: Optional[str] = None

    async def initialize(self) -> None:
        """
        STARTUP HOOK: Pre-loads Lua scripts into Redis RAM.
        Stores the resulting SHA-1 hashes for EVALSHA execution.
        """
        tb_script = (LUA_DIR / "token_bucket.lua").read_text(encoding="utf-8")
        swc_script = (LUA_DIR / "sliding_counter.lua").read_text(encoding="utf-8")

        self._token_bucket_sha = await self.client.script_load(tb_script)
        self._sliding_counter_sha = await self.client.script_load(swc_script)

    async def close(self) -> None:
        await self.client.aclose()
        await self.pool.disconnect()

    async def acquire_token_bucket(
        self, key: str, capacity: int, refill_rate_per_sec: float, cost: int = 1
    ) -> RateLimitResult:
        """Executes the distributed Token Bucket Lua script atomically."""
        now = time.time()
        redis_key = f"sf:tb:{key}"

        # EVALSHA executes compiled bytecode in 1 network round trip!
        res = await self.client.evalsha(
            self._token_bucket_sha,
            1,  # Number of keys
            redis_key,
            capacity,
            refill_rate_per_sec,
            cost,
            now
        )
        allowed_flag, metric = res[0], res[1]

        if allowed_flag == 1:
            return RateLimitResult(
                allowed=True,
                limit=capacity,
                remaining=metric,
                reset_after_seconds=0.0,
                reset_epoch_seconds=int(now)
            )

        return RateLimitResult(
            allowed=False,
            limit=capacity,
            remaining=0,
            reset_after_seconds=float(metric),
            reset_epoch_seconds=int(now + metric)
        )

    async def acquire_sliding_counter(
        self, key: str, limit: int, window_seconds: float, cost: int = 1
    ) -> RateLimitResult:
        """Executes the distributed Sliding Window Counter Lua script atomically."""
        now = int(time.time())
        redis_key = f"sf:swc:{key}"

        res = await self.client.evalsha(
            self._sliding_counter_sha,
            1,
            redis_key,
            limit,
            window_seconds,
            now,
            cost
        )
        allowed_flag, metric = res[0], res[1]

        if allowed_flag == 1:
            return RateLimitResult(
                allowed=True,
                limit=limit,
                remaining=metric,
                reset_after_seconds=0.0,
                reset_epoch_seconds=now
            )

        return RateLimitResult(
            allowed=False,
            limit=limit,
            remaining=0,
            reset_after_seconds=float(metric),
            reset_epoch_seconds=now + metric
        )

import pytest
import pytest_asyncio

@pytest_asyncio.fixture
async def redis_limiter(redis_container):

    limiter = RedisRateLimiter(redis_url=url)
    await limiter.initialize()
    
    yield limiter
    
    await limiter.client.flushdb()
    await limiter.close()


@pytest.mark.integration
class TestRedisLuaConcurrency:
    """Verifies that Redis Lua scripts execute atomically with ZERO race condition leaks."""

    async def test_token_bucket_lua_race_condition_proof(self, redis_limiter: RedisRateLimiter):
        """
        RACE CONDITION ELIMINATION TEST:
        Fires 50 concurrent requests simultaneously using asyncio.gather.
        Configured Capacity: Exactly 10 requests allowed.
        In an un-synchronized system, dozens leak through.
        In Lua: EXACTLY 10 pass, and EXACTLY 40 fail!
        """
        capacity = 10
        refill_rate = 0.1  # Very slow refill (1 token every 10s)

        # Fire 50 asynchronous tasks at the exact same millisecond
        tasks = [
            redis_limiter.acquire_token_bucket(
                key="race_test_client",
                capacity=capacity,
                refill_rate_per_sec=refill_rate
            )
            for _ in range(50)
        ]
        results = await asyncio.gather(*tasks)

        allowed_count = sum(1 for r in results if r.allowed)
        blocked_count = sum(1 for r in results if not r.allowed)

        # PROOF OF ATOMIC EXECUTION
        assert allowed_count == 10
        assert blocked_count == 40

    async def test_sliding_counter_lua_expiration_set_automatically(self, redis_limiter: RedisRateLimiter):
        # Verify that every executed rate limit key carries an automated TTL
        _ = await redis_limiter.acquire_sliding_counter(
            key="ttl_test_user",
            limit=20,
            window_seconds=60.0
        )
        
        # Keys matching pattern must have a positive TTL
        keys = await redis_limiter.client.keys("sf:swc:ttl_test_user:*")
        assert len(keys) > 0
        ttl = await redis_limiter.client.ttl(keys[0])
        assert ttl > 0 # Proof that key is guaranteed to expire and won't leak RAM!
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Long-Running Loops in Redis Lua

Writing complex nested for i=1, 10000 do ... end loops inside a Redis Lua script.

Why this causes full backend outages: Redis executes Lua in a single-threaded global lock. While your script is running, Redis cannot process any other command for any service in your company! If your Lua script takes 50ms to run, Redis's throughput drops from 100,000 ops/sec to 20 ops/sec, taking down caching, queues, and session lookups. Keep Lua scripts sub-millisecond ($O(1)$ ops only).

❌ The "Zombie Key" Memory Leak

Using redis.call("HSET", key, ...) without calling redis.call("EXPIRE", key, ttl).

Why this exhausts cluster RAM: Every unique IP, customer, or API key that visits your service creates a new key in Redis. If keys never expire, they remain resident in Redis RAM permanently. Over months of traffic, millions of abandoned keys accumulate until Redis triggers its maxmemory eviction policy, destroying your production cache!
