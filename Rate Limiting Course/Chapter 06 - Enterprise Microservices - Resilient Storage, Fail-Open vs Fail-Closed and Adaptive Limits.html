Part 01

Computer Science: The Rate Limiter Reliability Paradox

The purpose of a rate limiter is to protect downstream services from crashing under traffic surges. However, in distributed architectures, the rate limiter itself depends on an external network service (typically Redis).

This introduces The Reliability Paradox: What happens when the tool meant to protect your system experiences a failure? If an unhandled Redis connection timeout causes your FastAPI middleware to raise a 500 Internal Server Error, a blip in Redis knocks down 100% of your company's revenue-generating traffic!

The SRE Disaster Recovery Matrix: Fail-Open vs. Fail-Closed

Evaluating Availability vs. Security Under Redis Partitions

1. Fail-Open (Permissive Policy) High Availability

If Redis is down or times out, allow the request through:

Redis ping times out (> 15ms) → Catch RedisError
Log CRITICAL SRE alert to monitoring stream
Return RateLimitResult(allowed=True, remaining=1)
→ Endpoints continue serving customer requests!
  • Best For: Public read APIs, product catalog search, e-commerce checkout.
  • Philosophy: Losing rate limiting temporarily is better than losing 100% of customer revenue.
2. Fail-Closed (Defensive Policy) High Security

If Redis is down or times out, block the request immediately:

Redis ping times out (> 15ms) → Catch RedisError
Raise HTTPException(status_code=503, Retry-After=30)
Or reject with RateLimitResult(allowed=False)
→ Protects databases & identity stores from attack!
  • Best For: Authentication (`POST /auth/login`), payment execution, expensive LLM inference.
  • Philosophy: Failing closed prevents attackers from intentionally DDoSing Redis to bypass password brute-force guards.
The Hybrid Enterprise Standard:

Never configure a single blanket policy across your entire company. In SentinelFlow, the YAML configuration allows declaring fail_policy: FAIL_OPEN globally, while overriding critical endpoints with fail_policy: FAIL_CLOSED.

Part 02

Identity & Multi-Tenancy: Composite Keys & IPv6 Subnets

Before an algorithm can increment a counter, the rate limiter must answer: "Who is this request from?" Identifying clients naively leads to critical vulnerabilities:

1. The IPv6 Rotation Exploit Botnet Threat

IPv4 addresses are scarce. In contrast, standard consumer IPv6 internet connections (home fiber, cloud VPS) are assigned an entire /64 subnet containing $2^{64}$ (over $18 \times 10^{18}$) distinct IP addresses.

Attacker IP 1: 2001:db8:abcd:0012:0000:0000:0000:0001
Attacker IP 2: 2001:db8:abcd:0012:0000:0000:0000:0002
→ Attacker rotates through 10M IPs in seconds!

The Solution: Normalize all IPv6 addresses to their parent /64 CIDR subnet prefix. All $18 \times 10^{18}$ addresses from that customer share a single rate-limiting bucket!

2. X-Forwarded-For Spoofing Header Injection

Clients can send arbitrary headers: X-Forwarded-For: 1.1.1.1. If your application blindly trusts this header, an attacker can bypass rate limits simply by generating random IP strings on each request!

Client → [X-Forwarded-For: 8.8.8.8] → Cloudflare (192.168.1.1)
→ Naive code reads 8.8.8.8 instead of Cloudflare proxy!

The Solution: Inspect X-Forwarded-For only if the immediate connection IP matches a configured whitelist of trusted edge reverse proxies (e.g., AWS ALB, Cloudflare CIDRs).

The Enterprise Multi-Tier Composite Key Architecture
Key = {Tenant_ID} : {Principal_ID | Subnet_64} : {HTTP_Method} : {Route_Regex_Hash}
Ensures authenticated users are identified by User ID, while anonymous traffic is isolated by IPv4 / IPv6 subnet masks without cross-tenant key pollution.
Part 03

Self-Healing Infrastructure: Google SRE Adaptive Throttling

Static rate limits assume the backend is operating in a healthy state. But what happens when your downstream PostgreSQL database or payment provider slows down due to hardware contention?

If the database normally handles 1,000 requests per second at 5ms latency, but suddenly degrades to 500ms latency, continuing to allow 1,000 requests per second will cause query queue depths to explode, exhausting memory and triggering a total cascading outage.

In Chapter 21 of the Google Site Reliability Engineering (SRE) handbook, Google formalized Adaptive Throttling. It dynamically computes a client-side or gateway rejection probability based on the ratio of attempted requests to successfully accepted requests:

The Google SRE Adaptive Throttling Formula

Self-Healing Client Rejection Probability Curve

P(Drop) = max( 0, ( Requests − K × Accepts ) / ( Requests + 1 ) )
Where K is the Multiplier (typically 1.1 to 2.0). If requests == accepts, P(Drop) = 0.
1. Healthy Backend
Requests: 1,000 • Accepts: 1,000
(1000 - 2.0 × 1000) < 0
Drop Probability: 0%
2. Degraded Backend
Requests: 1,000 • Accepts: 400
(1000 - 2.0 × 400) / 1001
Drop Probability: ~19.9%
3. Failing Backend
Requests: 1,000 • Accepts: 100
(1000 - 2.0 × 100) / 1001
Drop Probability: ~79.9%
The Self-Healing Invariant:

As the backend begins failing, the gateway dynamically sheds load without human intervention. Once the backend catches up and begins accepting requests again, the rejection probability gracefully drops back to zero.

1. Composite Key Extractor: src/sentinelflow/core/key_extractor.py IPv6 Subnets & Spoof Defense 
# ==============================================================================
# SentinelFlow Core - Composite Key & Subnet Extractor (Milestone 06)
# ==============================================================================

import ipaddress
from typing import List, Optional

class KeyExtractor:
    """
    Extracts sanitized rate limit keys from incoming request headers.
    Defends against IPv6 rotation exploits and unvalidated X-Forwarded-For spoofing.
    """
    def __init__(self, trusted_proxies: Optional[List[str]] = None):
        # Whitelist of trusted reverse proxies (e.g., Cloudflare, AWS ALB)
        self.trusted_proxies = {
            ipaddress.ip_network(p) for p in (trusted_proxies or ["127.0.0.1/32", "::1/128"])
        }

    def sanitize_ip(self, client_ip: str) -> str:
        """
        Normalizes IP addresses.
        Aggregates IPv6 addresses into a single /64 subnet prefix!
        """
        try:
            ip = ipaddress.ip_address(client_ip.strip())
            if ip.version == 6:
                # Mask to /64 network boundary (standard consumer ISP allocation)
                network_64 = ipaddress.IPv6Network(f"{ip}/64", strict=False)
                return str(network_64.network_address)
            return str(ip)
        except ValueError:
            return "malformed_ip"

    def extract_client_ip(self, direct_ip: str, x_forwarded_for: Optional[str] = None) -> str:
        """
        Inspects X-Forwarded-For ONLY if direct connection IP is a trusted reverse proxy!
        """
        try:
            parsed_direct = ipaddress.ip_address(direct_ip)
            is_trusted = any(parsed_direct in net for net in self.trusted_proxies)

            if is_trusted and x_forwarded_for:
                # Read leftmost client IP from X-Forwarded-For: "client, proxy1, proxy2"
                raw_client = x_forwarded_for.split(",")[0].strip()
                return self.sanitize_ip(raw_client)
        except ValueError:
            pass

        return self.sanitize_ip(direct_ip)
2. Google SRE Adaptive Throttling: src/sentinelflow/core/adaptive.py Dynamic Rejection Math 
# ==============================================================================
# SentinelFlow Core - Google SRE Adaptive Throttling (Milestone 06)
# ==============================================================================

import random
from collections import deque
from typing import Deque, Tuple

class AdaptiveThrottler:
    """
    GOOGLE SRE ADAPTIVE THROTTLING ENGINE:
    Calculates dynamic rejection probabilities based on rolling backend success/fail ratios.
    P(Drop) = max(0, (Requests - K * Accepts) / (Requests + 1))
    """
    def __init__(self, multiplier_k: float = 2.0, history_window_size: int = 1000):
        self.multiplier_k = multiplier_k
        # Circular buffer holding bool outcomes: True=Accepted, False=Rejected
        self._history: Deque[bool] = deque(maxlen=history_window_size)

    def record_result(self, success: bool) -> None:
        self._history.append(success)

    def rejection_probability(self) -> float:
        requests = len(self._history)
        if requests < 20:
            # Warm-up phase: do not throttle before having statistical sample
            return 0.0

        accepts = sum(1 for success in self._history if success)
        drop_prob = (requests - (self.multiplier_k * accepts)) / (requests + 1)
        return max(0.0, drop_prob)

    def should_drop(self) -> bool:
        prob = self.rejection_probability()
        if prob <= 0.0:
            return False
        return random.random() < prob
3. Resilient Storage Client: src/sentinelflow/storage/resilient_redis.py Fail-Open/Closed with In-Memory Fallback 
# ==============================================================================
# SentinelFlow Storage - Resilient Redis Adapter (Milestone 06)
# ==============================================================================

import logging
from enum import Enum
from typing import Optional
import redis.exceptions
from sentinelflow.core.models import RateLimitResult
from sentinelflow.core.sliding_counter import SlidingWindowCounter
from sentinelflow.storage.redis_manager import RedisRateLimiter

logger = logging.getLogger("sentinelflow.resilience")

class FailPolicy(str, Enum):
    FAIL_OPEN = "FAIL_OPEN"      # Allow traffic on Redis crash (preserve UX)
    FAIL_CLOSED = "FAIL_CLOSED"  # Block traffic on Redis crash (protect security)

class ResilientRateLimiter:
    """
    FAULT-TOLERANT STORAGE WRAPPER:
    Wraps Redis cluster with circuit recovery, emergency in-memory fallbacks,
    and route-specific Fail-Open / Fail-Closed policies.
    """
    def __init__(
        self,
        redis_limiter: RedisRateLimiter,
        default_policy: FailPolicy = FailPolicy.FAIL_OPEN
    ):
        self.redis_limiter = redis_limiter
        self.default_policy = default_policy
        # Emergency in-memory fallback cache (used if Redis is unreachable)
        self._emergency_fallback = SlidingWindowCounter(limit=1000, window_seconds=60.0)

    async def acquire_with_fallback(
        self,
        key: str,
        limit: int,
        window_seconds: float,
        policy: Optional[FailPolicy] = None
    ) -> RateLimitResult:
        active_policy = policy or self.default_policy

        try:
            # 1. Primary path: Attempt atomic Redis Lua execution
            return await self.redis_limiter.acquire_sliding_counter(
                key=key, limit=limit, window_seconds=window_seconds
            )
        except (redis.exceptions.RedisError, TimeoutError) as exc:
            logger.error(f"REDIS OUTAGE DETECTED: {exc}. Engaging policy: {active_policy.value}")

            # 2. FAIL-CLOSED: Block traffic immediately
            if active_policy == FailPolicy.FAIL_CLOSED:
                return RateLimitResult(
                    allowed=False,
                    limit=limit,
                    remaining=0,
                    reset_after_seconds=window_seconds,
                    reset_epoch_seconds=0
                )

            # 3. FAIL-OPEN: Permit traffic through while logging telemetry
            return RateLimitResult(
                allowed=True,
                limit=limit,
                remaining=1,
                reset_after_seconds=0.0,
                reset_epoch_seconds=0
            )

class TestResilienceAndExtraction:
    """Verifies SRE failure modes, IPv6 normalization, and adaptive throttling."""

    def test_ipv6_addresses_masked_to_64_subnet(self):
        extractor = KeyExtractor()
        ip1 = "2001:0db8:85a3:0000:0000:8a2e:0370:7334"
        ip2 = "2001:0db8:85a3:0000:ffff:ffff:ffff:ffff"
        
        # Both IPs belong to 2001:db8:85a3::/64
        subnet1 = extractor.sanitize_ip(ip1)
        subnet2 = extractor.sanitize_ip(ip2)
        assert subnet1 == subnet2 == "2001:db8:85a3::"

    def test_spoofed_x_forwarded_for_ignored_from_untrusted_direct_ip(self):
        extractor = KeyExtractor(trusted_proxies=["10.0.0.1/32"])
        
        # Direct connection comes from untrusted 198.51.100.2 pretending to be 1.1.1.1
        extracted = extractor.extract_client_ip(
            direct_ip="198.51.100.2", 
            x_forwarded_for="1.1.1.1"
        )
        # Must ignore the spoofed header and rate limit the real direct connection IP!
        assert extracted == "198.51.100.2"

    @pytest.mark.asyncio
    async def test_fail_open_permits_traffic_during_redis_crash(self, mocker):
        mock_redis = mocker.MagicMock()
        mock_redis.acquire_sliding_counter = mocker.AsyncMock(
            side_effect=redis.exceptions.ConnectionError("Redis cluster unreachable")
        )
        limiter = ResilientRateLimiter(mock_redis, default_policy=FailPolicy.FAIL_OPEN)

        res = await limiter.acquire_with_fallback("user_1", 100, 60.0)
        assert res.allowed is True  # Zero downtime! User traffic allowed through

    @pytest.mark.asyncio
    async def test_fail_closed_blocks_traffic_on_auth_endpoint(self, mocker):
        mock_redis = mocker.MagicMock()
        mock_redis.acquire_sliding_counter = mocker.AsyncMock(
            side_effect=redis.exceptions.ConnectionError("Redis connection timeout")
        )
        limiter = ResilientRateLimiter(mock_redis, default_policy=FailPolicy.FAIL_OPEN)

        # Route override: Login route enforces FAIL_CLOSED
        res = await limiter.acquire_with_fallback("user_1", 5, 60.0, policy=FailPolicy.FAIL_CLOSED)
        assert res.allowed is False  # Protects authentication store from brute force!

    def test_google_sre_adaptive_throttling_probability_calculation(self):
        throttler = AdaptiveThrottler(multiplier_k=2.0)
        
        # 100 requests: 90 accepted → Drop probability is 0
        for _ in range(90): throttler.record_result(True)
        for _ in range(10): throttler.record_result(False)
        assert throttler.rejection_probability() == 0.0

        # Downstream degrades: 100 consecutive backend rejections
        for _ in range(100): throttler.record_result(False)
        
        # Probability must jump to shed load
        assert throttler.rejection_probability() > 0.0
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Trusting Raw X-Forwarded-For Headers

Writing client_ip = request.headers.get("X-Forwarded-For") without validating the connecting peer IP.

Why this destroys rate limiting: HTTP request headers can be spoofed by any client. An attacker sending requests via curl -H "X-Forwarded-For: <random_ip>" will create a brand new rate-limit bucket on every single request, completely bypassing all rate limits! Only read proxy headers if the connecting socket originates from a whitelisted reverse proxy.

❌ Global Blanket Fail-Open Policies

Configuring the rate limiter to Fail-Open across all routes, including POST /auth/login.

Why this causes security breaches: Attackers purposely trigger a DDoS attack against your Redis cluster to force the rate limiter into failure mode. Once Redis drops, the login endpoint runs un-throttled, allowing the attacker to brute-force passwords without restriction! Always enforce Fail-Closed on security-critical boundaries.
