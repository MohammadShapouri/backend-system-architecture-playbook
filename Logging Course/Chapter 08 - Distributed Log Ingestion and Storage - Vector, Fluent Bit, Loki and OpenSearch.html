Part 01

Computer Science: The Log Shipper Tier (Vector vs. Fluent Bit)

Log shippers are specialized background proxy daemons responsible for extracting log lines from input sources (files, sockets, pipes), applying transformations (parsing, filtering, masking), buffering data against downstream backpressure, and delivering packets to storage endpoints.

Legacy Java-based collectors (like Logstash) consumed gigabytes of memory per node. Modern cloud-native infrastructure has converged on two ultra-high-performance tools written in systems languages:

1. Vector (Datadog) Rust • Staff Pick

Memory-safe, multi-threaded engine written in Rust. Features Vector Remap Language (VRL) for high-speed in-flight payload transformations.

Strengths: Built-in disk-backed buffering, native OpenTelemetry support, rich metrics and traces routing, extreme reliability under heavy load.

Top Throughput • Memory-Safe
2. Fluent Bit C • Lightweight

Ultra-lightweight processor written in C with an asynchronous architecture.

Strengths: Microscopic memory footprint (typically 5MB–15MB of RAM per node). Perfect for resource-constrained edge nodes and lightweight Kubernetes DaemonSets.

Lowest Memory • K8s Default
3. Logstash Java • Legacy

The original ELK stack workhorse running on the JVM.

Trade-offs: Heavyweight (often requires 500MB–2GB of RAM per instance). Too resource-intensive to deploy as a node DaemonSet in modern microservice clusters.

Heavy Footprint • Centralized Only

Part 02

The Multi-Line Problem: Reassembling Fragmented Stack Traces

By default, container runtimes (CRI) treat every single newline character (\n) as the termination of a discrete log event.

When an application crashes or raises an exception, Python, Java, and Go print multi-line tracebacks. If PulsePay's payment router throws an unhandled BankingGatewayTimeout exception with a 35-line stack trace, a naive collector treats it as 35 distinct log entries!

✗ Default CRI Output (Fragmented)

Every single line of the traceback becomes an orphan log record in Loki or OpenSearch:

Entry #1: Traceback (most recent call last):
Entry #2: File "/app/pulsepay/services/banking.py", line 42
Entry #3: response = await client.post(...)
Entry #4: BankingGatewayTimeout: Upstream rail dropped

Hazard: Searching for error.action = "PAYMENT_SETTLE" returns only the first line; the actual exception type is stored 3 records later with zero correlation!

✓ Reassembled Multiline Event

Collector applies a multiline aggregation rule to stitch lines together:

{
"timestamp": "2026-11-10T05:22:01.104281Z",
"level": "ERROR",
"error_details": {
"stack_trace": "Traceback (most recent call last):\n File ...\nBankingGatewayTimeout"
}
}

Guarantee: The entire stack trace is preserved within a single JSON attribute, preserving full contextual integrity.

Vector Multiline Reassembly Regex Heuristic

We configure Vector's source parser to detect the boundary of a new event. A new log event starts *only* when a line begins with a JSON opening brace { or an ISO-8601 timestamp; all subsequent indented lines are collapsed into the preceding record: 

# In Vector configuration (vector.toml):
[sources.kubernetes_logs.multiline]
start_pattern = '^\{'             # New event starts ONLY on opening JSON brace
condition_pattern = '^\{'         # Lines not matching are appended to previous event
mode = "halt_before"
timeout_ms = 500                   # Flush if no new line arrives in 500ms
Part 03

Storage Paradigms: Grafana Loki vs. OpenSearch

Once logs pass through forwarders, where should they be indexed? The two dominant production standards represent opposite ends of the computer science storage spectrum:

Grafana Loki (Index-Free) Cloud-Native Standard

Design Philosophy: "Like Prometheus, but for logs." Loki indexes only metadata labels (stream selectors like namespace, app, environment).

The log payloads themselves are compressed into raw binary gzip/snappy chunks and streamed directly into cheap object storage (MinIO, AWS S3, GCS).

✓ 80% Cost Reduction: Zero inverted indexes to maintain. Storing petabytes in S3 costs cents per gigabyte.
✓ Zero Mapping Maintenance: Applications can change JSON fields without schema migration errors.
Query Strategy: Highly parallelized brute-force grep across compressed chunks in memory at query time.
OpenSearch / Elasticsearch Full-Text Inverted Index

Design Philosophy: "Index everything." Uses Apache Lucene to construct inverted indexes, mapping every word, token, and numeric field into memory-resident posting lists.

Sharded across cluster nodes; requires dedicated master nodes, data nodes, and coordinating proxies.

✓ Fast Ad-Hoc Analytics: Instant searches across billions of unstructured lines without specifying stream labels.
✗ High Infrastructure Costs: Massive RAM consumption, disk storage multipliers, and shard management overhead.
Query Strategy: Exact pointer lookups into Lucene posting lists.
⚠ The Fatal Loki Label Cardinality Trap

Because Loki indexes stream labels in memory, labels must be low-cardinality (e.g. app="pulsepay", env="prod").

If an engineer attaches a dynamic high-cardinality variable (such as transaction_id, user_id, or ip_address) as a Loki stream label, Loki creates a separate stream buffer for every unique ID. In a system processing 50,000 transactions, Loki attempts to maintain 50,000 open chunk streams simultaneously, exhausting ingester RAM and crashing the entire logging cluster!

Golden Rule: Stream Labels are for Stream Routing. Transaction IDs belong inside the JSON payload!
Part 04

LogQL Mastery: Filtering, JSON Parsing & Log-Derived Metrics

Grafana Loki uses **LogQL** (Log Query Language). LogQL queries evaluate in two stages: 1. **Stream Selector:** Narrows the search to specific index labels (fast chunk retrieval from S3). 2. **Pipeline Stages:** Parses JSON, extracts fields, applies numeric filters, and computes rates.

// Essential Production LogQL Patterns for PulsePay:
1. Stream Selection & Substring Search:
{namespace="pulsepay-production", app="pulsepay-api"} |= "PAYMENT_SETTLE"
2. Dynamic JSON Extraction & Numeric Filter (Find slow transfers > 500ms):
{app="pulsepay-api"} | json | action = "PAYMENT_SETTLE" | duration_ms > 500.0
3. Surgical Trace ID Lookup (Isolate entire distributed journey):
{environment="production"} | json | trace_id = "4bf92f3577b34da6a3ce929d0e0e4736"
4. Log-Derived Metric: Calculate Error Rate Per Second:
sum by (action) (rate({app="pulsepay-api"} |= "ERROR" [1m]))

# ==============================================================================
# PulsePay Observability - Production Vector Pipeline (Milestone 08)
# ==============================================================================

# ------------------------------------------------------------------------------
# 1. SOURCES: Ingest logs from Docker daemon containers
# ------------------------------------------------------------------------------
[sources.docker_logs]
type = "docker_logs"
include_containers = ["pulsepay-api"]

# ------------------------------------------------------------------------------
# 2. TRANSFORMS: Parse JSON, enrich labels, and handle multiline events
# ------------------------------------------------------------------------------
[transforms.parse_json]
type = "remap"
inputs = ["docker_logs"]
source = '''
  # Parse inner JSON payload emitted by PulsePay Structured Formatter
  parsed, err = parse_json(.message)
  if err == null {
    # Hoist structured attributes
    . = merge(., parsed)
  }
  
  # Ensure mandatory stream routing labels exist
  .service = "pulsepay-api"
  .environment = "production"
'''

# ------------------------------------------------------------------------------
# 3. SINKS: Ship compressed chunks to Grafana Loki
# ------------------------------------------------------------------------------
[sinks.loki]
type = "loki"
inputs = ["parse_json"]
endpoint = "http://loki:3100"
encoding.codec = "json"

# STRICT LOW-CARDINALITY STREAM LABELS ONLY:
labels.service = "{{ service }}"
labels.environment = "{{ environment }}"
labels.level = "{{ level }}"

# Buffer against downstream Loki storage spikes
[sinks.loki.buffer]
type = "disk"
max_size = 536870912  # 512 MB disk buffer

Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The "Elasticsearch Mapping Explosion" Outage

Allowing dynamic, unconstrained JSON keys (e.g. dumping dynamic customer metadata maps) into OpenSearch.

Why this destroys search clusters: Lucene maps every unique JSON key as a new index field. If dynamic user data introduces 15,000 distinct keys, the cluster state balloons to gigabytes in size, triggering cluster-wide RED status and refusing all queries.

❌ The "Uncompressed Raw Disk Sink" Trap

Writing uncompressed flat JSON logs directly to long-term storage buckets without gzip or zstandard compression.

Why this multiplies cloud costs: Structured JSON contains repetitive metadata keys (timestamp, correlation_id). Compressing with zstandard reduces log storage footprints by up to 88%. Storing uncompressed raw text increases cloud storage invoices by 8x!
