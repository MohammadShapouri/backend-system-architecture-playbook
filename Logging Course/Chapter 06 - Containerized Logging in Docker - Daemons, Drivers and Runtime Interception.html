Part 01

Computer Science: The Container Stream Interception Boundary

A container is not a virtual machine; it is a standard Linux process isolated by **Kernel Namespaces** (PID, Mount, Network, IPC, UTS, User) and constrained by **Control Groups (cgroups)**. When your application process (PID 1 inside the container) executes, how do its logs reach the host filesystem or the docker logs command?

When the container runtime (e.g. runc / containerd) spawns the containerized process, it does not attach it to a real hardware TTY terminal. Instead, it creates **unidirectional UNIX pipes** or **pseudo-terminals (`pty`)** mapped directly to the container's standard file descriptors: File Descriptor 1 (stdout) and File Descriptor 2 (stderr).

⚠ The Python Unbuffered Stream Requirement:

By default, CPython detects if file descriptor 1 is connected to an interactive terminal. When running inside a container without a pseudo-TTY, Python switches to block buffering (typically 4KB–8KB buffers). Log lines are held in memory and not flushed to the container pipe until the buffer fills up or the process exits! Containerized Python applications must set ENV PYTHONUNBUFFERED=1 in the Dockerfile to guarantee immediate log delivery.

Part 02

Docker Logging Drivers: Architecture, Formats & Rotation

When the Docker daemon reads stdout/stderr from the container pipe, its active **logging driver** dictates where those bytes are persisted. Selecting the wrong driver can exhaust host disk space or crash container processes during high-volume spikes.

1. json-file Driver Legacy Default

Serializes each container line into an envelope JSON document stored on the host at: /var/lib/docker/containers/<id>/<id>-json.log

✓ Pros: Universally compatible; readable by docker logs.
✗ Fatal Flaw: By default, has zero file size limits! A single noisy container will write unconstrained JSON until the host VM fills 100% of its disk, crashing the host.
2. local Driver Senior Choice

Stores container logs in an optimized, binary, compressed format with internal rotation enabled by default on the host filesystem.

✓ Advantages: Automatically rotates files (default: 5 files of 20MB); uses transparent zstd compression; protects host disk from runaway exhaustion. Fully compatible with docker logs.
Host-Wide Protection: /etc/docker/daemon.json Production Standard

Senior infrastructure engineers never rely on developers configuring log rotation in individual docker run commands. You enforce strict, global limits across the entire Docker daemon: 

{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "5",
    "compress": "true"
  }
}

With this configuration, Docker guarantees no single container can ever consume more than 250MB (5 × 50MB) of host storage. Rotated logs are compressed automatically in the background.

Part 03

Concurrency Hazards: mode=blocking vs. mode=non-blocking

A subtle but catastrophic failure mode in containerized systems occurs when Docker is configured to ship logs to an external daemon or search cluster (e.g. using syslog, fluentd, or awslogs).

By default, Docker logging operates in **blocking mode** (mode=blocking). If the logging driver is unable to deliver logs (due to host disk saturation, network latency, or an external aggregator outage), the logging pipeline backpressures directly into the container's UNIX pipe buffer.

The Default Trap

1. mode=blocking (Backpressure Cascade)

The 64KB kernel FIFO pipe fills up. The next time the container's application thread calls sys.stdout.write(), the operating system kernel suspends the thread on the write() system call.

Upstream log collector slow → Container write() blocks → Payment processing freezes → Customer HTTP requests timeout!
Enterprise Standard

2. mode=non-blocking (Ring Buffer)

Docker places an intermediate in-memory ring buffer (default: max-buffer-size=4m) between the container's stdout pipe and the logging driver.

If the logging driver stalls, the ring buffer absorbs the burst. If the buffer fills completely, Docker drops older logs to keep the application running. A dropped log is regrettable; a frozen financial clearing transaction is unacceptable.

Part 04

Storage Internals: The overlay2 File Logging Anti-Pattern

Developers transitioning from legacy monolithic VMs frequently configure Python's RotatingFileHandler to write log files *inside* the running container (e.g. to /app/logs/pulsepay.log). In container runtimes, this causes severe performance degradation due to the architecture of Docker's storage driver:

The Copy-on-Write (CoW) Overhead of overlay2

Docker containers use the overlay2 storage driver, stacking read-only image layers under a thin, read-write container layer. Every time an application appends bytes to an internal container file, the kernel must execute copy-on-write lookups across storage layers:

1. I/O Degradation

Writing to the writable container layer imposes severe I/O penalties compared to host disk sequential writes.

2. Image Bloat

Internal log files swell container layer sizes, complicating container migration and snapshotting.

3. Instant Data Loss

When the container terminates, its writable layer is deleted. All internal logs vanish forever.

# ==============================================================================
# PulsePay Container Build - Multi-Stage Rootless Dockerfile (Milestone 06)
# ==============================================================================

# Stage 1: Build Dependencies
FROM python:3.11-slim AS builder

WORKDIR /build
RUN apt-get update && apt-get install -y --no-install-recommends gcc && rm -rf /var/lib/apt/lists/*

COPY pyproject.toml .
RUN pip install --no-cache-dir --user fastapi uvicorn httpx pydantic

# Stage 2: Hardened Runtime Container
FROM python:3.11-slim AS runtime

# ------------------------------------------------------------------------------
# CRITICAL TELEMETRY SETTINGS:
# 1. PYTHONUNBUFFERED=1 forces Python to flush stdout immediately to the pipe!
# 2. PYTHONDONTWRITEBYTECODE=1 prevents stale .pyc clutter
# ------------------------------------------------------------------------------
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PULSEPAY_ENV="production" \
    PATH="/home/pulsepay/.local/bin:$PATH"

# Create non-root unprivileged service user
RUN groupadd -g 1001 pulsepay && \
    useradd -u 1001 -g pulsepay -s /bin/bash -m pulsepay

WORKDIR /app
COPY --from=builder /root/.local /home/pulsepay/.local
COPY --chown=pulsepay:pulsepay src/ /app/src/

USER pulsepay

# Expose HTTP port
EXPOSE 8000

# Boot Uvicorn with structured JSON output piped directly to stdout
CMD ["uvicorn", "src.pulsepay.web.app:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log"]

# PulsePay Container Orchestration - Hardened Logging Limits (Milestone 06)
# ==============================================================================

version: '3.8'

services:
  pulsepay-api:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: pulsepay-api
    ports:
      - "8000:8000"
    environment:
      - PULSEPAY_ENV=production
    # --------------------------------------------------------------------------
    # PRODUCTION LOGGING CONFIGURATION:
    # - mode: non-blocking prevents container lockups during logging backpressure!
    # - max-size & max-file prevent host VM disk exhaustion!
    # --------------------------------------------------------------------------
    logging:
      driver: "json-file"
      options:
        mode: "non-blocking"
        max-buffer-size: "4m"
        max-size: "25m"
        max-file: "3"
        compress: "true"
    restart: unless-stopped
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The "Silent Container Freeze" Anti-Pattern

Configuring Docker to log to an external syslog or Fluentd collector using default mode=blocking.

Why this causes major production outages: If the central logging collector restarts or experiences a network partition, Docker's 64KB kernel pipe buffer fills up within seconds. Your application's write() system calls block, freezing all payment processing. Fix: Always configure mode=non-blocking with max-buffer-size!

❌ The "Overlay2 Root Disk Exhaustion" Bomb

Writing log files directly to /var/log/app.log inside the container's writable layer.

Why this kills hosts: The writable layer of a container lives on the host's root filesystem (/var/lib/docker/overlay2). Writing unmanaged files inside the container bypasses Docker's max-size rotation limits entirely, eventually consuming 100% of the host disk space. Fix: Never write logs to files inside containers. Stream exclusively to stdout!
