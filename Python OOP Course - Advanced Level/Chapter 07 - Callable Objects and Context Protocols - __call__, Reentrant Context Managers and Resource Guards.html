Part 01

Computer Science: First-Class Callable Instances & Closures

In many languages, functions and class instances occupy entirely different architectural universes. In Python, following the foundational principle that "everything is an object", functions are simply instances of the built-in function class.

By implementing the __call__ dunder method on any custom class, you grant instances of that class the execution semantics of a function. When CPython encounters parentheses applied to an identifier (obj(*args, **kwargs)), it invokes type(obj).__call__(obj, *args, **kwargs).

Stateful Functional Abstractions: Function Closures vs. Callable Objects
1. Function Closure Lexical Scoping 
def make_rate_limiter(limit: int):
    count = 0
    def limiter():
        nonlocal count
        count += 1
        return count <= limit
    return limiter
  • Lightweight: Low overhead for single, stateless or minimal-state execution callbacks.
  • Opaque State: Captured state variables reside in __closure__ tuple cells. Difficult to inspect, serialize, reset, or unit test directly.
  • Single Operation: Only supports the direct execution signature; cannot cleanly expose companion management methods (e.g. reset(), status()).
2. Callable Class Instance __call__ Protocol 
class RateLimiter:
    def __init__(self, limit: int):
        self.limit = limit
        self.count = 0
    def __call__(self) -> bool:
        self.count += 1
        return self.count <= self.limit
    def reset(self) -> None:
        self.count = 0
  • Transparent State: State attributes live directly on self. Trivially inspected by debuggers and serializable to database state.
  • Multi-Faceted API: Executes as a function, but provides explicit companion control methods (reset(), audit()).
  • Composition & Inheritance: Can inherit shared validation behaviors, implement generic protocols, and adhere to structural interfaces!
Part 02

Under the Hood: The Context Protocol (__enter__ & __exit__)

The Python with statement (introduced in PEP 343) provides deterministic lifecycle setup and teardown boundaries. It is not merely syntactic sugar for a try...finally block; it coordinates an explicit contract between your runtime code and the object guarding the boundary.

The with Statement Lifecycle Pipeline
1. Target Evaluation & Setup (__enter__) CPython evaluates context expression and calls manager.__enter__(). The returned value is bound to the optional as target variable.
Phase 1: Enter
2. Inner Block Execution Business logic inside the indented with block executes.
Phase 2: Work
3. Teardown & Exception Inspection (__exit__) CPython unconditionally invokes manager.__exit__(exc_type, exc_val, exc_tb), passing either (None, None, None) or exception details.
Phase 3: Exit
// The Exception Suppression Invariant:

If an exception occurs within the inner block, __exit__ receives its runtime type, instance value, and traceback.

  • If __exit__ returns True: The exception is completely swallowed and suppressed. Execution continues cleanly immediately following the with block!
  • If __exit__ returns False (or None): The exception bubbles up normally to the outer caller.
  • Architectural Standard: Only suppress exceptions if the manager explicitly resolves the failure (e.g. falling back to an in-memory replica on database network drops). Never return True blindly!
Part 03

Advanced Architecture: Reentrancy & Nested Transaction Stacks

A simple context manager is often single-use: entering it a second time either raises a state error or closes prematurely when an inner block terminates.

In database transaction processing, workflow orchestration, and locking systems, architectures demand Reentrant Context Managers: guards that can be safely nested within themselves across recursive function calls or composite pipeline steps.

Recursion Depth Counter Pattern Nesting Invariant

To support safe nesting, the manager maintains an internal depth counter:

  • On __enter__: Increment self._depth. Only initiate the physical resource (e.g. acquire mutex, start top-level DB transaction) when depth == 1!
  • On __exit__: Decrement self._depth. Do NOT close the physical resource until depth == 0!
  • Inner with blocks create logical nested savepoints without prematurely releasing the outer connection.
// Nested Transaction Scoping Trace: 
with tx_guard:          # depth = 1 → BEGIN PHYSICAL TRANSACTION
    mutate_user_balance()
    with tx_guard:      # depth = 2 → SAVEPOINT level_2 (no commit/close!)
        mutate_order()
    # depth decrements to 1 (connection remains open and locked)
# depth decrements to 0 → COMMIT PHYSICAL TRANSACTION
Part 04

Dunder Method Matrix: Invocation & Lifecycle Scopes

The strict behavioral contracts for callability and context management:

Method Invocation Signature When to Override (✓) When NOT to Override (✗)
__call__ instance(*args, **kwargs) Stateful pipeline processors, strategy pattern dispatchers, parameterizable decorators maintaining historical metrics, memoized policy evaluators. Pure functions without internal mutable state (use standard def functions), or when instance behavior is already clearly served by a standard named method (e.g. .execute()).
__enter__ __enter__(self) → target Resource acquisition: opening database transactions, acquiring locks, starting high-resolution performance timers, establishing mock test boundaries. Classes where setup is entirely static and does not have an accompanying mandatory teardown phase.
__exit__ __exit__(self, exc_type, exc_val, exc_tb) → bool | None Guaranteed resource teardown: releasing locks, closing sockets, rolling back aborted transactions on failure, committing transactions on success. Suppressing exceptions blindly by returning True on arbitrary unhandled crashes (causes catastrophic silent failures in production).

# ==============================================================================
# EntityForge Core - Callable Pipeline Steps & Reentrant Guards (Milestone 07)
# ==============================================================================

from __future__ import annotations
import time
from typing import Any, Callable, Dict, List, Optional, Self, Type
from types import TracebackType
from entityforge.core.diagnostics import DiagnosticRendererMixin


class ExecutionStep(DiagnosticRendererMixin):
    """
    CALLABLE PIPELINE OPERATOR:
    Encapsulates domain transformation logic inside a stateful callable instance.
    Implements __call__ to execute transparently as a first-class function.
    """
    __slots__ = ("_name", "_action", "_execution_count", "_total_latency")

    def __init__(self, name: str, action: Callable[[Any], Any]) -> None:
        self._name = name
        self._action = action
        self._execution_count: int = 0
        self._total_latency: float = 0.0

    @property
    def name(self) -> str:
        return self._name

    @property
    def execution_count(self) -> int:
        return self._execution_count

    def __call__(self, payload: Any) -> Any:
        """
        FIRST-CLASS CALLABLE PROTOCOL:
        Executes the wrapped domain action, recording latency and call metrics.
        """
        start_time = time.perf_counter()
        try:
            result = self._action(payload)
            return result
        finally:
            duration = time.perf_counter() - start_time
            self._execution_count += 1
            self._total_latency += duration

    def reset_metrics(self) -> None:
        """Resets performance audit counters."""
        self._execution_count = 0
        self._total_latency = 0.0


class TransactionScopeGuard:
    """
    REENTRANT TRANSACTION CONTEXT MANAGER:
    Maintains a recursion depth counter to support arbitrary nested 'with' blocks.
    Guarantees state commit strictly at depth 0, and executes rollback on exceptions.
    """
    def __init__(self, state_store: Dict[str, Any]) -> None:
        self._state_store: Dict[str, Any] = state_store
        # Stack of state snapshots supporting multi-level nested rollbacks:
        self._snapshot_stack: List[Dict[str, Any]] = []
        # Nesting depth tracking:
        self._depth: int = 0
        self._is_committed: bool = False
        self._rollback_count: int = 0

    @property
    def depth(self) -> int:
        return self._depth

    @property
    def rollback_count(self) -> int:
        return self._rollback_count

    def __enter__(self) -> Self:
        """
        ENTER CONTEXT:
        1. Capture snapshot of state before mutations begin.
        2. Increment recursion depth counter.
        """
        # Capture deep copy / dictionary snapshot of active state
        self._snapshot_stack.append(self._state_store.copy())
        self._depth += 1
        self._is_committed = False
        return self

    def __exit__(
        self,
        exc_type: Optional[Type[BaseException]],
        exc_val: Optional[BaseException],
        exc_tb: Optional[TracebackType]
    ) -> bool:
        """
        EXIT CONTEXT:
        1. If exception occurred → revert state to snapshot and pop stack.
        2. If clean exit → decrement depth counter.
        3. Only commit changes when outermost context (depth == 0) terminates cleanly!
        """
        self._depth -= 1
        previous_snapshot = self._snapshot_stack.pop()

        if exc_type is not None:
            # Exception encountered: Roll back active state to previous snapshot!
            self._state_store.clear()
            self._state_store.update(previous_snapshot)
            self._rollback_count += 1
            # Return False: Do NOT suppress exception; allow it to bubble up to caller!
            return False

        # Outermost context completed successfully
        if self._depth == 0:
            self._is_committed = True

        return False

import pytest
from entityforge.core.execution import ExecutionStep, TransactionScopeGuard


class TestExecutionAndContextProtocols:
    """Unit tests asserting __call__ stateful invocations and reentrant context rollbacks."""

    def test_execution_step_callable_protocol_and_metrics(self):
        # 1. Define transformation action
        def normalize_string(text: str) -> str:
            return text.strip().upper()

        step = ExecutionStep(name="Normalizer", action=normalize_string)
        assert step.execution_count == 0

        # 2. Invoke instance directly as a function via __call__
        res1 = step("   user_alpha   ")
        res2 = step("  admin_beta ")

        assert res1 == "USER_ALPHA"
        assert res2 == "ADMIN_BETA"
        assert step.execution_count == 2

        # 3. Reset internal metric state
        step.reset_metrics()
        assert step.execution_count == 0

    def test_reentrant_transaction_guard_clean_commit(self):
        state = {"balance_alice": 1000, "balance_bob": 500}
        tx = TransactionScopeGuard(state)

        # 1. Nested reentrant context
        with tx:
            assert tx.depth == 1
            state["balance_alice"] -= 200

            with tx:
                assert tx.depth == 2
                state["balance_bob"] += 200

            assert tx.depth == 1

        # 2. Outermost context exited cleanly
        assert tx.depth == 0
        assert tx._is_committed is True
        assert state["balance_alice"] == 800
        assert state["balance_bob"] == 700
        assert tx.rollback_count == 0

    def test_reentrant_transaction_guard_rolls_back_on_failure(self):
        state = {"order_id": "ORD-101", "status": "DRAFT"}
        tx = TransactionScopeGuard(state)

        # Simulate transaction encountering mid-flight crash
        with pytest.raises(RuntimeError, match=r"Simulated database disk failure"):
            with tx:
                state["status"] = "PROCESSING"
                with tx:
                    state["status"] = "AUTHORIZED"
                    raise RuntimeError("Simulated database disk failure!")

        # CRITICAL ROLLBACK INVARIANT:
        # State must be perfectly reverted to initial snapshot!
        assert state["status"] == "DRAFT"
        assert tx.depth == 0
        assert tx._is_committed is False
        assert tx.rollback_count == 1
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Blindly Returning True from __exit__

Writing def __exit__(self, *args): self.cleanup(); return True.

Why this causes catastrophic silent failures: Returning True tells Python that all exceptions inside the with block were successfully resolved. Even fatal syntax errors, ZeroDivisionError, or KeyError are swallowed silently! Code continues executing as if nothing went wrong, leaving data corrupted. Only return True if you explicitly handled that specific exception type.

❌ Premature Resource Release in Nested Contexts

Writing a single-use context manager that calls self.conn.close() inside __exit__ without checking depth.

Why this breaks nested pipelines: If an inner helper method runs with my_guard:, its exit closes the connection immediately. When the outer calling function resumes, the connection is already dead, raising InterfaceError: Connection already closed! Maintain a recursion depth counter and close strictly when depth == 0.

❌ Overusing __call__ for Complex Domain Entities

Implementing __call__ on a core domain aggregate like UserEntity.

Why this obscures intent: What does executing user() actually do? Does it save the user? Authenticate them? Validate permissions? Calling an entity instance like a function is ambiguous and confusing. Reserve __call__ for action-centric objects (Pipelines, Operators, Tasks, Strategies).

❌ Acquiring Resources Outside __enter__

Opening network sockets or acquiring locks inside __init__ instead of __enter__.

Why this causes resource leaks: If an exception occurs between instantiating the manager and entering the with block, __exit__ will never run! The acquired resource remains orphaned in memory. Always defer physical resource acquisition until __enter__ executes.
