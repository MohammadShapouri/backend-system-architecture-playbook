Part 01

Computer Science: The Inviolable Hash-Equality Contract

In computer science, hash tables (Python dictionaries and sets) rely on a mathematical equivalence relation between equality functions and hash mappings. If this relation is violated, data structures break catastrophically: keys vanish from dictionaries, sets accumulate duplicate elements, and lookups fail intermittently.

Python formalizes this relationship through the Hash-Equality Contract:

The Formal Hash-Equality Axiom
if a == b ⇒ hash(a) == hash(b)

If two objects evaluate as equal under __eq__, their integer hash codes computed by __hash__ MUST be strictly identical throughout their entire lifetime.

1. The Forward Rule (Mandatory)

Equal objects must produce identical hashes so that when Python calculates the bucket index i = hash(key) & mask, both objects map to the exact same hash table bucket.

2. The Converse Rule (Not Required)

If hash(a) == hash(b), a and b are not necessarily equal. This is simply a hash collision, which Python's dictionary resolves cleanly via open addressing perturbation probing.

// CPython Type Invariant: Automatic Unhashability Sealing

In Python 3, if a class implements __eq__ but does not implement __hash__, CPython automatically sets __hash__ = None on the class dictionary.

Why? Because objects inherit a default __hash__ based on their memory pointer address from object. If you override __eq__ to compare attributes instead of memory pointers, two distinct instances with identical attributes would have equal values but different pointer hashes, violating the axiom! Python proactively disables hashing to save you from silent data corruption.

Part 02

Under the Hood: Cooperative Comparison Reflection & `NotImplemented`

When evaluating expressions involving binary operators (such as a == b or a < b), Python does not simply execute the left operand's method and give up if types mismatch.

Python features a cooperative Double-Dispatch Reflection Protocol. Understanding the critical difference between the singleton NotImplemented and the exception TypeError is the defining hallmark of a senior Python architect:

The CPython Rich Comparison Reflection Flow (Evaluating: a < b)
Step 1: Left Operand Invocation CPython calls type(a).__lt__(a, b).
Initial Attempt
Step 2: Check for NotImplemented Singleton Does __lt__ recognize type(b)? If not, it returns NotImplemented (it does NOT raise TypeError!).
Handshake
Step 3: Reflected Right Operand Invocation CPython automatically reflects the operator! It calls type(b).__gt__(b, a).
Cooperative Fallback
Step 4: Terminal Evaluation or Exception If the right operand also returns NotImplemented, CPython finally raises: TypeError: '<' not supported between instances of 'A' and 'B'.
Terminal Failure
The Catastrophic TypeError Trap:

If your class explicitly writes raise TypeError(...) inside a comparison method when receiving an unknown type, you sever the reflection protocol immediately! The right-hand operand never gets the chance to handle the comparison, breaking interoperability with numeric libraries, mock objects, and proxy frameworks.

Part 03

Domain-Driven Design: Entities vs. Value Objects

In enterprise architectures, domain objects fall into two fundamentally distinct categories. Conflating them leads to database state corruption and memory leaks:

1. Domain Entity (Ch. 01) Identity Driven
  • Identity Primacy: Defined by a continuous thread of identity (UUID). Two users with identical names are completely different entities.
  • Mutability: State changes continuously across time (e.g. balance updates, address edits).
  • Equality Contract: Compared strictly by self.id == other.id.
  • Unhashable: Because their internal attributes mutate, entities should generally remain unhashable or hash strictly by their immutable UUID.
2. Value Object (Ch. 05) Attribute Driven
  • Zero Identity: Defined purely by the composition of its attribute values (e.g., Money(100, USD)).
  • Strict Immutability: Once constructed, a Value Object can never be modified. Changes produce a new Value Object instance.
  • Equality Contract: Two value objects with identical attributes are completely interchangeable.
  • Hashable: Because they are immutable, they implement deterministic hashing and can serve as dictionary keys or set members.
Part 04

Dunder Method Matrix: Equivalence, Ordering & Hashing

Implementing ordering and hashing requires strict discipline. Here are the exact implementation rules for Python's comparison protocol:

Method Operator When to Override (✓) When NOT to Override (✗)
__eq__ a == b Whenever instances should compare by value rather than pointer identity. Return NotImplemented if other is of an unhandled type. When objects are unique stateful services (like database connections or worker threads) where pointer identity is the only meaningful comparison.
__hash__ hash(a) Strictly on immutable value objects that must act as dictionary keys or set elements. Compute by hashing a tuple of all fields evaluated in __eq__. Never on mutable classes. If an object's attributes can change after instantiation, hashing it will corrupt hash table bucket lookups!
__lt__, __le__
__gt__, __ge__		 <, ≤, >, ≥ When objects have a natural total ordering (dates, monetary amounts, semantic versions, priority scores). Return NotImplemented on incompatible types. When there is no natural linear order (e.g., comparing a User to a Product, or multidimensional spatial coordinates).
@functools.total_ordering Trade-Off Decorating a class with @total_ordering requires implementing only __eq__ and one ordering method (e.g. __lt__). It synthesizes the remaining 3 comparison methods automatically.
Warning: Adds ~2x function call overhead in tight sort loops. In ultra-hot paths, implement all 4 directly!

EntityForge Milestone 05: Immutable Monetary Value Object Implementation

We now assemble Milestone 05 of EntityForge: implementing src/entityforge/core/value_object.py.

The architecture features:

  • MonetaryAmount: An immutable, slotted domain value object managing high-precision financial amounts using Python's standard decimal.Decimal and Chapter 02's FlyweightStatus for currency deduplication.

1. Production Value Object Core: src/entityforge/core/value_object.py Total Ordering & Hashing Contracts 
# ==============================================================================
# EntityForge Core - Domain Value Objects & Ordering Contracts (Milestone 05)
# ==============================================================================

from __future__ import annotations
from decimal import Decimal, InvalidOperation
from functools import total_ordering
from typing import Any, Self, final, override
from entityforge.core.lifecycle import FlyweightStatus
from entityforge.core.diagnostics import DiagnosticRendererMixin


class CurrencyMismatchError(TypeError):
    """Raised when comparing or adding monetary values across incompatible currency codes."""
    pass


@final
@total_ordering
class MonetaryAmount(DiagnosticRendererMixin):
    """
    IMMUTABLE DOMAIN VALUE OBJECT:
    Models financial values with exact decimal precision and currency alignment.
    Enforces total ordering, reflection via NotImplemented, and mathematical hash invariants.
    """
    __slots__ = ("_amount", "_currency")

    def __init__(self, amount: int | float | str | Decimal, currency: str = "USD") -> None:
        # Convert to high-precision Decimal to avoid floating-point binary rounding errors
        try:
            normalized_amount = Decimal(str(amount)).quantize(Decimal("0.01"))
        except (InvalidOperation, TypeError) as err:
            raise ValueError(f"Invalid monetary numerical amount: '{amount}'") from err

        # Store currency as an immutable, deduplicated FlyweightStatus string (Ch. 02)
        normalized_currency = FlyweightStatus(currency)

        # Assign into slotted member descriptors directly
        super().__setattr__("_amount", normalized_amount)
        super().__setattr__("_currency", normalized_currency)

    @property
    def amount(self) -> Decimal:
        """Read-only property protecting the encapsulated decimal amount."""
        return self._amount

    @property
    def currency(self) -> str:
        """Read-only property protecting the currency code string."""
        return self._currency

    @override
    def __setattr__(self, name: str, value: Any) -> None:
        """SEALED VALUE OBJECT INVARIANT: Prevents attribute mutation after creation."""
        raise AttributeError("MonetaryAmount is strictly immutable and cannot be modified.")

    @override
    def __delattr__(self, name: str) -> None:
        """Prevents attribute deletion."""
        raise AttributeError("MonetaryAmount is strictly immutable.")

    @override
    def __eq__(self, other: object) -> bool:
        """
        EQUIVALENCE RELATION:
        Returns True if both amount and currency match exactly.
        Returns NotImplemented if other is not a MonetaryAmount to allow reflection!
        """
        if not isinstance(other, MonetaryAmount):
            return NotImplemented
        return self._amount == other._amount and self._currency == other._currency

    @override
    def __hash__(self) -> int:
        """
        MATHEMATICAL HASH INVARIANT:
        If self == other is True, hash(self) == hash(other) MUST be True.
        Hashes a composite tuple of all equality components.
        """
        return hash((self._amount, self._currency))

    def __lt__(self, other: object) -> bool:
        """
        RICH COMPARISON ORDERING:
        1. If foreign type → return NotImplemented (cooperative reflection).
        2. If currency mismatch → raise CurrencyMismatchError (business invariant).
        3. If matching → compare decimal amounts.
        """
        if not isinstance(other, MonetaryAmount):
            return NotImplemented
        if self._currency != other._currency:
            raise CurrencyMismatchError(
                f"Cannot compare amounts across distinct currencies: '{self._currency}' vs '{other._currency}'"
            )
        return self._amount < other._amount

    def add(self, other: MonetaryAmount) -> MonetaryAmount:
        """Algebraic addition returning a new immutable Value Object instance."""
        if not isinstance(other, MonetaryAmount):
            raise TypeError("Can only add MonetaryAmount to another MonetaryAmount.")
        if self._currency != other._currency:
            raise CurrencyMismatchError(f"Currency mismatch: '{self._currency}' != '{other._currency}'")
        return MonetaryAmount(amount=self._amount + other._amount, currency=self._currency)

# EntityForge Test Suite - Value Object Hashing & Ordering Verification (Milestone 05)

from decimal import Decimal
import pytest
from entityforge.core.value_object import MonetaryAmount, CurrencyMismatchError


class TestValueObjectContracts:
    """Unit tests asserting structural equality, hash invariants, reflection, and total ordering."""

    def test_structural_equality_and_hash_invariants(self):
        # 1. Instantiate separate objects with equal values
        m1 = MonetaryAmount(100.50, "usd")
        m2 = MonetaryAmount(Decimal("100.50"), "USD")

        # Separate pointers in memory
        assert m1 is not m2

        # Invariant 1: Structural value equality must be True
        assert m1 == m2

        # Invariant 2: Hash codes MUST be strictly identical!
        assert hash(m1) == hash(m2)

        # 2. Assert set deduplication works cleanly via hashing
        amount_set = {m1, m2}
        assert len(amount_set) == 1

        # 3. Assert usable as dictionary keys
        ledger_cache = {m1: "Standard Subscription Fee"}
        assert ledger_cache[m2] == "Standard Subscription Fee"

    def test_immutability_prevents_tampering(self):
        m = MonetaryAmount(50.00, "EUR")

        with pytest.raises(AttributeError, match=r"strictly immutable"):
            m.amount = 100.00  # Mutating amount blocked!

        with pytest.raises(AttributeError, match=r"strictly immutable"):
            m.currency = "GBP"  # Mutating currency blocked!

    def test_rich_comparison_and_total_ordering(self):
        m_small = MonetaryAmount(10.00, "USD")
        m_med = MonetaryAmount(50.00, "USD")
        m_large = MonetaryAmount(100.00, "USD")

        # Test operator evaluations synthesized by @total_ordering
        assert m_small < m_med
        assert m_med <= m_large
        assert m_large > m_med
        assert m_med >= m_small
        assert m_small != m_large

        # Test full collection sorting via Timsort
        scrambled = [m_large, m_small, m_med]
        ordered = sorted(scrambled)
        assert ordered == [m_small, m_med, m_large]

    def test_currency_mismatch_raises_domain_error(self):
        usd = MonetaryAmount(100.00, "USD")
        eur = MonetaryAmount(100.00, "EUR")

        # Equality across currencies evaluates to False cleanly
        assert usd != eur
        assert (usd == eur) is False

        # Relational ordering across distinct currencies must raise CurrencyMismatchError
        with pytest.raises(CurrencyMismatchError, match=r"Cannot compare amounts across distinct currencies"):
            _ = usd < eur

    def test_reflection_protocol_with_not_implemented(self):
        m = MonetaryAmount(100.00, "USD")

        # Comparing against foreign types (e.g. integer or string) must return False, NOT crash!
        assert (m == 100.00) is False
        assert (m == "100.00 USD") is False

        # Relational ordering against unhandled foreign types raises standard TypeError
        with pytest.raises(TypeError):
            _ = m < 100.00
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Raising TypeError in __eq__ Instead of NotImplemented

Writing if not isinstance(other, MyType): raise TypeError(...) inside __eq__.

Why this breaks Python conventions: Python expects __eq__ to return NotImplemented when handed an unexpected type. This allows Python to reflect the operator to the other object (other == self) or gracefully fall back to identity comparison (False). Raising TypeError causes unexpected crashes whenever checking if my_obj in my_list:!

❌ Hashing Mutable Objects (Bucket Corruption)

Implementing def __hash__(self): return hash(self.name) on a class where name can be reassigned.

Why this corrupts dictionaries and sets: If an object is inserted into a hash table and its attributes are subsequently modified, its hash code changes. The object is now stuck in the wrong bucket! Calling key in my_dict or my_dict[key] fails with KeyError even though the object is literally sitting right inside the table!

❌ Inconsistent Comparison Attributes

Comparing (self.a, self.b) in __eq__, but hashing only hash(self.a) in __hash__.

Why this causes subtle bugs: While it does not violate the letter of the hash axiom, it forces massive numbers of hash collisions on attribute a, degrading hash table lookups from $O(1)$ to $O(N)$ linear scans. Always hash the exact same combination of fields evaluated in __eq__!

❌ The Float-Decimal Equality Trap

Using raw binary floats for financial value objects: amount = 0.1 + 0.2.

Why this breaks business logic: IEEE-754 floating point arithmetic produces 0.30000000000000004. Checking Money(0.1 + 0.2) == Money(0.3) evaluates to False! Financial value objects must strictly parse and store values using Python's standard decimal.Decimal with explicit quantization.
