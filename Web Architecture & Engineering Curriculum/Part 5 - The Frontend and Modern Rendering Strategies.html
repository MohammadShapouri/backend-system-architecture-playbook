Orientation

0. Introduction: The Frontend Shift

In the early days of the web, "Frontend" simply meant writing static text in HTML and adding colors with CSS. Whenever a user wanted to see another page or submit a form, the browser discarded the entire screen, sent an HTTP request to the server, and waited for a brand-new HTML page to download.

Today, users expect websites to feel like native desktop apps: fast, fluid, instant, and responsive—without annoying white-screen flashes between clicks.

To achieve this, the frontend has transformed into a full engineering discipline. Instead of servers generating static pages, modern frontends run rich JavaScript engines directly in the user's browser that render views, track user input, and talk silently to backend REST APIs.

Concept 01

1. Traditional Multi-Page Applications (MPAs) vs. Single-Page Applications (SPAs)

The core evolutionary leap in modern web design is the shift from Multi-Page Applications (MPAs) to Single-Page Applications (SPAs).

// HTML/CSS Diagram: MPA Full-Page Reload vs. SPA Seamless Update
Traditional MPA Full Reload
1. User clicks /dashboard link
2. Browser screen goes blank (reloading)
3. Server generates & sends brand new HTML
4. Browser re-parses all HTML, CSS & JS
🐢 Noticeable pause & screen flicker between pages.
Modern SPA No Reload
1. User clicks /dashboard link
2. JavaScript intercepts click (No reload!)
3. Silent JSON fetch from API in background
4. JS updates only the changed UI on screen
⚡ Instantaneous transitions, feels like a mobile app.
How a Single-Page App Works

The server sends only one initial HTML file containing an empty container (<div id="root"></div>) and a JavaScript bundle. Once downloaded, the JavaScript engine takes over routing, draws the UI elements, and swaps screens without ever requesting another full HTML file.

The SPA Trade-off

While SPAs provide fluid experiences, they come with challenges: the initial JavaScript bundle can be large to download (slower initial loading), and search engine bots (like Google) historically struggled to index pages that require JavaScript execution to see content.

Concept 02

2. Rendering Paradigms: CSR vs. SSR vs. SSG

Where should the HTML of a webpage be constructed? On the user's phone/laptop (Client) or on the data center computer (Server)?

Modern web development categorizes rendering into three fundamental strategies:

1. CSR (Client-Side Rendering)

Pure React / Vue

The server sends a blank HTML shell. The client's browser downloads a JavaScript file, which runs locally, contacts your FastAPI/Django backend for JSON data, and creates the HTML elements on the fly.

✔ Great for dashboards & private logged-in portals. ❌ Slower first page load; poor public SEO.

2. SSR (Server-Side Rendering)

Next.js / Nuxt

Every time a user visits a URL, the server queries the database, constructs the complete HTML with all content pre-filled, and sends finished HTML to the browser. Once displayed, JavaScript attaches itself (a process called Hydration) to make it interactive.

✔ Blazing-fast first content paint & perfect SEO. ❌ Higher server compute cost per request.

3. SSG (Static Site Generation)

Astro / Next.js Export

All pages are pre-compiled into static HTML files during the build phase (before the website is ever deployed). When a user visits, the pages are served instantly from global CDN servers.

✔ Fastest possible loading speed; virtually free hosting. ❌ Not suitable for real-time, user-customized dynamic feeds.

Concept 03

3. Component-Based Architecture (UI Lego Blocks)

In old websites, an entire page lived in one monolithic 2,000-line HTML file. If you wanted to change the design of a button or the navigation menu, you had to manually copy-paste the changes across 40 different files.

Modern frontends solved this through Component-Based Architecture. You build an application out of small, self-contained, reusable building blocks called Components.

// HTML/CSS Diagram: Visual Decomposition of a Web Interface into Components

<Sidebar /> Reusable Category Links
<ProductGrid />
<ProductCard />
<ProductCard />
<Footer />
Python Analogy: Functions & Classes for UI

Think of a Component exactly like a Python function. In Python, you write a function once (def format_currency(val): ...) and call it 100 times with different inputs. In modern frontend development, a Component is a function that takes data inputs (called Props) and returns visual elements!

Concept 04

4. Frontend State: The UI's Live Memory

What makes a modern web page interactive? Why does a shopping cart badge update from 0 to 1 the instant you click "Add to Cart"?

The answer is State. In frontend terminology, State is a live JavaScript variable that holds the current condition of the user interface.

The Golden Rule of Modern Frontends (Reactivity):

In traditional JavaScript (from 2010), you had to manually find the HTML element on screen and rewrite its text using DOM operations. In modern component frameworks (like React), you never touch the HTML directly. You simply update the State variable. The framework automatically detects the change and updates the exact pixel on screen for you!

Props (Input Arguments)

Data passed downwards from a parent component to a child component (e.g. passing a product's price into a <PriceTag />). Props are read-only.

State (Internal Memory)

Data owned and managed internally by the component that can change over time based on user clicks or typing (e.g. isOpen: true).

Framework Spotlight: Modern UI Engineering with React & Next.js
Frontend Stack

What are React & Next.js?

React is the world's most popular JavaScript library for building component-based user interfaces. Next.js is a full-stack framework built on top of React that automatically provides Server-Side Rendering (SSR), file-based routing, and backend API endpoints in one unified package.

Create a React App (via Vite): 
npm create vite@latest my-app -- --template react
Create a Next.js App (SSR Fullstack): 
npx create-next-app@latest my-next-app

A Reactive Counter Component in React:

Notice how clean JSX blends HTML and JavaScript together:

import { useState } from 'react';

// Reusable Button Component with State
export default function CounterButton() {
  // 1. Declare a State variable named 'count', initialized to 0
  const [count, setCount] = useState(0);

  // 2. Click handler function
  function handleClick() {
    setCount(count + 1); // Updating state triggers an instant UI re-render!
  }

  // 3. Return visual JSX (looks like HTML inside JavaScript)
  return (
    <div className="p-4 bg-slate-100 rounded-lg">
      <p>You clicked the button: {count} times</p>
      <button 
        onClick={handleClick}
        className="px-3 py-1 bg-emerald-600 text-white rounded font-bold">
        Click Me
      </button>
    </div>
  );
}
Summary

6. Key Takeaways & Review

✔ MPA vs. SPA: MPAs reload the full browser window on every navigation; SPAs download one JavaScript shell and dynamically swap screens without reloading.
✔ Rendering Trade-offs: CSR constructs views in the user's browser; SSR renders HTML on the server on each request for SEO; SSG compiles static pages once during build time.
✔ Components: Modular, reusable UI building blocks combining HTML, styling, and interactivity into isolated units like Lego bricks.
✔ State & Reactivity: Updating state automatically re-renders affected UI components without manual DOM manipulation.
