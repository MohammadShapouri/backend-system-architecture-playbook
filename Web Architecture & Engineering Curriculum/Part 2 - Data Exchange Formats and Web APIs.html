0. Introduction & The Need for APIs

In Part 1, we learned about the Client-Server relationship and how traditional MVC (Model-View-Controller) servers assemble an entire HTML document on the server before sending it down to a web browser.

That pattern works great if your only user is sitting in front of a desktop web browser. But what happens when your business grows, and you need to build:

  • An iPhone / Android mobile app (which does not use HTML/CSS to draw screens).
  • A modern Single Page Application (SPA) written in React or Vue.
  • A Smart Watch or Internet of Things (IoT) thermostat.
  • An automated system that allows other companies' computers to query your inventory.

If your server sends back HTML filled with buttons, colors, and layout tags, mobile apps cannot easily understand it. Instead, the server must strip away all styling and visual layout, sending back only raw, structured data. This raw data bridge is called a Web API.

Concept 01

1. What is an API? (Application Programming Interface)

An API is not a physical device, a database, or a programming language. An API is an agreed-upon contract or rulebook that allows two completely independent software applications to talk to each other without needing to know how the other program is built internally.

💡 The Restaurant Waiter Analogy

Think of a restaurant. You (the Client) sit at a table. You do not walk into the kitchen (the Database/Backend) to cook or dig through the pantry.

Instead, the restaurant provides a Menu (the API Documentation) that lists exactly what items you are allowed to request. The Waiter (the API) takes your specific order, carries it back to the kitchen, waits for the meal to be prepared, and delivers the finished food back to your table. You do not care what kind of stove the kitchen uses; you only care that when you ask for item #4, you receive item #4.

What makes it a "Web API"?

In general computer science, an API can exist between any two software components (such as Python code calling a built-in math module). But when we say Web API, we mean an interface that communicates over the internet using the standard HTTP/HTTPS protocol that we explored in Part 1.

Concept 02

2. Data Formats: Why JSON Won the Web

When an API server talks across the internet, it cannot send live Python objects directly through fiber-optic cables. It must convert that data into a universal, human-readable text format.

Over web history, three primary text formats have competed:

1. Plain Text (text/plain)

Simple strings like: Alice,30,alice@example.com. Extremely lightweight, but very poor at representing nested or hierarchical structures (e.g. a user who has multiple addresses and a list of order numbers).

2. XML (application/xml)

An older markup format with opening and closing tags (e.g., <user><name>Alice</name></user>). It is verbose, heavy, and difficult to parse quickly in modern programming languages.

3. JSON (application/json) — The Undisputed King

JSON (JavaScript Object Notation) is clean, readable, minimal, and supported natively by virtually every single programming language in existence without needing special external tools.

Visual Proof: XML vs. JSON for the Exact Same Data

// XML (Heavy, Repetitive Tags) 
<user id="101">
    <name>Alice</name>
    <isActive>true</isActive>
    <skills>
        <skill>Python</skill>
        <skill>FastAPI</skill>
    </skills>
</user>
// JSON (Clean, Concise, Lightweight) 
{
  "id": 101,
  "name": "Alice",
  "is_active": true,
  "skills": ["Python", "FastAPI"]
}
Concept 03

3. How Python Translates into JSON (Serialization)

If you know basic Python, you already understand 95% of JSON. They share almost identical data structures:

Python Data Type JSON Equivalent Example
dict Object {"name": "Alice"}
list, tuple Array [1, 2, 3]
str String "Hello World"
int, float Number 42 or 3.14
True / False true / false true (lowercase in JSON)
None null null
Serialization (Dumping)

Taking an in-memory Python object (like a dict) and encoding it into a JSON formatted text string so it can be sent over HTTP.

Deserialization (Parsing)

Taking an incoming raw JSON string received over the network and converting it back into a native Python dictionary so your code can read its keys.

Concept 04

4. RESTful API Architecture

You can technically design an API any way you want, but chaos occurs when every developer makes up their own random rules. To bring consistency, the software industry follows an architectural style called REST (Representational State Transfer).

An API that follows these rules is described as RESTful. It relies on three fundamental conventions:

Rule 1: Treat Everything as a "Resource" (Use Nouns, Not Verbs)

In REST, your URLs represent things (data resources), not actions. Actions belong in the HTTP Method (GET, POST, etc.) that we learned in Part 1.

❌ Bad: POST /delete_user_by_id?id=5
✔ Clean REST: DELETE /users/5

Rule 2: Statelessness

The server never "remembers" previous requests automatically. Every single incoming request must include all the credentials, IDs, and payload data required to complete that task independently.

Rule 3: Standard HTTP Headers for Content Negotiation

Both the client and server must declare what format they are sending and expecting via HTTP headers: 

Content-Type: application/json  (Tells the receiver: "I am sending you JSON data")
Accept: application/json        (Tells the server: "Please respond to me in JSON")
Concept 05

5. Designing Clean CRUD Endpoints

Almost every database record in history undergoes four operations known as CRUD: Create, Read, Update, and Delete. In a REST API, these map directly onto the HTTP verbs:

Operation HTTP Verb Clean Endpoint URL Expected Status Code
Read All GET /items 200 OK
Read One GET /items/42 200 OK (or 404 Not Found)
Create POST /items 201 Created
Update (Full) PUT /items/42 200 OK
Update (Partial) PATCH /items/42 200 OK
Delete DELETE /items/42 204 No Content

Path Parameters vs. Query Parameters

1. Path Parameters (Identity)

Used to identify a specific single resource:

/products/841
2. Query Parameters (Filtering/Sorting)

Appended after a ? to filter, search, or paginate a collection:

/products?category=shoes&limit=10
Framework Spotlight: Building Real REST APIs with FastAPI
Tool Breakdown

Why FastAPI Shines for APIs:

As introduced in Part 1, FastAPI is a lightweight Python web framework. When building APIs, it has two super-powers:

  1. Automatic JSON Conversion: Any Python dictionary or model you return is automatically converted into pure JSON without extra code.
  2. Automatic Interactive Docs: Visiting /docs in your browser instantly gives you an interactive UI (Swagger) to test all your endpoints live.

Installation Reminder:

pip install fastapi uvicorn

A Fully Functional REST API in Python:

Save this as main.py and run it with uvicorn main:app --reload:

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

# In-memory database simulation (a list of Python dictionaries)
fake_database = [
    {"id": 1, "title": "Buy groceries", "completed": False},
    {"id": 2, "title": "Read Part 2 guide", "completed": True}
]

# Schema: Define what data a client must send when creating a todo
class TodoCreate(BaseModel):
    title: str
    completed: bool = False

# 1. READ ALL (GET)
@app.get("/todos")
def get_all_todos():
    return fake_database  # FastAPI automatically converts this to JSON!

# 2. READ ONE (GET with Path Parameter)
@app.get("/todos/{todo_id}")
def get_single_todo(todo_id: int):
    for item in fake_database:
        if item["id"] == todo_id:
            return item
    raise HTTPException(status_code=404, detail="Todo item not found")

# 3. CREATE (POST with JSON Body)
@app.post("/todos", status_code=201)
def create_todo(new_todo: TodoCreate):
    new_item = {
        "id": len(fake_database) + 1,
        "title": new_todo.title,
        "completed": new_todo.completed
    }
    fake_database.append(new_item)
    return new_item
Summary

7. Key Takeaways & Review

✔ APIs Decouple Presentation: Web APIs return pure structured data (JSON), allowing one backend to power mobile apps, web browsers, and external partners simultaneously.
✔ JSON Dominance: JSON won because it is minimal, human-readable, and maps directly to native dictionaries and lists across all languages.
✔ RESTful Convention: REST uses nouns in URL paths for resources (/users) and HTTP verbs for actions (GET, POST, DELETE).
✔ Status Code Accuracy: REST APIs communicate state using standard HTTP codes (e.g. 200 OK, 201 Created, 404 Not Found) alongside JSON response bodies.
