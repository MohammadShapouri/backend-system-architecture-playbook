Part 01

Computer Science: The RFC 7519 Registered Claims Specification

In JSON Web Token terminology, a Claim is a piece of information asserted about a subject. RFC 7519 categorizes claims into three tiers: Public (custom schemas registered in IANA), Private (bespoke application-level agreements like roles or tenant_id), and Registered Claims.

Registered claims are reserved three-letter abbreviations defined by the Internet Engineering Task Force (IETF). While RFC 7519 makes them technically optional, production systems must treat them as strictly mandatory to prevent token replay, privilege escalation, and domain contamination:

exp (Expiration Time) Mandatory

NumericDate (seconds since Unix epoch) identifying when the token ceases to be valid. PyJWT rejects tokens automatically if current UTC time exceeds this value.

nbf (Not Before) Temporal Guard

NumericDate stating the earliest exact moment this token can be accepted. Rejects premature token usage during staged multi-step activations.

iat (Issued At) Auditability

NumericDate indicating when the authentication authority minted the token. Critical for measuring token age and revoking tokens issued before password changes.

iss (Issuer) Identity Authority

Case-sensitive string/URI identifying the security entity that issued the claims (e.g., "https://iam.tokenforge.internal"). Prevents rogue authority spoofing.

aud (Audience) Target Boundary

String or array identifying the intended recipients of this token (e.g., "order-service"). If the current service is not listed, the token is rejected.

sub & jti Subject & Nonce

sub: The subject identifier (User ID / Principal).
jti: Unique UUID nonce preventing replay attacks and tracking revocations.

Part 02

Under the Hood: PyJWT Decoding Options & Strict Enforcement

By default, when you call jwt.decode(token, key, algorithms=["RS256"]), PyJWT verifies the signature and validates exp and nbf only if those keys are physically present in the incoming payload.

If an attacker manages to obtain a token emitted without an exp claim, or if a legacy IAM system omits the expiration entirely, PyJWT will treat the token as valid forever!

The PyJWT Defensive Decoding Pipeline
1. Cryptographic Check Verifies signature with Public Key / Secret
→ validates shape →
2. Mandatory Requirements options={"require": ["exp", "sub", "iat", "iss", "aud"]}
→ checks time/bounds →
3. Claims Verification Checks exp > now • matches iss/aud boundaries
The "require" Option Mandate:

To eliminate immortal tokens and anonymous claims, enterprise decoders must explicitly configure the options={"require": [...]} dictionary. If any specified claim is missing from the payload, PyJWT halts decoding and raises jwt.exceptions.MissingRequiredClaimError immediately!

PyJWT Built-in Exception Hierarchy

Senior engineers write exception handlers against PyJWT's exact inheritance hierarchy, never catching a generic Exception:

jwt.PyJWTError (Base class for all token faults)
 ├── jwt.InvalidTokenError (Signature or structure invalid)
 │   ├── jwt.DecodeError (Malformed Base64URL segment)
 │   ├── jwt.InvalidSignatureError (Cryptographic tamper detected)
 │   ├── jwt.ExpiredSignatureError (Token time has lapsed: exp < now)
 │   ├── jwt.ImmatureSignatureError (Token not yet active: nbf > now)
 │   ├── jwt.InvalidIssuerError (Issuer does not match expectation)
 │   ├── jwt.InvalidAudienceError (Audience mismatch detected)
 │   └── jwt.MissingRequiredClaimError (Mandatory claim omitted)
 └── jwt.InvalidAlgorithmError (Algorithm switching exploit attempt)
Part 03

Microservice Security: Audience Confusion & Clock Skew (Leeway)

In multi-tenant distributed cloud infrastructure, two subtle failure modes cause either severe security vulnerabilities or intermittent false-positive 401 Unauthorized errors:

1. Clock Skew Drift (NTP Desynchronization) leeway Parameter

Operating system hardware clocks across Kubernetes nodes inevitably drift by several milliseconds or seconds due to Network Time Protocol (NTP) adjustments.

IAM Node Clock: 12:00:00 (Issues token with exp=12:15:00)
Billing Node Clock: 12:15:02 (2 seconds ahead!)
→ Request fails with ExpiredSignatureError before its time!

The Solution: Pass leeway=timedelta(seconds=10) into jwt.decode(). PyJWT allows a tight, controlled margin for temporal boundary checks, neutralizing drift without compromising security.

2. Audience Confusion & Cross-Service Replay aud Claim

In a microservice ecosystem, an IAM authority issues tokens for various consumers. An Audience Confusion Exploit occurs when a token intended for an unprivileged service is replayed against a sensitive internal service.

User logs into Public Forum → Receives validly signed JWT
User takes that forum token → Dispatches to Bank Settlement API
→ If Settlement API only verifies signature, the request SUCCEEDS!

The Solution: Every microservice must configure audience="payment-settlement-service". If the token's aud array does not explicitly match, PyJWT raises InvalidAudienceError.

1. Defensive Token Validator: src/tokenforge/services/validator.py Claims Engine Core 
# ==============================================================================
# TokenForge Services - Defensive Claims Validator (Milestone 02)
# ==============================================================================

import jwt
from dataclasses import dataclass
from datetime import timedelta
from typing import Any, Dict, List, Optional
from tokenforge.core.crypto import TokenSecurityError, AlgorithmMismatchError

class TokenExpiredError(TokenSecurityError):
    """Raised when token expiration timestamp has elapsed."""
    pass

class TokenImmatureError(TokenSecurityError):
    """Raised when token is received prior to its 'nbf' (Not Before) timestamp."""
    pass

class AudienceMismatchError(TokenSecurityError):
    """Raised when token 'aud' does not match the target service audience."""
    pass

class IssuerMismatchError(TokenSecurityError):
    """Raised when token 'iss' does not match the sanctioned authority."""
    pass

class MissingClaimError(TokenSecurityError):
    """Raised when a mandatory RFC 7519 claim is omitted from payload."""
    pass


@dataclass(frozen=True)
class ValidatedToken:
    """Type-safe container holding verified claims extracted from decoded JWT."""
    subject: str
    issuer: str
    audience: List[str]
    issued_at: int
    expires_at: int
    claims: Dict[str, Any]


class TokenValidator:
    """
    PRODUCTION TOKEN VALIDATOR:
    Enforces mandatory registered claims, mitigates clock drift via leeway,
    and defends against audience confusion attacks across microservices.
    """
    def __init__(
        self,
        verification_key: str,
        expected_issuer: str,
        expected_audience: str,
        allowed_algorithms: Optional[List[str]] = None,
        leeway_seconds: int = 10,
        required_claims: Optional[List[str]] = None
    ):
        self.verification_key = verification_key
        self.expected_issuer = expected_issuer
        self.expected_audience = expected_audience
        self.allowed_algorithms = allowed_algorithms or ["RS256"]
        self.leeway = timedelta(seconds=leeway_seconds)
        # Defensive mandate: Require all critical claims by default
        self.required_claims = required_claims or ["exp", "sub", "iss", "aud", "iat"]

    def decode_and_validate(self, token: str) -> ValidatedToken:
        """
        Decodes and validates a token against strict RFC 7519 security criteria.
        Returns: ValidatedToken value object on success.
        Raises: Specific TokenSecurityError subclass on any failure.
        """
        try:
            claims = jwt.decode(
                jwt=token,
                key=self.verification_key,
                algorithms=self.allowed_algorithms,
                issuer=self.expected_issuer,
                audience=self.expected_audience,
                leeway=self.leeway,
                options={
                    "verify_signature": True,
                    "verify_exp": True,
                    "verify_nbf": True,
                    "verify_iat": True,
                    "verify_aud": True,
                    "verify_iss": True,
                    # CRITICAL DEFENSE: Enforce presence of all mandated claims
                    "require": self.required_claims
                }
            )
        except jwt.exceptions.ExpiredSignatureError as err:
            raise TokenExpiredError("Token signature has expired.") from err
        except jwt.exceptions.ImmatureSignatureError as err:
            raise TokenImmatureError("Token is not yet active (nbf in future).") from err
        except jwt.exceptions.InvalidAudienceError as err:
            raise AudienceMismatchError(f"Audience mismatch: expected '{self.expected_audience}'") from err
        except jwt.exceptions.InvalidIssuerError as err:
            raise IssuerMismatchError(f"Issuer mismatch: expected '{self.expected_issuer}'") from err
        except jwt.exceptions.MissingRequiredClaimError as err:
            raise MissingClaimError(f"Mandatory RFC 7519 claim omitted: {str(err)}") from err
        except jwt.exceptions.InvalidAlgorithmError as err:
            raise AlgorithmMismatchError("Token algorithm is not in the allowed whitelist.") from err
        except jwt.PyJWTError as err:
            raise TokenSecurityError(f"Token verification rejected: {str(err)}") from err

        # Normalize audience to list
        raw_aud = claims["aud"]
        aud_list = raw_aud if isinstance(raw_aud, list) else [raw_aud]

        return ValidatedToken(
            subject=claims["sub"],
            issuer=claims["iss"],
            audience=aud_list,
            issued_at=claims["iat"],
            expires_at=claims["exp"],
            claims=claims
        )

import time
import pytest
from tokenforge.core.crypto import TokenEngine
from tokenforge.services.validator import (
    TokenValidator,
    TokenExpiredError,
    TokenImmatureError,
    AudienceMismatchError,
    IssuerMismatchError,
    MissingClaimError
)

@pytest.fixture
def valid_claims():
    now = int(time.time())
    return {
        "iss": "https://iam.tokenforge.internal",
        "sub": "usr_99182",
        "aud": "settlement-service",
        "iat": now,
        "exp": now + 300,  # 5 minutes in future
        "scope": "settlement:execute"
    }

@pytest.fixture
def validator(rsa_keypair):
    return TokenValidator(
        verification_key=rsa_keypair["public"],
        expected_issuer="https://iam.tokenforge.internal",
        expected_audience="settlement-service",
        allowed_algorithms=["RS256"],
        leeway_seconds=5
    )


class TestClaimsValidation:
    """Unit tests asserting strict RFC 7519 claim verification and boundary defense."""

    def test_valid_token_decodes_successfully(self, rsa_keypair, validator, valid_claims):
        issuer_engine = TokenEngine(algorithm="RS256", signing_key=rsa_keypair["private"])
        token = issuer_engine.issue_token(valid_claims)

        result = validator.decode_and_validate(token)

        assert result.subject == "usr_99182"
        assert result.issuer == "https://iam.tokenforge.internal"
        assert "settlement-service" in result.audience
        assert result.claims["scope"] == "settlement:execute"

    def test_expired_token_is_rejected(self, rsa_keypair, validator, valid_claims):
        # Set expiration to 60 seconds in the past
        valid_claims["exp"] = int(time.time()) - 60
        valid_claims["iat"] = int(time.time()) - 300

        issuer_engine = TokenEngine(algorithm="RS256", signing_key=rsa_keypair["private"])
        token = issuer_engine.issue_token(valid_claims)

        with pytest.raises(TokenExpiredError, match=r"signature has expired"):
            validator.decode_and_validate(token)

    def test_clock_skew_within_leeway_passes(self, rsa_keypair, validator, valid_claims):
        # Token expired 3 seconds ago, but validator leeway is 5 seconds!
        valid_claims["exp"] = int(time.time()) - 3
        valid_claims["iat"] = int(time.time()) - 300

        issuer_engine = TokenEngine(algorithm="RS256", signing_key=rsa_keypair["private"])
        token = issuer_engine.issue_token(valid_claims)

        # Must pass cleanly due to clock drift leeway
        result = validator.decode_and_validate(token)
        assert result.subject == "usr_99182"

    def test_audience_confusion_is_blocked(self, rsa_keypair, validator, valid_claims):
        # Token was legitimately issued for the 'reporting-service', NOT 'settlement-service'
        valid_claims["aud"] = "reporting-service"

        issuer_engine = TokenEngine(algorithm="RS256", signing_key=rsa_keypair["private"])
        token = issuer_engine.issue_token(valid_claims)

        with pytest.raises(AudienceMismatchError, match=r"Audience mismatch"):
            validator.decode_and_validate(token)

    def test_issuer_mismatch_is_blocked(self, rsa_keypair, validator, valid_claims):
        valid_claims["iss"] = "https://rogue-authority.attacker.io"

        issuer_engine = TokenEngine(algorithm="RS256", signing_key=rsa_keypair["private"])
        token = issuer_engine.issue_token(valid_claims)

        with pytest.raises(IssuerMismatchError, match=r"Issuer mismatch"):
            validator.decode_and_validate(token)

    def test_missing_mandatory_claim_rejected(self, rsa_keypair, validator, valid_claims):
        # Omit the 'exp' claim entirely
        del valid_claims["exp"]

        issuer_engine = TokenEngine(algorithm="RS256", signing_key=rsa_keypair["private"])
        token = issuer_engine.issue_token(valid_claims)

        with pytest.raises(MissingClaimError, match=r"Mandatory RFC 7519 claim omitted"):
            validator.decode_and_validate(token)
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ verify_signature=False in Application Logic

Writing jwt.decode(token, options={"verify_signature": False}) to extract the user ID in a middleware or controller.

Why this is catastrophic: Disabling signature verification allows anyone on the internet to send arbitrary JSON payloads. An attacker can create a token with {"sub": "root", "role": "admin"} and your backend will accept it as valid! Only use verify_signature=False in offline diagnostic inspection tools.

❌ Putting Relational State in JWT Payloads

Embedding user billing addresses, shopping cart items, or dynamic permissions inside the token payload.

Why this causes data bugs: JWTs are immutable. If a user's permissions change in the database, their active token retains their old permissions until exp lapses. Furthermore, large payloads bloat HTTP request headers, causing reverse proxies (Nginx/Cloudflare) to reject requests with HTTP 431 Request Header Fields Too Large. Keep tokens under 1KB!
