Computer Science Foundations

Concurrency Physics: Event Loops, Threads & Contention

In modern asynchronous Python (FastAPI, Asyncio, AnyIO), understanding the physics of concurrent execution is essential. The Asyncio runtime operates on a single-threaded cooperative event loop.

While this design delivers massive I/O concurrency (>50,000 concurrent network sockets with minimal RAM overhead), it introduces severe failure modes when mismanaged:

1. Event Loop Starvation

If a single coroutine executes a blocking CPU-heavy task (such as verifying a cryptographic signature or running complex risk calculations for 100ms), the entire event loop freezes. No other coroutine can run, incoming TCP handshakes stall, and p99 latency spikes uncontrollably.

2. Unbounded Buffer Bloat

When producers ingest orders faster than consumers can process them, unconstrained in-memory queues expand without limit. In a high-traffic surge, millions of tasks pile into memory, triggering the Linux OOM-killer and crashing the container.

Concurrency Pattern #31

Pattern Name: Bounded Producer-Consumer (with Backpressure)

Formal Classification: POSA Vol. 2 • Architectural Concurrency Pattern

💡 The Real-World Metaphor (Plain English)

Imagine the drive-through lane at a busy fast-food restaurant.

Cars (Producers) arrive at the speaker box to order food. The kitchen staff (Consumers) prepare the meals in the back. Between the speaker box and the pickup window is a physical lane that fits exactly 5 cars (The Bounded Queue).

If the kitchen falls behind and the 5-car lane fills up completely, the restaurant employee asks incoming cars to wait at the entrance (Backpressure). Cars don't pile up infinitely across the street causing a gridlock accident. The bounded lane decouples arrival speed from cooking speed safely.

The Problem: Unbounded Async Queues

In Python, calling asyncio.Queue() with no arguments defaults to maxsize=0 (an infinite queue). During an exchange flash-crash, 500,000 trade events arrive in seconds. Without a buffer limit, the queue swallows all available server RAM: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: Unbounded In-Memory Queuing (OOM Disaster)
# ------------------------------------------------------------------------------

class UnsafeOrderIngestor:
    def __init__(self):
        # Maxsize=0 means UNBOUNDED! Can grow to millions of items!
        self.queue = asyncio.Queue()

    async def on_order_received(self, order_data: dict):
        # If consumers lag behind, this put() never pauses, consuming all server RAM!
        await self.queue.put(order_data)
✔ When to Use Bounded Producer-Consumer
  • Data arrives in volatile, bursty spikes but downstream consumers process at a steady, fixed throughput.
  • You must enforce physical memory caps by applying backpressure to producers when buffers reach capacity.
  • You want to decouple multiple producer coroutines from multiple consumer workers cleanly.
✘ When NOT to Use
  • Synchronous request-response endpoints where the caller must receive the processing result immediately before returning an HTTP response.
Concurrency Pattern #32

Pattern Name: Worker / Thread Pool (Async-Safe Offloading)

Formal Classification: POSA Vol. 2 • Resource Management Pattern

💡 The Real-World Metaphor (Plain English)

Imagine the head concierge at a busy hotel front desk.

If a guest arrives and asks to have their entire 12-page legal document translated into Japanese, the concierge does not sit down, pull out a dictionary, and spend 4 hours translating while 50 other guests wait in line at the desk!

Instead, the concierge hands the translation task to a dedicated Back-Office Translation Team (The Worker Pool). The concierge immediately resumes greeting new guests at the counter. When the back-office finishes, the document is returned seamlessly. The main counter never stops moving!

The Problem: Event Loop Freezes from CPU Workloads

Executing CPU-intensive algorithms (such as Argon2/Bcrypt password hashing, HMAC signature verification, or complex Monte Carlo risk simulations) directly inside an async def function locks the single thread running the Asyncio event loop: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: Running Heavy CPU Logic Directly in Async Event Loop
# ------------------------------------------------------------------------------

@app.post("/orders/verify")
async def verify_trade_signatures(payload: OrderVerificationDTO):
    # CPU-bound intensive cryptographic loop running in the main async thread:
    for _ in range(100_000):
        hmac.new(b"key", payload.signature.encode(), hashlib.sha512).digest()
        
    # CATASTROPHE: For 250 milliseconds, the event loop is 100% BLOCKED!
    # No other user can load pages, health probes fail, and timeouts cascade!
    return {"status": "VALID"}
✔ When to Use Worker Pool
  • You have heavy CPU-bound tasks (cryptography, image rendering, parsing large files) that would otherwise stall the event loop.
  • You are calling blocking third-party legacy C libraries or synchronous I/O drivers that don't support await.
  • You want to bound the maximum number of simultaneous threads to avoid thrashing system memory and CPU context switches.
✘ When NOT to Use
  • Standard non-blocking network I/O calls (e.g. database queries with asyncpg or HTTP calls with httpx). Plain await is far more efficient than allocating OS threads!
Concurrency Pattern #33

Pattern Name: Reader-Writer Lock (RWLock with Writer Priority)

Formal Classification: POSA Vol. 2 • Synchronization Pattern p. 99

💡 The Real-World Metaphor (Plain English)

Imagine the departure and arrivals board at a massive international train terminal.

At any given second, hundreds of passengers can look up and read the board simultaneously. Ten thousand people reading at the same time does not cause any confusion or data corruption.

However, when a technician needs to update the track number for the 5:00 PM Express, they must freeze the board exclusively. No passenger should read a half-updated, scrambled row. As soon as the technician finishes writing, all passengers can immediately resume reading in parallel.

Reader-Writer Concurrency Invariant Matrix
Concurrent Read Mode (Shared Lock)
• Reader 1: Reading OrderBook status → ALLOWED
• Reader 2: Reading OrderBook status → ALLOWED
• Reader 100: Reading OrderBook status → ALLOWED
✓ Infinite parallel readers permitted simultaneously!
Exclusive Write Mode (Exclusive Lock)
• Writer 1: Modifying order slot → GRANTED EXCLUSIVE LOCK
• Incoming Readers: QUEUED & BLOCKED
• Other Writers: QUEUED & BLOCKED
✗ Total mutual exclusion during updates!
The Writer Starvation Threat & Solution:

In naive RWLocks, if incoming readers arrive continuously without pause, a writer might wait forever (Writer Starvation). Our implementation uses Writer Preference: the moment a writer requests access, new readers are queued behind the writer, ensuring updates are never stalled indefinitely!

✔ When to Use RWLock
  • You have a shared in-memory data structure (like an OrderBook, configuration cache, or symbol registry) where reads outnumber writes by 10:1 or 100:1.
  • Standard locks (asyncio.Lock) are causing high read-latency bottlenecks under multi-tenant querying.
✘ When NOT to Use
  • Write frequency equals or exceeds read frequency (a standard Mutex has lower overhead).
  • Read operations take under 10 nanoseconds (the overhead of managing reader counters exceeds the locking savings).
Concurrency Pattern #34

Pattern Name: SingleFlight (Request Coalescing)

Formal Classification: High-Performance Distributed/Async Concurrency Pattern

💡 The Real-World Metaphor (Plain English)

Imagine 10 roommates sitting in a living room on a hot summer afternoon.

Roommate 1 stands up and says: "I'm walking to the corner store to buy ice cream."

The other 9 roommates do not all jump up, start 9 separate cars, drive to the exact same store, stand in 9 separate checkout lines, and buy 9 separate cartons of the exact same vanilla ice cream! Instead, they tell Roommate 1: "Grab some for me too." Roommate 1 makes a single trip, returns, and shares the result with everyone. That is SingleFlight.

The Problem: Identical In-Flight Redundant Workloads

When sudden volatility hits Bitcoin or Apple stock, 5,000 algorithmic bots and UI clients simultaneously request the exact same historical candlestick data or market index calculation:

SingleFlight In-Flight Request Deduplication
1,000 Concurrent Calls singleflight.do("btc_index", fetch_fn)
→ merged by key →
SingleFlight Leader Spawns 1 single in-flight task
999 callers await shared Future
→ single execution →
Backend Database Executes EXACTLY ONCE!
✔ When to Use SingleFlight
  • You have computationally expensive or I/O-intensive read queries that frequently experience concurrent duplicate requests for the identical key.
  • You want to eliminate cache stampedes and dogpiling spikes without requiring distributed Redis locks.
✘ When NOT to Use
  • Mutating write operations (such as transferring money or creating orders). Writes must not be deduplicated unless explicit idempotency rules dictate it!

1. Bounded Producer-Consumer Engine: src/nexuscore/concurrency/queue.py Backpressure Control 
# ==============================================================================
# NexusCore Concurrency - Bounded Producer-Consumer with Backpressure
# ==============================================================================

import asyncio
from typing import Any, Optional


class QueueBackpressureError(Exception):
    """Raised when the bounded queue cannot accept more items within timeout."""
    pass


class BoundedOrderQueue:
    """
    BOUNDED PRODUCER-CONSUMER QUEUE:
    Prevents memory exhaustion by fixing an immutable max capacity buffer.
    Applies backpressure by forcing producers to wait or fail when full.
    """
    def __init__(self, maxsize: int = 1000):
        if maxsize <= 0:
            raise ValueError("maxsize must be strictly greater than 0")
        self._queue: asyncio.Queue = asyncio.Queue(maxsize=maxsize)
        self._sentinel = object()  # Poison pill to signal consumers to stop cleanly

    async def produce(self, item: Any, timeout: Optional[float] = 2.0) -> None:
        """
        Produces an item into the queue.
        Enforces backpressure: if queue is full, awaits up to `timeout` seconds.
        """
        try:
            await asyncio.wait_for(self._queue.put(item), timeout=timeout)
        except asyncio.TimeoutError:
            raise QueueBackpressureError(
                f"Backpressure limit reached. Queue at capacity ({self._queue.maxsize})."
            )

    async def consume(self) -> Any:
        """Consumes an item from the queue, blocking until an item is available."""
        item = await self._queue.get()
        if item is self._sentinel:
            # Put sentinel back so all worker tasks receive the termination signal
            await self._queue.put(self._sentinel)
            self._queue.task_done()
            return None
        return item

    def task_done(self) -> None:
        self._queue.task_done()

    async def close(self) -> None:
        """Broadcasts termination sentinel to shutdown consumer loops."""
        await self._queue.put(self._sentinel)

    @property
    def size(self) -> int:
        return self._queue.qsize()
2. Async-Safe Managed Worker Pool: src/nexuscore/concurrency/worker_pool.py Thread Pool Offloading 
# ==============================================================================
# NexusCore Concurrency - Managed Worker Pool for CPU-Bound Offloading
# ==============================================================================

import asyncio
from concurrent.futures import ThreadPoolExecutor
from typing import Callable, Any


class CPUWorkerPool:
    """
    WORKER / THREAD POOL PATTERN:
    Manages dedicated OS worker threads to execute synchronous CPU-intensive tasks
    without blocking the single-threaded Asyncio event loop.
    """
    def __init__(self, max_workers: int = 4):
        self._executor = ThreadPoolExecutor(max_workers=max_workers, thread_name_prefix="nexus_cpu")

    async def execute(self, sync_fn: Callable[..., Any], *args: Any) -> Any:
        """Offloads synchronous work to thread pool and awaits result non-blockingly."""
        loop = asyncio.get_running_loop()
        return await loop.run_in_executor(self._executor, sync_fn, *args)

    def shutdown(self) -> None:
        self._executor.shutdown(wait=True)
3. Writer-Priority Async RWLock: src/nexuscore/concurrency/rwlock.py POSA Vol. 2 Synchronization 
# ==============================================================================
# NexusCore Concurrency - Async Reader-Writer Lock with Writer Priority
# ==============================================================================

import asyncio
from contextlib import asynccontextmanager


class AsyncRWLock:
    """
    READER-WRITER LOCK WITH WRITER PREFERENCE:
    Allows infinite concurrent readers when no writer is active.
    When a writer requests the lock, incoming readers are blocked, preventing writer starvation.
    """
    def __init__(self):
        self._readers: int = 0
        self._writers_waiting: int = 0
        self._writer_active: bool = False
        self._lock: asyncio.Lock = asyncio.Lock()
        self._read_ok: asyncio.Condition = asyncio.Condition(self._lock)
        self._write_ok: asyncio.Condition = asyncio.Condition(self._lock)

    @asynccontextmanager
    async def read_lock(self):
        """Acquires a shared read lock."""
        async with self._lock:
            # Block readers if a writer is active OR writers are waiting (Writer Preference)
            while self._writer_active or self._writers_waiting > 0:
                await self._read_ok.wait()
            self._readers += 1

        try:
            yield
        finally:
            async with self._lock:
                self._readers -= 1
                if self._readers == 0:
                    # Wake up waiting writers when all active readers exit
                    self._write_ok.notify()

    @asynccontextmanager
    async def write_lock(self):
        """Acquires an exclusive write lock."""
        async with self._lock:
            self._writers_waiting += 1
            while self._writer_active or self._readers > 0:
                await self._write_ok.wait()
            self._writers_waiting -= 1
            self._writer_active = True

        try:
            yield
        finally:
            async with self._lock:
                self._writer_active = False
                # Prefer waiting writers; if none, notify all waiting readers
                if self._writers_waiting > 0:
                    self._write_ok.notify()
                else:
                    self._read_ok.notify_all()
4. Async SingleFlight Coalescer: src/nexuscore/concurrency/singleflight.py Request Coalescing 
# ==============================================================================
# NexusCore Concurrency - Async SingleFlight Request Coalescing Engine
# ==============================================================================

import asyncio
from typing import Any, Callable, Dict, Awaitable


class SingleFlightGroup:
    """
    SINGLEFLIGHT PATTERN:
    Deduplicates concurrent in-flight requests for the identical key.
    Merges duplicate calls into a single execution, broadcasting the result to all callers.
    """
    def __init__(self):
        self._in_flight: Dict[str, asyncio.Future] = {}
        self._lock = asyncio.Lock()

    async def do(self, key: str, fn: Callable[[], Awaitable[Any]]) -> Any:
        # 1. Check or register in-flight future under lock
        async with self._lock:
            if key in self._in_flight:
                future = self._in_flight[key]
                is_leader = False
            else:
                loop = asyncio.get_running_loop()
                future = loop.create_future()
                self._in_flight[key] = future
                is_leader = True

        # 2. Leader executes underlying work
        if is_leader:
            try:
                result = await fn()
                future.set_result(result)
                return result
            except BaseException as exc:
                future.set_exception(exc)
                raise
            finally:
                async with self._lock:
                    if key in self._in_flight:
                        del self._in_flight[key]

        # 3. Followers await leader resolution
        return await asyncio.shield(future)

import asyncio
import time
import hashlib
import pytest
from nexuscore.concurrency.queue import BoundedOrderQueue, QueueBackpressureError
from nexuscore.concurrency.worker_pool import CPUWorkerPool
from nexuscore.concurrency.rwlock import AsyncRWLock
from nexuscore.concurrency.singleflight import SingleFlightGroup


class TestConcurrencyPatterns:
    """Validates bounded queuing, worker pools, RWLocks, and SingleFlight."""

    @pytest.mark.asyncio
    async def test_bounded_queue_enforces_backpressure_timeout(self):
        # Bounded queue with capacity 2
        q = BoundedOrderQueue(maxsize=2)
        await q.produce("order_1")
        await q.produce("order_2")

        # 3rd produce must raise QueueBackpressureError after timeout
        with pytest.raises(QueueBackpressureError, match="Backpressure limit reached"):
            await q.produce("order_3", timeout=0.05)

    @pytest.mark.asyncio
    async def test_worker_pool_executes_cpu_task_without_blocking_event_loop(self):
        pool = CPUWorkerPool(max_workers=2)

        def heavy_hashing(payload: str) -> str:
            # Heavy CPU synchronous loop
            val = payload.encode()
            for _ in range(50_000):
                val = hashlib.sha256(val).digest()
            return val.hex()[:8]

        # Concurrently execute CPU task while checking event loop responsiveness
        t0 = time.perf_counter()
        task = asyncio.create_task(pool.execute(heavy_hashing, "trade_data"))
        
        # Event loop should remain responsive to other tasks:
        await asyncio.sleep(0.01)
        res = await task
        pool.shutdown()

        assert len(res) == 8
        assert time.perf_counter() - t0 > 0.01

    @pytest.mark.asyncio
    async def test_rwlock_allows_parallel_readers_and_exclusive_writer(self):
        rwlock = AsyncRWLock()
        active_readers = 0
        max_parallel_readers = 0

        async def reader_task():
            nonlocal active_readers, max_parallel_readers
            async with rwlock.read_lock():
                active_readers += 1
                max_parallel_readers = max(max_parallel_readers, active_readers)
                await asyncio.sleep(0.05)
                active_readers -= 1

        # Launch 5 concurrent readers
        await asyncio.gather(*[reader_task() for _ in range(5)])
        # Proves all 5 readers ran simultaneously in parallel:
        assert max_parallel_readers == 5

    @pytest.mark.asyncio
    async def test_singleflight_deduplicates_concurrent_calls(self):
        sf = SingleFlightGroup()
        invocations = 0

        async def expensive_query():
            nonlocal invocations
            invocations += 1
            await asyncio.sleep(0.05)
            return "BTC_PRICE_65000"

        # 50 concurrent requests for the identical key
        tasks = [sf.do("btc_ticker", expensive_query) for _ in range(50)]
        results = await asyncio.gather(*tasks)

        # SingleFlight coalesced 50 requests into exactly 1 call:
        assert invocations == 1
        assert all(r == "BTC_PRICE_65000" for r in results)
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Blocking the Asyncio Event Loop

Executing long synchronous computations or blocking I/O calls (like time.sleep(), requests.get(), or heavy cryptography) inside an async endpoint.

Why this causes system-wide freezes: The Asyncio loop is single-threaded. While one coroutine runs a 200ms CPU calculation, the entire server stops processing other requests! Always offload blocking work to a Worker Pool via loop.run_in_executor().

❌ Writer Starvation in Naive RWLocks

Implementing a Reader-Writer Lock where incoming readers can always acquire the lock as long as other readers are active.

Why this causes update deadlocks: In a high-traffic read service, the active reader count never drops to zero. As a result, writers wait indefinitely, causing stale state and blocked write queues! Always use an RWLock with Writer Preference to queue incoming readers behind waiting writers.
