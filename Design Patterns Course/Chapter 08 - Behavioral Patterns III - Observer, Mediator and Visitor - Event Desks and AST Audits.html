Architecture Fundamentals

Communication Topologies & Extensibility Without Mutation

As enterprise software grows from small services into complex platforms, two major communication bottlenecks occur:

  1. Chaotic Coupling (The Mesh Anti-Pattern): When 6 components in a trading desk (Risk, OrderBook, Logger, Accounts, UI, Notification) hold direct references to one another, you get an $N \times (N-1) / 2$ mesh of hardcoded dependencies. Changing one class forces rewrites across all 5 other classes.
  2. Class Pollution for Operations: When a domain model (such as our AssetHolding tree from Chapter 04) is forced to implement dozens of unrelated operational methods (tax calculation, XML serialization, risk stress-testing, PDF export), the model bloats and constantly changes for reasons unrelated to its core domain responsibility.
// The Triad of Coordinated Behavior:

Observer decouples 1-to-many event notification. Mediator consolidates many-to-many communication into a single hub. Visitor lets you define new operations over existing complex object structures without modifying the structures themselves.

Design Pattern #18

Pattern Name: Observer (Publish-Subscribe / Dependents)

Formal Classification: Behavioral Pattern • Gang of Four (GoF) Reference p. 293

💡 The Real-World Metaphor (Plain English)

Imagine subscribing to a channel on YouTube or Substack.

You do not set an alarm to call the creator's phone every 5 minutes asking: "Did you upload a video yet? Did you publish an article yet?" (This is the costly Polling Anti-Pattern).

Instead, you hit the "Subscribe" button. The creator doesn't know who you are personally, where you live, or what hardware you use. All they maintain is a list of subscriber endpoints. When a new video drops, the platform sends a notification push to everyone on the list automatically. If you unsubscribe, you stop receiving alerts. The publisher is completely decoupled from the consumers!

The Problem: Polling Waste and Hardcoded Push Lists

In NexusCore, market exchange sockets emit thousands of price ticks per second. Five separate services need these updates: the WebSocket dashboard, the High-Frequency Trading (HFT) Arbitrage Bot, the Stop-Loss Monitoring Daemon, and the Risk Regulator.

Without the Observer pattern, developers either write inefficient polling loops that waste CPU cycles, or hardcode every consumer directly inside the market feed generator: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: Hardcoding Consumers into the Event Source
# ------------------------------------------------------------------------------

class MarketFeedSource:
    def __init__(self, bot_a, dashboard_ui, risk_guard):
        # The price feed generator is directly coupled to specific concrete consumers!
        self.bot_a = bot_a
        self.dashboard_ui = dashboard_ui
        self.risk_guard = risk_guard

    def on_price_tick(self, symbol: str, price: float):
        # If we want to add an AnalyticsEngine tomorrow, we must rewrite this file!
        self.bot_a.analyze_tick(symbol, price)
        self.dashboard_ui.render_update(symbol, price)
        self.risk_guard.inspect_margin(symbol, price)
        # If one consumer crashes or hangs, the entire market tick pipeline stalls!
The Observer Pattern Event Dispatch Pipeline
Subject / Publisher
MarketPriceFeed
Maintains list of: weakref(IObserver)
Emits: notify_observers(tick)
→ broadcasts event →
Observer 1: HftArbitrageBot
Reacts by placing limit order
Observer 2: StopLossMonitor
Triggers liquidation on dip
Observer 3: WebSocketDashboard
Pushes JSON frame to frontend
The Weak Reference Invariant (Preventing Lapsed Listeners):

If a Subject holds strong references to observers, those observers cannot be garbage collected even when their lifecycle ends elsewhere! Using Python's weakref module ensures that when an observer is destroyed, it is pruned from the subscriber registry automatically, eliminating memory leaks.

✔ When to Use Observer
  • A change to one object requires changing an unknown or dynamic number of other objects.
  • An object should be able to notify other objects without making any assumptions about what those objects actually are (loose coupling).
  • You want to avoid wasteful periodic polling loops for state changes.
✘ When NOT to Use Observer
  • Subscribers mutate the publisher during their update callback, triggering an accidental **infinite notification loop**.
  • You require strict, synchronous, deterministic ordering of notifications across observers.
Design Pattern #19

Pattern Name: Mediator (Intermediary / Controller Hub)

Formal Classification: Behavioral Pattern • Gang of Four (GoF) Reference p. 273

💡 The Real-World Metaphor (Plain English)

Imagine the Air Traffic Control (ATC) tower at a busy international airport with 50 commercial airplanes in the surrounding airspace.

Pilots do not broadcast radio messages directly to all other 49 pilots to negotiate who lands first: "Hey Flight 202, this is Flight 404, are you landing on runway 27L or should I?" If every plane had to coordinate directly with every other plane, communication complexity would grow at $O(N^2)$, causing chaos and mid-air collisions.

Instead, all planes communicate exclusively with the ATC Tower (The Mediator). The tower receives signals, enforces separation rules, and issues landing clearances. The planes do not even need to know each other exist; they only know the tower!

The Problem: The Spaghetti Mesh of Inter-Component Coupling

In NexusCore, a trade execution floor has multiple autonomous actors:

  • Order Desk: Ingests client trades.
  • Risk Desk: Checks margin and position limits.
  • Settlement Desk: Debits and credits funds.
  • Audit Logger: Writes regulatory event streams.
  • Notification Desk: Alerts customer via push notifications.

If each of these 5 components references and calls the other 4 directly, you end up with 10 tightly coupled, bidirectional dependencies. You cannot test or reuse the Order Desk without instantiating the entire trading floor!

Topology Shift: Chaotic Mesh vs. Hub-and-Spoke Mediator
Chaotic Mesh ($O(N^2)$ Connections)
OrderDesk ↔ RiskDesk
OrderDesk ↔ SettlementDesk
OrderDesk ↔ AuditLogger
RiskDesk ↔ SettlementDesk
SettlementDesk ↔ NotificationDesk
✗ Total tangle: 10 bidirectional links!
Mediator Hub ($O(N)$ Connections)
OrderDesk → [TradingFloorMediator]
RiskDesk → [TradingFloorMediator]
SettlementDesk → [TradingFloorMediator]
AuditLogger → [TradingFloorMediator]
NotificationDesk → [TradingFloorMediator]
✓ 5 clean spokes. Components never see each other!
✔ When to Use Mediator
  • A set of objects communicate in complex, tightly coupled ways, making individual components difficult to understand, test, or reuse.
  • You want to customize how components collaborate without having to subclass each component individually.
  • You are building complex dialogs, trading floor dashboards, or multi-step coordination workflows.
✘ When NOT to Use Mediator
  • Communication between components is simple and linear (Consider Chain of Responsibility).
  • The mediator takes on business logic and becomes an unmaintainable "God Object" with thousands of lines of monolithic procedural code.
Design Pattern #20

Pattern Name: Visitor (Double Dispatch / AST Traverser)

Formal Classification: Behavioral Pattern • Gang of Four (GoF) Reference p. 331

💡 The Real-World Metaphor (Plain English)

Imagine an international health insurance auditor visiting your home.

Your house contains different family members: a healthy teenager, an elderly grandparent, and an infant baby. The family members do not have medical diagnostic degrees embedded into their brains. They don't know how to measure cardiovascular risk or calculate pediatric vaccine schedules.

Instead, when the Doctor (The Visitor) enters the house, each person simply says: "I accept your inspection." The Doctor examines the teenager differently than the infant, bringing all specialized diagnostic algorithms with them. Next week, a Tax Auditor (another Visitor) can visit the exact same family and calculate property taxes without altering the family members at all!

Double Dispatch Mechanics: Adding Operations Without Modifying Classes

In Chapter 04, we designed recursive Composite trees for institutional portfolios: containing AssetHolding leaf nodes and PortfolioGroup composite nodes.

Now, legal and risk departments ask for three completely new operations across the portfolio:

  1. Regulatory Tax Compliance Audit: Calculates capital gains tax liability across jurisdictions.
  2. Value-at-Risk (VaR) Stress Test: Calculates liquidation risk during a 20% market crash.
  3. JSON/XML Regulatory Export: Serializes the tree into central bank filing format.

If you add these methods directly to AssetHolding and PortfolioGroup, you pollute pure domain models with external audit math. The Visitor Pattern lets you define all three operations in separate visitor classes without changing a single line of your portfolio classes!

The Double Dispatch Invariant in the Visitor Pattern
1. Dispatch #1
Client calls:
node.accept(visitor)
→ invokes →
2. Dispatch #2
Node calls back:
visitor.visit_asset(self)
→ executes →
3. Specialized Algorithm
Visitor executes logic
Calculates tax / risk
Why is it called "Double Dispatch"?

The operation executed depends on two runtime types: the type of the Visitor (e.g. TaxVisitor vs. RiskVisitor) AND the type of the Element (e.g. AssetHolding vs. PortfolioGroup).

✔ When to Use Visitor
  • You need to perform an operation across all elements of a complex object structure (like an Abstract Syntax Tree or Composite portfolio).
  • You want to clean up your business logic by moving unrelated auxiliary operations out of the domain classes.
  • The object structure classes rarely change, but you frequently need to add new operations over them.
✘ When NOT to Use Visitor
  • The object hierarchy changes constantly (adding a new node class requires updating every single visitor interface and all its subclasses!).
  • The visitor requires access to private, encapsulated attributes that the node objects should not expose publicly.

1. Weak-Reference Market Data Feed: src/nexuscore/events/observer.py Observer Pattern (Memory-Safe) 
# ==============================================================================
# NexusCore Events - Memory-Safe Observer Pattern for Market Data Ticks
# ==============================================================================

import weakref
from dataclasses import dataclass
from typing import Protocol, runtime_checkable, List


@dataclass(frozen=True)
class MarketTickEvent:
    """Immutable market price change payload."""
    symbol: str
    price: float
    volume: float
    timestamp: float


# ------------------------------------------------------------------------------
# THE OBSERVER INTERFACE
# ------------------------------------------------------------------------------
@runtime_checkable
class IMarketDataObserver(Protocol):
    """Subscribers must implement on_tick to receive price updates."""
    def on_tick(self, event: MarketTickEvent) -> None:
        ...


# ------------------------------------------------------------------------------
# THE SUBJECT (Publisher)
# ------------------------------------------------------------------------------
class MarketPriceFeedSubject:
    """
    MEMORY-SAFE OBSERVER PUBLISHER:
    Uses weak references (WeakSet) to hold subscriber instances.
    Eliminates the 'Lapsed Listener' memory leak: when a consumer bot is deleted,
    it is automatically purged from this registry without keeping memory alive!
    """
    def __init__(self, symbol: str):
        self.symbol = symbol
        # Holds weak references to subscribed observer objects
        self._subscribers: weakref.WeakSet[IMarketDataObserver] = weakref.WeakSet()

    def subscribe(self, observer: IMarketDataObserver) -> None:
        self._subscribers.add(observer)

    def unsubscribe(self, observer: IMarketDataObserver) -> None:
        self._subscribers.discard(observer)

    def broadcast_tick(self, price: float, volume: float, timestamp: float) -> None:
        event = MarketTickEvent(self.symbol, price, volume, timestamp)
        # Broadcast to all live subscribers
        for sub in list(self._subscribers):
            sub.on_tick(event)

    def subscriber_count(self) -> int:
        return len(self._subscribers)
2. Central Trading Floor Hub: src/nexuscore/floor/mediator.py Mediator Pattern 
# ==============================================================================
# NexusCore Floor - Central Trading Floor Mediator (Decoupled Hub & Spoke)
# ==============================================================================

from abc import ABC, abstractmethod
from typing import Any, Dict, List


class ITradingFloorMediator(ABC):
    """Mediator contract: Components notify the mediator instead of each other."""
    @abstractmethod
    def notify(self, sender: "BaseDeskComponent", event: str, payload: Dict[str, Any]) -> None:
        pass


class BaseDeskComponent:
    """Colleague base class: Holds a reference strictly to the mediator."""
    def __init__(self, mediator: ITradingFloorMediator):
        self._mediator = mediator


# ------------------------------------------------------------------------------
# COLLEAGUES (Trading Desks)
# ------------------------------------------------------------------------------
class OrderIntakeDesk(BaseDeskComponent):
    def submit_order(self, order_id: str, amount: float) -> None:
        # Tells mediator about the event; has NO idea who handles it!
        self._mediator.notify(self, "ORDER_SUBMITTED", {"id": order_id, "amount": amount})


class RiskInspectionDesk(BaseDeskComponent):
    def inspect_risk(self, amount: float) -> bool:
        # Max safe limit $100,000
        return amount <= 100_000.0


class AuditDesk(BaseDeskComponent):
    def __init__(self, mediator: ITradingFloorMediator):
        super().__init__(mediator)
        self.logs: List[str] = []

    def record(self, message: str) -> None:
        self.logs.append(message)


# ------------------------------------------------------------------------------
# CONCRETE MEDIATOR
# ------------------------------------------------------------------------------
class TradingFloorMediator(ITradingFloorMediator):
    """
    THE MEDIATOR HUB:
    Centralizes and coordinates all cross-component interactions.
    Desks hold ZERO references to one another!
    """
    def __init__(self):
        self.order_desk: OrderIntakeDesk = OrderIntakeDesk(self)
        self.risk_desk: RiskInspectionDesk = RiskInspectionDesk(self)
        self.audit_desk: AuditDesk = AuditDesk(self)
        self.approved_orders: List[str] = []
        self.rejected_orders: List[str] = []

    def notify(self, sender: BaseDeskComponent, event: str, payload: Dict[str, Any]) -> None:
        if event == "ORDER_SUBMITTED":
            order_id = payload["id"]
            amount = payload["amount"]

            # 1. Log receipt
            self.audit_desk.record(f"INTAKE:{order_id}:{amount}")

            # 2. Check risk
            if self.risk_desk.inspect_risk(amount):
                self.approved_orders.append(order_id)
                self.audit_desk.record(f"APPROVED:{order_id}")
            else:
                self.rejected_orders.append(order_id)
                self.audit_desk.record(f"REJECTED_RISK:{order_id}")
3. Portfolio Audit Visitor: src/nexuscore/compliance/visitor.py Visitor Pattern (Double Dispatch) 
# ==============================================================================
# NexusCore Compliance - Visitor Pattern for Portfolio Audits & Tax Valuations
# ==============================================================================

from abc import ABC, abstractmethod
from typing import List, Dict


# ------------------------------------------------------------------------------
# THE VISITOR INTERFACE
# ------------------------------------------------------------------------------
class IPortfolioVisitor(ABC):
    """Defines a visit method for every concrete element type in the tree."""
    @abstractmethod
    def visit_holding(self, element: "VisitableHolding") -> None:
        pass

    @abstractmethod
    def visit_group(self, element: "VisitablePortfolioGroup") -> None:
        pass


# ------------------------------------------------------------------------------
# VISITABLE ELEMENTS (Extended from Chapter 04 Composite)
# ------------------------------------------------------------------------------
class IVisitableComponent(ABC):
    @abstractmethod
    def accept(self, visitor: IPortfolioVisitor) -> None:
        """Double-dispatch hook: calls visitor.visit_xxx(self)"""
        pass


class VisitableHolding(IVisitableComponent):
    """Leaf Node representing a stock/crypto holding."""
    def __init__(self, symbol: str, units: float, unit_price: float, asset_class: str):
        self.symbol = symbol
        self.units = units
        self.unit_price = unit_price
        self.asset_class = asset_class  # "EQUITY", "CRYPTO", "COMMODITY"

    @property
    def market_value(self) -> float:
        return self.units * self.unit_price

    def accept(self, visitor: IPortfolioVisitor) -> None:
        # DISPATCH #2: Dispatches to visit_holding
        visitor.visit_holding(self)


class VisitablePortfolioGroup(IVisitableComponent):
    """Composite Node representing a multi-asset fund or client trust."""
    def __init__(self, name: str):
        self.name = name
        self.children: List[IVisitableComponent] = []

    def add(self, component: IVisitableComponent) -> None:
        self.children.append(component)

    def accept(self, visitor: IPortfolioVisitor) -> None:
        # DISPATCH #2: Dispatches to visit_group, then cascades to children
        visitor.visit_group(self)
        for child in self.children:
            child.accept(visitor)


# ------------------------------------------------------------------------------
# CONCRETE VISITOR 1: Capital Gains Tax Calculator
# ------------------------------------------------------------------------------
class CapitalGainsTaxVisitor(IPortfolioVisitor):
    """
    VISITOR IMPLEMENTATION:
    Calculates tax liability across the entire portfolio tree.
    Crypto is taxed at 30%; Equities at 15%; Commodities at 20%.
    Cleanly externalized: zero tax math inside the VisitableHolding classes!
    """
    def __init__(self):
        self.total_tax: float = 0.0

    def visit_holding(self, element: VisitableHolding) -> None:
        rates = {"CRYPTO": 0.30, "EQUITY": 0.15, "COMMODITY": 0.20}
        tax_rate = rates.get(element.asset_class, 0.10)
        self.total_tax += element.market_value * tax_rate

    def visit_group(self, element: VisitablePortfolioGroup) -> None:
        # Groups hold zero intrinsic tax liability; container only
        pass


# ------------------------------------------------------------------------------
# CONCRETE VISITOR 2: Regulatory Exposure Stress-Test Auditor
# ------------------------------------------------------------------------------
class AssetExposureVisitor(IPortfolioVisitor):
    """Aggregates market exposure percentages by asset class across all funds."""
    def __init__(self):
        self.exposure_by_class: Dict[str, float] = {}

    def visit_holding(self, element: VisitableHolding) -> None:
        self.exposure_by_class[element.asset_class] = (
            self.exposure_by_class.get(element.asset_class, 0.0) + element.market_value
        )

    def visit_group(self, element: VisitablePortfolioGroup) -> None:
        pass

import time
import pytest
from nexuscore.events.observer import MarketPriceFeedSubject, MarketTickEvent
from nexuscore.floor.mediator import TradingFloorMediator
from nexuscore.compliance.visitor import (
    VisitableHolding, VisitablePortfolioGroup, CapitalGainsTaxVisitor, AssetExposureVisitor

class TestBehavioralThreeSuite:
    """Verifies Observer push mechanics, Mediator decoupling, and Visitor double dispatch."""

    def test_observer_broadcast_and_lapsed_listener_garbage_collection(self):
        feed = MarketPriceFeedSubject("BTC/USD")
        received_ticks = []

        class MockTradingBot:
            def on_tick(self, event: MarketTickEvent) -> None:
                received_ticks.append(event.price)

        bot = MockTradingBot()
        feed.subscribe(bot)
        assert feed.subscriber_count() == 1

        feed.broadcast_tick(price=64000.0, volume=1.5, timestamp=time.time())
        assert received_ticks == [64000.0]

        # Proof of Lapsed Listener resolution:
        # Delete bot reference → weakref must automatically prune subscriber!
        del bot
        assert feed.subscriber_count() == 0

    def test_mediator_coordinates_trade_floor_without_direct_colleague_coupling(self):
        mediator = TradingFloorMediator()

        # 1. Order below risk threshold ($50k <= $100k)
        mediator.order_desk.submit_order("ord_safe", amount=50_000.0)
        assert "ord_safe" in mediator.approved_orders
        assert "APPROVED:ord_safe" in mediator.audit_desk.logs

        # 2. Order exceeding risk threshold ($250k > $100k)
        mediator.order_desk.submit_order("ord_risky", amount=250_000.0)
        assert "ord_risky" in mediator.rejected_orders
        assert "REJECTED_RISK:ord_risky" in mediator.audit_desk.logs

    def test_visitor_double_dispatch_calculates_taxes_and_exposure(self):
        # Assemble Portfolio Tree (Root → Sub-Fund → Assets)
        root = VisitablePortfolioGroup("Apex Capital")
        tech_subfund = VisitablePortfolioGroup("Tech Desk")

        aapl = VisitableHolding("AAPL", units=100, unit_price=150.0, asset_class="EQUITY")      # $15,000 (15% tax = $2,250)
        btc = VisitableHolding("BTC", units=1, unit_price=50000.0, asset_class="CRYPTO")         # $50,000 (30% tax = $15,000)
        gold = VisitableHolding("GOLD", units=10, unit_price=1000.0, asset_class="COMMODITY")   # $10,000 (20% tax = $2,000)

        tech_subfund.add(aapl)
        tech_subfund.add(btc)
        root.add(tech_subfund)
        root.add(gold)

        # Execute Visitor 1: Capital Gains Tax
        tax_visitor = CapitalGainsTaxVisitor()
        root.accept(tax_visitor)
        assert tax_visitor.total_tax == 19250.0  # 2,250 + 15,000 + 2,000

        # Execute Visitor 2: Asset Class Exposure Auditor
        exposure_visitor = AssetExposureVisitor()
        root.accept(exposure_visitor)
        assert exposure_visitor.exposure_by_class == {
            "EQUITY": 15000.0,
            "CRYPTO": 50000.0,
            "COMMODITY": 10000.0
        }
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The Lapsed Listener Memory Leak

Subscribing short-lived UI or bot components to a long-lived singleton event publisher with strong references: self.subscribers.append(obs).

Why this causes memory crashes: The publisher's internal list holds a strong pointer to the subscriber. Even if the consumer component is closed and no other code references it, Python's Garbage Collector cannot free it! Millions of dead objects accumulate in RAM over days of uptime. Always use weakref.WeakSet or enforce explicit unsubscription!

❌ The "God Mediator" Anti-Pattern

Writing a Mediator that implements core domain algorithms directly instead of purely routing notifications between specialized colleagues.

Why this causes architectural collapse: If the Mediator calculates margin ratios, formats database SQL strings, and renders UI templates, it turns into an unmaintainable 10,000-line monolith. Keep Mediators focused strictly on traffic direction, notification routing, and workflow orchestration.
