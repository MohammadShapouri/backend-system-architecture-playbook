Computer Science Foundations

Computer Science: The Object-Relational Impedance Mismatch

Relational databases (PostgreSQL, MySQL, Oracle) and Object-Oriented programming languages (Python, Java, C#) view data through fundamentally incompatible paradigms. This friction is known in computer science as the Object-Relational Impedance Mismatch.

Objects organize data using graphs, references, encapsulation, and polymorphic inheritance. Relational databases organize data using flat mathematical relations (tables), rows, primary keys, and foreign-key joins.

Architectural Divergence: Active Record vs. Data Mapper
1. Active Record (Django ORM / Rails) 1:1 Schema Coupling

An entity represents both business logic AND a database row:

order = Order(symbol="AAPL", qty=10)
order.calculate_tax() # Business method
order.save() # DIRECT DATABASE CALL!
  • Tight Coupling: The domain entity inherits from the ORM base class. If database columns change, domain code breaks.
  • Testing Friction: You cannot instantiate or test an Order object in unit tests without an active database connection.
2. Data Mapper (Fowler / Clean Architecture) Zero Database Coupling

Domain models are 100% pure Python. A separate layer maps to tables:

order = Order(symbol="AAPL", qty=10) # Pure dataclass
order.calculate_tax() # Pure CPU business logic
mapper.save(order) # Isolated mapper handles SQL!
  • Loose Coupling: Domain entity has ZERO imports of SQLAlchemy, database drivers, or SQL syntax.
  • Blazing Fast Unit Tests: Unit tests execute in nanoseconds with zero database setup or mocking required.
Enterprise Pattern #24

Pattern Name: Data Mapper

Formal Classification: Object-Relational Structural Pattern • Martin Fowler (P of EAA p. 165)

💡 The Real-World Metaphor (Plain English)

Imagine an international diplomatic summit between a French ambassador and a Japanese ambassador.

The French ambassador speaks only French. The Japanese ambassador speaks only Japanese. You do not force the French ambassador to abandon their native language, enroll in a 5-year Japanese language course, and alter their brain physiology just to communicate.

You hire a Professional Diplomatic Translator (The Data Mapper). The translator sits between them, translates French statements into Japanese grammar, and translates Japanese responses into French. Both ambassadors speak their native tongue without knowing the internal rules of the other's language.

The Problem: Domain Models Infected with SQL Concerns

When business models inherit directly from database ORMs, domain logic becomes coupled to database quirks (column types, foreign key constraints, nullable flags, table migration hooks). If a database administrator decides to normalize a table into two tables, business code must be rewritten: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: The Database-Infected Domain Model
# ------------------------------------------------------------------------------

from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

class TradeOrder(DeclarativeBase):
    __tablename__ = "orders"
    
    # Domain entity is forced to understand SQL column mechanics:
    order_id: Mapped[str] = mapped_column(primary_key=True)
    symbol: Mapped[str] = mapped_column(index=True)
    amount: Mapped[float]
    
    def validate_risk_limits(self):
        # Business rules live inside an ORM database model!
        # To test this method in a unit test, you MUST spin up a SQLite database!
        if self.amount > 1_000_000:
            raise ValueError("Risk ceiling exceeded")

✔ When to Use Data Mapper
  • You have rich, complex domain logic that must be tested in sub-millisecond isolation without database connections.
  • The database schema diverges significantly from the object domain model (e.g., legacy column names or normalized joins).
  • You are building enterprise systems where domain models must remain stable even when underlying database engines are swapped.
✘ When NOT to Use Data Mapper
  • Simple CRUD applications (Create, Read, Update, Delete) with virtually zero business logic. Active Record is faster to write.
  • Rapid prototyping or hackathon projects where architectural purity is secondary to development speed.
Enterprise Pattern #25

Pattern Name: Repository

Formal Classification: Domain Logic & Data Source Pattern • Martin Fowler (P of EAA p. 322) & Eric Evans (DDD)

💡 The Real-World Metaphor (Plain English)

Imagine a public library bookshelf.

When you ask the librarian for a book, you say: "Please get me book with ISBN 978-0321127426." When you return a book, you hand it over: "Please place this book on the shelf."

You do not know whether the library stores books on metal shelves, in deep underground mechanical conveyor basements, or in an off-site digital warehouse. To you, the library behaves exactly like an **in-memory collection of books**. You add books, remove books, and query books using collection methods.

The Problem: Raw Database Queries Scattered Across Business Services

Without a Repository, raw database queries permeate every layer of the application. If a developer needs all open orders for an account, they write a query directly in a FastAPI endpoint or Celery task. When another service needs the same data, they copy-paste the query: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: Leaking SQL Queries Directly into Services
# ------------------------------------------------------------------------------

class OrderExecutionService:
    async def get_user_open_orders(self, user_id: str, session: AsyncSession):
        # Raw ORM query written directly in business service!
        stmt = select(OrderModel).where(
            OrderModel.user_id == user_id,
            OrderModel.status.in_(["PENDING", "APPROVED"])
        ).order_by(OrderModel.created_at.desc())
        
        result = await session.execute(stmt)
        # If this query needs an index optimization, you must find and update 10 different files!
        return result.scalars().all()

The Testing Superpower:

In your unit tests, you can swap SqlAlchemyOrderRepository with a FakeOrderRepository backed by a simple Python dictionary. Tests run in 2 milliseconds with zero Docker databases or database teardown fixtures!

✔ When to Use Repository
  • You want to centralize data retrieval logic and queries into single, testable classes.
  • You want to shield business logic from database schema changes and ORM version upgrades.
  • You want to test business services using in-memory mock repositories for lightning-fast test suites.
✘ When NOT to Use Repository
  • You write an "Anemic Repository" that just blindly duplicates basic ORM query methods without abstracting anything.
  • Your application consists only of read-only analytics dashboards querying denormalized reporting views.
Enterprise Pattern #26

Pattern Name: Unit of Work

Formal Classification: Object-Relational Behavioral Pattern • Martin Fowler (P of EAA p. 184)

💡 The Real-World Metaphor (Plain English)

Imagine an e-commerce checkout shopping cart at an online electronics store.

You add a laptop to your cart, remove a mouse, and apply a 20% discount code. The store does not charge your credit card, debit warehouse stock, and create shipping labels every time you click an item in your browser.

The shopping cart is a Unit of Work: it tracks all changes (items inserted, items updated, items removed). When you finally click "Confirm Purchase", the Unit of Work commits the entire batch in a single atomic transaction. If your card is declined, all changes are rolled back completely!

The Problem: Repositories Committing Independently (The Micro-Commit Flaw)

A catastrophic junior developer mistake is placing session.commit() inside individual repository methods: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: The Micro-Commit Transactional Flaw
# ------------------------------------------------------------------------------

class OrderExecutionService:
    async def execute_trade(self, order, account):
        # Step 1: Order repository saves and COMMITS to database
        await self.order_repo.add(order)      # Internally executes session.commit()!
        
        # Step 2: Account repository attempts to deduct funds
        try:
            await self.account_repo.debit(account, order.amount)
        except InsufficientFundsError:
            # DISASTER: Account debit fails, but Order was ALREADY COMMITTED in Step 1!
            # The database now has a committed order with NO money debited! Data corrupted!
            raise
The Unit of Work Atomic Transaction Boundary
async with UnitOfWork() as uow: Single ACID Boundary
1. uow.orders.add(order) Appends order to session (NO commit!)
2. uow.accounts.debit(acc) Updates account balance (NO commit!)
↓ on success ↓
await uow.commit() → Single Atomic Database Commit
• If any exception occurs anywhere inside the block → Automatic Rollback •
✔ When to Use Unit of Work
  • A business transaction involves updating multiple tables or aggregates that must succeed or fail together atomically.
  • You want to maintain a single database transaction across multiple repository instances.
  • You want to cleanly manage database session lifecycles using Python's async with context manager syntax.
✘ When NOT to Use Unit of Work
  • You are writing read-only data queries. Unit of Work adds unnecessary overhead when no state mutations occur.
  • You are working with distributed microservices where data spans multiple physical databases (Use the Saga Pattern in Chapter 15 instead).

1. Domain Entities & ORM Tables: src/nexuscore/storage/models.py Data Mapper Pattern 
# ==============================================================================
# NexusCore Storage - Pure Domain Entities & Decoupled ORM Tables (Data Mapper)
# ==============================================================================

from dataclasses import dataclass
from typing import Optional
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy import String, Float


# ------------------------------------------------------------------------------
# 1. PURE DOMAIN ENTITIES (Zero Database ORM Dependencies)
# ------------------------------------------------------------------------------
@dataclass
class DomainOrder:
    """Pure business entity: Zero knowledge of SQLAlchemy, columns, or tables."""
    order_id: str
    user_id: str
    symbol: str
    amount: float
    status: str = "PENDING"


@dataclass
class DomainAccount:
    """Pure business entity: Represents an account balance."""
    account_id: str
    user_id: str
    balance: float


# ------------------------------------------------------------------------------
# 2. SQLALCHEMY ORM TABLE MODELS (Data Mapper Storage Representation)
# ------------------------------------------------------------------------------
class Base(DeclarativeBase):
    pass


class OrderModel(Base):
    __tablename__ = "orders"

    order_id: Mapped[str] = mapped_column(String(50), primary_key=True)
    user_id: Mapped[str] = mapped_column(String(50), index=True)
    symbol: Mapped[str] = mapped_column(String(20))
    amount: Mapped[float] = mapped_column(Float)
    status: Mapped[str] = mapped_column(String(20))

    def to_domain(self) -> DomainOrder:
        """Maps ORM Table row into Pure Domain Entity."""
        return DomainOrder(
            order_id=self.order_id,
            user_id=self.user_id,
            symbol=self.symbol,
            amount=self.amount,
            status=self.status,
        )

    @classmethod
    def from_domain(cls, domain: DomainOrder) -> "OrderModel":
        """Maps Pure Domain Entity into ORM Table row."""
        return cls(
            order_id=domain.order_id,
            user_id=domain.user_id,
            symbol=domain.symbol,
            amount=domain.amount,
            status=domain.status,
        )


class AccountModel(Base):
    __tablename__ = "accounts"

    account_id: Mapped[str] = mapped_column(String(50), primary_key=True)
    user_id: Mapped[str] = mapped_column(String(50), index=True)
    balance: Mapped[float] = mapped_column(Float)

    def to_domain(self) -> DomainAccount:
        return DomainAccount(
            account_id=self.account_id,
            user_id=self.user_id,
            balance=self.balance,
        )

    @classmethod
    def from_domain(cls, domain: DomainAccount) -> "AccountModel":
        return cls(
            account_id=domain.account_id,
            user_id=domain.user_id,
            balance=domain.balance,
        )
2. Async SQLAlchemy Repositories: src/nexuscore/storage/repository.py Repository Pattern 
# ==============================================================================
# NexusCore Storage - Async Repositories for Collection-Like Access
# ==============================================================================

from abc import ABC, abstractmethod
from typing import Optional, List
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy import select
from nexuscore.storage.models import (
    DomainOrder, DomainAccount, OrderModel, AccountModel
)

# ------------------------------------------------------------------------------
# REPOSITORY INTERFACES
# ------------------------------------------------------------------------------
class IOrderRepository(ABC):
    @abstractmethod
    async def add(self, order: DomainOrder) -> None: pass

    @abstractmethod
    async def get(self, order_id: str) -> Optional[DomainOrder]: pass

    @abstractmethod
    async def list_by_user(self, user_id: str) -> List[DomainOrder]: pass


class IAccountRepository(ABC):
    @abstractmethod
    async def add(self, account: DomainAccount) -> None: pass

    @abstractmethod
    async def get(self, account_id: str) -> Optional[DomainAccount]: pass


# ------------------------------------------------------------------------------
# CONCRETE ASYNC SQLALCHEMY REPOSITORIES
# ------------------------------------------------------------------------------
class SqlAlchemyOrderRepository(IOrderRepository):
    """Encapsulates all SQLAlchemy queries for Orders. NEVER calls commit()!"""
    def __init__(self, session: AsyncSession):
        self.session = session

    async def add(self, order: DomainOrder) -> None:
        orm_model = OrderModel.from_domain(order)
        self.session.add(orm_model)

    async def get(self, order_id: str) -> Optional[DomainOrder]:
        stmt = select(OrderModel).where(OrderModel.order_id == order_id)
        result = await self.session.execute(stmt)
        orm_row = result.scalar_one_or_none()
        return orm_row.to_domain() if orm_row else None

    async def list_by_user(self, user_id: str) -> List[DomainOrder]:
        stmt = select(OrderModel).where(OrderModel.user_id == user_id)
        result = await self.session.execute(stmt)
        return [row.to_domain() for row in result.scalars().all()]


class SqlAlchemyAccountRepository(IAccountRepository):
    """Encapsulates all SQLAlchemy queries for Accounts. NEVER calls commit()!"""
    def __init__(self, session: AsyncSession):
        self.session = session

    async def add(self, account: DomainAccount) -> None:
        orm_model = AccountModel.from_domain(account)
        self.session.add(orm_model)

    async def get(self, account_id: str) -> Optional[DomainAccount]:
        stmt = select(AccountModel).where(AccountModel.account_id == account_id)
        result = await self.session.execute(stmt)
        orm_row = result.scalar_one_or_none()
        return orm_row.to_domain() if orm_row else None
3. Async Unit of Work Context Manager: src/nexuscore/storage/unit_of_work.py Unit of Work Pattern 
# ==============================================================================
# NexusCore Storage - Asynchronous Unit of Work Pattern
# ==============================================================================

from abc import ABC, abstractmethod
from sqlalchemy.ext.asyncio import async_sessionmaker, AsyncSession
from nexuscore.storage.repository import (
    IOrderRepository, IAccountRepository,
    SqlAlchemyOrderRepository, SqlAlchemyAccountRepository
)

class IUnitOfWork(ABC):
    """Unit of Work interface: Coordinates repositories and transaction lifecycles."""
    orders: IOrderRepository
    accounts: IAccountRepository

    async def __aenter__(self) -> "IUnitOfWork": pass
    async def __aexit__(self, exc_type, exc_val, exc_tb): pass

    @abstractmethod
    async def commit(self) -> None: pass

    @abstractmethod
    async def rollback(self) -> None: pass


class SqlAlchemyUnitOfWork(IUnitOfWork):
    """
    UNIT OF WORK PATTERN:
    Manages an AsyncSession. Exposes orders and accounts repositories.
    Guarantees atomic commit across all repositories or automatic rollback on error.
    """
    def __init__(self, session_factory: async_sessionmaker[AsyncSession]):
        self.session_factory = session_factory
        self.session: Optional[AsyncSession] = None

    async def __aenter__(self) -> "SqlAlchemyUnitOfWork":
        # Start transaction
        self.session = self.session_factory()
        self.orders = SqlAlchemyOrderRepository(self.session)
        self.accounts = SqlAlchemyAccountRepository(self.session)
        return self

    async def __aexit__(self, exc_type, exc_val, exc_tb):
        if exc_type is not None:
            # Roll back on any unhandled exception automatically:
            await self.rollback()
        await self.session.close()

    async def commit(self) -> None:
        # Single atomic commit across both repositories!
        await self.session.commit()

    async def rollback(self) -> None:
        await self.session.rollback()
4. Async Persistence Test Battery: tests/test_repository_uow.py SQLite in-Memory Integration 
import pytest
import pytest_asyncio
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession
from nexuscore.storage.models import Base, DomainOrder, DomainAccount
from nexuscore.storage.unit_of_work import SqlAlchemyUnitOfWork

@pytest_asyncio.fixture
async def session_factory():
    # Ephemeral in-memory SQLite database for high-speed integration testing
    engine = create_async_engine("sqlite+aiosqlite:///:memory:", echo=False)
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)

    factory = async_sessionmaker(engine, expire_on_commit=False, class_=AsyncSession)
    yield factory
    await engine.dispose()


class TestRepositoryAndUnitOfWork:
    """Verifies Data Mapper decoupling, Repository queries, and Unit of Work rollback safety."""

    @pytest.mark.asyncio
    async def test_atomic_commit_across_multiple_repositories(self, session_factory):
        uow = SqlAlchemyUnitOfWork(session_factory)

        # Execute atomic transaction adding both an account and an order
        async with uow:
            await uow.accounts.add(DomainAccount("acc_10", "user_1", 50_000.0))
            await uow.orders.add(DomainOrder("ord_99", "user_1", "BTC/USD", 5000.0))
            await uow.commit()

        # Verify persistence in a completely separate transaction session:
        async with uow:
            saved_acc = await uow.accounts.get("acc_10")
            saved_ord = await uow.orders.get("ord_99")
            assert saved_acc.balance == 50_000.0
            assert saved_ord.symbol == "BTC/USD"
            assert isinstance(saved_ord, DomainOrder)  # Pure Domain Entity!

    @pytest.mark.asyncio
    async def test_automatic_rollback_on_exception_prevents_partial_writes(self, session_factory):
        uow = SqlAlchemyUnitOfWork(session_factory)

        with pytest.raises(RuntimeError, match="Mid-transaction failure"):
            async with uow:
                await uow.accounts.add(DomainAccount("acc_20", "user_2", 1000.0))
                # Simulate error after account write but before commit
                raise RuntimeError("Mid-transaction failure!")

        # VERIFICATION: Transaction MUST have rolled back cleanly!
        async with uow:
            acc = await uow.accounts.get("acc_20")
            assert acc is None  # Zero dirty rows persisted!
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Calling session.commit() Inside Repositories

Writing def add(self, item): session.add(item); session.commit().

Why this causes data corruption: Repositories manage collections; they do NOT own transaction lifecycles! Committing inside add() makes atomic multi-repository operations impossible. If Step 1 commits and Step 2 fails, your database is permanently corrupted. Always leave commits exclusively to the Unit of Work.

❌ Leaking ORM Models into API Controllers

Returning SQLAlchemy table objects (OrderModel) directly from repository methods to FastAPI route endpoints.

Why this causes crashes: When FastAPI attempts to serialize SQLAlchemy objects outside the transaction session context, it accesses lazily-loaded relationships, raising DetachedInstanceError! Furthermore, it couples your HTTP API directly to your SQL column names. Repositories must always return Pure Domain Entities.
