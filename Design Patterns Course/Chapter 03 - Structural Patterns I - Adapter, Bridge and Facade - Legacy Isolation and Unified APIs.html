Architecture Fundamentals

Structural Design Patterns: The Art of Composition

If Creational Patterns are about instantiating objects, Structural Patterns are about how classes and objects are assembled into larger, flexible structures.

A classic architectural trap in object-oriented programming is over-relying on class inheritance (class SubClass(BaseClass)). Inheritance creates compile-time rigidity: you cannot change an inherited behavior at runtime, subclasses are tightly coupled to parent internal details (the "fragile base class" problem), and combining features across dimensions produces a combinatoric class explosion.

// The Cardinal Rule of Gang of Four Structural Design:

"Favor object composition over class inheritance." By referencing other objects through abstract interfaces rather than inheriting their implementation, systems remain decoupled, modular, and testable.

Design Pattern #06

Pattern Name: Adapter (Wrapper)

Formal Classification: Structural Pattern • Gang of Four (GoF) Reference p. 139

💡 The Real-World Metaphor (Plain English)

Imagine traveling from the United States to the United Kingdom with your favorite laptop. Your laptop's power plug has two flat parallel prongs (US standard). The wall socket in London has three massive rectangular prongs configured in a triangle (UK standard).

You do not slice open your laptop cord, strip the copper wires, and rebuild your laptop's power supply! You also do not call a London electrician to tear down the wall and replace the municipal power grid.

You buy a $10 Travel Adapter. The travel adapter plugs into the British wall socket on the outside, and exposes a clean American plug socket on the inside. The Adapter bridges two completely incompatible interfaces without modifying either side.

The Problem: Legacy Incompatibility in Enterprise Software

In enterprise finance, new systems run on modern asynchronous JSON APIs. However, legacy core-banking networks (such as 30-year-old COBOL mainframes or older SWIFT payment processors) speak exclusively in raw, cumbersome SOAP/XML envelopes with esoteric status codes.

Without an adapter, developers litter their modern services with messy XML string construction, manual regex extraction, and vendor-specific error parsing: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: Polluting Business Logic with Legacy Protocol Details
# ------------------------------------------------------------------------------

class OrderService:
    def settle_order(self, order_id: str, amount_cents: int):
        # Business logic is now infected with raw XML, SOAP envelopes, and headers!
        xml_payload = f"""<?xml version="1.0"?>
        <soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/">
            <soapenv:Body>
                <ExecuteWireTransfer>
                    <AccountRef>ACC-9981</AccountRef>
                    <AmountInCents>{amount_cents}</AmountInCents>
                </ExecuteWireTransfer>
            </soapenv:Body>

        raw_response = legacy_mainframe_socket_call(xml_payload)
        
        # Ugly XML parsing in the middle of core order processing:
        if "<StatusCode>200_SUCCESS</StatusCode>" not in raw_response:
            raise RuntimeError("Legacy banking wire transfer failed!")
        
        # If the legacy bank changes an XML tag tomorrow, our order service crashes!

Object Adapter vs. Class Adapter:

In Python, an Object Adapter uses composition (it holds an instance of the legacy class internally: self._legacy_client = legacy_client). A Class Adapter uses multiple inheritance (class Adapter(IPaymentGateway, LegacyClient)). In production, always prefer Object Adapters: they decouple your class from the adaptee's internal inheritance tree and allow wrapping any subclass of the adaptee seamlessly.

✔ When to Use Adapter
  • You want to use an existing class or 3rd-party library, but its interface does not match the rest of your application's architecture.
  • You need to integrate legacy components, SOAP web services, or external APIs without polluting your clean domain layer.
  • You want to create a reusable library that integrates with multiple legacy vendors that all have different method names for the same fundamental concept.
✘ When NOT to Use Adapter
  • You have full control over both classes and can easily refactor them to share a common interface directly.
  • The behavior of the adaptee is fundamentally incompatible with the target interface (e.g. attempting to adapt an asynchronous streaming WebSocket into a single blocking integer getter).
  • You simply want to group complex subsystems together (Use a Facade instead).
Design Pattern #07

Pattern Name: Bridge

Formal Classification: Structural Pattern • Gang of Four (GoF) Reference p. 151

💡 The Real-World Metaphor (Plain English)

Imagine a universal TV remote control. The remote control provides high-level user buttons: "Power On", "Volume Up", and "Channel Down" (This is the Abstraction).

However, the TV itself could be a Sony TV, a Samsung TV, or an LG TV (These are the Implementations). Each brand uses a completely different infrared frequency protocol to change volume or power down.

You do not manufacture a "SonyBasicRemote", "SonyAdvancedTouchRemote", "SamsungBasicRemote", and "SamsungAdvancedTouchRemote"! Instead, the Remote has a reference (a Bridge) to an abstract TV interface. The remote features can evolve independently from the underlying TV hardware brands.

The Problem: The $M \times N$ Combinatoric Class Explosion

In NexusCore, we manage financial account ledgers. We have multiple types of accounts with distinct business rules: Standard Ledger, Margin Trading Ledger, and High-Audit Regulatory Ledger.

At the same time, ledger transactions can be stored across different physical storage engines: PostgreSQL, high-speed In-Memory RAM, or an append-only Immutable Audit File.

If an engineer uses inheritance to combine these two orthogonal dimensions, the codebase explodes exponentially:

Combinatoric Explosion: Inheritance ($M \times N$) vs. Bridge Pattern ($M + N$)
Inheritance Explosion ($3 \times 3 = 9$ Classes)
• StandardPostgresLedger
• StandardMemoryLedger
• StandardAuditFileLedger
• MarginPostgresLedger
• MarginMemoryLedger
• MarginAuditFileLedger
• RegulatoryPostgresLedger
• RegulatoryMemoryLedger
• RegulatoryAuditFileLedger

The Bridge Invariant:

The Abstraction defines high-level business operations (record_debit, calculate_interest), while the Implementor provides primitive platform operations (write_row, read_rows). Any account can run on any database at runtime!

✔ When to Use Bridge
  • You have two independent, orthogonal dimensions of variation (e.g. GUI Window types × Operating System drivers, or Account Types × Database Engines).
  • You want to avoid compile-time binding between an abstraction and its implementation, allowing you to swap storage engines on the fly.
  • You see a proliferation of subclasses named like LinuxDirectXWindow and WindowsDirectXWindow.
✘ When NOT to Use Bridge
  • There is only one single dimension of variation. Using Bridge for a simple class with two subclasses is massive over-engineering.
  • The abstraction and implementation cannot be logically decoupled because their lifecycles and behaviors are inextricably intertwined.
Design Pattern #08

Pattern Name: Facade

Formal Classification: Structural Pattern • Gang of Four (GoF) Reference p. 185

💡 The Real-World Metaphor (Plain English)

Imagine staying at a luxury five-star hotel. You want dinner reservations at an exclusive restaurant, a pressed tuxedo delivered to your room, and a limousine waiting at the front entrance at 8:00 PM.

You do not hunt down the hotel's head chef, navigate the basement laundry tunnels to find the dry-cleaning technicians, and negotiate with the local limousine garage directly. That would require learning 30 internal phone extensions and coordinating four complex schedules.

You call the Front Desk Concierge (The Facade). You make one simple request: "Please arrange my evening." The Concierge coordinates all underlying hotel departments behind the scenes and returns a single confirmation.

The Problem: High-Cognitive Subsystem Sprawl

Executing a single market order in NexusCore requires orchestrating multiple independent subsystems:

  1. Validating order syntax and risk thresholds (RiskParameterRegistry).
  2. Translating payment details with the legacy banking adapter (BankWireAdapter).
  3. Deducting funds and recording journal entries (LedgerAccount).
  4. Routing the order to an external exchange socket (ExchangeRouter).
  5. Emitting regulatory compliance records (ComplianceLogger).

If an API router or frontend controller must instantiate and coordinate all five subsystems, the controller becomes fragile, impossible to unit test cleanly, and duplicates orchestration code across web, mobile, and CLI gateways.

The Facade Architectural Shield
FastAPI Controller
Calls 1 simple method:
.execute_trade(...)
→ calls →
TradingEngineFacade
Orchestrates all 5 subsystems in proper sequence with error rollbacks
→ coordinates →
Risk Registry
Bank Adapter
Ledger Bridge
Audit Logger
The Subsystem Independence Invariant:

Subsystems remain completely unaware of the Facade. They hold zero references to the facade class, allowing power users to bypass the Facade and interact with individual subsystems directly when specialized low-level control is needed.

Structural Pattern Core Intent Interface Relationship When is it Applied?
Adapter Makes two existing, incompatible interfaces work together without modifying their source code. Converts an old/foreign interface into an expected interface. Typically applied after a system is designed to integrate legacy code.
Bridge Decouples an abstraction from its implementation so that both can vary independently. Defines two parallel, independent class hierarchies linked via composition. Designed up-front when planning multi-dimensional variation.
Facade Provides a simplified, higher-level interface to a complex set of classes or subsystems. Defines a brand-new, clean interface that encapsulates many existing interfaces. Applied anytime a client needs an easy entry point into a complex library.

1. Legacy SOAP Banking Adapter: src/nexuscore/adapters/soap_adapter.py Adapter Pattern 
# ==============================================================================
# NexusCore Adapters - Object Adapter for Legacy XML/SOAP Core Banking
# ==============================================================================

import xml.etree.ElementTree as ET
from typing import Optional
from nexuscore.payments.contracts import IPaymentGateway, PaymentResult

# ------------------------------------------------------------------------------
# THE ADAPTEE: Simulates an antiquated 1990s mainframe web service (Incompatible)
# ------------------------------------------------------------------------------
class LegacySoapMainframeClient:
    """
    LEGACY THIRD-PARTY ADAPTEE:
    This class cannot be modified. It expects raw XML and returns XML envelopes.
    """
    def execute_wire_xml(self, xml_envelope: str) -> str:
        # Simulates mainframe parsing of SOAP payload:
        try:
            root = ET.fromstring(xml_envelope)
            amount_node = root.find(".//AmountInCents")
            account_node = root.find(".//AccountRef")

            if amount_node is not None and account_node is not None:
                cents = int(amount_node.text)
                if cents > 50_000_000:  # $500,000 threshold reject
                    return "<WireResponse><Status>REJECTED_LIMIT</Status><TxCode>ERR_01</TxCode></WireResponse>"
                
                return "<WireResponse><Status>200_OK</Status><TxCode>MF_WIRE_774921</TxCode></WireResponse>"
        except Exception:
            pass
        return "<WireResponse><Status>PARSE_ERROR</Status></WireResponse>"


# ------------------------------------------------------------------------------
# THE ADAPTER: Wraps the Adaptee and implements modern IPaymentGateway
# ------------------------------------------------------------------------------
class BankWireSoapAdapter(IPaymentGateway):
    """
    OBJECT ADAPTER PATTERN:
    Implements standard modern IPaymentGateway.
    Wraps legacy LegacySoapMainframeClient, translating JSON/Python parameters into
    XML SOAP envelopes, and parsing the response back into a clean PaymentResult.
    """
    def __init__(self, legacy_client: Optional[LegacySoapMainframeClient] = None):
        # Composition: Holds private reference to the adaptee
        self._legacy = legacy_client or LegacySoapMainframeClient()

    def charge(self, amount: float, currency: str, source_token: str) -> PaymentResult:
        # 1. Adapt input parameters to legacy XML schema:
        amount_in_cents = int(amount * 100)
        soap_envelope = f"""<?xml version="1.0" encoding="UTF-8"?>
        <soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/">
            <soapenv:Body>
                <ExecuteWireTransfer>
                    <AccountRef>{source_token}</AccountRef>
                    <AmountInCents>{amount_in_cents}</AmountInCents>
                    <Currency>{currency.upper()}</Currency>
                </ExecuteWireTransfer>
            </soapenv:Body>
        </soapenv:Envelope>"""

        # 2. Call incompatible legacy client:
        raw_xml_response = self._legacy.execute_wire_xml(soap_envelope)

        # 3. Adapt legacy output to standard modern PaymentResult domain model:
        root = ET.fromstring(raw_xml_response)
        status_node = root.find("Status")
        tx_node = root.find("TxCode")

        status_text = status_node.text if status_node is not None else "UNKNOWN"
        tx_code = tx_node.text if tx_node is not None else ""

        if status_text == "200_OK":
            return PaymentResult(
                success=True,
                transaction_id=tx_code,
                amount=amount,
                currency=currency.upper(),
                provider_name="LegacyMainframeBank"
            )

        return PaymentResult(
            success=False,
            transaction_id="",
            amount=amount,
            currency=currency.upper(),
            provider_name="LegacyMainframeBank",
            error_message=f"Mainframe rejected transaction with status: {status_text}"
        )
2. Multi-Dimensional Ledger Bridge: src/nexuscore/ledger/bridge.py Bridge Pattern 
# ==============================================================================
# NexusCore Ledger - Multi-Dimensional Account Bridge Pattern
# ==============================================================================

from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import List, Dict

@dataclass(frozen=True)
class LedgerEntry:
    entry_id: str
    account_id: str
    amount: float
    description: str

# ------------------------------------------------------------------------------
# IMPLEMENTATION HIERARCHY: Low-Level Storage Engines
# ------------------------------------------------------------------------------
class ILedgerStorageImplementor(ABC):
    """The Implementation Interface: Defines primitive persistence primitives."""
    @abstractmethod
    def save_entry(self, entry: LedgerEntry) -> None:
        pass

    @abstractmethod
    def fetch_entries(self, account_id: str) -> List[LedgerEntry]:
        pass


class InMemoryLedgerStorage(ILedgerStorageImplementor):
    """Concrete Implementor 1: High-speed RAM storage for tests and low-latency cache."""
    def __init__(self):
        self._store: Dict[str, List[LedgerEntry]] = {}

    def save_entry(self, entry: LedgerEntry) -> None:
        self._store.setdefault(entry.account_id, []).append(entry)

    def fetch_entries(self, account_id: str) -> List[LedgerEntry]:
        return list(self._store.get(account_id, []))


class PostgresAuditLedgerStorage(ILedgerStorageImplementor):
    """Concrete Implementor 2: Persistent relational database simulation with audit stamping."""
    def __init__(self):
        self._rows: List[LedgerEntry] = []

    def save_entry(self, entry: LedgerEntry) -> None:
        # In production: INSERT INTO ledger_entries (...)
        self._rows.append(entry)

    def fetch_entries(self, account_id: str) -> List[LedgerEntry]:
        return [row for row in self._rows if row.account_id == account_id]


# ------------------------------------------------------------------------------
# ABSTRACTION HIERARCHY: High-Level Business Domain Rules
# ------------------------------------------------------------------------------
class LedgerAccount(ABC):
    """
    THE ABSTRACTION:
    Maintains a reference (the Bridge) to an ILedgerStorageImplementor.
    Executes domain rules while delegating primitive storage to the bridge!
    """
    def __init__(self, account_id: str, storage: ILedgerStorageImplementor):
        self.account_id = account_id
        self._storage = storage  # THE BRIDGE REFERENCE

    def get_current_balance(self) -> float:
        return sum(e.amount for e in self._storage.fetch_entries(self.account_id))

    @abstractmethod
    def post_transaction(self, entry_id: str, amount: float, description: str) -> bool:
        """Subclasses enforce distinct domain rules (overdrafts, margin interest)."""
        pass


class StandardRetailAccount(LedgerAccount):
    """Refined Abstraction 1: No negative balances permitted."""
    def post_transaction(self, entry_id: str, amount: float, description: str) -> bool:
        current_bal = self.get_current_balance()
        if current_bal + amount < 0.0:
            raise ValueError(f"Insufficient funds: Balance ${current_bal:,.2f} cannot absorb ${amount:,.2f}")

        self._storage.save_entry(LedgerEntry(entry_id, self.account_id, amount, description))
        return True


class MarginTradingAccount(LedgerAccount):
    """Refined Abstraction 2: Allows overdraft borrowing up to a credit limit."""
    def __init__(self, account_id: str, storage: ILedgerStorageImplementor, overdraft_limit: float = 50_000.0):
        super().__init__(account_id, storage)
        self.overdraft_limit = overdraft_limit

    def post_transaction(self, entry_id: str, amount: float, description: str) -> bool:
        current_bal = self.get_current_balance()
        if (current_bal + amount) < -self.overdraft_limit:
            raise ValueError(f"Margin call exceeded: Limit ${self.overdraft_limit:,.2f} breached.")

        self._storage.save_entry(LedgerEntry(entry_id, self.account_id, amount, description))
        return True
3. Unified Trading Engine Facade: src/nexuscore/facade/trading_facade.py Facade Pattern 
# ==============================================================================
# NexusCore Facade - Consolidated Trading & Clearing Gateway Facade
# ==============================================================================

import uuid
from typing import Dict, Any
from nexuscore.orders.models import TradeOrder, OrderSide
from nexuscore.orders.builder import OrderBuilder
from nexuscore.payments.contracts import IPaymentGateway
from nexuscore.ledger.bridge import LedgerAccount

class NexusTradingFacade:
    """
    FACADE PATTERN:
    Provides a dead-simple, unified entry point for web APIs and trading bots.
    Coordinates:
      1. Order Validation & Building (OrderBuilder)
      2. Payment Settlement / Wire Charging (IPaymentGateway / Adapter)
      3. Ledger Accounting & Balance Verification (LedgerAccount / Bridge)
    Shields client callers from complex cross-subsystem orchestration.
    """
    def __init__(self, gateway: IPaymentGateway, ledger_account: LedgerAccount):
        # Injects the underlying subsystems into the facade
        self._gateway = gateway
        self._account = ledger_account

    def execute_market_buy(
        self,
        symbol: str,
        quantity: float,
        unit_price: float,
        payment_source_token: str
    ) -> Dict[str, Any]:
        """
        The Simple Facade Method:
        Takes simple primitive parameters, orchestrates all 3 subsystems,
        and returns a clean standardized dictionary result.
        """
        total_cost = quantity * unit_price

        # Subsystem 1: Construct & validate immutable domain order via Builder
        order: TradeOrder = (
            OrderBuilder()
            .for_instrument(symbol, OrderSide.BUY)
            .with_sizing(quantity, unit_price)
            .build()
        )

        # Subsystem 2: Deduct funds via Ledger Account (Bridge)
        tx_id = f"tx_{uuid.uuid4().hex[:8]}"
        self._account.post_transaction(
            entry_id=tx_id,
            amount=-total_cost,
            description=f"Buy order execution: {order.symbol}"
        )

        # Subsystem 3: Clear transaction through Gateway (Adapter or Direct Vendor)
        pay_result = self._gateway.charge(
            amount=total_cost,
            currency="USD",
            source_token=payment_source_token
        )

        if not pay_result.success:
            # Automated compensation: Roll back ledger deduction
            self._account.post_transaction(
                entry_id=f"rollback_{tx_id}",
                amount=total_cost,
                description="Charge failed rollback"
            )
            return {
                "status": "FAILED",
                "reason": pay_result.error_message
            }

        return {
            "status": "EXECUTED",
            "order_id": order.order_id,
            "symbol": order.symbol,
            "filled_amount": total_cost,
            "remaining_balance": self._account.get_current_balance(),
            "clearing_ref": pay_result.transaction_id
        }

class TestStructuralPatterns:
    """Verifies Adapter protocol translation, Bridge dimension isolation, and Facade execution."""

    def test_soap_adapter_translates_xml_to_payment_result(self):
        # The adapter satisfies standard modern IPaymentGateway contract
        adapter = BankWireSoapAdapter()

        # Execute normal charge: translates to XML and extracts status 200_OK
        res = adapter.charge(amount=1200.0, currency="USD", source_token="ACC-449")

        assert res.transaction_id == "MF_WIRE_774921"

        res_limit = adapter.charge(amount=600_000.0, currency="USD", source_token="ACC-449")
        assert res_limit.success is False
        assert "REJECTED_LIMIT" in res_limit.error_message

    def test_bridge_pattern_allows_independent_dimension_pairing(self):
        # Bridge Pairing 1: Retail Account on In-Memory Storage
        mem_storage = InMemoryLedgerStorage()
        retail_acc = StandardRetailAccount("acc_retail", mem_storage)
        retail_acc.post_transaction("init", 1000.0, "Deposit")

        margin_acc.post_transaction("m_tx1", -15000.0, "Leverage position")

    def test_nexus_trading_facade_coordinates_full_flow(self):
        # Setup Subsystems: Mock Gateway + Funded Retail Account on Memory Storage
        gateway = MockGateway()
        storage = InMemoryLedgerStorage()

        account.post_transaction("seed", 10000.0, "Initial cash deposit")

        # Execute 1 simple facade call
        res = facade.execute_market_buy(
            symbol="AAPL",
            quantity=10,
            unit_price=150.0,  # Cost: $1,500
            payment_source_token="tok_customer_card"

        assert res["filled_amount"] == 1500.0

        assert "mock_tx_" in res["clearing_ref"]
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The "God Facade" Anti-Pattern

Writing a Facade that directly implements complex business calculations, SQL queries, and encryption math instead of delegating to underlying subsystems.

Why this causes architectural rot: A Facade is meant to be a thin orchestrator. If you write core business logic inside the facade itself, it becomes a bloated "God Object" with 5,000 lines of unmaintainable code. Keep your facades thin: they should only coordinate and delegate.

❌ Two-Way Adapter Data Truncation

Building an Adapter where converting between formats drops required fields silently (e.g. converting 64-bit integer timestamps to lossy 32-bit floats).

Why this causes critical production bugs: An adapter must perform bidirectional data mapping faithfully. If the target interface requires fields that the adaptee cannot provide, the adapter must raise an explicit validation error rather than silently defaulting fields to zero or null!
