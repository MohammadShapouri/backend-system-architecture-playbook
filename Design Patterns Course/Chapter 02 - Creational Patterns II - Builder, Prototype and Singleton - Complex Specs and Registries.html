Design Pattern #03

Pattern Name: Builder

Formal Classification: Creational Pattern • Gang of Four (GoF) Reference p. 97

💡 The Real-World Metaphor (Plain English)

Imagine assembling a custom luxury car at a dealership. You don't dump 2,000 loose components (chassis, engine, leather seats, sunroof, navigation, sport brakes) into a single giant crate and try to assemble it in one second.

Instead, you go through an assembly line or a custom configuration wizard: step 1 chooses the chassis and transmission; step 2 installs the interior trim; step 3 adds optional performance modules; step 4 runs structural quality validation. Only when every stage passes is the completed car rolled off the floor.

The Builder Pattern separates the step-by-step construction of a complex object from its actual representation, allowing the exact same construction workflow to create different variations safely.

The Problem: The Telescoping Constructor Anti-Pattern

In complex software, domain objects often contain dozens of attributes—some mandatory, many optional. Without the Builder Pattern, engineers fall into the Telescoping Constructor trap: a massive constructor accepting 10 to 20 positional parameters, leading to fragile code, silent argument-swapping bugs, and unreadable call sites: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: The Telescoping Constructor (Blind Argument Swapping)
# ------------------------------------------------------------------------------

class TradeOrder:
    def __init__(
        self, symbol, side, quantity, price, stop_loss, take_profit,
        trailing_stop, time_in_force, leverage, post_only, reduce_only,
        iceberg_qty, client_order_id, routing_venue
    ):
        # 14 positional parameters!
        self.symbol = symbol
        self.side = side
        # ... (snip 12 assignments)

# The Disastrous Call Site:
# Notice how easy it is to accidentally swap `price` (150.0) with `stop_loss` (145.0)!
# A junior developer writes:
order = TradeOrder(
    "AAPL", "BUY", 100, 145.0, 150.0, None, 
    0.02, "GTC", 1, False, True, 
    None, "client_99", "NASDAQ"
)
# Python cannot catch this mistake at compile-time! A catastrophic trade executes immediately!
Fluent Staged Builder Pipeline Architecture
Stage 1: Identity .set_symbol("BTC/USD")
.set_side(Side.BUY)
→
Stage 2: Sizing .set_quantity(2.5)
.set_price(65000.0)
→
Stage 3: Risk Controls .with_stop_loss(64000.0)
.with_take_profit(68000.0)
→
Stage 4: Validation .build()
Enforces all invariants!
Immutability & Safety Invariant:

The concrete product (TradeOrder) is instantiated strictly during the final .build() step. If a required parameter is omitted or if stop_loss > price on a BUY order, the builder raises an explicit domain exception before any corrupted object can ever exist in memory.

✔ When to Use Builder
  • The object requires more than 4 or 5 constructor parameters, especially when many parameters are optional or mutually exclusive.
  • The object construction involves complex step-by-step assembly where intermediate states must be verified before the final object is finalized.
  • You want to produce immutable objects (frozen=True dataclasses) whose internal attributes cannot be modified after construction.
✘ When NOT to Use Builder
  • The target class has only 2 or 3 attributes. A simple standard constructor with keyword arguments is far cleaner.
  • The domain model is fundamentally a simple data transfer object (DTO) without validation invariants or multi-stage lifecycles.
  • You create a builder class that just mirrors the model without performing any validation or abstraction (pure overhead).
Design Pattern #04

Pattern Name: Prototype

Formal Classification: Creational Pattern • Gang of Four (GoF) Reference p. 117

💡 The Real-World Metaphor (Plain English)

Imagine creating a complex legal corporate contract. You don't hire attorneys to write 80 pages of boilerplate clauses, confidentiality terms, and dispute resolutions by hand from scratch for every single client.

Instead, law firms maintain a standardized Master Template (The Prototype) that has already passed legal review. When a new deal arrives, they make a photocopy of the master template and quickly fill in the client's name and payment amount.

The Prototype Pattern creates new objects by cloning a pre-configured prototype instance in memory, bypassing expensive database lookups, network handshakes, or heavy initialization logic.

Computer Science: Memory Models of Shallow vs. Deep Cloning

In high-frequency trading (HFT) and microservice routing, creating a fully initialized trade template (pre-loaded with market exchange metadata, compliance policies, fee rules, and routing credentials) can take 5ms of database I/O. But when an algorithmic surge occurs, your system must produce 10,000 orders per second.

However, junior programmers often trigger severe production bugs when cloning objects because they do not understand the difference between Shallow Copy and Deep Copy:

Cloning Topology: Shallow Reference Duplication vs. Deep Value Isolation
1. Shallow Copy (copy.copy) • Dangerous

Creates a new outer object, but copies pointers/references to nested mutable collections:

OrderPrototype.metadata → Memory Address [0x00FF]
ClonedOrder.metadata → Memory Address [0x00FF] (SHARED!)
✗ Modifying ClonedOrder corrupts the original Prototype!
2. Deep Copy (copy.deepcopy) • Safe Isolation

Recursively traverses the entire object graph, allocating new independent memory for all nested mutable state:

OrderPrototype.metadata → Memory Address [0x00FF]
ClonedOrder.metadata → Memory Address [0x77AA] (INDEPENDENT!)
✓ Completely isolated in memory. Safe for concurrent mutation!
✔ When to Use Prototype
  • Object creation via constructor is computationally expensive (requires parsing large XML/JSON files, querying slow remote databases, or heavy initialization).
  • You need hundreds of similar objects that differ only slightly in a few parameters (e.g. pre-configured trade templates with identical exchange credentials).
  • You want to avoid an explosion of factory subclasses just to instantiate slightly different configurations of the same product.
✘ When NOT to Use Prototype
  • The object contains circular object references or holds raw OS resources (such as active TCP network sockets, database transaction handles, or file descriptors).
  • Standard instantiation is fast and straightforward (Order(qty=10) takes under 50 nanoseconds in pure Python).
  • Over-relying on generic copy.deepcopy(), which is notoriously slow in Python due to recursive reflection dictionaries.
Design Pattern #05

Pattern Name: Singleton

Formal Classification: Creational Pattern • Gang of Four (GoF) Reference p. 127

💡 The Real-World Metaphor (Plain English)

Imagine the Central Air Traffic Control (ATC) tower at a major international airport. You cannot have 5 independent control towers with 5 different controllers issuing conflicting takeoff and landing commands to planes on the exact same runway!

There must be strictly one, authoritative source of truth for the entire airport. Every pilot, radar system, and ground vehicle coordinates through that exact same centralized entity.

The Singleton Pattern ensures that a class has strictly ONE instance in memory throughout the application's entire lifetime and provides a global, synchronized point of access to it.

Thread-Safety Mechanics: The Double-Checked Locking Problem

Many beginner Python tutorials implement Singleton by overriding __new__ with a naive if not hasattr(cls, 'instance'): cls.instance = super().__new__(cls).

In a multi-threaded web server (such as FastAPI running with Gunicorn/Uvicorn worker threads), this naive implementation suffers from a critical Race Condition: two threads invoke the constructor at the exact same microsecond, both see that the instance is None, and both instantiate separate objects—destroying the singleton guarantee!

The Thread-Safe Metaclass Double-Checked Locking Topology
1. Thread 1 & Thread 2 Call SingletonRegistry()
→ check 1 →
2. Lock Acquisition First check: if not in _instances → acquire threading.RLock()
→ check 2 →
3. Guaranteed Single Instance Second check inside lock ensures exactly one instantiation!
Why We Use Python Metaclasses for Singletons:

Implementing Singleton via a reusable metaclass (class SingletonMeta(type): ...) completely decouples the singleton lifecycle mechanics from your actual business logic. Any class in your architecture can become a thread-safe singleton simply by specifying metaclass=SingletonMeta!

✔ When to Use Singleton
  • You need strictly one instance of a shared coordinator, such as a hardware driver handle, a centralized in-memory risk registry, or an audit log dispatcher.
  • Strict synchronization across multiple concurrent threads is required to prevent split-brain state divergence.
  • You want to replace messy, uncoordinated global variables with an encapsulated, lazy-initialized class structure.
✘ When NOT to Use Singleton
  • You are simply trying to pass data between classes. Use standard dependency injection instead.
  • In unit tests where tests need clean, isolated, independent state. Singletons carry global state across tests unless an explicit reset mechanism is provided.
  • In distributed multi-process environments (e.g. multiple Kubernetes pods). A Singleton is only single per Python process, not across an entire cluster!

1. Thread-Safe Singleton Metaclass: src/nexuscore/core/singleton.py Concurrency Barrier 
# ==============================================================================
# NexusCore Core - Thread-Safe Singleton Metaclass with Double-Checked Locking
# ==============================================================================

import threading
from typing import Any, Dict

class SingletonMeta(type):
    """
    THREAD-SAFE SINGLETON METACLASS:
    Guarantees that any class using this metaclass has strictly one instance per process.
    Implements double-checked locking using a re-entrant lock (RLock) to prevent
    race conditions in high-concurrency multi-threaded environments.
    """
    _instances: Dict[type, Any] = {}
    _lock: threading.RLock = threading.RLock()

    def __call__(cls, *args, **kwargs) -> Any:
        # First Check (without lock) for high-speed performance:
        if cls not in cls._instances:
            # Acquire lock only when instantiation is required:
            with cls._lock:
                # Second Check (inside lock) to eliminate race conditions:
                if cls not in cls._instances:
                    instance = super().__call__(*args, **kwargs)
                    cls._instances[cls] = instance
        return cls._instances[cls]

    def reset_instance(cls) -> None:
        """
        TESTING HARNESS HOOK:
        Allows isolated unit test suites to clear the singleton instance cleanly.
        """
        with cls._lock:
            if cls in cls._instances:
                del cls._instances[cls]

from dataclasses import dataclass, field
from enum import Enum
from typing import Optional, Dict, Any

class OrderSide(str, Enum):
    BUY = "BUY"
    SELL = "SELL"

class OrderType(str, Enum):
    LIMIT = "LIMIT"
    MARKET = "MARKET"
    STOP_LIMIT = "STOP_LIMIT"

class TimeInForce(str, Enum):
    GTC = "GTC"  # Good Till Cancelled
    IOC = "IOC"  # Immediate Or Cancel
    FOK = "FOK"  # Fill Or Kill


@dataclass(frozen=True)
class TradeOrder:
    """
    IMMUTABLE TRADE ORDER:
    Constructed strictly via OrderBuilder.
    Cannot be modified post-creation, eliminating race conditions in concurrent matching engines.
    """
    order_id: str
    symbol: str
    side: OrderSide
    order_type: OrderType
    quantity: float
    price: float
    stop_loss: Optional[float] = None
    take_profit: Optional[float] = None
    time_in_force: TimeInForce = TimeInForce.GTC
    post_only: bool = False
    metadata: Dict[str, Any] = field(default_factory=dict)

    @property
    def notional_value(self) -> float:
        return self.quantity * self.price
4. Staged Fluent Order Builder: src/nexuscore/orders/builder.py Builder Pattern Implementation 
# ==============================================================================
# NexusCore Orders - Fluent Staged Order Builder with Invariant Validation
# ==============================================================================

import uuid
from typing import Optional, Dict, Any
from nexuscore.orders.models import TradeOrder, OrderSide, OrderType, TimeInForce
from nexuscore.core.risk_registry import RiskParameterRegistry

class OrderBuilder:
    """
    BUILDER PATTERN:
    Step-by-step assembly of complex financial orders.
    Enforces business validation invariants at build() time.
    """
    def __init__(self):
        self._order_id: str = f"ord_{uuid.uuid4().hex[:10]}"
        self._symbol: Optional[str] = None
        self._side: Optional[OrderSide] = None
        self._order_type: OrderType = OrderType.LIMIT
        self._quantity: Optional[float] = None
        self._price: Optional[float] = None
        self._stop_loss: Optional[float] = None
        self._take_profit: Optional[float] = None
        self._time_in_force: TimeInForce = TimeInForce.GTC
        self._post_only: bool = False
        self._metadata: Dict[str, Any] = {}

    def for_instrument(self, symbol: str, side: OrderSide) -> "OrderBuilder":
        """Stage 1: Bind financial symbol and buy/sell side."""
        self._symbol = symbol.upper().strip()
        self._side = side
        return self

    def with_sizing(self, quantity: float, price: float) -> "OrderBuilder":
        """Stage 2: Specify order volume and execution price."""
        self._quantity = quantity
        self._price = price
        return self

    def as_type(self, order_type: OrderType) -> "OrderBuilder":
        self._order_type = order_type
        return self

    def with_risk_brackets(self, stop_loss: float, take_profit: float) -> "OrderBuilder":
        """Stage 3 (Optional): Attach stop loss and profit targets."""
        self._stop_loss = stop_loss
        self._take_profit = take_profit
        return self

    def set_time_in_force(self, tif: TimeInForce) -> "OrderBuilder":
        self._time_in_force = tif
        return self

    def set_post_only(self, post_only: bool) -> "OrderBuilder":
        self._post_only = post_only
        return self

    def add_metadata(self, key: str, value: Any) -> "OrderBuilder":
        self._metadata[key] = value
        return self

    def build(self) -> TradeOrder:
        """
        FINAL STAGE: Validates all domain invariants before object creation.
        """
        # Invariant 1: Mandatory Parameters
        if not self._symbol or not self._side:
            raise ValueError("OrderBuilder: symbol and side are mandatory.")
        if self._quantity is None or self._quantity <= 0:
            raise ValueError("OrderBuilder: quantity must be strictly positive.")
        if self._price is None or self._price <= 0:
            raise ValueError("OrderBuilder: price must be strictly positive.")

        # Invariant 2: Symbol Restriction via Risk Registry (Singleton Check)
        risk_registry = RiskParameterRegistry()
        if risk_registry.is_symbol_restricted(self._symbol):
            raise PermissionError(f"OrderBuilder: Symbol '{self._symbol}' is restricted by Risk Registry.")

        # Invariant 3: Notional Ceiling
        notional = self._quantity * self._price
        if notional > risk_registry.get_max_notional():
            raise ValueError(f"OrderBuilder: Notional ${notional:,.2f} exceeds limit of ${risk_registry.get_max_notional():,.2f}.")

        # Invariant 4: Logical Bracket Sanity Checks
        if self._stop_loss is not None and self._take_profit is not None:
            if self._side == OrderSide.BUY:
                if not (self._stop_loss < self._price < self._take_profit):
                    raise ValueError("BUY order bracket must satisfy: stop_loss < price < take_profit.")
            elif self._side == OrderSide.SELL:
                if not (self._take_profit < self._price < self._stop_loss):
                    raise ValueError("SELL order bracket must satisfy: take_profit < price < stop_loss.")

        return TradeOrder(
            order_id=self._order_id,
            symbol=self._symbol,
            side=self._side,
            order_type=self._order_type,
            quantity=self._quantity,
            price=self._price,
            stop_loss=self._stop_loss,
            take_profit=self._take_profit,
            time_in_force=self._time_in_force,
            post_only=self._post_only,
            metadata=dict(self._metadata)
        )
5. Prototype Cloning Repository: src/nexuscore/orders/prototype.py Prototype Pattern Implementation 
# ==============================================================================
# NexusCore Orders - Prototype Cloning Engine & Template Registry
# ==============================================================================

import copy
import uuid
from typing import Dict, Any, Optional
from dataclasses import replace
from nexuscore.orders.models import TradeOrder

class OrderPrototypeRegistry:
    """
    PROTOTYPE PATTERN REGISTRY:
    Maintains pre-configured, validated TradeOrder prototypes.
    Produces clones in microseconds, bypassing validation pipeline overhead
    during high-frequency algorithmic surges.
    """
    def __init__(self):
        self._prototypes: Dict[str, TradeOrder] = {}

    def register_prototype(self, template_name: str, order: TradeOrder) -> None:
        """Registers a master prototype template."""
        self._prototypes[template_name.lower().strip()] = order

    def clone(
        self,
        template_name: str,
        override_quantity: Optional[float] = None,
        override_price: Optional[float] = None,
        extra_metadata: Optional[Dict[str, Any]] = None
    ) -> TradeOrder:
        """
        Clones prototype using deep copy isolation and applies runtime overrides.
        Generates a fresh unique order_id for the newly spawned order.
        """
        name = template_name.lower().strip()
        if name not in self._prototypes:
            raise KeyError(f"Prototype template '{template_name}' not found.")

        prototype = self._prototypes[name]

        # 1. Deep copy metadata to guarantee zero memory pointer sharing:
        isolated_metadata = copy.deepcopy(prototype.metadata)
        if extra_metadata:
            isolated_metadata.update(extra_metadata)

        # 2. Duplicate order with clean fresh ID:
        new_id = f"ord_clone_{uuid.uuid4().hex[:10]}"
        
        # Using dataclass replace to generate clean immutable copy:
        cloned_order = replace(
            prototype,
            order_id=new_id,
            quantity=override_quantity if override_quantity is not None else prototype.quantity,
            price=override_price if override_price is not None else prototype.price,
            metadata=isolated_metadata
        )
        return cloned_order

Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The Blind Shallow Copy Prototype Bug

Using copy.copy() instead of copy.deepcopy() when cloning prototypes that contain nested dictionaries or lists.

Why this causes catastrophic silent data corruption: In a shallow copy, Python duplicates only the outer object; nested dictionaries (such as trade routing tags or compliance flags) continue pointing to the identical memory address! When Thread A modifies a cloned order's metadata, it invisibly mutates the master prototype in memory, corrupting every subsequent order spawned across the entire company!

❌ The Unresetable Singleton (Testing Nightmare)

Writing a Singleton with no harness hook to reset or mock state between unit tests.

Why this creates flaky CI pipelines: When Test 1 modifies the global registry (e.g. restricts symbol AAPL), Test 50 (running seconds later in the same runner process) unexpectedly fails because AAPL is still restricted! Always provide an internal reset_instance() method for test fixtures.
