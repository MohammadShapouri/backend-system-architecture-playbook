Architecture Fundamentals

Clean Layering: Separating Presentation, Application & Domain

A software system degrades when boundaries between responsibilities blur. When an API route function parses JSON parameters, executes business calculations, queries a database, and generates an invoice all within a single file, the system becomes impossible to test, maintain, or adapt.

In Martin Fowler's Patterns of Enterprise Application Architecture and Clean Architecture, a robust system is divided into four distinct concentric layers with a strict unidirectional dependency rule:

The Enterprise Layered Architecture Topology
1. Presentation Layer (Front Controller & DTOs) FastAPI Routes • HTTP Status Codes • Input Validation • JSON Serialization
↓ calls with DTOs ↓
2. Application Layer (Service Layer) Use Case Coordination • Transaction Management (Unit of Work) • Security • Notifications
↓ mutates ↓
3. Domain Layer (Rich Domain Model) Pure Business Rules • Invariant Validation • Entities & Value Objects • ZERO External Dependencies
↓ persists via ↓
4. Infrastructure Layer (Repository & Data Mapper) SQLAlchemy 2.0 • Database Connections • Redis Sockets • External Message Queues
The Dependency Rule Invariant:

Dependencies only point inwards. The Domain Layer knows nothing about the Service Layer, the Web Layer, or the Database. You can replace FastAPI with a CLI or replace PostgreSQL with MongoDB without changing a single line of your core domain business rules!

Enterprise Pattern #27

Pattern Name: Domain Model (Rich Domain vs. Anemic Anti-Pattern)

Formal Classification: Domain Logic Pattern • Martin Fowler (P of EAA p. 116)

💡 The Real-World Metaphor (Plain English)

Imagine a living human being versus a plastic display mannequin in a department store.

A plastic mannequin has physical dimensions, plastic arms, and clothes (data), but zero autonomous behavior. If you want the mannequin to wave, an external human puppeteer must physically walk over, grab its plastic wrist, and move it back and forth. The mannequin has no say in whether its arm is ripped off.

A real human being (A Rich Domain Model) encapsulates both anatomy (data) and autonomous reflexes (behavior). If you tell a person: "Run a marathon," their brain evaluates internal invariants (heart rate, stamina, hydration). If they are completely exhausted, they refuse. They protect their own internal state from corruption.

The Problem: The Dreaded Anemic Domain Model

Martin Fowler coined the term Anemic Domain Model to describe one of the most common architectural antipatterns in modern software engineering. It occurs when domain classes are nothing more than hollow bags of fields (getters and setters), while all business rules and state validations are smeared across arbitrary controller functions: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: The Anemic Domain Model (Zero Behavior / Naked Data)
# ------------------------------------------------------------------------------

class AnemicSettlementAccount:
    # Just a dumb container with zero logic or invariants:
    def __init__(self, account_id: str, balance: float, is_frozen: bool):
        self.account_id = account_id
        self.balance = balance
        self.is_frozen = is_frozen

# The Catastrophe: Business logic leaks directly into FastAPI controllers!
@app.post("/settle")
def settle_endpoint(account: AnemicSettlementAccount, amount: float):
    # Controller is forced to enforce fundamental domain rules:
    if account.is_frozen:
        raise HTTPException(400, "Account frozen!")
    if account.balance < amount:
        raise HTTPException(400, "Insufficient balance!")
    
    # Direct naked state mutation:
    account.balance -= amount
    # If another developer writes a BackgroundJob, they must copy-paste these exact checks!
    # If they forget, invalid or negative balances are silently written to the database!
✔ When to Use Rich Domain Model
  • Your domain contains complex business invariants, calculations, state transitions, and validation rules.
  • You want to test core business rules in pure, sub-millisecond unit tests without mocking databases or spinning up web servers.
  • Multiple entry points (REST API, Celery worker, CLI, event consumer) interact with the same business concepts.
✘ When NOT to Use Rich Domain Model
  • The application is pure CRUD (Create, Read, Update, Delete) where data is simply stored and retrieved with zero business rules.
  • The system is an ETL pipeline whose sole purpose is copying data from one schema format to another without business transformations.
Enterprise Pattern #28

Pattern Name: Service Layer (Application Service)

Formal Classification: Enterprise Application Pattern • Martin Fowler (P of EAA p. 133)

💡 The Real-World Metaphor (Plain English)

Imagine the Head General Manager of a fine-dining restaurant.

The General Manager does not chop onions or season steaks (that is the domain of the Chef). The General Manager also does not seat guests or pour water at tables (that is the job of the Host).

Instead, the General Manager coordinates the complete operational workflow: When a VIP table reservation occurs, the General Manager opens the booking register, instructs the cellar master to pull a vintage bottle of wine, coordinates with the chef on dietary restrictions, and ensures the billing transaction executes cleanly. The Service Layer coordinates the use case from start to finish!

The Problem: The "Fat Controller" Antipattern

Without a Service Layer, web route controllers become bloated. They take on the responsibility of managing database transactions, calling multiple repositories, checking permissions, sending notification emails, and handling retries. When a CLI command or asynchronous task queue needs to perform the identical use case, code must be copied:

Separation of Concerns: Service Layer vs. Domain Model
Service Layer (Application Scope)
  • Transaction Boundaries: Opens and commits the Unit of Work.
  • Orchestration: Loads entities via Repositories.
  • External Collaborators: Sends email alerts, publishes events to RabbitMQ.
  • Security: Verifies user permissions and access rights.
  • No Business Rules: Never calculates interest rates, discounts, or risk limits directly!
Domain Model (Business Scope)
  • Business Rules: Calculates fees, validates settlement conditions.
  • Invariant Protection: Guarantees balance never drops below overdraft limit.
  • Pure Logic: No knowledge of HTTP, sessions, SQL, or email senders.
  • Self-Contained: Operates entirely on internal memory attributes.
✔ When to Use Service Layer
  • You have multiple operations that must execute as a single atomic transaction across multiple entities and repositories.
  • The application has multiple clients (e.g. REST API, CLI tool, background Celery queue) that need to invoke the exact same business use case.
  • You want to keep web route controllers ultra-thin (1 to 3 lines of code).
✘ When NOT to Use Service Layer
  • You create an anemic 1-line service layer that just passes calls directly from controller to repository without coordinating any use case logic.
Enterprise Pattern #29

Pattern Name: Data Transfer Object (DTO)

Formal Classification: Enterprise Distribution Pattern • Martin Fowler (P of EAA p. 401)

💡 The Real-World Metaphor (Plain English)

Imagine shipping valuable goods internationally through customs.

When you ship a package, you do not hand the customs border officer your company's entire internal filing cabinet, payroll ledger, and confidential trade secrets.

You fill out a standardized Customs Declaration Manifest (The DTO). The manifest includes only the specific fields necessary for transit: destination address, item weight, and declared value. It is a sealed, plain data envelope containing no internal business behavior.

The Problem: Exposing Internal Domain Entities Over the Wire

When API controllers serialize internal domain entities or database models directly to JSON, two severe hazards arise:

  1. Security Data Leaks: Internal fields (password hashes, tax IDs, internal risk scores, audit timestamps) are accidentally leaked to public web clients.
  2. API Contract Rigidity: Renaming an internal attribute in your Python class immediately breaks mobile apps and external API consumers because the JSON payload structure changed.

DTOs (implemented via Pydantic v2 schemas in Python) act as strict firewalls between external network payloads and internal domain objects.

✔ When to Use DTO
  • Validating incoming wire data before passing it to the application or domain layers.
  • Projecting filtered, safe response payloads that hide sensitive internal fields.
  • Decoupling public API version contracts from internal database schema refactoring.
✘ When NOT to Use DTO
  • Passing data strictly between internal functions within the same domain boundary. Use domain models or dataclasses directly.
Enterprise Pattern #30

Pattern Name: Front Controller

Formal Classification: Web Presentation Pattern • Martin Fowler (P of EAA p. 344)

💡 The Real-World Metaphor (Plain English)

Imagine the main entrance security lobby of a corporate skyscraper.

Visitors do not wander directly into the CEO's office, server rooms, or marketing suites through random open windows. Every single person enters through the Front Lobby Desk.

The front lobby handles cross-cutting concerns: badge scanning, visitor logging, weapon detection, and elevator routing. Once cleared, the visitor is directed to the specific floor they requested. In web engineering, a Front Controller centralizes all request intake before routing to specific handlers.

Modern Realization: FastAPI as the Master Front Controller

Historically in Java or PHP, developers manually wrote a massive FrontControllerServlet with giant regex matching tables.

In modern Python architecture, FastAPI acts as your production Front Controller:

  • It intercepts 100% of incoming HTTP request streams.
  • It executes cross-cutting concerns (CORS, TLS termination, global error handlers, authentication tokens).
  • It injects application dependencies via Depends().
  • It validates incoming DTO payloads before delegating control to the Service Layer.

1. Rich Domain Model: src/nexuscore/domain/settlement.py Encapsulated Invariants 
# ==============================================================================
# NexusCore Domain - Rich Domain Model (Behavior + State Encapsulation)
# ==============================================================================

from dataclasses import dataclass
from enum import Enum


class AccountStatus(str, Enum):
    ACTIVE = "ACTIVE"
    FROZEN = "FROZEN"


class DomainValidationError(ValueError):
    """Raised when a business invariant is violated."""
    pass


@dataclass
class SettlementAccount:
    """
    RICH DOMAIN MODEL:
    Encapsulates state AND core financial behavior.
    Guarantees internal invariants: balance, status checks, and overdraft ceilings.
    Has ZERO knowledge of databases, SQL, or web frameworks!
    """
    account_id: str
    user_id: str
    balance: float
    status: AccountStatus = AccountStatus.ACTIVE
    overdraft_limit: float = 0.0

    def debit(self, amount: float) -> None:
        # Invariant 1: Positive amounts
        if amount <= 0:
            raise DomainValidationError("Debit amount must be strictly positive.")

        # Invariant 2: Active account status
        if self.status == AccountStatus.FROZEN:
            raise DomainValidationError(f"Cannot debit frozen account '{self.account_id}'.")

        # Invariant 3: Overdraft limits
        if (self.balance - amount) < -self.overdraft_limit:
            raise DomainValidationError(
                f"Insufficient funds: Balance ${self.balance:,.2f} with overdraft limit "
                f"${self.overdraft_limit:,.2f} cannot absorb debit of ${amount:,.2f}."
            )

        self.balance -= amount

    def credit(self, amount: float) -> None:
        if amount <= 0:
            raise DomainValidationError("Credit amount must be strictly positive.")

        if self.status == AccountStatus.FROZEN:
            raise DomainValidationError(f"Cannot credit frozen account '{self.account_id}'.")

        self.balance += amount

    def freeze(self) -> None:
        self.status = AccountStatus.FROZEN
2. Data Transfer Objects: src/nexuscore/api/dto.py Pydantic v2 Wire Schemas 
# ==============================================================================
# NexusCore API - Data Transfer Objects (Pydantic v2 Wire Contracts)
# ==============================================================================

from pydantic import BaseModel, Field, field_validator


class SettlementRequestDTO(BaseModel):
    """
    INCOMING DTO:
    Validates external JSON input before it touches domain or service layers.
    """
    sender_account_id: str = Field(..., min_length=3, max_length=50)
    receiver_account_id: str = Field(..., min_length=3, max_length=50)
    amount: float = Field(..., gt=0.0, description="Settlement amount in fiat units")
    idempotency_key: str = Field(..., min_length=10)

    @field_validator("receiver_account_id")
    @classmethod
    def prevent_self_transfer(cls, v: str, info) -> str:
        sender = info.data.get("sender_account_id")
        if sender and v == sender:
            raise ValueError("Sender and receiver accounts must be distinct.")
        return v


class SettlementResponseDTO(BaseModel):
    """
    OUTGOING DTO:
    Projects filtered, safe response data. Hides internal database keys and schemas.
    """
    settlement_id: str
    status: str
    amount: float
    sender_account_id: str
    receiver_account_id: str
    sender_new_balance: float
3. Application Service Layer: src/nexuscore/services/settlement_service.py Use Case Orchestrator 
# ==============================================================================
# NexusCore Services - Application Service Layer (Transactional Orchestrator)
# ==============================================================================

import uuid
from typing import Callable
from nexuscore.domain.settlement import SettlementAccount, DomainValidationError
from nexuscore.api.dto import SettlementRequestDTO, SettlementResponseDTO
from nexuscore.storage.unit_of_work import IUnitOfWork

class SettlementService:
    """
    APPLICATION SERVICE LAYER:
    Coordinates the use case:
    1. Manages Unit of Work transaction boundary.
    2. Loads domain models via repositories.
    3. Invokes rich business logic on domain entities.
    4. Commits atomic state changes.
    5. Returns a clean DTO projection.
    """
    def __init__(self, uow_factory: Callable[[], IUnitOfWork]):
        self.uow_factory = uow_factory

    async def execute_settlement(self, dto: SettlementRequestDTO) -> SettlementResponseDTO:
        uow = self.uow_factory()

        # Atomic Transaction Boundary
        async with uow:
            # 1. Fetch entities
            sender_domain = await uow.accounts.get(dto.sender_account_id)
            if not sender_domain:
                raise DomainValidationError(f"Sender account '{dto.sender_account_id}' does not exist.")

            receiver_domain = await uow.accounts.get(dto.receiver_account_id)
            if not receiver_domain:
                raise DomainValidationError(f"Receiver account '{dto.receiver_account_id}' does not exist.")

            # Map to Rich Domain Models
            sender = SettlementAccount(
                account_id=sender_domain.account_id,
                user_id=sender_domain.user_id,
                balance=sender_domain.balance
            )
            receiver = SettlementAccount(
                account_id=receiver_domain.account_id,
                user_id=receiver_domain.user_id,
                balance=receiver_domain.balance
            )

            # 2. Invoke Domain Behavior (Enforces business invariants!)
            sender.debit(dto.amount)
            receiver.credit(dto.amount)

            # 3. Update storage models
            sender_domain.balance = sender.balance
            receiver_domain.balance = receiver.balance
            await uow.accounts.add(sender_domain)
            await uow.accounts.add(receiver_domain)

            # 4. Atomic Commit
            await uow.commit()

            # 5. Return projected DTO
            return SettlementResponseDTO(
                settlement_id=f"stl_{uuid.uuid4().hex[:10]}",
                status="COMPLETED",
                amount=dto.amount,
                sender_account_id=sender.account_id,
                receiver_account_id=receiver.account_id,
                sender_new_balance=sender.balance
            )
4. FastAPI Front Controller Router: src/nexuscore/api/router.py Front Controller Pattern 
# ==============================================================================
# NexusCore API - FastAPI Front Controller & Settlement Endpoints
# ==============================================================================

from fastapi import APIRouter, Depends, HTTPException, status
from nexuscore.api.dto import SettlementRequestDTO, SettlementResponseDTO
from nexuscore.services.settlement_service import SettlementService
from nexuscore.domain.settlement import DomainValidationError

router = APIRouter(prefix="/api/v1/settlements", tags=["Settlements"])

# Dependency injection stub (overridden in application startup or tests)
def get_settlement_service() -> SettlementService:
    raise NotImplementedError


@router.post(
    "",
    response_model=SettlementResponseDTO,
    status_code=status.HTTP_201_CREATED,
    summary="Execute Account-to-Account Financial Settlement"
)
async def create_settlement(
    dto: SettlementRequestDTO,
    service: SettlementService = Depends(get_settlement_service)
) -> SettlementResponseDTO:
    """
    ULTRA-THIN CONTROLLER:
    Front controller validates DTO and handles HTTP exceptions.
    100% of transaction logic is delegated to the Service Layer!
    """
    try:
        return await service.execute_settlement(dto)
    except DomainValidationError as exc:
        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST,
            detail=str(exc)
        )

import pytest
import pytest_asyncio
from fastapi import FastAPI
import httpx
from httpx import ASGITransport

from nexuscore.domain.settlement import SettlementAccount, AccountStatus, DomainValidationError
from nexuscore.api.dto import SettlementRequestDTO
from nexuscore.services.settlement_service import SettlementService
from nexuscore.api.router import router, get_settlement_service
from nexuscore.storage.models import DomainAccount
from nexuscore.storage.unit_of_work import IUnitOfWork


# In-Memory Fake Unit of Work for sub-millisecond service layer testing
class FakeAccountRepository:
    def __init__(self, accounts):
        self._accounts = accounts

    async def get(self, account_id: str):
        return self._accounts.get(account_id)

    async def add(self, account: DomainAccount):
        self._accounts[account.account_id] = account


class FakeUnitOfWork(IUnitOfWork):
    def __init__(self, accounts_dict):
        self._accounts_dict = accounts_dict
        self.committed = False

    async def __aenter__(self):
        self.accounts = FakeAccountRepository(self._accounts_dict)
        return self

    async def __aexit__(self, exc_type, exc_val, exc_tb):
        pass

    async def commit(self):
        self.committed = True

    async def rollback(self):
        pass


class TestCleanArchitectureSuite:
    """Verifies Rich Domain invariants, Service orchestration, and Front Controller routing."""

    def test_rich_domain_model_enforces_invariants_in_isolation(self):
        # 1. Successful debit
        acc = SettlementAccount("acc_1", "user_1", balance=500.0, overdraft_limit=100.0)
        acc.debit(550.0)
        assert acc.balance == -50.0

        # 2. Rejects exceeding overdraft
        with pytest.raises(DomainValidationError, match="Insufficient funds"):
            acc.debit(100.0)  # -50 - 100 = -150 < -100

        # 3. Rejects operation on frozen account
        acc.freeze()
        with pytest.raises(DomainValidationError, match="frozen"):
            acc.credit(50.0)

    @pytest.mark.asyncio
    async def test_service_layer_orchestration(self):
        accounts = {
            "src": DomainAccount("src", "u1", 1000.0),
            "dst": DomainAccount("dst", "u2", 200.0)
        }
        service = SettlementService(uow_factory=lambda: FakeUnitOfWork(accounts))

        dto = SettlementRequestDTO(
            sender_account_id="src",
            receiver_account_id="dst",
            amount=400.0,
            idempotency_key="idemp_key_12345"
        )

        res = await service.execute_settlement(dto)
        assert res.status == "COMPLETED"
        assert res.sender_new_balance == 600.0
        assert accounts["src"].balance == 600.0
        assert accounts["dst"].balance == 600.0

    @pytest.mark.asyncio
    async def test_front_controller_http_api_validation(self):
        accounts = {
            "acc_a": DomainAccount("acc_a", "u1", 100.0),
            "acc_b": DomainAccount("acc_b", "u2", 50.0)
        }
        service = SettlementService(uow_factory=lambda: FakeUnitOfWork(accounts))

        app = FastAPI()
        app.include_router(router)
        app.dependency_overrides[get_settlement_service] = lambda: service

        transport = ASGITransport(app=app)
        async with httpx.AsyncClient(transport=transport, base_url="http://test") as client:
            # Test 1: Self-transfer rejected by DTO validation
            bad_res = await client.post("/api/v1/settlements", json={
                "sender_account_id": "acc_a",
                "receiver_account_id": "acc_a",
                "amount": 50.0,
                "idempotency_key": "1234567890"
            })
            assert bad_res.status_code == 422  # Pydantic validation error

            # Test 2: Successful settlement execution
            good_res = await client.post("/api/v1/settlements", json={
                "sender_account_id": "acc_a",
                "receiver_account_id": "acc_b",
                "amount": 40.0,
                "idempotency_key": "1234567890"
            })
            assert good_res.status_code == 201
            assert good_res.json()["sender_new_balance"] == 60.0
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The Anemic Domain Model

Writing domain classes with only public fields and placing all validation logic in controllers or service procedures.

Why this causes system degradation: As the application grows, developers write duplicate validation rules across multiple controllers. If a rule changes (e.g. overdraft limit calculation), it must be updated in 10 different files. Inevitably, one is forgotten, leading to data corruption! Keep entities rich: let the entity protect its own invariants.

❌ Leaking Entities Across Wire Boundaries

Returning domain or ORM objects directly from route handlers: return account.

Why this causes outages and security leaks: Public API clients become tightly coupled to internal model attribute names. Renaming an internal Python variable immediately breaks external mobile apps! Furthermore, sensitive internal fields (hashed passwords, internal risk scores) are accidentally leaked over the network. Always project safe responses using explicit DTOs.
