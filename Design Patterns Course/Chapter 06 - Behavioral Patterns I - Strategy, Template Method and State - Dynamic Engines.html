Architecture Fundamentals

Behavioral Patterns: The Mechanics of Algorithmic Control

In software architecture, systems fail to scale not because classes are structured poorly, but because control flow becomes tangled.

As business logic evolves, codebases frequently degrade into massive, 500-line conditional ladders: checking which algorithm to apply, which steps in a procedure must run, and which state transitions are permitted. Behavioral patterns shift the focus from class inheritance and object composition to how responsibilities are distributed across independent objects at runtime.

// The Core Behavioral Tenet:

Encapsulate what varies. If an algorithm changes frequently, isolate it behind a Strategy. If a workflow has immutable invariant steps with customizable details, fix the skeleton in a Template Method. If an object acts completely differently depending on its current mode or lifecycle, delegate that behavior to a State object.

Design Pattern #13

Pattern Name: Strategy (Policy)

Formal Classification: Behavioral Pattern • Gang of Four (GoF) Reference p. 315

💡 The Real-World Metaphor (Plain English)

Imagine you need to get to the airport to catch an international flight. You have several transportation options: you can take a Bicycle, ride the City Subway, or hail an expensive Airport Taxi.

Your destination (the airport) and your identity (the traveler) remain identical in all three cases. What varies is the algorithm for reaching the destination: speed, cost, and route calculation.

You do not physically rebuild your body to become a bicycle or a taxi! Instead, you select a transportation strategy based on your current budget and time constraints, and switch strategies seamlessly when circumstances demand.

The Problem: Sprawling Conditional Fee Calculations

In a financial clearing system, trading fees are dynamic. Retail users pay standard percentage fees, VIP algorithmic desks receive tiered volume discounts, market makers earn negative liquidity rebates, and promotional holidays apply flat zero-fee structures.

Without the Strategy Pattern, fee logic becomes an unmaintainable monster inside the order processing service: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: Hardcoded Algorithmic Conditional Sprawl
# ------------------------------------------------------------------------------

class TradingExecutionService:
    def calculate_transaction_fee(self, user_tier: str, notional: float, is_maker: bool) -> float:
        # Every time a marketing campaign or new tier is added, this core service file changes!
        if user_tier == "RETAIL":
            return notional * 0.0020  # 0.20% flat fee
        elif user_tier == "VIP_TIER_1":
            if is_maker:
                return notional * 0.0005  # 0.05% maker fee
            else:
                return notional * 0.0010  # 0.10% taker fee
        elif user_tier == "MARKET_MAKER_TIER_A":
            # Negative rebate: Exchange pays the market maker!
            return - (notional * 0.0002)
        elif user_tier == "PROMO_BLACK_FRIDAY":
            return 1.0  # Flat $1 surcharge
        else:
            raise ValueError(f"Unknown user tier: {user_tier}")
        
        # Violates Open-Closed Principle (OCP)! Cannot unit-test fee calculations in isolation.

✔ When to Use Strategy
  • You have multiple variants of an algorithm that can be swapped dynamically at runtime depending on client context, geographical rules, or user tiers.
  • You want to isolate the business logic of an algorithm completely from the caller class that utilizes its results.
  • Your class is littered with a giant if/elif/else ladder selecting different behaviors.
✘ When NOT to Use Strategy
  • You have only one algorithm that never changes. Introducing a strategy interface just adds pointless indirection.
  • In Python, simple variations are often handled cleaner using plain **first-class functions** or lambdas passed as arguments without creating separate classes.
Design Pattern #14

Pattern Name: Template Method

Formal Classification: Behavioral Pattern • Gang of Four (GoF) Reference p. 325

💡 The Real-World Metaphor (Plain English)

Imagine the construction blueprint of a residential housing development. Every house built in the development follows an invariant construction sequence:

  1. Pour the concrete foundation.
  2. Erect the structural framing.
  3. Install plumbing and electrical conduits.
  4. Install customized interior drywall and paint.
  5. Conduct municipal safety inspection.

No homebuilder is allowed to paint walls before pouring the concrete foundation! The skeleton sequence is locked in stone. However, individual buyers can customize specific hook steps: they can choose hardwood vs. carpet floors, or granite vs. marble countertops. The overarching algorithm is immutable; specific steps are open to customization.

// The Inversion of Control Principle (The Hollywood Principle):

Template Method is the quintessential demonstration of the Hollywood Principle: "Don't call us, we'll call you."

In traditional subclassing, child classes invoke parent methods directly (super().do_something()). In the Template Method pattern, the parent class controls the entire flow of execution and calls *down* into the child class's overridden hooks at the exact right moment. The child class never dictates the sequence.

Template Method Invariant Execution Flow
1. validate_trade_parameters() Invariant Base Step (Final)
↓ next ↓
2. apply_regional_withholding_tax() Abstract Hook (Overridden by US / EU / APAC)
↓ next ↓
3. execute_ledger_balance_transfer() Invariant Base Step (Final)
↓ next ↓
4. emit_regulatory_compliance_record() Abstract Hook (SEC vs. MiFID II vs. MAS)
Sequence Safety:

Because the overarching template method execute_clearing() is non-overridable, a junior developer implementing the APAC regional clearing pipeline cannot accidentally bypass regulatory compliance reporting or skip balance validation!

✔ When to Use Template Method
  • You want to let clients extend only particular steps of an algorithm, but not the overarching algorithm's execution structure.
  • You have multiple classes that contain almost identical algorithms with only minor step differences, leading to copy-paste code drift.
  • You need to enforce strict regulatory, audit, or security sequences that must never be bypassed by subclasses.
✘ When NOT to Use Template Method
  • Subclasses need to completely alter the order of execution steps.
  • You have too many abstract hook steps (e.g. 15 abstract methods), creating a brittle base class that is painful to implement.
Design Pattern #15

Pattern Name: State (Objects for States)

Formal Classification: Behavioral Pattern • Gang of Four (GoF) Reference p. 305

💡 The Real-World Metaphor (Plain English)

Imagine the lock button on a modern smartphone.

When the phone is in the Unlocked State, pressing the main screen button opens your home screen applications. When the phone is in the Locked State, pressing the exact same button awakens the screen and prompts for your FaceID or PIN code. When the phone is in the Dead Battery State, pressing the exact same button shows a flashing red battery icon and does nothing else.

The phone button does not contain a giant 1,000-line conditional checking if-else flags. The phone delegates behavior to an active State object. As the phone's battery dies or unlocks, the internal State object is swapped!

The Problem: Brittle Order Status Enum Checkers

In NexusCore, a limit trade order transitions through a strict lifecycle: PENDING_VALIDATION → APPROVED → PARTIALLY_FILLED → FILLED.

Without the State pattern, every single operation (such as cancel() or fill()) requires checking every possible status enumeration, leading to catastrophic bugs where an already-filled order is illegally cancelled: 

# ------------------------------------------------------------------------------
# ANTI-PATTERN: The Sprawling Enum Conditional State Checker
# ------------------------------------------------------------------------------

class BrittleOrder:
    def cancel(self):
        if self.status == "PENDING_VALIDATION":
            self.status = "CANCELLED"
        elif self.status == "APPROVED":
            self.status = "CANCELLED"
            self.release_risk_reservation()
        elif self.status == "PARTIALLY_FILLED":
            self.status = "CANCELLED"
            self.release_remaining_unfilled_balance()
        elif self.status == "FILLED":
            raise RuntimeError("Cannot cancel an already filled order!")
        elif self.status == "CANCELLED":
            return  # No-op

    def fill(self, qty: float):
        if self.status == "PENDING_VALIDATION":
            raise RuntimeError("Cannot fill unvalidated order!")
        # ... 40 more lines of duplicated if/elif conditions across 10 methods!

Illegal Transitions Blocked at Runtime:

In the State pattern, if a caller calls order.cancel() while the order is in FilledState, the FilledState object itself throws an explicit IllegalStateTransitionError without the context needing any conditional logic!

Behavioral Pattern Primary Intent Structural Mechanism Who Drives State/Changes?
Strategy Provides interchangeable algorithms to achieve the exact same calculation/goal. Composition: Context holds 1 strategy reference. Client caller explicitly chooses and injects strategy.
Template Method Fixes an immutable algorithmic sequence while letting subclasses override individual steps. Inheritance: Abstract parent defines final execution pipeline. Parent class orchestrates flow (Hollywood Principle).
State Allows an object to alter its entire behavior when its internal state lifecycle changes. Composition: Context delegates method execution to the active State object. State transitions occur automatically based on actions.

1. Dynamic Fee Strategy Engine: src/nexuscore/fees/strategy.py Strategy Pattern 
# ==============================================================================
# NexusCore Fees - Strategy Pattern for Runtime Dynamic Fee Calculations
# ==============================================================================

from typing import Protocol, runtime_checkable

# ------------------------------------------------------------------------------
# THE STRATEGY INTERFACE
# ------------------------------------------------------------------------------
@runtime_checkable
class IFeeCalculationStrategy(Protocol):
    """
    STRATEGY INTERFACE:
    Encapsulates a fee calculation algorithm. Callers can switch strategies
    at runtime without knowing internal formula details.
    """
    def calculate_fee(self, notional: float, is_maker: bool) -> float:
        ...


# ------------------------------------------------------------------------------
# CONCRETE STRATEGIES
# ------------------------------------------------------------------------------
class RetailFlatPercentageStrategy:
    """Strategy 1: Retail user pays 0.20% fee unconditionally."""
    def calculate_fee(self, notional: float, is_maker: bool) -> float:
        return round(notional * 0.0020, 2)


class MakerTakerTieredStrategy:
    """
    Strategy 2: Institutional volume tier:
    Maker provides liquidity: pays only 0.02%.
    Taker removes liquidity: pays 0.08%.
    """
    def calculate_fee(self, notional: float, is_maker: bool) -> float:
        rate = 0.0002 if is_maker else 0.0008
        return round(notional * rate, 2)


class ZeroFeePromotionalStrategy:
    """Strategy 3: Promotional campaign with flat zero trading fees."""
    def calculate_fee(self, notional: float, is_maker: bool) -> float:
        return 0.0


# ------------------------------------------------------------------------------
# THE CONTEXT
# ------------------------------------------------------------------------------
class FeeComputationContext:
    """Context class holding a reference to the active strategy."""
    def __init__(self, strategy: IFeeCalculationStrategy):
        self._strategy = strategy

    def set_strategy(self, new_strategy: IFeeCalculationStrategy) -> None:
        """Dynamically swaps the fee calculation algorithm at runtime."""
        self._strategy = new_strategy

    def compute(self, notional: float, is_maker: bool) -> float:
        return self._strategy.calculate_fee(notional, is_maker)
2. Regulatory Clearing Pipeline: src/nexuscore/clearing/template.py Template Method Pattern 
# ==============================================================================
# NexusCore Clearing - Template Method for Immutable Regulatory Pipelines
# ==============================================================================

from abc import ABC, abstractmethod
from typing import Dict, Any, List

class ClearingPipeline(ABC):
    """
    TEMPLATE METHOD PATTERN:
    Defines the invariant multi-step regulatory trade clearing sequence.
    Subclasses CANNOT modify the order of execution, but MUST implement
    regional tax and compliance reporting hooks.
    """
    
    # THE TEMPLATE METHOD (Invariant Skeleton)
    def execute_clearing(self, trade_id: str, gross_amount: float) -> Dict[str, Any]:
        # Step 1: Invariant parameter validation
        self._validate_trade(trade_id, gross_amount)

        # Step 2: Regional Tax Hook (Overridden by subclasses)
        tax_amount = self._calculate_regional_tax(gross_amount)

        # Step 3: Invariant settlement transfer
        net_amount = gross_amount - tax_amount
        self._transfer_funds(trade_id, net_amount)

        # Step 4: Regional Regulatory Compliance Hook (Overridden by subclasses)
        compliance_ref = self._emit_regulatory_report(trade_id, net_amount, tax_amount)

        return {
            "trade_id": trade_id,
            "gross": gross_amount,
            "tax": tax_amount,
            "net": net_amount,
            "compliance_ref": compliance_ref,
            "status": "SETTLED"
        }

    # Invariant Step 1 (Private/Common)
    def _validate_trade(self, trade_id: str, gross_amount: float) -> None:
        if gross_amount <= 0:
            raise ValueError("ClearingPipeline: Gross trade amount must be positive.")

    # Invariant Step 3 (Private/Common)
    def _transfer_funds(self, trade_id: str, net_amount: float) -> None:
        # Internal ledger debit/credit logic
        pass

    # Abstract Hook 2: Regional Tax
    @abstractmethod
    def _calculate_regional_tax(self, gross_amount: float) -> float:
        pass

    # Abstract Hook 4: Regulatory Dispatch
    @abstractmethod
    def _emit_regulatory_report(self, trade_id: str, net_amount: float, tax: float) -> str:
        pass


# ------------------------------------------------------------------------------
# CONCRETE PIPELINES
# ------------------------------------------------------------------------------
class UsSecClearingPipeline(ClearingPipeline):
    """United States SEC / FINRA Clearing implementation."""
    def _calculate_regional_tax(self, gross_amount: float) -> float:
        # SEC Section 31 transaction fee (negligible fraction)
        return round(gross_amount * 0.0000278, 2)

    def _emit_regulatory_report(self, trade_id: str, net_amount: float, tax: float) -> str:
        return f"FINRA_OATS_REC_{trade_id}"


class EuMifidClearingPipeline(ClearingPipeline):
    """European Union MiFID II / ESMA Clearing implementation."""
    def _calculate_regional_tax(self, gross_amount: float) -> float:
        # Financial Transaction Tax (FTT 0.20%)
        return round(gross_amount * 0.0020, 2)

    def _emit_regulatory_report(self, trade_id: str, net_amount: float, tax: float) -> str:
        return f"ESMA_MIFIR_RTS22_{trade_id}"
3. Order Lifecycle Finite State Machine: src/nexuscore/orders/state_machine.py State Pattern 
# ==============================================================================
# NexusCore Orders - State Pattern for Finite State Machine Order Lifecycles
# ==============================================================================

from abc import ABC, abstractmethod
from typing import TYPE_CHECKING

class IllegalStateTransitionError(RuntimeError):
    """Raised when an action is executed on an incompatible state."""
    pass


# ------------------------------------------------------------------------------
# THE ABSTRACT STATE INTERFACE
# ------------------------------------------------------------------------------
class IOrderLifecycleState(ABC):
    """Abstract State defining all supported domain lifecycle events."""
    @property
    @abstractmethod
    def status_name(self) -> str:
        pass

    def validate(self, context: "ManagedTradeOrder") -> None:
        raise IllegalStateTransitionError(f"Cannot validate order in state: {self.status_name}")

    def fill(self, context: "ManagedTradeOrder", quantity: float) -> None:
        raise IllegalStateTransitionError(f"Cannot fill order in state: {self.status_name}")

    def cancel(self, context: "ManagedTradeOrder") -> None:
        raise IllegalStateTransitionError(f"Cannot cancel order in state: {self.status_name}")


# ------------------------------------------------------------------------------
# CONCRETE STATES
# ------------------------------------------------------------------------------
class PendingValidationState(IOrderLifecycleState):
    status_name = "PENDING_VALIDATION"

    def validate(self, context: "ManagedTradeOrder") -> None:
        # Transition to ApprovedState
        context.transition_to(ApprovedState())

    def cancel(self, context: "ManagedTradeOrder") -> None:
        context.transition_to(CancelledState())


class ApprovedState(IOrderLifecycleState):
    status_name = "APPROVED"

    def fill(self, context: "ManagedTradeOrder", quantity: float) -> None:
        context.filled_quantity += quantity
        if context.filled_quantity >= context.total_quantity:
            context.transition_to(FilledState())
        else:
            context.transition_to(PartiallyFilledState())

    def cancel(self, context: "ManagedTradeOrder") -> None:
        context.transition_to(CancelledState())


class PartiallyFilledState(IOrderLifecycleState):
    status_name = "PARTIALLY_FILLED"

    def fill(self, context: "ManagedTradeOrder", quantity: float) -> None:
        context.filled_quantity += quantity
        if context.filled_quantity >= context.total_quantity:
            context.transition_to(FilledState())

    def cancel(self, context: "ManagedTradeOrder") -> None:
        context.transition_to(CancelledState())


class FilledState(IOrderLifecycleState):
    status_name = "FILLED"
    # Terminal State: Cannot validate, fill, or cancel! (Inherits default raises)


class CancelledState(IOrderLifecycleState):
    status_name = "CANCELLED"
    # Terminal State


# ------------------------------------------------------------------------------
# THE CONTEXT CLASS
# ------------------------------------------------------------------------------
class ManagedTradeOrder:
    """
    THE STATE CONTEXT:
    Maintains an active reference to an IOrderLifecycleState instance.
    All state transitions pass through this class.
    """
    def __init__(self, order_id: str, symbol: str, total_quantity: float):
        self.order_id = order_id
        self.symbol = symbol
        self.total_quantity = total_quantity
        self.filled_quantity: float = 0.0
        # Initial State
        self._state: IOrderLifecycleState = PendingValidationState()

    @property
    def status(self) -> str:
        return self._state.status_name

    def transition_to(self, new_state: IOrderLifecycleState) -> None:
        """Internal hook for state objects to advance context lifecycle."""
        self._state = new_state

    def validate(self) -> None:
        self._state.validate(self)

    def fill(self, quantity: float) -> None:
        self._state.fill(self, quantity)

    def cancel(self) -> None:
        self._state.cancel(self)

import pytest
from nexuscore.fees.strategy import (
    FeeComputationContext, RetailFlatPercentageStrategy,
    MakerTakerTieredStrategy, ZeroFeePromotionalStrategy
)
from nexuscore.clearing.template import (
    UsSecClearingPipeline, EuMifidClearingPipeline
)
from nexuscore.orders.state_machine import (
    ManagedTradeOrder, IllegalStateTransitionError
)

class TestBehavioralEnginesSuite:
    """Verifies Strategy swapping, Template Method invariant flows, and State transitions."""

    def test_strategy_pattern_dynamic_algorithm_swapping(self):
        ctx = FeeComputationContext(RetailFlatPercentageStrategy())
        assert ctx.compute(notional=100_000.0, is_maker=False) == 200.0  # 0.20%

        # Swap Strategy at runtime to MakerTaker
        ctx.set_strategy(MakerTakerTieredStrategy())
        assert ctx.compute(notional=100_000.0, is_maker=True) == 20.0   # 0.02% maker
        assert ctx.compute(notional=100_000.0, is_maker=False) == 80.0  # 0.08% taker

        # Swap to Zero Fee Promo
        ctx.set_strategy(ZeroFeePromotionalStrategy())
        assert ctx.compute(notional=100_000.0, is_maker=False) == 0.0

    def test_template_method_regional_clearing_invariants(self):
        us_pipeline = UsSecClearingPipeline()
        eu_pipeline = EuMifidClearingPipeline()

        us_res = us_pipeline.execute_clearing("tx_us_01", gross_amount=50_000.0)
        eu_res = eu_pipeline.execute_clearing("tx_eu_01", gross_amount=50_000.0)

        # Verify Invariant sequence execution with regional hook differences:
        assert us_res["status"] == "SETTLED"
        assert us_res["compliance_ref"] == "FINRA_OATS_REC_tx_us_01"
        assert us_res["tax"] == 1.39  # US SEC Fee

        assert eu_res["status"] == "SETTLED"
        assert eu_res["compliance_ref"] == "ESMA_MIFIR_RTS22_tx_eu_01"
        assert eu_res["tax"] == 100.0  # EU FTT (0.2%)

    def test_state_pattern_valid_lifecycle_transitions(self):
        order = ManagedTradeOrder("ord_1", "BTC/USD", total_quantity=10.0)
        assert order.status == "PENDING_VALIDATION"

        # Legal transition: validate
        order.validate()
        assert order.status == "APPROVED"

        # Legal transition: partial fill
        order.fill(4.0)
        assert order.status == "PARTIALLY_FILLED"
        assert order.filled_quantity == 4.0

        # Legal transition: complete fill
        order.fill(6.0)
        assert order.status == "FILLED"
        assert order.filled_quantity == 10.0

    def test_state_pattern_blocks_illegal_transitions(self):
        order = ManagedTradeOrder("ord_2", "ETH/USD", total_quantity=5.0)

        # ILLEGAL: Cannot fill an order before it is validated!
        with pytest.raises(IllegalStateTransitionError, match="Cannot fill order in state: PENDING_VALIDATION"):
            order.fill(2.0)

        # Advance to FilledState
        order.validate()
        order.fill(5.0)
        assert order.status == "FILLED"

        # ILLEGAL: Cannot cancel an already FILLED order!
        with pytest.raises(IllegalStateTransitionError, match="Cannot cancel order in state: FILLED"):
            order.cancel()
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Stateful Strategies (Concurrency Corrupter)

Writing Strategy classes that store mutable caller data as internal instance variables: self.last_calculated_amount = amt.

Why this causes race conditions: Strategy objects are typically shared across multiple concurrent worker threads. If a strategy holds mutable internal state from one caller, another concurrent thread's calculation will overwrite that state mid-flight! Strategies must be strictly stateless. Pass all required inputs as method parameters.

❌ The State Object Memory Leak

Instantiating new state objects on every transition: self.state = NewState() without clearing bidirectional references between context and state.

Why this causes memory bloat: In high-frequency systems processing millions of transitions per minute, creating new state objects causes high GC allocation churn. If state objects are completely stateless, reuse singleton/shared flyweight state instances instead of instantiating new objects on every transition!
