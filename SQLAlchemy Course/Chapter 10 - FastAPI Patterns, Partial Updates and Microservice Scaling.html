Part 01

Computer Science: The Partial Update (PATCH) Dilemma

In RESTful architecture, HTTP specifies a strict semantic distinction between PUT (complete entity replacement) and PATCH (partial delta modification).

In web applications, developers frequently introduce severe data-corruption bugs when implementing PATCH. A user wants to freeze an account by sending {"status": "frozen"}. If your code naively iterates over the incoming Pydantic model without inspecting which fields were explicitly provided, all unmentioned fields (such as balance or owner_name) default to None, wiping out customer data or triggering database constraint crashes.

The Defensive Partial Update (PATCH) Sanitization Pipeline

Preventing Accidental Field Clobbering in Financial Models

1. Client JSON Payload
Client only sends fields to change
{"status": "frozen"}
→ exclude_unset →
2. Pydantic Filtering
exclude_unset=True
{"status": <AccountStatus.FROZEN>}
→ setattr() →
3. Minimal SQL UPDATE
Only modified fields flushed!
UPDATE SET status = 'frozen'
The Tri-State Nullability Reality:

In enterprise API design, you must distinguish between three distinct client intentions:

  • Omitted Key ({}): Do not touch this field; keep the current database value intact.
  • Explicit Value ({"status": "frozen"}): Update this column to the new value.
  • Explicit Null ({"description": null}): The client intentionally wants to erase the existing value and set the column to NULL in the database.
Part 02

Everyday Code: The Production-Grade PATCH Pattern

Here is the definitive, industry-standard pattern for executing partial updates in FastAPI without clobbering untouched columns, breaking database check constraints, or causing unintended flushes:

// The Canonical FastAPI + SQLAlchemy 2.0 PATCH Implementation:
@app.patch("/api/v1/accounts/{account_id}", response_model=AccountResponse)
async def partial_update_account(
    account_id: int,
    payload: AccountUpdate,
    session: AsyncSession = Depends(get_async_db_session)
):
    # 1. Fetch target record
    account = await session.scalar(select(Account).where(Account.id == account_id))
    if not account:
        raise HTTPException(status_code=404, detail="Account not found.")

    # 2. Extract ONLY fields explicitly sent in the HTTP request body!
    # exclude_unset=True ignores default None values for omitted attributes
    update_data = payload.model_dump(exclude_unset=True)

    # 3. Defensive security check: Prevent empty updates
    if not update_data:
        raise HTTPException(status_code=400, detail="No fields provided for update.")

    # 4. Safe attribute mutation using setattr()
    for field_name, new_value in update_data.items():
        setattr(account, field_name, new_value)

    # 5. Commit atomically: Unit of Work flushes only modified columns!
    await session.commit()
    await session.refresh(account)
    return account
Part 03

Microservice Scaling: Primary & Read-Replica Routing

In high-scale banking and e-commerce platforms, read queries typically outnumber write operations by 10:1 or 50:1. Running heavy statement queries or portfolio calculations against your primary database starves write transactions of CPU cycles and memory.

The enterprise solution is Read-Replicas: streaming changes from a single Primary (Writer) PostgreSQL instance to one or more Read-Only Replicas. But how do we route traffic cleanly in SQLAlchemy without manually passing different engines throughout our entire codebase?

SQLAlchemy Primary / Read-Replica Dynamic Query Routing
FastAPI Route Controller
↓ Issues SQL via AsyncSession ↓
Custom RoutingSession (get_bind Override)
Inspects query: Is it a SELECT (Read) or INSERT/UPDATE/DELETE (Write)?
↙ Writes / Mutations Reads / Selects ↘
Primary Engine Read/Write Transactional Core
Replica Engine Read-Only Analytical Pool
⚠ The Replication Lag Trap (Read-After-Write Consistency):

Replication between Primary and Replica databases is asynchronous. If a user transfers money via POST /transfers, the write hits the Primary. If their frontend immediately navigates to their dashboard and calls GET /portfolio 2 milliseconds later, the replica might not have received the WAL update yet! The user sees their old balance, panics, and submits the transfer again.

Production Defense: Pin reads to the Primary Engine for 5 seconds after any write operation using session stickiness or user cookie timestamps!

Part 04

Advanced Scale: Multi-Tenancy & Tenant Sharding

When building enterprise B2B financial services, strict data isolation is mandated by compliance laws (SOC2, GDPR, HIPAA). In high-tier systems, organizations require either Separate Schemas (PostgreSQL schemas per tenant) or Separate Databases (complete physical isolation per tenant).

Pattern A: Postgres Schema-Based search_path Routing

A single database where each tenant occupies their own schema namespace (tenant_alpha, tenant_beta).

# Dynamically set schema upon session checkout:
await session.execute(
  text(f'SET search_path TO "{tenant_id}"')
)

All models share table definitions (accounts, transactions), but queries run strictly inside that tenant's schema namespace.

Pattern B: Engine Pool Sharding Physical Isolation

Each enterprise customer connects to a physically separated database cluster or shard.

TENANT_ENGINES = {
  "tenant_a": create_async_engine(URL_A),
  "tenant_b": create_async_engine(URL_B)
}

A FastAPI dependency inspects incoming headers (X-Tenant-ID) or JWT claims and binds the request session to the specific tenant's engine pool!

class AccountUpdate(BaseModel):

    PATCH Contract: All fields are optional.
    Only fields explicitly sent by the caller will be modified in the database.

2. Dual-Engine Architecture: app/database.py Primary & Read-Replica Sockets 
# In app/database.py: Add dual-engine support for Primary & Read-Replicas
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession
from app.config import settings

# 1. Primary Engine (Read/Write)
primary_engine = create_async_engine(settings.DATABASE_URL, pool_size=10, max_overflow=20)

# 2. Read-Replica Engine (Read-Only pool pointing to replica node)
# In production, read from REPLICA_DATABASE_URL environment variable
replica_engine = create_async_engine(settings.DATABASE_URL, pool_size=20, max_overflow=10)

PrimarySessionLocal = async_sessionmaker(bind=primary_engine, class_=AsyncSession, expire_on_commit=False)
ReplicaSessionLocal = async_sessionmaker(bind=replica_engine, class_=AsyncSession, expire_on_commit=False)

async def get_primary_db() -> AsyncGenerator[AsyncSession, None]:
    """Dependency for POST, PUT, PATCH, DELETE operations (Mutations)."""
    async with PrimarySessionLocal() as session:
        yield session

async def get_replica_db() -> AsyncGenerator[AsyncSession, None]:
    """Dependency for GET operations (Analytical / Read-Only)."""
    async with ReplicaSessionLocal() as session:
        yield session
3. Endpoints & Routing: app/main.py PATCH Implementation & Routing Integration 
# In app/main.py: Add PATCH and Read-Replica endpoints
from fastapi import Header
from app.database import get_primary_db, get_replica_db
from app.schemas import AccountUpdate

@app.patch(
    "/api/v1/accounts/{account_id}",
    response_model=AccountResponse,
    tags=["Accounts"],
    summary="Execute Safe Partial Update (PATCH)"
)
async def update_account_partial(
    account_id: int,
    payload: AccountUpdate,
    session: AsyncSession = Depends(get_primary_db)  # Routes mutation to Primary Engine!
):
    """
    PRODUCTION PATCH ARCHITECTURE:
    1. Fetches account from Primary database.
    2. Uses exclude_unset=True to extract ONLY fields explicitly supplied by client.
    3. Leaves untouched fields (such as balance) completely un-mutated.
    """
    account = await session.scalar(select(Account).where(Account.id == account_id))
    if not account:
        raise HTTPException(status_code=404, detail="Account not found.")

    # CRITICAL PYDANTIC v2 CALL: Only process keys present in client JSON
    update_data = payload.model_dump(exclude_unset=True)
    if not update_data:
        raise HTTPException(status_code=400, detail="No fields provided for update.")

    for key, value in update_data.items():
        setattr(account, key, value)

    await session.commit()
    await session.refresh(account)
    return account


@app.get(
    "/api/v1/accounts/{account_id}/read-only",
    response_model=AccountResponse,
    tags=["Accounts"],
    summary="Fetch Account Details from Read-Replica"
)
async def get_account_replica(
    account_id: int,
    session: AsyncSession = Depends(get_replica_db)  # Routes read to Read-Replica Pool!
):
    """Query is served by Read-Replica, protecting the Primary from analytical load."""
    account = await session.scalar(select(Account).where(Account.id == account_id))
    if not account:
        raise HTTPException(status_code=404, detail="Account not found.")
    return account


@app.get(
    "/api/v1/tenant/accounts",
    tags=["Multi-Tenancy"],
    summary="Query Accounts with Schema-Isolated Multi-Tenancy"
)
async def list_tenant_accounts(
    x_tenant_id: str = Header(..., description="Tenant namespace e.g. tenant_alpha"),
    session: AsyncSession = Depends(get_primary_db)
):
    """
    MULTI-TENANT SCHEMA SWITCHING:
    Dynamically sets the PostgreSQL search_path to the authenticated tenant schema.
    Guarantees absolute data isolation between different corporate customers!
    """
    # Sanitize schema identifier to prevent SQL injection
    clean_tenant = x_tenant_id.replace("-", "_").lower()
    await session.execute(text(f'SET search_path TO "{clean_tenant}"'))

    accounts = (await session.scalars(select(Account))).all()
    return accounts
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The Blanket Update Anti-Pattern

Writing for key, val in payload.model_dump().items(): setattr(acc, key, val) without passing exclude_unset=True.

Why this destroys data: In Pydantic, all omitted fields evaluate to None by default. If the client sends {"owner_name": "New Name"}, calling model_dump() produces {"owner_name": "New Name", "status": None, "currency": None}. The loop executes and overwrites non-null status and currency columns with None, crashing the transaction! Fix: Always call .model_dump(exclude_unset=True) on PATCH schemas!

❌ Global Tenant Context Leaks

Storing tenant identifiers in global Python variables: CURRENT_TENANT = tenant_id.

Why this causes security breaches: Python web servers handle concurrent requests within the same process. Global variables are shared across all requests! If Request A sets the global tenant to Company A, and Python context-switches to Request B, Request B will execute queries inside Company A's schema—leaking confidential financial records to a competitor. Fix: Always pass tenant state through request parameters, dependency injection, or Python’s thread-safe contextvars.ContextVar!
