Part 01

Computer Science: Schema Drift & The Revision DAG

In production, relational databases are stateful, long-lived infrastructure. Unlike stateless application containers that can be deleted and redeployed at will, the database accumulates gigabytes of customer state.

Calling Base.metadata.create_all(bind=engine) emits CREATE TABLE IF NOT EXISTS. It only creates tables that are completely missing. It cannot alter existing columns, add check constraints, adjust index types, or rename fields. Over time, code definitions and database schemas diverge—a catastrophic state known as Schema Drift.

The Alembic Revision Directed Acyclic Graph (DAG)

How Alembic Tracks Version History Inside the Database

Rev: a1b2c3d4e5f6
"create_initial_tables"
down_revision = None
→ upgrade →
Rev: f6e5d4c3b2a1
"add_currency_to_accounts"
down_revision = "a1b2c3d4e5f6"
→ upgrade →
table "alembic_version"
Physical DB Tracker Row
version_num: "f6e5d4c3b2a1"
The Migration Mechanism:

Alembic maintains a physical 1-row table inside your database named alembic_version. When you execute alembic upgrade head, Alembic reads the current version_num from the database, inspects the migration files in alembic/versions/, builds a dependency graph via down_revision pointers, and executes the upgrade() functions sequentially until the database reaches the target revision head.

Part 02

Inside the Engine: Hardening alembic/env.py

When you run alembic init alembic, the default configuration file (alembic/env.py) is completely disconnected from your application’s models and environment settings.

To make Alembic production-ready, we must configure three critical architectural hooks inside alembic/env.py:

1. Model Binding

target_metadata

By default, target_metadata = None. You must point this to Base.metadata and import all your models (Account, Transaction). Without this, --autogenerate detects zero tables!

2. Type Detection

compare_type=True

By default, Alembic ignores column type changes! If you change String(50) to String(100), or alter numeric precision, Alembic does nothing unless compare_type=True is explicitly enabled.

3. SQLite Safety

render_as_batch=True

SQLite does not support ALTER COLUMN or DROP CONSTRAINT. Enabling render_as_batch=True instructs Alembic to create a shadow copy table, transfer rows, and swap tables seamlessly.

The Autogenerate Radar: What Alembic Sees vs. Misses

Schema Mutation Autogenerate Support Required Engineering Intervention
Adding or Dropping Tables ✓ Fully Supported Automatic op.create_table / op.drop_table
Adding or Dropping Columns ✓ Fully Supported Automatic op.add_column / op.drop_column
Renaming Tables or Columns ✗ Dangerous Failure Alembic emits DROP old_column + ADD new_column, destroying data! Must manually edit to use op.alter_column(..., new_column_name=...).
Changing Column Types • Conditional Requires compare_type=True in env.py
Part 03

The 3-Step Zero-Downtime Non-Nullable Data Backfill

Consider this real-world scenario: LedgerCore has 500,000 existing accounts in production. The business mandates that every account must have a currency: Mapped[str] = mapped_column(String(3), nullable=False).

If you run alembic revision --autogenerate and apply it, PostgreSQL will immediately abort with: ERROR: column "currency" contains null values! You cannot add a NOT NULL column to a table that already contains rows without providing a value for every existing row.

The 3-Step Zero-Downtime Data Migration Pipeline
Step 1: Add Nullable

Add the new column with nullable=True. Existing rows receive NULL without error.

batch_op.add_column(...)
→ backfill →
Step 2: Data Backfill

Execute an inline SQL update to populate historical rows with the default currency code: 'USD'.

op.execute("UPDATE accounts...")
→ enforce →
Step 3: Alter to NOT NULL

Now that zero NULL rows remain, safely lock the constraint to nullable=False!

batch_op.alter_column(...)
Part 04

Team Engineering: Branch Divergence & alembic merge

In engineering teams, multiple developers work on separate Git feature branches simultaneously:

  • Developer Alice branches from Revision Rev A and creates Rev B (adding user settings).
  • Developer Bob branches from Revision Rev A at the same time and creates Rev C (adding audit logs).

When both branches merge into the main branch, Alembic fails on deployment with a fatal error: CommandError: Multiple head revisions are present for given argument 'head'.

Resolving Multiple Head Revisions via alembic merge
Base: Revision A
↙ Alice Bob ↘
Revision B (Head 1) down_rev = A
Revision C (Head 2) down_rev = A
↓ alembic merge -m "merge_heads" B C ↓
Revision D (Merge Revision) down_revision = ('B', 'C')
The Terminal Fix:

Never manually edit revision IDs in the Python files! Simply run alembic merge heads -m "merge branch conflicts". Alembic automatically creates a new revision file with a tuple of both heads as its down_revision, re-unifying the DAG into a single head.

1. Hardened Migration Runner: alembic/env.py Target Metadata & Batch Mode 
# ==============================================================================
# LedgerCore Backend - Hardened Alembic Environment Runner (Milestone 08)
# ==============================================================================

from logging.config import fileConfig
from sqlalchemy import engine_from_config, pool
from alembic import context

# 1. Import application configuration and declarative Base
from app.config import settings
from app.database import Base

# CRITICAL: Import all models so Base.metadata registers every table!
from app.models import Account, Transaction, TransferTransaction, FeeTransaction

config = context.config

# Overwrite sqlalchemy.url dynamically from our validated Pydantic settings
config.set_main_option("sqlalchemy.url", settings.DATABASE_URL)

if config.config_file_name is not None:
    fileConfig(config.config_file_name)

# Bind target_metadata for autogenerate detection
target_metadata = Base.metadata

def run_migrations_online() -> None:
    """Run migrations in 'online' mode against an active database connection."""
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )

    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata,
            # HARDENING HOOK 1: Catch changes in column types and sizes
            compare_type=True,
            # HARDENING HOOK 2: Catch changes in server defaults
            compare_server_default=True,
            # HARDENING HOOK 3: Cross-database compatibility (enables SQLite table-swapping)
            render_as_batch=True,
        )

        with context.begin_transaction():
            context.run_migrations()

if context.is_offline_mode():
    # Emits raw SQL DDL scripts without connecting (for DBA review)
    context.configure(url=settings.DATABASE_URL, target_metadata=target_metadata, literal_binds=True)
    with context.begin_transaction():
        context.run_migrations()
else:
    run_migrations_online()
2. Adding Multi-Currency to Account: app/models.py Schema Evolution 
# In app/models.py: Add currency field to Account model
class Account(Base, TimestampMixin, SoftDeleteMixin):
    __tablename__ = "accounts"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    uuid: Mapped[uuid.UUID] = mapped_column(default=uuid.uuid4, unique=True, index=True, nullable=False)
    account_number: Mapped[str] = mapped_column(String(32), unique=True, index=True, nullable=False)
    owner_name: Mapped[str] = mapped_column(String(100), nullable=False)
    balance: Mapped[Decimal] = mapped_column(Numeric(14, 4), default=Decimal("0.0000"), nullable=False)

    # --------------------------------------------------------------------------
    # NEW BUSINESS FIELD (Milestone 08): ISO-4217 Currency Code (USD, EUR, GBP)
    # Non-nullable in Python and DB!
    # --------------------------------------------------------------------------
    currency: Mapped[str] = mapped_column(String(3), default="USD", nullable=False)

    status: Mapped[AccountStatus] = mapped_column(SQLEnum(AccountStatus, native_enum=False), default=AccountStatus.ACTIVE, nullable=False)
    version_id: Mapped[int] = mapped_column(default=1, nullable=False)

    transactions: Mapped[list["Transaction"]] = relationship(back_populates="account")

    __mapper_args__ = {
        "version_id_col": version_id
    }

    __table_args__ = (
        CheckConstraint("balance >= 0", name="ck_account_balance_non_negative"),
    )
3. The 3-Step Data Backfill Migration: alembic/versions/0002_add_currency.py Zero-Downtime Data Migration Script 
"""add_currency_to_accounts

Revision ID: 0002_add_currency
Revises: 0001_initial_tables
Create Date: 2026-11-01 10:00:00.000000
"""
from alembic import op
import sqlalchemy as sa

revision = "0002_add_currency"
down_revision = "0001_initial_tables"
branch_labels = None
depends_on = None

def upgrade() -> None:
    # --------------------------------------------------------------------------
    # STEP 1: Add the column as nullable=True to accept existing rows
    # --------------------------------------------------------------------------
    with op.batch_alter_table("accounts", schema=None) as batch_op:
        batch_op.add_column(sa.Column("currency", sa.String(length=3), nullable=True))

    # --------------------------------------------------------------------------
    # STEP 2: DATA BACKFILL
    # Populate all existing historical accounts with default 'USD'
    # --------------------------------------------------------------------------
    op.execute("UPDATE accounts SET currency = 'USD' WHERE currency IS NULL")

    # --------------------------------------------------------------------------
    # STEP 3: Enforce strict NOT NULL constraint now that 0 nulls remain!
    # --------------------------------------------------------------------------
    with op.batch_alter_table("accounts", schema=None) as batch_op:
        batch_op.alter_column("currency", existing_type=sa.String(length=3), nullable=False)

def downgrade() -> None:
    with op.batch_alter_table("accounts", schema=None) as batch_op:
        batch_op.drop_column("currency")
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Blindly Trusting Autogenerate on Renames

Renaming a column from owner_name to full_name, running autogenerate, and applying it immediately.

Why this causes catastrophic data loss: Relational databases do not communicate intent. Alembic sees that owner_name disappeared and full_name appeared. Autogenerate generates: op.drop_column('owner_name') followed by op.add_column('full_name')! All existing customer names are permanently deleted! Fix: Always inspect generated scripts. Manually replace the drop/add calls with op.alter_column(..., new_column_name='full_name').

❌ Running Migrations Inside Application Worker Startup

Placing alembic.command.upgrade(config, 'head') inside your FastAPI lifespan startup hook.

Why this deadlocks production deployments: If your cluster starts 4 pods concurrently, all 4 processes execute alembic upgrade simultaneously at the exact same millisecond. They collide on database table locks, corrupting the alembic_version table. Rule: Migrations must run exactly once in an isolated CI/CD step or Kubernetes Job before application containers start.
