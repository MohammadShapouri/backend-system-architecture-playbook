Part 01

Computer Science: Event Loops vs. OS Threadpools

When you run synchronous SQLAlchemy code inside an async def FastAPI route, you commit the "Sync Library Trap": the blocking DBAPI network call halts Python's single-threaded event loop, freezing all concurrent requests.

To prevent this freeze, traditional synchronous architectures declare routes as plain def. FastAPI detects the synchronous function and offloads execution to an AnyIO **worker threadpool** (capped at 40 threads by default). But OS threads carry significant systems overhead:

Concurrency Architecture: Worker Threadpools vs. Non-Blocking Event Loops

Handling 5,000 Concurrent Database Queries

1. Synchronous Threadpool (def) Thread-Bound

Each concurrent query requires an individual operating system thread:

Thread 1: [Blocked waiting for PostgreSQL response...]
Thread 2: [Blocked waiting for PostgreSQL response...]
... 38 Threads Active (Threadpool 100% Saturation) ...
→ Request #41 is queued! Latency surges.
  • Each thread allocates 8MB stack memory in the OS.
  • CPU thrashes on register and cache-line context switches.
  • Cannot scale past ~200-500 concurrent connections per container.
2. True Async Event Loop (async def) Socket Multiplexed

A single OS thread manages thousands of non-blocking sockets using Linux epoll:

Task 1: awaits db.execute() → registers socket with epoll
Event Loop immediately switches to Task 2, 3, 4...
When DB packets arrive, kernel wakes coroutine instantly!
→ Zero threads blocked. Flat RAM consumption.
  • Each coroutine occupies less than 1KB of Python RAM.
  • Zero OS thread context-switching overhead.
  • Easily holds 10,000+ concurrent connections on a single container.
Part 02

Under the Hood: The Greenlet Bridge

SQLAlchemy’s ORM architecture was originally designed around synchronous paradigms: accessing account.transactions is a synchronous Python property access, not an await expression.

To enable non-blocking database drivers (asyncpg, aiosqlite) without completely throwing away 15 years of battle-tested ORM internals, SQLAlchemy utilizes the C-extension library greenlet:

The Greenlet Execution Context Switch Pipeline
1. User Coroutine await session.execute(stmt)
→ greenlet_spawn →
2. Synchronous ORM Core Compiles SQL, generates mappings in isolated greenlet
→ context switch →
3. asyncpg / aiosqlite Awaits non-blocking socket I/O on main event loop
How it Works:

When you call await session.execute(...), SQLAlchemy spawns an isolated micro-thread of execution via greenlet_spawn. The synchronous ORM logic runs inside this greenlet. Whenever the greenlet reaches a database I/O boundary, it suspends itself, yields control back to the outer Python asyncio event loop to await the network socket, and resumes seamlessly when the bytes arrive!

Part 03

The MissingGreenlet Exception & Solutions

Almost every engineer migrating to async SQLAlchemy encounters this runtime crash: sqlalchemy.exc.MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here. Was IO attempted in an unexpected place?

Why Does MissingGreenlet Happen?

Python property access is fundamentally synchronous. When you write account.transactions, Python's language grammar does not permit an implicit await.

If transactions was not eager-loaded, SQLAlchemy attempts to trigger a lazy-load query. But because there is no await expression attached to property access, SQLAlchemy cannot yield to the event loop. The driver cannot emit I/O, and the greenlet bridge panics with MissingGreenlet!

Solution 1: Eager Load Upfront (Recommended)

Always explicitly load relationships in the initial query using selectinload() or joinedload(): 

stmt = (
    select(Account)
    .options(selectinload(Account.transactions))
)
account = await session.scalar(stmt)
# Now safe to access account.transactions with zero I/O!
Solution 2: Explicit await session.refresh()

If you already hold an instance and need to populate a relationship later, use the asynchronous refresh method: 

await session.refresh(
    account, 
    attribute_names=["transactions"]
)
# Awaits explicitly on the event loop cleanly!
Part 04

Schema Evolution: Asynchronous Alembic Architecture

When your application switches its connection URL to an asynchronous driver like postgresql+asyncpg:// or sqlite+aiosqlite:///, the standard synchronous Alembic runner from Chapter 08 crashes because it attempts to use synchronous DBAPI connection methods against an async driver.

Alembic provides a native asynchronous template using async_engine_from_config and connection.run_sync():

// How Alembic Executes Synchronous DDL over an Async Connection in env.py:
import asyncio
from sqlalchemy.ext.asyncio import async_engine_from_config

def do_run_migrations(connection):
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        compare_type=True,
        render_as_batch=True
    )
    with context.begin_transaction():
        context.run_migrations()

async def run_async_migrations():
    # 1. Spawn asynchronous engine from configuration
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    # 2. Acquire async connection and run migrations via run_sync bridge
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()

def run_migrations_online():
    asyncio.run(run_async_migrations())

from sqlalchemy.ext.asyncio import (
    create_async_engine, async_sessionmaker, AsyncSession, AsyncEngine

# 1. Configure Async Engine singleton
engine_kwargs = {
    "echo": settings.DB_ECHO_SQL,
}

if settings.DATABASE_URL.startswith("sqlite"):
    engine_kwargs["connect_args"] = {"check_same_thread": False}
else:
    engine_kwargs.update({
        "poolclass": AsyncAdaptedQueuePool,
        "pool_size": settings.DB_POOL_SIZE,
        "max_overflow": settings.DB_MAX_OVERFLOW,
        "pool_pre_ping": True,
    })

async_engine: AsyncEngine = create_async_engine(settings.DATABASE_URL, **engine_kwargs)

# 2. AsyncSession Factory
AsyncSessionLocal = async_sessionmaker(
    bind=async_engine,
    class_=AsyncSession,
    autocommit=False,
    autoflush=False,
    expire_on_commit=False  # CRITICAL: Prevents MissingGreenlet on response serialization!
)

# 3. FastAPI Asynchronous Yielding Dependency
async def get_async_db_session() -> AsyncGenerator[AsyncSession, None]:
    """Yields an isolated AsyncSession cleanly attached to the request event loop."""
    async with AsyncSessionLocal() as session:
        yield session
3. Native Async API Endpoints: app/main.py Asynchronous Operations 
# In app/main.py: Refactored async endpoints
from fastapi import FastAPI, Depends, HTTPException, status
from sqlalchemy import select
from sqlalchemy.orm import selectinload
from sqlalchemy.ext.asyncio import AsyncSession
from app.database import async_engine, get_async_db_session
from app.models import Account, AccountStatus, TransferTransaction
from app.schemas import AccountCreate, AccountResponse, TransferRequest, TransferResponse

@app.post("/api/v1/accounts", response_model=AccountResponse, status_code=status.HTTP_201_CREATED)
async def create_account(
    payload: AccountCreate,
    session: AsyncSession = Depends(get_async_db_session)
):
    # Non-blocking query execution
    stmt = select(Account).where(Account.account_number == payload.account_number)
    existing = await session.scalar(stmt)
    if existing:
        raise HTTPException(status_code=409, detail="Account number registered.")

    new_account = Account(
        account_number=payload.account_number,
        owner_name=payload.owner_name,
        balance=payload.initial_balance,
        currency="USD"
    )
    session.add(new_account)
    await session.commit()
    await session.refresh(new_account)
    return new_account


@app.post("/api/v1/transfers", response_model=TransferResponse)
async def transfer_funds_async(
    payload: TransferRequest,
    session: AsyncSession = Depends(get_async_db_session)
):
    """
    NATIVE ASYNCHRONOUS ROW-LOCKED TRANSFER:
    Acquires exclusive locks using .with_for_update() non-blockingly over TCP!
    """
    sender_basic = await session.scalar(select(Account.id).where(Account.account_number == payload.sender_account_number))
    recipient_basic = await session.scalar(select(Account.id).where(Account.account_number == payload.recipient_account_number))

    if not sender_basic or not recipient_basic:
        raise HTTPException(status_code=404, detail="Account not found.")

    sorted_ids = sorted([sender_basic, recipient_basic])

    try:
        stmt = (
            select(Account)
            .where(Account.id.in_(sorted_ids))
            .order_by(Account.id.asc())
            .with_for_update()
        )
        locked_accounts = (await session.scalars(stmt)).all()
        account_map = {acc.id: acc for acc in locked_accounts}

        sender = account_map[sender_basic]
        recipient = account_map[recipient_basic]

        if sender.balance < payload.amount:
            raise HTTPException(status_code=400, detail="Insufficient funds.")

        sender.balance -= payload.amount
        recipient.balance += payload.amount

        transfer_record = TransferTransaction(
            account_id=sender.id,
            amount=payload.amount,
            destination_account_number=recipient.account_number,
            routing_reference=payload.routing_reference
        )
        session.add(transfer_record)
        await session.commit()

        return TransferResponse(
            status="success",
            transfer_uuid=transfer_record.uuid,
            sender_account_number=sender.account_number,
            recipient_account_number=recipient.account_number,
            transferred_amount=payload.amount,
            fee_applied=False,
            sender_new_balance=sender.balance
        )
    except HTTPException:
        await session.rollback()
        raise
    except Exception as exc:
        await session.rollback()
        raise HTTPException(status_code=500, detail=str(exc))
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Sharing AsyncSessions Across asyncio.gather()

Passing the same session to multiple coroutines running in parallel via asyncio.gather(task1(session), task2(session)).

Why this corrupts transactions: An AsyncSession is not task-safe or concurrent-safe. It wraps a single underlying database connection socket. If two concurrent coroutines try to emit queries across the same socket simultaneously, asyncpg will immediately crash with InterfaceError: cannot perform operation: another operation is in progress. Rule: Never share an AsyncSession across concurrent tasks. Each task must check out its own session from the factory!

❌ Forgetting to await session.commit()

Writing session.commit() without the await keyword.

Why this causes silent failures: In an async session, session.commit() returns a coroutine object. If you omit await, Python creates the coroutine but never executes it! The transaction never commits to disk, the HTTP request returns successfully, but the database changes vanish completely into thin air with zero errors raised.
