Part 01

Computer Science: The Floating-Point Catastrophe

In software engineering, using a floating-point data type (Float, DOUBLE PRECISION, or Python's native float) for monetary balances, accounting entries, or pricing is an immediate production liability.

IEEE 754 Binary Floating-Point vs. Exact Decimal Representation

Why Computers Cannot Store 10 Cents Accurately in Binary

IEEE 754 Floating-Point (Float) Unsafe for Money

Computers count in base 2. In binary, numbers like $0.10$ ($1/10$) produce an infinite repeating fraction:

0.10 → 0.000110011001100110011... (binary)
0.1 + 0.2 == 0.300000000000000044408920985...

✗ Over millions of ledger entries, fractional truncation causes balance sheets to go out of balance, violating GAAP/IFRS accounting standards.

Exact Fixed-Point (Numeric / Decimal) Financial Standard

Stores numbers as base-10 scaled integers with explicit scale and precision definitions:

Numeric(14, 4) → Stores $12,500.5000 as scaled int 125005000
Decimal('0.10') + Decimal('0.20') == Decimal('0.3000')

✓ 100% deterministic precision. Python maps SQLAlchemy Numeric columns directly to decimal.Decimal objects.

// Anatomy of Numeric(precision, scale):

Numeric(precision=14, scale=4) means the column can store a maximum of 14 total digits (the precision), of which 4 digits are reserved after the decimal point (the scale). This allows values up to 9,999,999,999.9999—large enough for multi-billion-dollar enterprise ledgers, with 4 decimal places to handle currency exchange spreads, crypto micro-fees, and interest rates.

Part 02

The 2.0 Paradigm: Mapped[] & mapped_column()

In SQLAlchemy 1.x, models were declared using untyped columns: balance = Column(Numeric(14, 4), nullable=False). Python type checkers (Mypy, Pyright) and IDEs had no idea what Python type account.balance represented at runtime, leading to frequent runtime bugs and requiring verbose plugin extensions.

SQLAlchemy 2.0 rewrote the declarative layer around Python 3 PEP 484 type annotations. The type annotation is now the single source of truth for runtime ORM typing and static analysis:

Legacy 1.x (Untyped Declarative)
# Legacy: IDEs see `id` as Column[Any], not int
class Account(Base):
    __tablename__ = "accounts"
    id = Column(Integer, primary_key=True)
    balance = Column(Numeric(14, 4), nullable=False)
    name = Column(String(100), nullable=True)

Requires third-party plugins like sqlalchemy-stubs. Nullability must be repeated across both column definitions and documentation.

Modern 2.0 (Type-Annotated Declarative)
# Modern: Python type dictates nullability & IDE type
class Account(Base):
    __tablename__ = "accounts"
    id: Mapped[int] = mapped_column(primary_key=True)
    balance: Mapped[Decimal] = mapped_column(Numeric(14, 4))
    name: Mapped[Optional[str]] = mapped_column(String(100))

Full IDE autocompletion. Mypy validates assignments. Nullability is automatically inferred: Optional[T] marks nullable=True automatically!

How 2.0 Infers Database Nullability from Type Annotations

Type Annotation Inferred DB Nullability Python Runtime Type Generated DDL
Mapped[str] nullable=False str (Cannot be None) VARCHAR NOT NULL
Mapped[Optional[str]] nullable=True str | None VARCHAR NULL
Mapped[Decimal] nullable=False decimal.Decimal NUMERIC(14, 4) NOT NULL

Note: You can still override nullability explicitly with mapped_column(nullable=True), but adhering to the Python type annotation is considered standard enterprise best practice.

Part 03

Primary Key Architecture: Integer vs. UUID & B-Tree Health

Choosing the identifier type for our LedgerCore tables has massive architectural consequences for database indexing, horizontal sharding, and security.

B-Tree Index Physical Layout Under Heavy Write Loads

Why Completely Random UUIDv4 Degrades PostgreSQL Performance Over Time

Sequential Keys (BigInteger / UUIDv7)

Every newly generated ID is chronologically larger than the previous one:

ID: 101 → ID: 102 → ID: 103 (Appends to Rightmost Page)
  • Inserts only append to the rightmost leaf of the B-Tree index.
  • Index pages remain densely packed (~90%+ fillfactor).
  • Hot index pages stay resident in RAM buffer cache.
Random Keys (Standard UUIDv4)

UUIDv4 generates pseudorandom bits without temporal ordering:

4f82... → 1a03... → e9b1... (Inserts Everywhere)
  • Random writes strike arbitrary leaf pages throughout the B-Tree.
  • Forces expensive Page Splits on disk, fragmenting index storage.
  • Causes high disk I/O because index pages cannot stay cached in RAM.
The LedgerCore Design Decision:

For LedgerCore, we use UUIDs for Public External IDs (preventing enumeration attacks where competitors guess transaction volume via sequential IDs like /transactions/101), and BigInteger Sequences for Internal Database Primary Keys where extreme insertion throughput and index compactness are paramount.

1. Declarative Models: app/models.py ORM Entities & Constraints 
# ==============================================================================
# LedgerCore Backend - Declarative Schema Models (Milestone 02)
# ==============================================================================

import uuid
from decimal import Decimal
from enum import Enum
from typing import Optional
from datetime import datetime, timezone
from sqlalchemy import (
    String, Numeric, DateTime, Boolean, 
    CheckConstraint, ForeignKey, Enum as SQLEnum, Index
)
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

# 1. Base Class definition for all models
class Base(DeclarativeBase):
    pass

# 2. Strict Enum definitions for Account & Transaction states
class AccountStatus(str, Enum):
    ACTIVE = "active"
    FROZEN = "frozen"
    CLOSED = "closed"

class TransactionType(str, Enum):
    DEPOSIT = "deposit"
    WITHDRAWAL = "withdrawal"
    TRANSFER = "transfer"

# ==============================================================================
# Model: Account
# ==============================================================================
class Account(Base):
    __tablename__ = "accounts"

    # Primary Key: BigInteger sequence for fast clustered index lookups
    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    
    # Public ID: UUIDv4 exposed to clients to prevent sequential enumeration
    uuid: Mapped[uuid.UUID] = mapped_column(default=uuid.uuid4, unique=True, index=True, nullable=False)
    
    # Account Holder Reference
    account_number: Mapped[str] = mapped_column(String(32), unique=True, index=True, nullable=False)
    owner_name: Mapped[str] = mapped_column(String(100), nullable=False)

    # FINANCIAL PRECISION: 14 total digits, 4 decimal places
    # Maps to decimal.Decimal in Python. Guaranteed zero floating-point drift!
    balance: Mapped[Decimal] = mapped_column(Numeric(precision=14, scale=4), default=Decimal("0.0000"), nullable=False)
    
    # Portable Enum: native_enum=False creates VARCHAR + CHECK constraint (cross-DB safe)
    status: Mapped[AccountStatus] = mapped_column(
        SQLEnum(AccountStatus, native_enum=False), 
        default=AccountStatus.ACTIVE, 
        nullable=False
    )

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc),
        nullable=False
    )

    # DEFENSIVE DATABASE CONSTRAINT: Enforce positive balance at the RDBMS level!
    __table_args__ = (
        CheckConstraint("balance >= 0", name="ck_account_balance_non_negative"),
    )


# ==============================================================================
# Model: Transaction
# ==============================================================================
class Transaction(Base):
    __tablename__ = "transactions"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    uuid: Mapped[uuid.UUID] = mapped_column(default=uuid.uuid4, unique=True, index=True, nullable=False)

    # Foreign Key binding to Account
    account_id: Mapped[int] = mapped_column(ForeignKey("accounts.id", ondelete="RESTRICT"), index=True, nullable=False)
    
    # Exact Transaction Amount
    amount: Mapped[Decimal] = mapped_column(Numeric(precision=14, scale=4), nullable=False)
    
    transaction_type: Mapped[TransactionType] = mapped_column(
        SQLEnum(TransactionType, native_enum=False), 
        nullable=False
    )

    description: Mapped[Optional[str]] = mapped_column(String(255), nullable=True)

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc),
        nullable=False
    )

    # DEFENSIVE DATABASE CONSTRAINT: Amount must never be zero or negative!
    __table_args__ = (
        CheckConstraint("amount > 0", name="ck_transaction_amount_positive"),
        Index("ix_transactions_account_created", "account_id", "created_at"),
    )

from uuid import UUID
from decimal import Decimal
from datetime import datetime
from pydantic import BaseModel, Field, ConfigDict
from app.models import AccountStatus

class AccountCreate(BaseModel):
    account_number: str = Field(..., min_length=5, max_length=32, examples=["ACC-US-98214"])
    owner_name: str = Field(..., min_length=2, max_length=100, examples=["Jane Doe"])
    initial_balance: Decimal = Field(default=Decimal("0.0000"), ge=0, examples=["1000.5000"])

class AccountResponse(BaseModel):
    uuid: UUID
    account_number: str
    owner_name: str
    balance: Decimal
    status: AccountStatus
    created_at: datetime

    # Pydantic v2 configuration to serialize from SQLAlchemy ORM instances
    model_config = ConfigDict(from_attributes=True)
3. API Wire-Up: app/main.py Creating & Reading Decimal Accounts 
# ==============================================================================
# LedgerCore Backend - API Endpoints (Milestone 02)
# ==============================================================================

from contextlib import asynccontextmanager
from fastapi import FastAPI, status, HTTPException
from sqlalchemy.orm import Session
from sqlalchemy import select

from app.config import settings
from app.database import engine, probe_database_connectivity
from app.models import Base, Account
from app.schemas import AccountCreate, AccountResponse

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Create tables on boot (Used in Dev/Test; replaced by Alembic in Chapter 8)
    Base.metadata.create_all(bind=engine)
    yield
    engine.dispose()

app = FastAPI(title=settings.APP_NAME, lifespan=lifespan)

@app.post("/api/v1/accounts", response_model=AccountResponse, status_code=status.HTTP_201_CREATED)
def create_account(payload: AccountCreate):
    """Creates a new financial account with exact Decimal balance."""
    with Session(engine) as session:
        # Verify account number uniqueness
        stmt = select(Account).where(Account.account_number == payload.account_number)
        if session.scalar(stmt):
            raise HTTPException(status_code=409, detail="Account number already registered.")

        new_account = Account(
            account_number=payload.account_number,
            owner_name=payload.owner_name,
            balance=payload.initial_balance
        )
        session.add(new_account)
        session.commit()
        session.refresh(new_account)
        return new_account
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Passing Executed Callables to Defaults

Writing created_at: Mapped[datetime] = mapped_column(default=datetime.now()).

Why this causes subtle bugs: The parentheses () execute the function once when the Python module is first imported by the server. Every row inserted for the next 3 weeks will receive the exact same static timestamp—the millisecond the server process started! Fix: Pass the callable reference without parentheses: default=lambda: datetime.now(timezone.utc).

❌ Using Naive Timestamps

Using mapped_column(DateTime) instead of DateTime(timezone=True).

Why this is dangerous: In PostgreSQL, standard DateTime compiles to TIMESTAMP WITHOUT TIME ZONE. If your server runs in UTC and your database runs in US/Eastern, or when Daylight Saving Time shifts, calculations comparing transactions become unreliable. Fix: Always specify DateTime(timezone=True).
