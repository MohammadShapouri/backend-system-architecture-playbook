Part 01

Computer Science: The Unit of Work & The Identity Map

In simplistic database libraries (like raw SQL scripts or basic Active Record patterns), modifying an object issues an immediate SQL UPDATE statement directly over the network. If your business logic updates a user's address, recalculates their tax, and adjusts their balance, it executes three separate SQL statements over three round-trips.

SQLAlchemy implements Martin Fowler’s Unit of Work and Identity Map patterns inside the Session. The Session acts as an in-memory staging area and transaction coordinator:

IM

The Identity Map (Single Source of Truth)

The Session maintains a dictionary mapping (ModelClass, primary_key) → instance. If you query Account #42 five times during a single API request, SQLAlchemy queries the database once. Subsequent queries return the exact same Python object reference in RAM:

acc_a = session.get(Account, 42)
acc_b = session.get(Account, 42)
assert acc_a is acc_b # True! Same memory pointer

Prevents conflicting updates: You cannot accidentally load two separate copies of Account #42 with conflicting balances in the same request.

UoW

Unit of Work (Dirty Tracking & Batching)

When you mutate attributes (account.balance += 50), SQLAlchemy emits no SQL immediately. The Session tracks the object as "dirty".

When you reach the transaction boundary, the Unit of Work calculates the minimal SQL changeset, reorders inserts/updates to respect foreign key hierarchies (preventing constraint violations), and flushes all changes to the database in an optimized batch.

account.balance += 50 → No SQL emitted
session.commit() → Calculates diff & emits UPDATE
Part 02

Under the Hood: The Four Entity States

At any given microsecond, an ORM model instance exists in one of four distinct lifecycle states inside Python's memory space. Understanding these states is essential to mastering when data is safe to read and avoiding the dreaded DetachedInstanceError.

The SQLAlchemy Entity State Lifecycle
1. Transient Memory Only

Created via Python constructor: acc = Account(...).

  • Not in any Session
  • No database identity (id is None)
  • Not tracked by Unit of Work
2. Pending Staged

Registered via: session.add(acc).

  • Bound to active Session
  • No SQL emitted yet
  • Will be saved on next flush
3. Persistent Synchronized

Loaded from DB query or after flush().

  • Has database primary key
  • Tracked in Identity Map
  • Attribute changes marked "dirty"
4. Detached Disconnected

Session closed via session.close().

  • Has database ID
  • Session connection severed
  • Accessing unloaded fields crashes!
Transition Trigger:

Account() (Transient) → session.add() → (Pending) → session.flush() → (Persistent) → session.close() → (Detached).

Part 03

Transaction Boundaries: flush() vs. commit() & Savepoints

Many developers treat session.flush() and session.commit() as synonymous. They operate at completely different layers of the database pipeline:

The Flush vs. Commit Execution Pipeline
1. Python Memory Objects added, modified, dirty-tracked in RAM
→ session.flush() →
2. DB Transaction Buffer SQL emitted over TCP. PKs generated, constraints checked. NOT permanent!
→ session.commit() →
3. Durable Storage (WAL) COMMIT sent. Written to WAL disk. Locks released. Permanent!
Why call session.flush()?

When you need the database to assign an autoincrement primary key ID or fire triggers, but you are not yet ready to finalize the transaction. For example: creating an Account, flushing it to obtain its id, and using that ID to insert child transaction records before committing.

Why call session.commit()?

Finalizes the entire Unit of Work. Writes all buffered SQL to the database Write-Ahead Log (WAL), releases all row-level and table-level locks, and returns the underlying connection back to the connection pool.

Savepoints & Sub-Transactions via session.begin_nested()

Handling Partial Failures Without Aborting the Entire Transaction

In financial applications, you often encounter optional sub-actions: for instance, attempting to deduct an optional service fee or send a webhook notification record. If the fee fails (e.g., negative balance check constraint), you do not want to cancel the entire core transfer.

Standard relational databases do not allow "nested" physical transactions. Instead, SQLAlchemy uses Savepoints: 

# Outer transaction starts
with Session(engine) as session:
    # 1. Primary Action: Deduct and Credit Core Transfer
    sender.balance -= Decimal("100.0000")
    recipient.balance += Decimal("100.0000")
    session.flush()

    # 2. Sub-Action: Attempt Platform Fee inside a Savepoint
    try:
        with session.begin_nested():  # Emits: SAVEPOINT sa_savepoint_1
            fee = FeeTransaction(account_id=sender.id, amount=Decimal("5.0000"), fee_code="WIRE")
            sender.balance -= fee.amount
            session.add(fee)
            session.flush()  # If this violates a check constraint, only the savepoint rolls back!
    except Exception:
        # Emits: ROLLBACK TO SAVEPOINT sa_savepoint_1
        print("Optional fee failed. Outer transfer continues unaffected!")

    # 3. Commit the entire outer transaction
    session.commit()  # Core transfer is permanently committed!

from sqlalchemy.orm import sessionmaker, Session

# ------------------------------------------------------------------------------
# CRITICAL WEB CONFIGURATION: expire_on_commit=False
# In FastAPI, response serialization happens AFTER the session commits.
# If expire_on_commit=True (default), accessing attributes outside the session
# triggers a reload query against a closed connection, crashing with DetachedInstanceError!
# ------------------------------------------------------------------------------
SessionLocal = sessionmaker(
    bind=engine,
    autocommit=False,
    autoflush=False,
    expire_on_commit=False
)

def get_db_session():
    """Dependency yielding a dedicated session with guaranteed cleanup."""
    session: Session = SessionLocal()
    try:
        yield session
    finally:
        session.close()

3. The Atomic Transfer Endpoint: app/main.py Transaction & Savepoint Engine 
# In app/main.py: Atomic transfer endpoint
from decimal import Decimal
from fastapi import Depends, HTTPException, status
from sqlalchemy import select
from sqlalchemy.orm import Session
from app.database import get_db_session
from app.models import Account, AccountStatus, TransferTransaction, FeeTransaction
from app.schemas import TransferRequest, TransferResponse

@app.post(
    "/api/v1/transfers",
    response_model=TransferResponse,
    status_code=status.HTTP_200_OK,
    tags=["Transactions"],
    summary="Execute Atomic Double-Entry Fund Transfer"
)
def transfer_funds(
    payload: TransferRequest,
    session: Session = Depends(get_db_session)
):
    """
    ATOMIC TRANSACTION PIPELINE:
    1. Loads sender and recipient accounts.
    2. Validates operational account statuses and balance sufficiency.
    3. Flushes core double-entry balance mutations & records TransferTransaction.
    4. Executes optional service fee deduction within a SAVEPOINT.
    5. Commits atomically. If any error occurs, rolls back cleanly.
    """
    # --------------------------------------------------------------------------
    # STEP 1: Query Sender and Recipient
    # --------------------------------------------------------------------------
    sender = session.scalar(
        select(Account).where(Account.account_number == payload.sender_account_number)
    )
    if not sender:
        raise HTTPException(status_code=404, detail="Sender account not found.")

    recipient = session.scalar(
        select(Account).where(Account.account_number == payload.recipient_account_number)
    )
    if not recipient:
        raise HTTPException(status_code=404, detail="Recipient account not found.")

    if sender.id == recipient.id:
        raise HTTPException(status_code=400, detail="Cannot transfer to the same account.")

    if sender.status != AccountStatus.ACTIVE or recipient.status != AccountStatus.ACTIVE:
        raise HTTPException(status_code=400, detail="Both accounts must be ACTIVE to transfer.")

    # Application-level check (backed up by database CheckConstraint!)
    if sender.balance < payload.amount:
        raise HTTPException(status_code=400, detail="Insufficient funds for transfer.")

    try:
        # ----------------------------------------------------------------------
        # STEP 2: Atomic Balance Mutations (Core Action)
        # ----------------------------------------------------------------------
        sender.balance -= payload.amount
        recipient.balance += payload.amount

        # Record polymorphic TransferTransaction bound to sender
        transfer_record = TransferTransaction(
            account_id=sender.id,
            amount=payload.amount,
            destination_account_number=recipient.account_number,
            routing_reference=payload.routing_reference
        )
        session.add(transfer_record)

        # FLUSH: Emits SQL to the DB buffer. Generates transfer_record.uuid & validates constraints
        session.flush()

        # ----------------------------------------------------------------------
        # STEP 3: Optional Fee Sub-Action inside a SAVEPOINT
        # ----------------------------------------------------------------------
        fee_applied = False
        if payload.apply_fee:
            fee_amount = Decimal("10.0000")
            try:
                # Emits: SAVEPOINT fee_subaction
                with session.begin_nested():
                    if sender.balance < fee_amount:
                        raise ValueError("Sender cannot afford wire fee.")
                    
                    sender.balance -= fee_amount
                    fee_record = FeeTransaction(
                        account_id=sender.id,
                        amount=fee_amount,
                        fee_code="WIRE_SERVICE_FEE",
                        waivable=True
                    )
                    session.add(fee_record)
                    session.flush()  # Triggers DB check constraints for the fee
                    fee_applied = True
            except Exception as fee_err:
                # Savepoint automatically rolled back! Outer transfer is preserved
                print(f"[NOTICE] Optional fee aborted: {fee_err}. Outer transfer continues.")

        # ----------------------------------------------------------------------
        # STEP 4: Commit the Transaction
        # ----------------------------------------------------------------------
        session.commit()

        return TransferResponse(
            status="success",
            transfer_uuid=transfer_record.uuid,
            sender_account_number=sender.account_number,
            recipient_account_number=recipient.account_number,
            transferred_amount=payload.amount,
            fee_applied=fee_applied,
            sender_new_balance=sender.balance
        )

    except Exception as exc:
        # GUARANTEED ROLLBACK: Discards all pending mutations if an unhandled error occurs
        session.rollback()
        raise HTTPException(
            status_code=500,
            detail=f"Atomic transfer failed: {str(exc)}"
        )
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The PendingRollbackError Trap

Catching a database exception (like a unique constraint violation) and immediately trying to run another query on the same session without calling session.rollback().

Why this crashes: When PostgreSQL encounters a SQL error inside a transaction block, it enters an aborted state (ERROR: current transaction is aborted, commands ignored until end of transaction block). SQLAlchemy mirrors this with a PendingRollbackError. You must call session.rollback() to reset the connection before issuing any new queries!

❌ Committing Inside Helper / Service Functions

Writing def deduct_balance(): ... session.commit() inside lower-level utility functions.

Why this breaks Atomicity: Committing inside child functions destroys the Unit of Work. If step 1 (deduct) commits, and step 2 (credit) crashes due to a network glitch, step 1 is permanently committed on disk! The user lost money with no recipient credit. Rule: Only the top-level request orchestrator (the controller/handler) should call commit().
