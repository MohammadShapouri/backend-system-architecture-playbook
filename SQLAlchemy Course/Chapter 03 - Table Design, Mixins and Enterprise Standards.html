Part 01

Computer Science: The Constraint Naming Dilemma

When you define a column with unique=True or declare a ForeignKey("accounts.id") without an explicit name, the underlying database creates the constraint internally and assigns it an autogenerated identifier.

The Anonymous Constraint Trap in Cloud Migrations

Why Unnamed Constraints Cause Alembic Migrations to Crash

1. Anonymous Constraint (Anti-Pattern) Postgres & SQLite Risk

If you write account_number: Mapped[str] = mapped_column(unique=True):

PostgreSQL autogenerates: "accounts_account_number_key"
SQLite autogenerates: (No name assigned at all!)

✗ Months later, when you write an Alembic migration to drop or alter this constraint (op.drop_constraint(...)), SQLite crashes immediately, and PostgreSQL fails if the database name differs from Alembic's guess!

2. Explicit Naming Convention Dictionary Alembic-Ready

We configure an explicit naming pattern dictionary in MetaData:

uq: "uq_%(table_name)s_%(column_0_name)s"
→ Generates: "uq_accounts_account_number" everywhere!

✓ 100% deterministic constraint names across local SQLite, staging PostgreSQL, and production clusters. Alembic can drop, rename, and mutate constraints seamlessly.

// The Official 5-Key Enterprise Naming Convention Matrix
Key Constraint Type Format String Template Concrete Example
ix Index ix_%(column_0_label)s ix_accounts_account_number
uq Unique Constraint uq_%(table_name)s_%(column_0_name)s uq_accounts_uuid
ck Check Constraint ck_%(table_name)s_%(constraint_name)s ck_accounts_balance_non_negative
fk Foreign Key fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s fk_transactions_account_id_accounts
pk Primary Key pk_%(table_name)s pk_accounts
Part 02

DRY Architecture: Declarative Mixins & Server Defaults

In real-world applications, almost every table requires common audit columns: created_at, updated_at, and soft-delete flags. Duplicating these definitions across 30 models leads to typos, mismatched timezone semantics, and maintenance nightmares.

SQLAlchemy supports Python Mixins. A Mixin is an uninstantiated class that bundles common columns, relationships, and table arguments. Python's Method Resolution Order (MRO) compiles these columns directly into the target declarative class.

Declarative Mixin Composition Pipeline (Python MRO)
TimestampMixin created_at • updated_at
+
SoftDeleteMixin is_deleted • deleted_at
+
Base DeclarativeBase
↓ Composed Inheritance: class Account(Base, TimestampMixin, SoftDeleteMixin) ↓
Physical Table: accounts Combines business columns (balance, account_number) + audit timestamps + soft delete

Deep Dive Database Clock vs. Python Clock: server_default=func.now()

A frequent architectural flaw in database design is relying on Python's local system clock for timestamps via default=datetime.now. In distributed cloud environments, different application servers experience Clock Drift (their operating system clocks differ by several milliseconds or seconds).

Client-Side Default (default=...)

Timestamp is generated inside Python on the web server container before the SQL query is emitted. If Pod A and Pod B have slight clock skews, transaction ordering can appear non-chronological.

Server-Side Default (server_default=func.now())

SQLAlchemy generates DDL with DEFAULT CURRENT_TIMESTAMP. The timestamp is assigned atomically by the central database engine at commit time, guaranteeing total chronological consistency.

Part 03

ORM Inheritance: Single-Table vs. Joined-Table

In object-oriented programming, classes inherit from other classes. In relational databases, tables have flat, rectangular structures with fixed columns. Mapping an inheritance hierarchy into relational tables requires choosing between two primary design patterns:

On-Disk Representation: STI vs. JTI

How Polymorphic Classes are physically stored in PostgreSQL / SQLite

1. Single-Table Inheritance (STI) 1 Physical Table

Every subclass's fields are crammed into a single wide table with a discriminator column.

table "transactions":
[id] [type] [amount] [fee_category] [recipient_id]
1 • 'fee' • 15.00 • 'atm_fee' • NULL
2 • 'transfer' • 100.00 • NULL • 42
+ Ultra-fast reads: Zero SQL JOINs required.
− Sparse table: Subclass columns MUST be nullable, defeating database constraints!
2. Joined-Table Inheritance (JTI) Normalized N+1 Tables

Common fields live in the base table. Specific subclass fields live in dedicated child tables linked by primary key foreign keys.

table "transactions" (Base):
[id=1] [type='fee'] [amount=15.00]
table "fee_transactions" (Child):
[id=1 (FK)] [fee_category='atm_fee' (NOT NULL)]
+ Perfectly normalized: Allows strict NOT NULL constraints on child fields.
− Slight read overhead: Queries automatically emit an OUTER JOIN to fetch child rows.
The LedgerCore Architecture Decision:

For financial ledgers, data integrity and strict non-null constraints always outweigh microsecond join optimizations. We use Joined-Table Inheritance (JTI): a base Transaction table, joined with specialized TransferTransaction and FeeTransaction tables.

# Essential for Alembic migrations. Guarantees deterministic constraint names.
# ------------------------------------------------------------------------------
POSTGRES_NAMING_CONVENTION = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s"
}

# Inject naming convention directly into the shared Base metadata
metadata_obj = MetaData(naming_convention=POSTGRES_NAMING_CONVENTION)

class Base(DeclarativeBase):
    metadata = metadata_obj
2. Mixins & Polymorphic JTI: app/models.py Standardized Schema Models 
# ==============================================================================
# LedgerCore Backend - Models, Mixins & Polymorphism (Milestone 03)
# ==============================================================================

import uuid
from decimal import Decimal
from enum import Enum
from typing import Optional
from datetime import datetime
from sqlalchemy import String, Numeric, DateTime, Boolean, ForeignKey, func, Enum as SQLEnum
from sqlalchemy.orm import Mapped, mapped_column, relationship
from app.database import Base

# ==============================================================================
# Declarative Mixins
# ==============================================================================

class TimestampMixin:
    """
    Provides audit timestamps generated atomically by the database clock (func.now()).
    Eliminates server clock drift between web workers.
    """
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
        nullable=False
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
        onupdate=func.now(),
        nullable=False
    )

class SoftDeleteMixin:
    """
    Financial records must never be physically deleted from disk.
    Flags rows as deleted while preserving immutability for compliance.
    """
    is_deleted: Mapped[bool] = mapped_column(Boolean, default=False, nullable=False, index=True)
    deleted_at: Mapped[Optional[datetime]] = mapped_column(DateTime(timezone=True), nullable=True)


# ==============================================================================
# Refactored Account Model (Using Mixins)
# ==============================================================================

class AccountStatus(str, Enum):
    ACTIVE = "active"
    FROZEN = "frozen"
    CLOSED = "closed"

class Account(Base, TimestampMixin, SoftDeleteMixin):
    __tablename__ = "accounts"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    uuid: Mapped[uuid.UUID] = mapped_column(default=uuid.uuid4, unique=True, index=True, nullable=False)
    account_number: Mapped[str] = mapped_column(String(32), unique=True, index=True, nullable=False)
    owner_name: Mapped[str] = mapped_column(String(100), nullable=False)
    balance: Mapped[Decimal] = mapped_column(Numeric(14, 4), default=Decimal("0.0000"), nullable=False)
    status: Mapped[AccountStatus] = mapped_column(SQLEnum(AccountStatus, native_enum=False), default=AccountStatus.ACTIVE, nullable=False)

    # Relationships
    transactions: Mapped[list["Transaction"]] = relationship(back_populates="account")


# ==============================================================================
# Joined-Table Polymorphic Inheritance Hierarchy: Transactions
# ==============================================================================

class Transaction(Base, TimestampMixin):
    """
    BASE TABLE: Contains columns shared by all transaction types.
    'polymorphic_on' tells SQLAlchemy which column acts as the discriminator.
    """
    __tablename__ = "transactions"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    uuid: Mapped[uuid.UUID] = mapped_column(default=uuid.uuid4, unique=True, index=True, nullable=False)
    account_id: Mapped[int] = mapped_column(ForeignKey("accounts.id", ondelete="RESTRICT"), index=True, nullable=False)
    amount: Mapped[Decimal] = mapped_column(Numeric(14, 4), nullable=False)
    
    # Discriminator column identifying the child type
    transaction_type: Mapped[str] = mapped_column(String(30), nullable=False, index=True)

    account: Mapped[Account] = relationship(back_populates="transactions")

    __mapper_args__ = {
        "polymorphic_on": "transaction_type",
        "polymorphic_identity": "base_transaction"
    }


class TransferTransaction(Transaction):
    """
    CHILD TABLE 1: Holds specific transfer destination metadata.
    id links directly to the base transactions.id primary key.
    """
    __tablename__ = "transfer_transactions"

    id: Mapped[int] = mapped_column(ForeignKey("transactions.id", ondelete="CASCADE"), primary_key=True)
    destination_account_number: Mapped[str] = mapped_column(String(32), nullable=False)
    routing_reference: Mapped[str] = mapped_column(String(64), nullable=False)

    __mapper_args__ = {
        "polymorphic_identity": "transfer"
    }


class FeeTransaction(Transaction):
    """
    CHILD TABLE 2: Holds administrative fee categories.
    """
    __tablename__ = "fee_transactions"

    id: Mapped[int] = mapped_column(ForeignKey("transactions.id", ondelete="CASCADE"), primary_key=True)
    fee_code: Mapped[str] = mapped_column(String(20), nullable=False)  # e.g. "WIRE_OUTBOUND", "ATM_SURCHARGE"
    waivable: Mapped[bool] = mapped_column(Boolean, default=False, nullable=False)

    __mapper_args__ = {
        "polymorphic_identity": "fee"
    }
3. Querying Polymorphism: app/main.py Polymorphic Query Execution 
# Append to app/main.py: Polymorphic query endpoint
from app.models import Transaction, TransferTransaction, FeeTransaction

@app.get("/api/v1/accounts/{account_id}/transactions", tags=["Transactions"])
def list_account_transactions(account_id: int):
    """
    POLYMORPHIC QUERY MAGIC:
    Querying the base 'Transaction' class automatically performs an OUTER JOIN
    across 'transfer_transactions' and 'fee_transactions', returning typed instances
    of TransferTransaction or FeeTransaction automatically based on the discriminator!
    """
    with Session(engine) as session:
        stmt = (
            select(Transaction)
            .where(Transaction.account_id == account_id)
            .order_by(Transaction.created_at.desc())
        )
        records = session.scalars(stmt).all()

        results = []
        for tx in records:
            tx_data = {
                "uuid": str(tx.uuid),
                "amount": str(tx.amount),
                "transaction_type": tx.transaction_type,
                "created_at": tx.created_at.isoformat(),
            }
            # Introspect polymorphic subclass attributes seamlessly
            if isinstance(tx, TransferTransaction):
                tx_data["destination"] = tx.destination_account_number
                tx_data["routing_ref"] = tx.routing_reference
            elif isinstance(tx, FeeTransaction):
                tx_data["fee_code"] = tx.fee_code
                tx_data["waivable"] = tx.waivable

            results.append(tx_data)

        return results
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The Sparse Table Anti-Pattern (STI Overuse)

Using Single-Table Inheritance (STI) for 15 subclasses, each introducing 8 distinct fields.

Why this destroys schemas: All subclass fields must be declared nullable=True. You cannot enforce database-level NOT NULL constraints on crucial business logic. Furthermore, rows become physically sparse on disk, increasing storage bloat and degrading index cache efficiency. Use Joined-Table Inheritance (JTI) when subclasses have distinct non-nullable constraints.

❌ Missing Discriminator Index

Declaring transaction_type: Mapped[str] without index=True.

Why this causes slow queries: When querying specific child types (e.g. select(FeeTransaction)), SQLAlchemy appends WHERE transaction_type = 'fee' to filter the rows. Without an index on the polymorphic discriminator column, the database performs a full table scan over millions of transaction rows. Always index the discriminator!
