Hardware Mechanical Sympathy

Storage Physics: The Mechanical Sympathy of Disk & Flash

A storage engine is the software translation layer between abstract application data structures (objects, rows, documents) and the physical properties of magnetic platters or silicon flash cells.

Regardless of whether an engine runs on a rotating HDD or a PCIe Gen5 NVMe SSD, one fundamental hardware law remains invariant: Sequential disk writes are orders of magnitude faster and less damaging to flash media than random in-place updates.

The RUM Conjecture (Athanassoulis et al., Harvard Database Group)
Read Overhead (R)

How many disk seeks/pages must be read to return a record? B-Trees optimize for this ($O(\log_B N)$).

Update Overhead (U)

How much data must be written to disk when modifying a value? LSM-Trees optimize for this via append-only logs.

Memory / Space Overhead (M)

How much extra disk space and RAM is wasted on indexes, fragmentation, and deleted tombstones?

The Trilemma Invariant:

The RUM Conjecture proves that you can optimize for at most two of these three dimensions. Designing a storage engine that simultaneously delivers minimum Read cost, minimum Write cost, and minimum Storage space is physically impossible.

💡 The Real-World Metaphor (Plain English)

Imagine keeping an inventory catalog of 50,000 car parts in a retail repair shop.

A B-Tree is like an encyclopedia with rigid 500-page leather-bound volumes. When a customer buys a spark plug, you walk to Volume 4, Page 212, erase the pencil number "14", and write "13". Finding parts is fast because pages are in strict alphabetical order. But updating is slow and tedious, and constantly erasing pages wears physical holes in the paper (Write Amplification).

An LSM-Tree is like a legal pad on the shop counter. When a customer buys a spark plug, you simply write a one-line note on the next available line: "Sold 1 spark plug at 2:15 PM". Writing takes 1 second (append-only speed!). But when someone asks: "How many spark plugs do we have?", you have to read the notebook backwards and scan older archived notebooks (Compaction) to calculate the final tally.

Core Storage Architecture

B-Trees vs. LSM-Trees: The Architectural Divide

In-Place Mutation • Log-Structured Append • Write Amplification Factor (WAF)

B-Trees (PostgreSQL, MySQL, SQLite) Read-Optimized

Data is organized into fixed-size pages (typically 4KB to 16KB). Pages form a balanced tree with a massive branching factor (often 100 to 500 children per node).

• Tree Height: Typically 3 to 4 levels for 1 Billion rows!
• Read Path: $O(\log_B N)$ → Max 3-4 page reads to find any record
• Write Path: In-place page rewrite + Write-Ahead Log (WAL)
• Downside: Modifying 8 bytes rewrites entire 8KB page (WAF ~50-100x!)

Best For: Strong consistency, range queries, read-heavy workloads, and multi-column secondary indexes.

LSM-Trees (RocksDB, Cassandra, ScyllaDB) Write-Optimized

Writes never mutate disk data in place. Incoming writes append to an in-memory sorted structure (MemTable) and a sequential disk log (WAL).

• Write Path: Zero random I/O. Pure sequential appends at memory speed
• Disk Flush: MemTable flushes to immutable SSTables on disk
• Background Compaction: Merges SSTable files and removes tombstones
• Downside: Read amplification (must check MemTable + multiple SSTables)

Best For: Extreme write throughput, time-series telemetry, financial ledgers, and append-heavy events.

The Magic of Bloom Filters in LSM-Trees:

Because SSTables on disk are immutable, a single key lookup might have to check 10 different SSTable files. A **Bloom Filter** (a space-efficient probabilistic data structure) is loaded in RAM for every SSTable. The filter can say with 100% mathematical certainty if a key is definitely NOT in that SSTable file, preventing 99% of useless random disk reads!

Industrial Case Study

Case Study: Why Uber Migrated from PostgreSQL to MySQL and then RocksDB

The Write Amplification Crisis in High-Frequency Geo-Telemetry

In 2016, Uber engineering published one of the most famous database architectural post-mortems in internet history: Why Uber, an early adopter of PostgreSQL, migrated its core dispatch and trip database back to MySQL (InnoDB) and subsequently built Docstore on top of RocksDB.

The PostgreSQL B-Tree Write Amplification Problem at Uber PostgreSQL HOT Tuple Limitation

In PostgreSQL, row versions are stored directly in the primary table heap. If you have an `orders` table with 5 secondary indexes (e.g., `user_id`, `driver_id`, `created_at`, `status`, `city_id`), and you update a single column (e.g. `status = 'IN_TRANSIT'`):

1. Postgres allocates a brand new row tuple in the table page heap.
2. Because the physical disk tuple address changes, all 5 secondary B-Tree indexes must be updated!
3. Modifying 5 indexes writes 5 random 8KB B-tree leaf pages to disk + WAL records.
→ A 10-byte status update generated over 40 Kilobytes of random disk writes!

Under millions of driver location and ride status updates, PostgreSQL saturated Uber’s NVMe SSD write endurance and overwhelmed database replication streams.

The LSM-Tree Solution (Docstore on RocksDB): In RocksDB, updating a ride status requires only a single append to the in-memory MemTable and write-ahead log. There are zero random page rewrites. Storage bandwidth dropped by over 80%, and write latency tail drops (p99) stabilized from seconds to sub-10 milliseconds!

2. LSM-Tree Engine with MemTable & Bloom Filter: src/omniroute/storage/lsm_engine.py Append-Only Ingestion Physics 
# ==============================================================================
# OmniRoute Storage - Log-Structured Merge-Tree (LSM) Engine with Bloom Filters
# ==============================================================================

import os
import json
import hashlib
import asyncio
from typing import Dict, Optional, List


class BloomFilter:
    """
    SPACE-EFFICIENT PROBABILISTIC FILTER:
    Guarantees 0% false negatives.
    If the filter says 'No', the key is 100% guaranteed not in the SSTable file.
    """
    def __init__(self, size_bits: int = 2048, hash_count: int = 3):
        self.size_bits = size_bits
        self.hash_count = hash_count
        self.bit_array = [0] * size_bits

    def _get_hashes(self, key: str) -> List[int]:
        hashes = []
        for i in range(self.hash_count):
            digest = hashlib.md5(f"{key}:{i}".encode("utf-8")).hexdigest()
            hashes.append(int(digest, 16) % self.size_bits)
        return hashes

    def add(self, key: str) -> None:
        for bit_idx in self._get_hashes(key):
            self.bit_array[bit_idx] = 1

    def contains(self, key: str) -> bool:
        return all(self.bit_array[bit_idx] == 1 for bit_idx in self._get_hashes(key))


class LSMStorageEngine:
    """
    LSM-TREE STORAGE ENGINE (RocksDB Architecture):
    1. MemTable: In-memory sorted dictionary for O(1) writes.
    2. Write-Ahead Log (WAL): Sequential append-only disk log for crash recovery.
    3. SSTable: Immutable flushed disk files guarded by in-memory Bloom Filters.
    """
    def __init__(self, wal_path: str = "lsm_wal.log", memtable_flush_threshold: int = 5):
        self.wal_path = wal_path
        self.memtable_flush_threshold = memtable_flush_threshold
        self._memtable: Dict[str, dict] = {}
        self._sstables: List[Dict[str, dict]] = []
        self._bloom_filters: List[BloomFilter] = []
        self._lock = asyncio.Lock()

    async def put(self, key: str, value: dict) -> None:
        async with self._lock:
            # 1. Append to Write-Ahead Log (Sequential Write)
            log_entry = json.dumps({"key": key, "val": value}) + "\n"
            with open(self.wal_path, "a", encoding="utf-8") as wal_file:
                wal_file.write(log_entry)

            # 2. Write to in-memory sorted MemTable
            self._memtable[key] = value

            # 3. Check flush threshold
            if len(self._memtable) >= self.memtable_flush_threshold:
                self._flush_memtable_to_sstable()

    def _flush_memtable_to_sstable(self) -> None:
        """Flushes sorted MemTable to an immutable SSTable and builds a Bloom filter."""
        sstable = dict(sorted(self._memtable.items()))
        bf = BloomFilter()
        for k in sstable.keys():
            bf.add(k)

        self._sstables.insert(0, sstable)  # Most recent SSTable first
        self._bloom_filters.insert(0, bf)
        self._memtable = {}

        # Truncate WAL because state is safely committed to SSTable
        if os.path.exists(self.wal_path):
            open(self.wal_path, "w").close()

    async def get(self, key: str) -> Optional[dict]:
        """
        READ PATH:
        1. Check in-memory MemTable (O(1)).
        2. Scan SSTables guarded by Bloom filters (skips non-matching files).
        """
        async with self._lock:
            # Step 1: Check MemTable
            if key in self._memtable:
                return self._memtable[key]

            # Step 2: Check SSTables with Bloom Filter defense
            for idx, sstable in enumerate(self._sstables):
                if not self._bloom_filters[idx].contains(key):
                    # Bloom filter says NO → Skip SSTable completely without searching!
                    continue
                if key in sstable:
                    return sstable[key]

            return None
3. Hybrid Storage FastAPI Controller: src/omniroute/storage/router.py FastAPI & Polyglot Dispatch 
from fastapi import APIRouter, Depends, HTTPException, status
from pydantic import BaseModel
from sqlalchemy.ext.asyncio import AsyncSession
from typing import AsyncGenerator

from omniroute.storage.lsm_engine import LSMStorageEngine
from omniroute.storage.models import TripSettlementBTreeModel

router = APIRouter(prefix="/api/v1/storage", tags=["Hybrid Storage Engines"])
lsm_engine = LSMStorageEngine(wal_path="omniroute_wal.log", memtable_flush_threshold=3)


class TelemetryWriteDTO(BaseModel):
    driver_id: str
    lat: float
    lng: float
    speed: float


class TripOrderSettlementDTO(BaseModel):
    rider_id: str
    driver_id: str
    fare_amount: float


async def get_session() -> AsyncGenerator[AsyncSession, None]:
    raise NotImplementedError


@router.post("/lsm/telemetry", status_code=status.HTTP_201_CREATED)
async def write_high_frequency_telemetry(dto: TelemetryWriteDTO):
    """LSM-TREE PATH: High-throughput write via MemTable append and WAL."""
    await lsm_engine.put(dto.driver_id, dto.model_dump())
    return {"engine": "LSM-Tree", "driver_id": dto.driver_id, "status": "APPENDED"}


@router.get("/lsm/telemetry/{driver_id}")
async def read_telemetry_lsm(driver_id: str):
    """LSM-TREE READ PATH: Evaluates MemTable -> Bloom Filter -> SSTable."""
    val = await lsm_engine.get(driver_id)
    if not val:
        raise HTTPException(status_code=404, detail="Telemetry record not found.")
    return {"engine": "LSM-Tree", "record": val}


@router.post("/btree/settlement", status_code=status.HTTP_201_CREATED)
async def commit_acid_trip_settlement(
    dto: TripOrderSettlementDTO,
    db: AsyncSession = Depends(get_session)
):
    """B-TREE PATH: Relational database write with ACID transactional semantics."""
    record = TripSettlementBTreeModel(
        rider_id=dto.rider_id,
        driver_id=dto.driver_id,
        fare_amount=dto.fare_amount
    )
    db.add(record)
    await db.commit()
    await db.refresh(record)
    return {"engine": "B-Tree RDBMS", "trip_id": record.trip_id, "status": "COMMITTED"}

class TestStorageEnginesSuite:
    """Verifies LSM-Tree MemTable/SSTable flushes, Bloom filter accuracy, and B-Tree models."""

    def test_bloom_filter_zero_false_negatives(self):
        bf = BloomFilter(size_bits=1024, hash_count=3)
        bf.add("driver_42")
        bf.add("driver_99")

        # Invariant: If added, MUST evaluate to True
        assert bf.contains("driver_42") is True
        assert bf.contains("driver_99") is True
        # Non-existent key (99% probability False)
        assert bf.contains("driver_non_existent") is False

    @pytest.mark.asyncio
    async def test_lsm_memtable_flush_and_sstable_retrieval(self):
        wal_file = "test_lsm_flush.log"
        if os.path.exists(wal_file):
            os.remove(wal_file)

        engine = LSMStorageEngine(wal_path=wal_file, memtable_flush_threshold=2)

        # Write 2 entries → Triggers automatic SSTable flush
        await engine.put("k1", {"lat": 1.0})
        await engine.put("k2", {"lat": 2.0})

        assert len(engine._sstables) == 1
        assert len(engine._memtable) == 0  # MemTable cleared post-flush!

        # Read back from SSTable via Bloom Filter
        val = await engine.get("k1")
        assert val == {"lat": 1.0}

        if os.path.exists(wal_file):
            os.remove(wal_file)

    @pytest.mark.asyncio
    async def test_btree_relational_settlement_persistence(self, in_memory_db):

            record = TripSettlementBTreeModel(
                rider_id="rider_1",
                driver_id="driver_1",
                fare_amount=35.50
            )
            session.add(record)
            await session.commit()
            assert record.trip_id is not None
            assert record.status == "COMPLETED"
Warning Track

Beginner Pitfalls & Storage Anti-Patterns

❌ The B-Tree Append-Log Trap

Using traditional relational databases (PostgreSQL/MySQL) with 8 secondary indexes to ingest 150,000 real-time location events per second.

Why this destroys storage hardware: Each event update mutates multiple 8KB B-Tree index pages randomly across disk, generating a catastrophic Write Amplification Factor of 50x to 100x. The database saturates SSD IOPS, causes replication lag to blow out to hours, and prematurely burns through physical flash endurance! Use LSM-Trees (RocksDB/Cassandra) or in-memory ring buffers for high-velocity ingest.

❌ Neglecting LSM-Tree Compaction Stall

Writing data into an LSM-Tree engine faster than the background compaction threads can merge SSTables on disk.

Why this causes tail latency collapse: If writes outpace compaction, hundreds of unmerged SSTable files accumulate. Read queries must now scan 50 different files per lookup. Eventually, RocksDB triggers a Write Stall (hard-throttling incoming writes to 0) to allow compaction to catch up, spiking p99 latency from 5ms to 10,000ms! Always budget dedicated disk I/O bandwidth for compaction.
