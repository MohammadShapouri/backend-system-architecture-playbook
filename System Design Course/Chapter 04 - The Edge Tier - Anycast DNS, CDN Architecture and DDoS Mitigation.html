Edge Routing Physics

BGP Anycast: How Multiple Servers Share a Single IP Address

In traditional internet routing (**Unicast**), a single IP address maps to exactly one physical network interface card (NIC) located in one specific datacenter. If your server is in Virginia, a rider in Tokyo must traverse underwater trans-Pacific fiber cables for every packet, paying an inescapable 150ms roundtrip penalty.

Modern edge providers (Cloudflare, AWS CloudFront, Google Cloud) operate on BGP Anycast. In Anycast, hundreds of edge data centers worldwide announce the exact same IP address and prefix to upstream internet service providers using the Border Gateway Protocol (BGP).

Unicast vs. BGP Anycast Global Routing Topology
1. Unicast Routing (Centralized Fragility)
Rider (Tokyo) → Trans-Pacific Fiber (150ms) → US Origin
Rider (London) → Trans-Atlantic Fiber (75ms) → US Origin
DDoS Attacker (1 Tbps) → All packets converge on ONE Origin!
✗ Massive latency, single point of failure, immediate overload.
2. BGP Anycast Routing (Decentralized Resilience)
Rider (Tokyo) → Local Tokyo PoP (2ms) [TLS Terminated]
Rider (London) → Local London PoP (3ms) [TLS Terminated]
DDoS Attacker (1 Tbps) → Traffic diluted across 300 global PoPs!
✓ Sub-5ms TLS handshake, automatic volumetric DDoS scrubbing.
The Anycast BGP Convergence Principle:

Routers across the internet choose the path to an Anycast IP using standard BGP metrics (primarily shortest AS-Path). If the London PoP undergoes catastrophic failure or drops power, its BGP daemon ceases route announcements. Upstream European routers automatically reconverge and route packets to the next closest PoP (e.g., Frankfurt or Paris) in seconds without client DNS changes!

💡 The Real-World Metaphor (Plain English)

Imagine calling 911 (Emergency Services).

Everyone across the United States dials the exact same three digits: 9-1-1. However, there is no single, gigantic warehouse in Kansas where five dispatchers answer calls for all 330 million citizens.

The telephone switching network uses Anycast telephone routing: dialing 911 in Seattle routes your call to the local Seattle police precinct. Dialing 911 in Miami routes your call to the local Miami dispatch desk. The number is identical; the physical destination is topologically nearest to you. If a local station is evacuated, calls route to the adjacent county dispatch center.

CDN Architecture, Origin Shields & RFC 9111 Cache-Control

Multi-Tier Edge Hierarchies • Dynamic vs. Static Caching • Cache Invalidation

A Content Delivery Network (CDN) is not merely a static asset dump for images and JavaScript bundles. In modern system design, the CDN is an intelligent reverse-proxy shield that terminates TLS, compresses payloads (Brotli/Gzip), caches dynamic API query reads, and prevents cache stampedes against backend origins.

Why an Origin Shield is Essential:

Without an Origin Shield, if a popular cache key expires across a CDN with 300 Points of Presence, all 300 edge nodes simultaneously send an origin-fetch request to your backend. The Origin Shield sits as a centralized caching tier right next to your primary datacenter: the first edge miss populates the Shield, and the remaining 299 edge nodes fetch from the Shield at local LAN speeds!

Header Directive Architectural Meaning Production Use Case (OmniRoute)
s-maxage=60 Shared Cache TTL: Tells the CDN proxy to cache for 60 seconds, while client browsers ignore it. Surge pricing zones, city heatmaps, driver dispatch tiers.
stale-while-revalidate=30 Returns expired content instantly in 1ms while fetching a fresh copy in the background asynchronously. Map tile rendering, airport terminal pickup zone parameters.
stale-if-error=300 If the origin backend crashes (5xx error), the CDN serves stale cached content for 5 minutes instead of displaying an error screen. High Availability fallback during database failovers.
private, no-store FORBIDS all intermediaries and CDNs from storing the payload in memory or disk. Rider account profiles, credit card tokens, driver bank payout details.
Perimeter Defense

DDoS Mitigation & The 5 Core Rate Limiting Algorithms

L3/L4 vs. L7 Floods • Token Bucket • Leaky Bucket • Sliding Window Counter

Distributed Denial of Service (DDoS) attacks operate at different layers of the OSI stack:

Layer 3 & 4 (Volumetric & Protocol Floods)
  • UDP Amplification: Spoofing victim IP to open NTP/DNS servers, reflecting 50x amplified data volume.
  • TCP SYN Flood: Sending thousands of initial SYN packets without completing the 3-way handshake, exhausting kernel backlog tables.
  • Mitigation: Anycast edge bandwidth absorption, SYN Cookies (stateless TCP handshakes), and BGP Flowspec scrubbing.
Layer 7 (Application & Semantic Floods)
  • HTTP Flood: Thousands of legitimate-looking HTTP POST/GET requests targeting expensive database endpoints.
  • Slowloris: Opening HTTP connections and sending headers at a rate of 1 byte every 10 seconds, keeping reverse proxy threads trapped indefinitely.
  • Mitigation: Aggressive HTTP header timeouts, WAF rules, and algorithmic **Rate Limiting**.

Comparing the 5 Algorithmic Rate Limiting Paradigms

Algorithm Time Complexity Memory Complexity Pros & Strengths Cons & Failure Modes
Token Bucket O(1) O(1) Permits controlled bursts; simple mathematical refill formula. Requires atomic synchronization (Redis Lua) in multi-node setups.
Leaky Bucket O(1) O(Queue Depth) Smooths traffic output to a constant, predictable trickle. Bursts fill the buffer; drops newest requests even if server has spare capacity.
Fixed Window Counter O(1) O(1) Trivial to implement via Redis `INCR` and `EXPIRE`. Boundary spike vulnerability: Allows 2x limit at window edges!
Sliding Window Log O(log N + M) O(N Requests) 100% mathematically exact rate limiting. Stores timestamps for every call; consumes gigabytes of RAM under load.
Sliding Window Counter O(1) O(1) Industry Standard: Approximates sliding window smoothly with minimal memory. Minor mathematical estimation error (~0.05%), completely negligible in practice.
The Sliding Window Counter Formula (Cloudflare Architecture)
\text{Requests} = \text{Count}_{\text{current}} + \left( \text{Count}_{\text{previous}} \times \left( 1 - \frac{\text{Time}_{\text{elapsed}}}{\text{WindowSize}} \right) \right)

Instead of storing millions of individual log timestamps, we store only two integer counters: the count of the previous window and the count of the current window. By weighting the previous window by the remaining fractional time, boundary spikes are mathematically eliminated while consuming only 8 bytes of memory per user!

2. Sliding Window Counter Engine: src/omniroute/edge/rate_limiter.py O(1) Memory Algorithm 
# ==============================================================================
# OmniRoute Edge - High-Performance Sliding Window Counter Rate Limiter
# ==============================================================================

import time
import asyncio
from dataclasses import dataclass
from typing import Dict


@dataclass
class WindowState:
    current_window_idx: int
    current_count: int
    previous_count: int


class SlidingWindowCounter:
    """
    SLIDING WINDOW COUNTER (Cloudflare Algorithm):
    Combines previous and current fixed window counts via weighted time decay.
    Smooths boundary spikes with strictly O(1) memory overhead.
    """
    def __init__(self, window_size_sec: int = 60, max_requests: int = 100):
        self.window_size_sec = window_size_sec
        self.max_requests = max_requests
        self._states: Dict[str, WindowState] = {}
        self._lock = asyncio.Lock()

    async def is_allowed(self, client_key: str) -> tuple[bool, int]:
        """
        Evaluates whether an incoming request breaches the rate ceiling.
        Returns: (is_permitted: bool, current_estimated_requests: int)
        """
        now = time.time()
        current_window = int(now // self.window_size_sec)
        time_into_current = now % self.window_size_sec

        async with self._lock:
            state = self._states.get(client_key)

            if not state:
                self._states[client_key] = WindowState(
                    current_window_idx=current_window,
                    current_count=1,
                    previous_count=0
                )
                return True, 1

            # Transition windows
            if state.current_window_idx == current_window:
                state.current_count += 1
            elif state.current_window_idx == current_window - 1:
                state.previous_count = state.current_count
                state.current_window_idx = current_window
                state.current_count = 1
            else:
                # More than 1 window elapsed; reset history
                state.previous_count = 0
                state.current_window_idx = current_window
                state.current_count = 1

            # Apply Sliding Window Approximation Formula
            weight = (self.window_size_sec - time_into_current) / self.window_size_sec
            estimated_requests = int(state.previous_count * weight + state.current_count)

            if estimated_requests > self.max_requests:
                return False, estimated_requests

            return True, estimated_requests
3. Edge Perimeter WAF Middleware: src/omniroute/edge/middleware.py FastAPI & Starlette Middleware 
# ==============================================================================
# OmniRoute Edge - Perimeter WAF & Cache-Control Security Middleware
# ==============================================================================

from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from starlette.responses import Response, JSONResponse
from omniroute.edge.rate_limiter import SlidingWindowCounter


class EdgeSecurityMiddleware(BaseHTTPMiddleware):
    """
    PERIMETER SECURITY GATEWAY:
    1. Intercepts L7 rate-limit violations using Sliding Window Counter.
    2. Drops malicious cache-busting random query attacks.
    3. Injects RFC 9111 Cache-Control headers based on endpoint classification.
    """
    def __init__(self, app, rate_limiter: SlidingWindowCounter):
        super().__init__(app)
        self.rate_limiter = rate_limiter

    async def dispatch(self, request: Request, call_next) -> Response:
        client_ip = request.headers.get("X-Forwarded-For", request.client.host if request.client else "127.0.0.1").split(",")[0].strip()

        # 1. Anti-DDoS Rate Limit Verification
        allowed, count = await self.rate_limiter.is_allowed(client_ip)
        if not allowed:
            return JSONResponse(
                status_code=429,
                content={"error": "RATE_LIMIT_EXCEEDED", "message": f"Limit exceeded. Count: {count}"},
                headers={"Retry-After": "60"}
            )

        # 2. Cache-Busting Attack Protection (Randomized query floods)
        if len(request.query_params) > 10:
            return JSONResponse(
                status_code=400,
                content={"error": "SUSPICIOUS_QUERY_PARAMETERS"}
            )

        # 3. Process Downstream Request
        response = await call_next(request)

        # 4. Inject RFC 9111 Cache-Control Directives
        if request.url.path.startswith("/api/v1/public/zones"):
            # Public cacheable data with background revalidation
            response.headers["Cache-Control"] = "public, s-maxage=60, stale-while-revalidate=30"
        elif request.url.path.startswith("/api/v1/driver/profile"):
            # Strictly forbid edge proxies from caching private PII
            response.headers["Cache-Control"] = "private, no-store, no-cache"

        return response

import pytest
import pytest_asyncio
from fastapi import FastAPI
from httpx import AsyncClient, ASGITransport
from omniroute.edge.rate_limiter import SlidingWindowCounter

class TestEdgeSecuritySuite:
    """Verifies Sliding Window Counter, DDoS thresholds, and Cache-Control headers."""

    @pytest.mark.asyncio
    async def test_sliding_window_counter_rate_limiting(self):
        limiter = SlidingWindowCounter(window_size_sec=60, max_requests=3)
        client = "192.168.1.50"

        # 3 requests allowed
        assert (await limiter.is_allowed(client))[0] is True
        assert (await limiter.is_allowed(client))[0] is True
        assert (await limiter.is_allowed(client))[0] is True

        # 4th request MUST be blocked (Capacity 3 breached)
        allowed, count = await limiter.is_allowed(client)
        assert allowed is False
        assert count == 4

    @pytest.mark.asyncio
    async def test_edge_middleware_drops_ddos_floods_and_applies_caching(self):
        app = FastAPI()
        limiter = SlidingWindowCounter(window_size_sec=60, max_requests=2)
        app.add_middleware(EdgeSecurityMiddleware, rate_limiter=limiter)

        @app.get("/api/v1/public/zones")
        async def get_zones():
            return {"zones": ["DOWNTOWN", "AIRPORT"]}

        @app.get("/api/v1/driver/profile")
        async def get_profile():
            return {"ssn": "SECRET"}

        transport = ASGITransport(app=app)
        async with AsyncClient(transport=transport, base_url="http://test") as client:
            headers = {"X-Forwarded-For": "203.0.113.195"}

            # Call 1 → OK, verifies public cache header
            r1 = await client.get("/api/v1/public/zones", headers=headers)

            r2 = await client.get("/api/v1/public/zones", headers=headers)

Warning Track

Beginner Pitfalls & Edge Anti-Patterns

❌ The Direct Origin IP Leak

Allowing your backend AWS EC2/ALB IP address to be publicly accessible instead of strictly restricting ingress to CDN/WAF IP ranges.

Why this invalidates your security: An attacker scans Shodan or looks at historical DNS records to find your actual origin IP address. They send volumetric SYN floods directly to your origin IP, bypassing your Cloudflare Anycast shield and taking down your platform completely! Always place origin instances in private subnets with security groups permitting traffic ONLY from CDN IP prefixes.

❌ The Cache-Busting Query Flood Vulnerability

Configuring CDNs to cache queries individually while allowing arbitrary query parameters without edge filtering.

Why this causes origin death: Attackers send 100,000 requests/sec with random query parameters (/search?q=cars&bust=897214, /search?q=cars&bust=992812). Because every URL is unique, the CDN registers a 100% Cache Miss rate and forwards all 100,000 requests directly to your origin database! Always configure CDNs to strip unrecognized query parameters at the edge.
