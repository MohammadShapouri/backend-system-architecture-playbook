Part 01

Computer Science: Distributed Mutation Topologies & Mutation Semantics

A distributed cache does not automatically stay synchronized with your database. The application architecture dictates which system is the system of record, which layer handles errors, and whether reads or writes absorb synchronization latency.

1. Cache-Aside (Look-Aside) Standard

The application coordinates both stores directly. The cache has no awareness of the underlying database.

• Read: Check cache → on miss, read DB → write cache.
• Write: Write to DB directly → delete/evict cache key.
• Resilience: Cache failure does not halt application writes.
• Latency: Absorbed by cache miss reads.

Best For: General web APIs, read-heavy e-commerce, and unpredictable sparse query workloads.

2. Write-Through Synchronous

The application treats the cache as the primary data store. The cache layer synchronously writes to the database before acknowledging success.

• Read: Always served from cache (guaranteed warm).
• Write: Cache updates DB in a single synchronous transaction.
• Latency: Increased write latency (dual network round-trip).
• Consistency: High; cache is never stale relative to DB.

Best For: Critical entity updates where read misses cannot be tolerated (e.g., account profile updates).

3. Write-Behind (Write-Back) Asynchronous

The application writes exclusively to the cache/buffer queue. A background daemon asynchronously flushes batches to the database.

• Write: Absorbed at in-memory speed (< 1ms).
• Coalescing: Multiple updates to same key merged into 1 write.
• Risk: Data loss if the cache crashes before buffer drains.
• Complexity: Requires persistent queues & retry handlers.

Best For: Massive write spikes (view counters, telemetry ingestion, gaming leaderboards).

The Invalidation Concurrency Trap: Why You Must Invalidate (Delete), Not Update

A recurring bug in distributed systems is updating the cache directly when a database write succeeds: db.update(user); cache.set(user.id, user). Under high concurrency, this produces a permanent **Stale Data Overwrite**:

T1: Request A updates Database: name = "Alice"
T2: Request B updates Database: name = "Bob" (Committed after A)
T3: Request B writes to Cache: key = "Bob"
T4: Request A (delayed by network jitter) writes to Cache: key = "Alice"!
→ DATABASE HAS "Bob" • CACHE IS PERMANENTLY CORRUPTED WITH "Alice"!

✓ The Invalidation Invariant: Never update the cache on write. Always cache.delete(key). Evicting the entry forces the next reader to read the single authoritative truth from the database transaction log.

Part 02

Outage Metrology: Cache Penetration, Avalanche & Breakdown

In distributed systems, the sudden failure of a cache layer rarely stays isolated. It cascades directly into downstream storage engines. Architects classify cache-induced database crashes into three distinct failure modes:

1. Cache Penetration Non-Existent Keys

Occurs when requests query keys that exist neither in the cache nor in the database (e.g., automated vulnerability scanners probing for /item/-99999 or random UUIDs).

Request: key="user:non_existent"
Cache check: Miss! → Passes to DB
DB check: Not found (0 rows returned)
→ Nothing is cached! 100% of future requests hit DB!

Defenses: Bloom Filters (Part 03) & Null-Value Sentinel Caching.

2. Cache Avalanche Synchronized Expiration

Occurs when hundreds of thousands of keys are configured with the exact same TTL (e.g., standard SETEX key 3600 at midnight) or when the cache server restarts cold.

T=00:00: 50,000 keys loaded with TTL=3600s
T=01:00: ALL 50,000 KEYS EXPIRE AT ONCE!
Traffic surges → 50k simultaneous DB queries
→ Database CPU spikes to 100%, pool exhausted!

Defenses: TTL Random Jitter ($\pm 15\%$) & Cache Pre-Warming.

3. Cache Breakdown Hotspot Invalidated

Occurs when a single **hyper-popular key** (e.g., Black Friday homepage deal or viral news post) expires while receiving thousands of requests per second.

Key "deal:iphone" receives 10,000 req/sec
Key expires at T=12.000s
5,000 parallel workers observe cache miss
→ 5,000 identical heavy SQL queries execute at once!

Defenses: Mutex Locks & Probabilistic Early Refresh (XFetch - Chapter 05).

Part 03

Algorithmic Defense: Scalable Bloom Filters & Negative Caching

To neutralize Cache Penetration attacks, an application must determine whether a key definitely does not exist before sending a query across the network to PostgreSQL or MongoDB.

A **Bloom Filter** is a space-efficient probabilistic data structure invented by Burton Howard Bloom. It answers set-membership queries with a unique mathematical guarantee:

// The Bloom Filter Invariant:
• Can yield False Positives: It may report that an element is present when it is not.
• NEVER yields False Negatives: If it reports an element is absent, it is 100% mathematically guaranteed not to exist.

Hashes key across $k=3$ functions → bits [1, 4, 11] are flipped to 1.

2. Querying Key "user:999":

// Mathematical Dimensioning Formula:

For an expected capacity of $n$ items and an acceptable false positive rate $p \in (0, 1)$, the optimal number of bits $m$ and hash functions $k$ are:

m = - \frac{n \ln p}{(\ln 2)^2} \qquad \text{and} \qquad k = \frac{m}{n} \ln 2

For 1,000,000 items with a 1% false positive probability, a Bloom Filter requires only 1.14 Megabytes of RAM and 7 hash iterations!

Layer 2 Defense: Null-Value Sentinel Caching

What happens if a non-existent key slips past the Bloom filter due to a false positive? To prevent continuous penetration, CacheForge implements Negative Caching:

1. Database returns None / 0 rows
2. CacheForge sets: SET key "__NULL_SENTINEL__" EX 30
3. Subsequent penetration attempts in the next 30 seconds return null immediately from cache!

Critical Rule: Null sentinels must carry a very short TTL (30 to 120 seconds). If a user creates that account 2 seconds later, a permanent null entry would falsely hide the new record from the application.

1. Probabilistic Bloom Filter: src/cacheforge/patterns/bloom.py Kirsch-Mitzenmacher Double Hashing 
# ==============================================================================
# CacheForge Patterns - High-Performance Bloom Filter (Milestone 04)
# ==============================================================================

import math
import zlib
import hashlib
from typing import List

class BloomFilter:
    """
    PROBABILISTIC MEMBERSHIP FILTER:
    Guarantees ZERO false negatives.
    Uses Kirsch-Mitzenmacher optimization: generates k hash values using
    only two hash computations: gi(x) = (h1(x) + i * h2(x)) mod m.
    """
    def __init__(self, expected_elements: int, false_positive_rate: float = 0.01):
        if expected_elements <= 0 or not (0.0 < false_positive_rate < 1.0):
            raise ValueError("Invalid Bloom filter dimensions")

        self.n = expected_elements
        self.p = false_positive_rate

        # Calculate optimal size (m) and hash function count (k)
        self.m = int(- (self.n * math.log(self.p)) / (math.log(2) ** 2))
        self.k = int((self.m / self.n) * math.log(2))
        
        # Bit array allocated as bytearray (8 bits per byte)
        self._bit_array = bytearray(math.ceil(self.m / 8))

    def _hashes(self, key: str) -> List[int]:
        """Computes k bit positions using dual hash generation."""
        key_bytes = key.encode("utf-8")
        h1 = zlib.adler32(key_bytes)
        h2 = int(hashlib.md5(key_bytes).hexdigest()[:8], 16)

        return [
            (h1 + i * h2) % self.m
            for i in range(self.k)
        ]

    def add(self, key: str) -> None:
        """Sets the k corresponding bits to 1."""
        for bit_pos in self._hashes(key):
            byte_idx = bit_pos // 8
            bit_mask = 1 << (bit_pos % 8)
            self._bit_array[byte_idx] |= bit_mask

    def contains(self, key: str) -> bool:
        """
        Checks membership.
        Returns False if ANY bit is 0 (100% guarantee key does not exist).
        """
        for bit_pos in self._hashes(key):
            byte_idx = bit_pos // 8
            bit_mask = 1 << (bit_pos % 8)
            if not (self._bit_array[byte_idx] & bit_mask):
                return False
        return True
2. Resilient Cache-Aside Manager: src/cacheforge/patterns/cache_aside.py Jitter & Null Sentinel Interceptor 
# ==============================================================================
# CacheForge Patterns - Resilient Cache-Aside Orchestrator (Milestone 04)
# ==============================================================================

import random
from typing import Any, Callable, Optional, Awaitable
from cacheforge.storage.remote_client import RemoteCacheDriver
from cacheforge.patterns.bloom import BloomFilter

# Distinct marker to distinguish a cached null from an actual cache miss
NULL_SENTINEL = "__CF_NULL_SENTINEL_VAL__"

class CacheAsideManager:
    """
    ORCHESTRATES RESILIENT CACHE-ASIDE DATA FLOWS:
    1. Intercepts non-existent keys via Bloom Filter (Penetration Defense).
    2. Enforces Null-Value caching on missing DB rows (Layer 2 Defense).
    3. Adds randomized jitter to TTL expirations (Avalanche Defense).
    4. Enforces Cache Invalidation (Delete on Write) over Stale Overwrite.
    """
    def __init__(
        self,
        driver: RemoteCacheDriver,
        bloom_filter: Optional[BloomFilter] = None,
        default_ttl: int = 3600,
        null_sentinel_ttl: int = 60,
        jitter_ratio: float = 0.15
    ):
        self.driver = driver
        self.bloom = bloom_filter
        self.default_ttl = default_ttl
        self.null_ttl = null_sentinel_ttl
        self.jitter_ratio = jitter_ratio

    def _apply_jitter(self, base_ttl: int) -> int:
        """Disperses synchronized expiration across +/- jitter_ratio."""
        delta = int(base_ttl * self.jitter_ratio)
        return max(1, base_ttl + random.randint(-delta, delta))

    async def get_or_load(
        self,
        key: str,
        db_loader: Callable[[], Awaitable[Any]],
        ttl: Optional[int] = None
    ) -> Optional[Any]:
        # Step 1: Bloom Filter Pre-Check (Zero DB IO if absent)
        if self.bloom and not self.bloom.contains(key):
            return None  # 100% guarantee key does not exist

        # Step 2: Query Cache Layer
        cached_val = await self.driver.get(key)
        if cached_val == NULL_SENTINEL:
            return None  # Intercepted by null sentinel

        if cached_val is not None:
            return cached_val

        # Step 3: Cache Miss → Execute Database Loader
        db_data = await db_loader()

        if db_data is None:
            # Mitigate penetration: Cache null sentinel with very short TTL
            await self.driver.set(key, NULL_SENTINEL, ttl_seconds=self.null_ttl)
            return None

        # Step 4: Populate Cache with Jittered TTL
        active_ttl = self._apply_jitter(ttl or self.default_ttl)
        await self.driver.set(key, db_data, ttl_seconds=active_ttl)

        # Add key to Bloom filter if configured
        if self.bloom:
            self.bloom.add(key)

        return db_data

    async def write_through_mutation(
        self,
        key: str,
        db_writer: Callable[[], Awaitable[None]]
    ) -> None:
        """
        SAFE MUTATION INVARIANT:
        1. Write update to persistent database transactionally.
        2. Invalidate (delete) cache key to prevent stale race conditions.
        """
        await db_writer()
        await self.driver.delete(key)
3. Asynchronous Write-Behind Buffer: src/cacheforge/patterns/write_behind.py Write Coalescing Queue 
# ==============================================================================
# CacheForge Patterns - Write-Behind Asynchronous Batcher (Milestone 04)
# ==============================================================================

import asyncio
from typing import Dict, Any, Callable, Awaitable

class WriteBehindQueue:
    """
    WRITE-BEHIND (WRITE-BACK) BUFFER:
    Coalesces rapid write mutations in memory.
    Asynchronously flushes aggregated batches to persistent DB on interval ticks.
    """
    def __init__(
        self,
        flush_callback: Callable[[Dict[str, Any]], Awaitable[None]],
        flush_interval_seconds: float = 1.0,
        max_batch_size: int = 1000
    ):
        self.flush_callback = flush_callback
        self.flush_interval = flush_interval_seconds
        self.max_batch_size = max_batch_size
        self._buffer: Dict[str, Any] = {}
        self._lock = asyncio.Lock()
        self._running = False
        self._flush_task: Optional[asyncio.Task] = None

    async def start(self) -> None:
        self._running = True
        self._flush_task = asyncio.create_task(self._periodic_flush())

    async def stop(self) -> None:
        self._running = False
        if self._flush_task:
            self._flush_task.cancel()
        await self.flush_now()  # Drain remaining items on shutdown

    async def enqueue(self, key: str, value: Any) -> None:
        """Coalesces mutation into memory buffer."""
        async with self._lock:
            self._buffer[key] = value
            if len(self._buffer) >= self.max_batch_size:
                asyncio.create_task(self.flush_now())

    async def flush_now(self) -> None:
        async with self._lock:
            if not self._buffer:
                return
            batch = self._buffer
            self._buffer = {}

        try:
            await self.flush_callback(batch)
        except Exception as exc:
            # Restore unflushed items on database failure
            async with self._lock:
                for k, v in batch.items():
                    self._buffer.setdefault(k, v)

    async def _periodic_flush(self) -> None:
        while self._running:
            await asyncio.sleep(self.flush_interval)
            await self.flush_now()

Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Synchronized Static TTLs (Avalanche)

Setting identical fixed TTLs: driver.set(k, v, ttl=3600) across millions of products.

Why this crashes databases: When products are bulk-loaded or refreshed at 2:00 AM, all 500,000 keys expire at exactly 3:00:00 AM. Traffic surges into the database at the exact same second, completely crashing connection pools. Always apply randomized jitter ($\pm 15\%$) to disperse expirations smoothly over time.

❌ Ignoring Non-Existent Keys (Penetration)

Writing cache-aside logic that returns None on database misses without caching a null marker.

Why this causes DoS outages: An attacker scripts queries for random negative or missing IDs (/api/v1/orders/-1234). Because nothing is cached, 100% of the attack requests bypass the cache and hammer the database directly. Always pair Cache-Aside with Bloom Filters or Negative Caching.
