Part 01

Computer Science: The Dual-Write Distributed Race Condition

Phil Karlton famously observed: "There are only two hard things in Computer Science: cache invalidation and naming things."

The core source of cache corruption in microservices is the Dual-Write Hazard. When an application mutates state, it must write to two completely independent distributed systems: the relational database (System of Record) and the distributed cache (Redis).

Because distributed two-phase commit (2PC) transactions across disparate storage engines are prohibitively slow, developers write sequential updates. No matter which order you choose, a plain dual-write without an outbox pattern guarantees eventual data corruption:

The Dual-Write Failure Sequences

Why Sequential Dual Writes Inevitably Corrupt Data

Sequence A: Write DB → Delete Cache Crash Window
1. Worker writes update to PostgreSQL (COMMIT successful)
2. Worker container crashes (OOM / SIGKILL / Network partition)
3. cache.delete(key) IS NEVER EXECUTED!

✗ The Outage: Database holds fresh state, but Redis holds the stale record indefinitely. Future readers read stale data until TTL expires or manual intervention occurs.

Sequence B: Delete Cache → Write DB Interleaved Read Race
1. Worker 1 evicts key from Redis: cache.delete("user:42")
2. Concurrent Worker 2 reads "user:42" → Cache Miss!
3. Worker 2 reads OLD state from DB and repopulates Redis!
4. Worker 1 FINALLY commits new state to PostgreSQL

✗ Permanent Desynchronization: Redis is re-populated with the stale pre-mutation value after the deletion occurred, corrupting the cache permanently!

The Distributed Systems Conclusion:

Application code cannot reliably coordinate dual writes across network boundaries. The only way to guarantee cache consistency is to make the database mutation and the invalidation intent strictly atomic within a single local database transaction.

Part 02

Architecture: The Transactional Outbox Pattern & Change Data Capture (CDC)

To guarantee zero cache desynchronization across independent microservices, enterprise cloud platforms employ the Transactional Outbox Pattern coupled with Change Data Capture (CDC).

Instead of attempting to talk to Redis during an HTTP request, the application writes both the domain entity and an outbox invalidation event into the database inside the exact same local ACID transaction:

The Transactional Outbox & CDC Invalidation Pipeline
1. FastAPI Service
Atomic Local Transaction
BEGIN TX
UPDATE products ...
INSERT INTO outbox ...
COMMIT TX
→ WAL stream →
2. Debezium / CDC
Zero Overhead Tailer
Reads Postgres WAL
Extracts outbox events
Pushes to Kafka / PubSub
→ broadcast →
3. CacheForge Invalidator
Event-Driven Worker
Consumes event stream
Atomic Redis DEL
Sub-millisecond latency
Why CDC Guarantees 100% Invalidation Reliability:

Because the outbox event is committed to PostgreSQL in the same transaction as the row update, it is physically impossible for the data update to succeed while the invalidation event fails. If the database rolls back, the outbox record rolls back. If the application pod dies immediately after commit, Debezium tails the Write-Ahead Log (WAL) independently and executes the eviction asynchronously.

Part 03

Tagging Mechanics: Eliminating Dangerous $O(N)$ Wildcard Scans

In real-world web APIs, entities do not exist in isolation. Consider an e-commerce platform where a merchant updates their store settings:

  • You have cached the merchant's profile: merchant:42:profile
  • You have cached 50 paginated product listing pages: merchant:42:products:page_1, merchant:42:products:page_2 ...
  • You have cached discounted deals: merchant:42:deals

When the merchant updates their business name, how do you invalidate all 52 keys simultaneously?

❌ The Antipattern: Wildcard Scans O(N) Disastrous

Junior engineers write: keys = redis.keys("merchant:42:*"); redis.delete(*keys).

• Redis is SINGLE THREADED!
• KEYS * scans every single key in the entire cluster (e.g. 50,000,000 keys)
• Global lock held for 8,000ms → Cluster freezes!

Production databases crash from timeouts when KEYS * is called under load.

✔ The Industrial Fix: Cache Tagging O(1) Atomic

Maintain secondary inverted indexes using Redis Sets:

• When caching: SADD tag:merchant:42 "m:42:page_1"
• To invalidate tag: Fetch set members via SMEMBERS
• Atomic Lua script unlinks keys and tag in < 0.5ms!

Zero cluster iteration overhead. Executes in constant time proportional only to the merchant's items ($O(K)$).

1. Set-Based Cache Tagging Engine: src/cacheforge/patterns/tagging.py Atomic Lua Tag Eviction 
# ==============================================================================
# CacheForge Patterns - Redis Set-Based Cache Tagging Engine (Milestone 08)
# ==============================================================================

from typing import Any, List, Optional
from cacheforge.storage.remote_client import RemoteCacheDriver

# Atomic Lua script: Fetches all keys mapped to a tag, deletes the keys, and deletes the tag set
INVALIDATE_TAG_LUA = """
local tag_key = KEYS[1]
local members = redis.call('SMEMBERS', tag_key)
if #members > 0 then
    redis.call('DEL', unpack(members))
end
redis.call('DEL', tag_key)
return #members
"""

class TaggingCacheManager:
    """
    ATOMIC CACHE TAGGING ENGINE:
    Maintains secondary inverted indexes using Redis Sets.
    Eliminates dangerous KEYS * wildcard scans completely.
    Invalidates thousands of related keys atomically in sub-millisecond Lua operations.
    """
    def __init__(self, driver: RemoteCacheDriver):
        self.driver = driver
        self._invalidate_lua_sha: Optional[str] = None

    async def initialize(self) -> None:
        """Pre-compiles the tag invalidation Lua script in Redis RAM."""
        self._invalidate_lua_sha = await self.driver.client.script_load(INVALIDATE_TAG_LUA)

    async def set_with_tags(
        self,
        key: str,
        value: Any,
        tags: List[str],
        ttl_seconds: Optional[int] = None
    ) -> None:
        """Stores value and associates key with one or more invalidation tags."""
        await self.driver.set(key, value, ttl_seconds=ttl_seconds)

        if tags:
            pipe = self.driver.client.pipeline()
            for tag in tags:
                tag_key = f"tag:{tag}"
                pipe.sadd(tag_key, key)
                if ttl_seconds:
                    pipe.expire(tag_key, ttl_seconds * 2)  # Tag set outlives members slightly
            await pipe.execute()

    async def invalidate_tag(self, tag: str) -> int:
        """
        Atomically evicts all keys associated with the given tag.
        Returns the count of deleted keys.
        """
        if not self._invalidate_lua_sha:
            await self.initialize()

        tag_key = f"tag:{tag}"
        deleted_count = await self.driver.client.evalsha(
            self._invalidate_lua_sha, 1, tag_key
        )
        return int(deleted_count)
2. Transactional Outbox CDC Consumer: src/cacheforge/patterns/outbox.py Asynchronous Event-Driven Eviction 
# ==============================================================================
# CacheForge Patterns - Transactional Outbox & CDC Streamer (Milestone 08)
# ==============================================================================

from dataclasses import dataclass, asdict
import json
from typing import Any, List, Optional
from cacheforge.patterns.tagging import TaggingCacheManager

@dataclass
class OutboxEvent:
    """Represents an atomic outbox event written inside database transactions."""
    event_id: str
    aggregate_type: str  # e.g., "product", "merchant", "user"
    aggregate_id: str    # e.g., "42"
    event_type: str      # e.g., "UPDATED", "DELETED"
    invalidation_keys: List[str]
    invalidation_tags: List[str]


class CDCOutboxConsumer:
    """
    CHANGE DATA CAPTURE (CDC) EVENT CONSUMER:
    Emulates a Debezium / Kafka stream tailer.
    Consumes outbox events emitted by database WAL commits and executes
    targeted key deletions and tag invalidations in CacheForge.
    """
    def __init__(self, tag_manager: TaggingCacheManager):
        self.tag_manager = tag_manager

    async def process_cdc_message(self, raw_message: str | bytes) -> int:
        """Parses CDC payload and executes cache invalidations."""
        data = json.loads(raw_message)
        event = OutboxEvent(**data)

        total_evictions = 0

        # 1. Direct Key Evictions
        for key in event.invalidation_keys:
            if await self.tag_manager.driver.delete(key):
                total_evictions += 1

        # 2. Tag-Based Cascade Evictions
        for tag in event.invalidation_tags:
            evicted = await self.tag_manager.invalidate_tag(tag)
            total_evictions += evicted

        return total_evictions

import json
import pytest
from testcontainers.redis import RedisContainer
from cacheforge.storage.remote_client import RemoteCacheDriver
from cacheforge.patterns.tagging import TaggingCacheManager
from cacheforge.patterns.outbox import CDCOutboxConsumer, OutboxEvent

@pytest.fixture(scope="session")

@pytest.mark.integration
class TestCDCTaggingInvalidation:
    """Verifies atomic tag invalidations and CDC outbox event consumption."""

    @pytest.mark.asyncio
    async def test_tag_invalidation_evicts_all_associated_entries(self, redis_server):
        url = f"redis://{redis_server.get_container_host_ip()}:{redis_server.get_exposed_port(6379)}/0"
        driver = RemoteCacheDriver(redis_url=url)
        tag_manager = TaggingCacheManager(driver)
        await tag_manager.initialize()

        # Cache 3 distinct product pages under the same tag "merchant:88"
        await tag_manager.set_with_tags("m:88:p1", {"page": 1}, tags=["merchant:88"])
        await tag_manager.set_with_tags("m:88:p2", {"page": 2}, tags=["merchant:88"])
        await tag_manager.set_with_tags("m:88:p3", {"page": 3}, tags=["merchant:88"])

        # Unrelated merchant
        await tag_manager.set_with_tags("m:99:p1", {"page": 1}, tags=["merchant:99"])

        # Invalidate tag "merchant:88"
        evicted = await tag_manager.invalidate_tag("merchant:88")
        assert evicted == 3

        # All 3 pages for merchant 88 MUST be evicted
        assert await driver.get("m:88:p1") is None
        assert await driver.get("m:88:p2") is None
        assert await driver.get("m:88:p3") is None

        # Unrelated merchant remains active and intact
        assert await driver.get("m:99:p1") is not None
        await driver.close()

    @pytest.mark.asyncio
    async def test_cdc_outbox_consumer_processes_stream_message(self, redis_server):
        url = f"redis://{redis_server.get_container_host_ip()}:{redis_server.get_exposed_port(6379)}/0"
        driver = RemoteCacheDriver(redis_url=url)
        tag_manager = TaggingCacheManager(driver)
        await tag_manager.initialize()

        await tag_manager.set_with_tags("user:500:profile", {"name": "Alice"}, tags=["user:500"])

        consumer = CDCOutboxConsumer(tag_manager)
        event_payload = json.dumps({
            "event_id": "evt_101",
            "aggregate_type": "user",
            "aggregate_id": "500",
            "event_type": "UPDATED",
            "invalidation_keys": ["user:500:profile"],
            "invalidation_tags": ["user:500"]

        # Process simulated CDC stream event
        total = await consumer.process_cdc_message(event_payload)
        assert total >= 1

        # Profile key is evicted
        assert await driver.get("user:500:profile") is None
        await driver.close()
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Deleting Cache Inside DB Transactions

Writing with db.transaction(): db.update(); redis.delete(key).

Why this causes severe bugs: If your database transaction takes 50ms to finish committing after the Redis deletion occurs, a concurrent reader can experience a cache miss, read the uncommitted old state from the database, and write it back to Redis! Furthermore, if the database transaction rolls back, your cache was deleted for an update that never happened. Always emit outbox records or invalidate strictly after commit.

❌ Unbounded Cache Tag Set Accumulation

Adding millions of unique product keys to a single tag set without setting a TTL or cleaning up expired keys.

Why this causes memory leaks: In Redis, Set members do not expire individually when the underlying target key expires. Over months of traffic, tag sets accumulate millions of dead string keys. Always attach a safety TTL to the tag set itself or periodically prune stale tag members.
