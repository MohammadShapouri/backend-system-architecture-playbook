Part 01

Computer Science: Dependency Injection (DI)

If an object needs another object to do its job (e.g., a CheckoutService needs a PaymentGateway), how does it get it?

Junior developers instantiate dependencies inside the class. This is called Hardcoding Dependencies. Senior architects pass dependencies into the class from the outside. This is called Dependency Injection. It perfectly fulfills the 'D' in SOLID: The Dependency Inversion Principle.

Architectural Coupling: Hardcoding vs. Injection
1. Hardcoded (Anti-Pattern) Tight Coupling

The service creates its own Stripe gateway. It is now permanently glued to Stripe.

class CheckoutService:
def __init__(self):
# FATAL: Hardcoded instantiation
self.gateway = StripeGateway('sk_live_...')
  • Testing Nightmare: You cannot test the checkout logic without actually hitting the live Stripe API.
  • Zero Flexibility: Switching to PayPal requires editing this class source code, violating the Open/Closed Principle.
2. Constructor Injection (Clean) Loose Coupling

The service accepts ANY object that fulfills the PaymentGateway abstract contract.

class CheckoutService:
def __init__(self, gateway: PaymentGateway):
# CLEAN: Passed in from outside
self.gateway = gateway
  • Easily Testable: Pass in a dummy MockGateway to test logic safely and instantly.
  • Perfectly Polymorphic: Accepts Stripe, PayPal, or Crypto seamlessly.

1. Orchestration Service: src/orderforge/engine/checkout.py Dependency Injection 
# ==============================================================================
# OrderForge Engine - Orchestration & Dependency Injection (Milestone 06)
# ==============================================================================

from orderforge.domain.order import Order
from orderforge.domain.gateway import PaymentGateway

class CheckoutService:
    """
    High-level Use Case Orchestrator.
    Adheres strictly to the Dependency Inversion Principle.
    """
    
    def __init__(self, gateway: PaymentGateway) -> None:
        # DEPENDENCY INJECTION: We accept the abstract interface PaymentGateway.
        # This service is completely decoupled from Stripe or PayPal specifics!
        self.gateway: PaymentGateway = gateway

    def process_checkout(self, order: Order) -> str:
        """
        Executes the business workflow: 
        Validates order, charges via gateway, updates status.
        """
        if len(order.items) == 0:
            raise ValueError("Cannot checkout an empty order.")
            
        if order._is_paid:
            raise RuntimeError("Order has already been processed.")

        amount_due = order.total_amount
        
        # POLYMORPHIC DISPATCH: 
        # The service asks the gateway to charge, completely unaware of HOW it happens.
        transaction_receipt = self.gateway.process_payment(amount_due)
        
        # Mutate order state upon success
        order.mark_as_paid()
        
        return transaction_receipt
2. The Master Executable: src/orderforge/main.py End-to-End Orchestration

# OrderForge - The Master Executable Runbook (Milestone 06)

from orderforge.domain.item import Item
from orderforge.domain.order import Address, Customer, Order
from orderforge.domain.gateways import StripeGateway, PayPalGateway
from orderforge.engine.checkout import CheckoutService

def main():
    print("--- Initializing OrderForge Engine ---")

    # 1. Instantiate Core Value Objects & Entities
    shipping_addr = Address(street="123 Tech Lane", city="Austin", zip_code="78701")
    customer = Customer(customer_id="CUST-001", name="Alice Engineer", address=shipping_addr)

    # 2. Instantiate Catalog Items
    laptop = Item(sku="TECH-101", name="Pro Laptop", price=1200.00)
    mouse = Item(sku="TECH-102", name="Wireless Mouse", price=50.00)

    # 3. Assemble the Order Aggregate (Composition)
    order = Order(order_id="ORD-999", customer=customer)
    order.add_product(laptop, quantity=1)
    order.add_product(mouse, quantity=2)  # Total should be $1300.00

    print(f"\nCart Assembled for {order.customer.name}:")
    for line in order.items:
        print(f"  - {line}")
    print(f"Grand Total: ${order.total_amount:.2f}")

    # 4. Configure concrete Gateway & Inject into Service
    stripe_provider = StripeGateway(secret_key="sk_live_abc123")
    
    # DEPENDENCY INJECTION IN ACTION
    checkout_service = CheckoutService(gateway=stripe_provider)

    # 5. Execute Checkout
    print("\nProcessing Payment via Stripe...")
    receipt = checkout_service.process_checkout(order)
    print(f"Success! Receipt ID: {receipt}")
    print(f"Order Status (Paid): {order._is_paid}")

    # 6. Demonstrate Strategy Swapping (Polymorphism)
    print("\n--- Swapping to PayPal for New Order ---")
    order2 = Order(order_id="ORD-1000", customer=customer)
    order2.add_product(mouse, quantity=1)
    
    paypal_provider = PayPalGateway(client_email="admin@shop.com")
    
    # Swap the strategy transparently!
    checkout_service.gateway = paypal_provider
    receipt2 = checkout_service.process_checkout(order2)
    print(f"Success! Receipt ID: {receipt2}")


if __name__ == "__main__":
    main()

# OrderForge Test Suite - Checkout Service Integration (Milestone 06)

import pytest
from orderforge.domain.item import Item
from orderforge.domain.order import Address, Customer, Order
from orderforge.domain.gateway import PaymentGateway
from orderforge.engine.checkout import CheckoutService


class MockGateway(PaymentGateway):
    """
    A fake gateway built specifically for fast, isolated unit testing.
    Proves the value of Dependency Injection!
    """
    def authenticate(self) -> bool:
        return True

    def process_payment(self, amount: float) -> str:
        return f"MOCK_TXN_{amount}"


class TestCheckoutIntegration:
    """End-to-End tests asserting the master service behavior."""

    def setup_method(self):
        address = Address("1 St", "City", "000")
        self.customer = Customer("C-1", "Bob", address)
        self.order = Order("O-1", self.customer)
        
        # Inject the MOCK gateway instead of live Stripe!
        self.service = CheckoutService(gateway=MockGateway())

    def test_successful_checkout_flow(self):
        item = Item("SKU-1", "Item", 100.0)
        self.order.add_product(item, 1)

        receipt = self.service.process_checkout(self.order)

        # Confirm the mock gateway was called successfully
        assert receipt == "MOCK_TXN_100.0"
        # Confirm the order's state was mutated appropriately
        assert self.order._is_paid is True

    def test_checkout_fails_on_empty_order(self):
        with pytest.raises(ValueError, match=r"empty order"):
            self.service.process_checkout(self.order)
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Instantiating Concrete Classes inside Services

Writing self.db = MySQLConnection() inside your __init__.

Why this causes technical debt: You have hardcoded the dependency. You cannot write unit tests without spinning up a live MySQL database container! Always inject dependencies through the constructor: def __init__(self, db: DatabaseProtocol):

❌ Catching Broad Exceptions Blindly

Writing try: process() except Exception: print("Error") in your orchestration layers.

Why this hides catastrophic bugs: Catching Exception blindly swallows everything, including `KeyError`, `TypeError` and basic typos in your code. You will see "Error" printed out, but you won't know that it crashed because you misspelled a variable name! Catch only the specific exceptions you intend to handle (e.g. `PermissionError`).
