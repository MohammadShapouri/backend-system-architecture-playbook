Part 01

Computer Science: Composition over Inheritance

When beginners learn Object-Oriented Programming, they are immediately taught Inheritance (e.g., Dog inherits from Animal). This leads to a dangerous habit: using inheritance to share code everywhere.

Inheritance implies an "Is-A" relationship. It is the tightest form of coupling in software. If the parent class changes, the child class breaks. Modern software architecture relies on the golden rule: Favor Composition Over Inheritance. Composition implies a "Has-A" relationship. Instead of inheriting behavior, an object simply contains (or references) an instance of another object and delegates work to it.

Structural Relationships: Is-A vs. Has-A
1. Inheritance ("Is-A") Tight Coupling

class SpecialOrder(Order):

  • The Gorilla/Banana Problem: You just wanted a single method from the parent class, but you get the entire parent class, all its state, and all its bugs.
  • Fragile Base Class: Changing a private method in the parent can unknowingly break the child class.
2. Composition ("Has-A") Loose Coupling

class Order:
    def __init__(self): self.customer = Customer()

  • Encapsulation Preserved: The Order interacts with the Customer only through its public methods.
  • Dynamic Assembly: You can swap out which Customer is attached at runtime!
Part 02

Under the Hood: Protecting Internal Lists & Aggregations

When you compose objects into a collection (like storing multiple OrderItem instances inside a list in the Order), a new danger emerges: State Leakage.

If your Order has an internal list self._items, and you expose it via a standard property, any external code can mutate the list directly (e.g., order.items.clear()). This completely bypasses your class's validation rules!

State Protection

Defensive Copying via list.copy()

To protect internal state, never return a direct reference to a mutable internal collection. Instead, return a shallow copy using Python's native .copy() method (or list(items)). 

class Order:
    def __init__(self):
        self._items = []

    @property
    def items(self):
        # Caller receives a brand new list pointer.
        # Mutating it won't affect self._items!
        return self._items.copy()
Data Synthesis

Aggregating Data with sum()

When an object owns nested objects, it acts as the "Aggregate Root". If you need the total cost of an order, the Order shouldn't store a hardcoded self.total (which can go out of sync). It should dynamically aggregate the data using Python's built-in sum() combined with a generator expression: 

@property
def total_amount(self) -> float:
    # Dynamic O(n) calculation guarantees accuracy.
    return sum(item.subtotal for item in self._items)
Part 03

Class Mechanics: Alternative Constructors with `@classmethod`

Sometimes the standard __init__ constructor is too restrictive. What if you want to create an Order directly from a JSON dictionary? Or create an "empty" order with default values?

Python does not support method overloading (you can't write two __init__ methods). Instead, the standard practice is to use the @classmethod decorator to build Factory Methods.

// How @classmethod Works:

When a method is decorated with @classmethod, Python automatically passes the class itself as the first argument (conventionally named cls), rather than the instance (self).

Inside the method, calling cls(...) invokes the __init__ method, allowing you to return a perfectly constructed instance without hardcoding the class name.

1. Domain Model: src/orderforge/domain/order.py Composition & Defensive State 
# ==============================================================================
# OrderForge Domain - Composition & Nested Instances (Milestone 03)
# ==============================================================================

from typing import List
from orderforge.domain.item import Item
from orderforge.domain.order_item import OrderItem


class Address:
    """Simple value object representing a physical location."""
    def __init__(self, street: str, city: str, zip_code: str) -> None:
        self.street = street
        self.city = city
        self.zip_code = zip_code

    def __repr__(self) -> str:
        return f"{self.street}, {self.city} ({self.zip_code})"


class Customer:
    """Entity representing a buyer. Demonstrates deep nesting by composing an Address."""
    def __init__(self, customer_id: str, name: str, address: Address) -> None:
        self.customer_id = customer_id
        self.name = name
        # Composition: Customer *has an* Address
        self.address: Address = address

    def __repr__(self) -> str:
        return f"Customer(id={self.customer_id!r}, name={self.name!r})"


class Order:
    """
    The Aggregate Root. Coordinates the Customer and multiple OrderItems.
    Responsible for maintaining cart state integrity.
    """
    def __init__(self, order_id: str, customer: Customer) -> None:
        self.order_id = order_id
        self.customer = customer
        
        # Protected internal list. Must not be exposed directly!
        self._items: List[OrderItem] = []
        self._is_paid: bool = False

    @classmethod
    def create_empty(cls, order_id: str, customer: Customer) -> "Order":
        """
        FACTORY METHOD: Alternative constructor.
        Note the use of 'cls(order_id, customer)' instead of hardcoding 'Order(...)'.
        """
        return cls(order_id=order_id, customer=customer)

    def add_product(self, item: Item, quantity: int = 1) -> None:
        """Encapsulated business logic for adding items."""
        if self._is_paid:
            raise RuntimeError("Cannot modify an order that has already been paid.")
            
        # The Order manages the instantiation of the OrderItem
        order_item = OrderItem(item=item, quantity=quantity)
        self._items.append(order_item)

    @property
    def items(self) -> List[OrderItem]:
        """
        DEFENSIVE COPY: 
        Returns a shallow copy so external code cannot run `order.items.clear()` 
        and bypass our validation rules.
        """
        return self._items.copy()

    @property
    def total_amount(self) -> float:
        """Dynamically calculates sum across all nested items."""
        return sum(line_item.subtotal for line_item in self._items)

    def mark_as_paid(self) -> None:
        self._is_paid = True

    def __repr__(self) -> str:
        return f"Order(id={self.order_id!r}, items={len(self._items)}, total=${self.total_amount:.2f})"

# OrderForge Test Suite - Order Composition Verification (Milestone 03)
# ==============================================================================

import pytest
from orderforge.domain.item import Item
from orderforge.domain.order import Address, Customer, Order


class TestOrderComposition:
    """Unit tests asserting nested state, defensive copies, and factory methods."""

    def setup_method(self):
        self.address = Address("123 Main St", "Tech City", "99999")
        self.customer = Customer("C-1", "Alice", self.address)
        self.laptop = Item("SKU-1", "Laptop", 1000.0)
        self.mouse = Item("SKU-2", "Mouse", 50.0)

    def test_factory_method_creation(self):
        # Instantiate using @classmethod
        order = Order.create_empty("ORD-1", self.customer)
        assert order.order_id == "ORD-1"
        assert len(order.items) == 0

    def test_aggregate_calculations_with_nested_items(self):
        order = Order("ORD-2", self.customer)
        
        # Add 1 Laptop ($1000) and 2 Mice ($50 * 2 = $100)
        order.add_product(self.laptop, 1)
        order.add_product(self.mouse, 2)

        # Total should aggregate dynamically
        assert order.total_amount == 1100.0
        assert len(order.items) == 2

    def test_defensive_copy_protects_internal_state(self):
        order = Order("ORD-3", self.customer)
        order.add_product(self.laptop, 1)

        # External caller retrieves the items list
        exposed_items = order.items
        
        # Malicious or accidental modification
        exposed_items.clear()

        # The internal state must remain unharmed!
        assert len(order.items) == 1

    def test_business_rules_block_modifying_paid_orders(self):
        order = Order("ORD-4", self.customer)
        order.mark_as_paid()

        with pytest.raises(RuntimeError, match=r"already been paid"):
            order.add_product(self.mouse, 1)
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Primitive Obsession (Passing Dicts instead of Objects)

Writing def __init__(self, customer_dict: dict): instead of accepting a strong Customer object instance.

Why this is terrible: Passing raw dictionaries around destroys Type Hinting, bypasses any validation rules defined inside the Customer class, and forces the `Order` class to guess if the dictionary contains the correct keys (like `"name"` or `"id"`). Always compose strong, validated objects.

❌ The "God Class" Subclassing

Trying to add functionality by doing class Order(Customer, Address):

Why this fails: An Order *is not* a Customer, and it *is not* an Address. Using inheritance here creates a bizarre, bloated "God Class" that attempts to be everything at once. Use composition: an Order *has a* Customer, who *has an* Address. Keep classes small and focused on a single responsibility.
