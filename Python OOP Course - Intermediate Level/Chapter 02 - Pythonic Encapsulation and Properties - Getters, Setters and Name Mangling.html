Part 01

Computer Science: The Uniform Access Principle

Encapsulation is the practice of hiding the internal state of an object and requiring all interactions to be performed through an object's methods. In static languages (like Java), this is rigidly enforced by making attributes private and exposing public getPrice() and setPrice() methods from day one, "just in case" you need validation later.

Python rejects this boilerplate in favor of Bertrand Meyer's Uniform Access Principle. In Python, you start with simple, public attributes. If business rules change and you suddenly need to validate an attribute, you wrap it in a @property.

The caller continues using standard dot notation (obj.price = 50), completely unaware that they are now triggering hidden validation methods under the hood!

Encapsulation Mechanics: Java Boilerplate vs. Pythonic Properties
1. Explicit Getters/Setters (Un-Pythonic) Verbose API 
class OrderItem:
    def __init__(self, qty: int):
        self.set_quantity(qty)

    def get_quantity(self) -> int:
        return self._qty
        
    def set_quantity(self, value: int):
        if value <= 0: raise ValueError()
        self._qty = value

# Caller usage is clunky:
item.set_quantity(item.get_quantity() + 1)
2. Python @property (Uniform Access) Clean API 
class OrderItem:
    def __init__(self, qty: int):
        self.quantity = qty # Triggers setter!

    @property
    def quantity(self) -> int:
        return self._qty
        
    @quantity.setter
    def quantity(self, value: int):
        if value <= 0: raise ValueError()
        self._qty = value

# Caller usage is elegant and natural:
item.quantity += 1
Part 02

Visibility Conventions: Protected vs. Name Mangling

Because Python has no compiler-enforced private keyword, it relies on two primary mechanisms to signal visibility to developers:

The Cultural Convention

Protected (_single_leading)

A single leading underscore (e.g., self._quantity) is purely a cultural convention. It does nothing at runtime.

It signals to other developers: "This is an internal implementation detail. If you access it directly from outside the class, your code might break in the next version." It is the standard way to store the actual data behind a @property.

The Runtime Mechanism

Name Mangling (__double_leading)

A double leading underscore (e.g., self.__secret) triggers Name Mangling. CPython dynamically rewrites the attribute name during compilation to include the class name: _ClassName__secret.

This is not for security! Its sole architectural purpose is to prevent accidental attribute name collisions in deep inheritance trees (where a subclass might unknowingly use the same variable name as a parent class).

Part 03

Computed Attributes: Read-Only Properties

A powerful feature of the @property decorator is the ability to create Computed Attributes (also known as Read-Only properties).

If you define a @property but intentionally omit the @name.setter, the attribute becomes strictly read-only from the outside. Attempting to assign a value to it raises an immediate AttributeError: can't set attribute. This is highly effective for dynamically calculated totals (like subtotal = price * quantity) where storing the result in a separate variable would risk state de-synchronization.

OrderForge Milestone 02: The OrderItem & Validation

We now assemble Milestone 02 of OrderForge. We implement src/orderforge/domain/order_item.py.

The architecture features:

  • OrderItem: Composes the Item from Chapter 1 with a purchase quantity.
  • Validation on Initialization: Passing self.quantity = quantity inside __init__ intentionally triggers the property setter, ensuring validation rules run immediately upon creation.
  • Data Encapsulation: The true integer is stored safely in the protected _quantity variable.
  • Computed Property: subtotal dynamically calculates the total cost, preventing out-of-sync data if the quantity is later updated.

# ==============================================================================
# OrderForge Domain - Pythonic Encapsulation & Properties (Milestone 02)
# ==============================================================================

from orderforge.domain.item import Item


class OrderItem:
    """
    Domain Model: Represents a specific quantity of an Item added to an Order.
    Demonstrates the Uniform Access Principle via @property validation.
    """
    def __init__(self, item: Item, quantity: int) -> None:
        self.item: Item = item
        
        # TRICK: Assigning to the public attribute `self.quantity`
        # automatically triggers the `@quantity.setter` method below!
        # This ensures validation runs immediately upon instantiation.
        self.quantity = quantity

    @property
    def quantity(self) -> int:
        """Getter: Exposes the protected _quantity attribute seamlessly."""
        return self._quantity

    @quantity.setter
    def quantity(self, value: int) -> None:
        """Setter: Enforces domain business rules before modifying internal state."""
        if not isinstance(value, int):
            raise TypeError("Quantity must be a whole integer.")
        if value <= 0:
            raise ValueError(f"Quantity must be greater than zero. Received: {value}")
        
        # Safe assignment to the protected convention variable
        self._quantity: int = value

    @property
    def subtotal(self) -> float:
        """
        Computed / Read-Only Property.
        Has no @subtotal.setter. Cannot be manually overridden.
        Dynamically calculates the total based on current price and quantity.
        """
        return self.item.price * self.quantity

    def __repr__(self) -> str:
        return f"OrderItem(item={self.item.sku!r}, quantity={self.quantity}, subtotal={self.subtotal:.2f})"

import pytest
from orderforge.domain.item import Item
from orderforge.domain.order_item import OrderItem


class TestOrderItemProperties:
    """Unit tests asserting property validation, computed attributes, and error boundaries."""

    def setup_method(self):
        # Reusable base item for tests
        self.item = Item(sku="SKU-100", name="Monitor", price=200.0)

    def test_successful_creation_and_computed_subtotal(self):
        order_item = OrderItem(self.item, quantity=3)
        
        # Test standard property access
        assert order_item.quantity == 3
        # Test computed read-only property
        assert order_item.subtotal == 600.0

    def test_setter_validation_blocks_invalid_quantity(self):
        order_item = OrderItem(self.item, quantity=1)
        
        with pytest.raises(ValueError, match=r"greater than zero"):
            order_item.quantity = -5  # Triggers setter validation

        with pytest.raises(ValueError, match=r"greater than zero"):
            order_item.quantity = 0

        with pytest.raises(TypeError, match=r"whole integer"):
            order_item.quantity = "five"

    def test_computed_property_is_read_only(self):
        order_item = OrderItem(self.item, quantity=2)
        
        with pytest.raises(AttributeError, match=r"can't set attribute"):
            # subtotal lacks a @subtotal.setter, so it cannot be manually overridden
            order_item.subtotal = 999.99

    def test_subtotal_dynamically_updates_on_state_change(self):
        order_item = OrderItem(self.item, quantity=2)
        assert order_item.subtotal == 400.0
        
        # Mutate the quantity through the public property
        order_item.quantity = 5
        
        # Subtotal must dynamically reflect the new state!
        assert order_item.subtotal == 1000.0
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The Infinite Recursion Trap in Setters

Writing self.quantity = value inside the @quantity.setter.

Why it crashes: Assigning to the public property name inside the setter triggers the setter *again*, which assigns the name *again*, resulting in an infinite loop that crashes Python with a RecursionError: maximum recursion depth exceeded. You must store the value in a protected attribute, e.g., self._quantity = value.

❌ Expensive Logic in Properties

Putting a database query or network request inside a @property, like @property def current_weather(self): return api.get('/weather').

Why this is terrible for maintenance: Python developers naturally assume that accessing an attribute (e.g. obj.weather) is a cheap, instant, in-memory operation. If someone puts obj.weather inside a `for` loop, your app will make 10,000 API calls and lock up. Rule: If an operation requires heavy computation or external I/O, expose it as an explicit method (def fetch_weather():).
