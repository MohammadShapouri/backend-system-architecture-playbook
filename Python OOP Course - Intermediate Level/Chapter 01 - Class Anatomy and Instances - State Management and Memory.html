Part 01

Computer Science: The Blueprint vs. The House

In Object-Oriented Programming, a Class is a blueprint. It defines the structure, behavior (methods), and rules for a concept, but it takes up almost no active data memory. An Instance is a physical object constructed from that blueprint, residing in your computer's RAM with its own distinct, isolated state.

When you create an instance, Python passes a special pointer to every method inside the class. By convention, this pointer is called self. self ensures that when you change a price on Item A, it does not accidentally change the price on Item B.

Memory Topologies: Class Definitions vs. Instance Allocations

Visualizing how 'self' separates memory spaces

1. The Class (Blueprint)
// Memory space: class Item
__init__(self, name, price)
apply_discount(self, percent)
  • Resides in memory exactly once.
  • Holds the logic (methods) that all instances will share and execute.
2. Instance A (Memory)
// obj = Item("Laptop", 1200)
self.name = "Laptop"
self.price = 1200.00
  • A dedicated dictionary in RAM holding specific state.
  • When calling obj.apply_discount(), Python implicitly passes this specific dictionary as self.
3. Instance B (Memory)
// obj2 = Item("Mouse", 49)
self.name = "Mouse"
self.price = 49.00
  • Completely isolated from Instance A.
  • Changing Instance B's price has zero effect on Instance A.
Part 02

Architecture Warning: Instance vs. Class Attributes

A crucial distinction in Python OOP is where variables are declared. Variables defined inside __init__ attached to self are Instance Attributes. Variables defined directly under the class declaration (outside of any method) are Class Attributes.

✗ The Mutable Class Attribute Trap

Beginners frequently declare default lists or dictionaries at the class level: 

class Order:
    # FATAL: Declared at class level!
    items = []  

    def add_item(self, item):
        self.items.append(item)

Because items is created once on the blueprint, all instances share the exact same list in memory. If Customer A adds a laptop to their cart, it magically appears in Customer B's cart!

✓ The Correct Pattern: Instance Attributes

Mutable state (lists, dicts, custom objects) must always be initialized inside __init__ attached to self: 

class Order:
    def __init__(self):
        # SAFE: A brand new list allocated per instance
        self.items = []  

    def add_item(self, item):
        self.items.append(item)

Class attributes should be strictly reserved for immutable constants (e.g. DEFAULT_CURRENCY = "USD").

Part 03

Dunder Methods: `__repr__` vs. `__str__`

By default, if you print a custom object in Python, you get a useless memory pointer: <Item object at 0x7f81a>. To fix this, Python provides two "dunder" (double-underscore) methods to control string representation.

Dunder Method Target Audience Goal Execution Trigger
__repr__(self) Developers (Debugging) Must be unambiguous. It should reveal the object's class and internal state, looking like a valid Python constructor if possible (e.g. Item(sku='123', price=10.0)). Logging, Exception Tracebacks, inspecting items inside Lists/Dicts, and the interactive REPL.
__str__(self) End Users (UI / Output) Must be highly readable and nicely formatted (e.g. "Wireless Mouse ($10.00)"). Can safely hide complex internal identifiers. Calling print(obj), str(obj), or using simple f-strings f"{obj}".

Best Practice Rule: Always implement __repr__ first. If __str__ is missing, Python will safely fall back to using __repr__.

1. Domain Model: src/orderforge/domain/item.py Class Anatomy & State 
# ==============================================================================
# OrderForge Domain - Class Anatomy & The Item Model (Milestone 01)
# ==============================================================================

class Item:
    """
    Domain Model: Represents a distinct product available for purchase.
    Demonstrates proper isolation of instance state and the representation contract.
    """
    # CLASS ATTRIBUTE: Shared across all instances of Item.
    # Safe because strings are immutable. All items default to USD.
    DEFAULT_CURRENCY: str = "USD"

    def __init__(self, sku: str, name: str, price: float) -> None:
        # INSTANCE ATTRIBUTES: Appended to 'self'.
        # Each instance gets its own isolated memory space.
        self.sku: str = sku
        self.name: str = name
        
        # Ensure price is converted to a float (basic validation)
        if price < 0:
            raise ValueError("Price cannot be negative.")
        self.price: float = float(price)

    def apply_discount(self, discount_percent: float) -> None:
        """Instance Method: Mutates the internal state of THIS specific instance."""
        if 0 < discount_percent <= 100:
            multiplier = 1 - (discount_percent / 100)
            self.price = self.price * multiplier
        else:
            raise ValueError("Discount must be between 1 and 100.")

    def __repr__(self) -> str:
        """
        DEVELOPER DIAGNOSTIC: 
        Unambiguous representation. Mimics valid Python instantiation syntax.
        The !r formatting applies repr() to the strings, wrapping them in quotes.
        """
        return f"Item(sku={self.sku!r}, name={self.name!r}, price={self.price:.2f})"

    def __str__(self) -> str:
        """
        USER PRESENTATION:
        Clean, readable output hiding technical details like the SKU.
        """
        return f"{self.name} - {self.DEFAULT_CURRENCY} ${self.price:.2f}"
2. Unit Test Battery: tests/test_item.py Testing Instantiation & Identity 
# ==============================================================================
# OrderForge Test Suite - Item Model Verification (Milestone 01)
# ==============================================================================

import pytest
from orderforge.domain.item import Item


class TestItemModel:
    """Unit tests asserting instance isolation, validation, and representations."""

    def test_instance_isolation(self):
        # Create two distinct instances
        item1 = Item("SKU-01", "Laptop", 1000.0)
        item2 = Item("SKU-02", "Mouse", 50.0)

        # Mutating item1 must NOT affect item2
        item1.apply_discount(10)  # 10% off
        
        assert item1.price == 900.0
        assert item2.price == 50.0   # Untouched!
        assert item1 is not item2    # Distinct memory pointers

    def test_class_attribute_sharing(self):
        item1 = Item("SKU-01", "Laptop", 1000.0)
        item2 = Item("SKU-02", "Mouse", 50.0)

        # Both share the class attribute
        assert item1.DEFAULT_CURRENCY == "USD"
        assert item2.DEFAULT_CURRENCY == "USD"

    def test_price_validation(self):
        with pytest.raises(ValueError, match=r"Price cannot be negative"):
            Item("SKU-03", "Broken Item", -5.0)

    def test_representations(self):
        item = Item("TECH-101", "Keyboard", 120.5)

        # __repr__ for developers
        assert repr(item) == "Item(sku='TECH-101', name='Keyboard', price=120.50)"

        # __str__ for users
        assert str(item) == "Keyboard - USD $120.50"
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ Forgetting the `self` Parameter

Writing def apply_discount(percent): instead of def apply_discount(self, percent):.

Why it crashes: When you call item.apply_discount(10), Python secretly translates this to Item.apply_discount(item, 10). If your method signature doesn't accept that first self argument, Python throws a TypeError: apply_discount() takes 1 positional argument but 2 were given!

❌ Defining Attributes Outside __init__

Attaching new variables to self lazily inside other methods, like creating self.discount_applied = True inside the apply_discount method.

Why this is terrible for maintenance: It alters the "shape" of the object at runtime. If another method tries to read self.discount_applied before apply_discount is called, the program crashes with an AttributeError. Rule: Define *all* instance attributes inside __init__, even if you just set them to None or False initially.
