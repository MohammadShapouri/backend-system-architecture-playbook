Part 01

Computer Science: Polymorphism & Dynamic Dispatch

Polymorphism (from Greek, meaning "many forms") is the ability to present the same interface for differing underlying data types. In practical terms, it means you can call gateway.process_payment(100.0), and the system automatically figures out which version of the method to run.

This is powered by Dynamic Dispatch. When Python executes a method, it does not look at the static type hints you wrote in your code. It looks at the object sitting in memory at that exact millisecond, checks its `ob_type` pointer, and dispatches the call to the appropriate class dictionary.

Dynamic Dispatch: Eliminating Type Conditionals
Static Type Ladder (Anti-Pattern)

Procedural code relies on branching. If you add a new payment method, you must rewrite this function!

def charge_customer(provider, amt):
if provider.name == "stripe":
provider.charge_card(amt)
elif provider.name == "paypal":
provider.send_money(amt)
elif provider.name == "crypto":
provider.transfer_eth(amt)
Polymorphic Dispatch (Pythonic)

The caller doesn't care what the object is, only what it can do. Adding a new provider requires zero changes to this function!

def charge_customer(gateway: PaymentGateway, amt):
# Python dynamically routes the call
gateway.process_payment(amt)
Part 02

Under the Hood: Duck Typing & the Strategy Pattern

In strict languages (Java, C#), an object must explicitly declare its lineage: class Stripe implements Gateway. This is called Nominal Subtyping (typing by name).

Python strongly embraces Structural Subtyping, famously known as Duck Typing: "If it walks like a duck and quacks like a duck, it must be a duck." While we used abc.ABC in Chapter 04 to enforce a contract, Python's runtime dispatch does not actually care if you inherited from the ABC! As long as your class provides the exact process_payment method expected by the caller, the call will succeed.

Design Pattern

The Strategy Pattern

Polymorphism powers one of the most vital design patterns in modern software architecture: the Strategy Pattern. Instead of hardcoding behavior, a class accepts an external object (a "strategy") that encapsulates the varying algorithm.

// Swapping Strategies at Runtime:
# Start with Stripe
service = CheckoutService(gateway=StripeGateway())
service.checkout(order)
# Oh no, Stripe is down! Swap to PayPal seamlessly!
service.gateway = PayPalGateway()
service.checkout(order)

# OrderForge Domain - Concrete Payment Gateways (Milestone 05)
# ==============================================================================

from orderforge.domain.gateway import PaymentGateway


class StripeGateway(PaymentGateway):
    """
    Concrete implementation of the PaymentGateway contract.
    Contains internal state specific to Stripe (secret_key).
    """
    def __init__(self, secret_key: str) -> None:
        self._secret_key = secret_key

    def authenticate(self) -> bool:
        # Specialized authentication logic for Stripe
        return self._secret_key.startswith("sk_live_")

    def process_payment(self, amount: float) -> str:
        # Must obey the interface: Accept float, return str
        if not self.authenticate():
            raise PermissionError("Stripe authentication failed: Invalid live API key.")
        
        # Simulate processing...
        cents = int(amount * 100)
        return f"STRIPE_TXN_{cents}_SUCCESS"


class PayPalGateway(PaymentGateway):
    """
    A second concrete implementation.
    Operates entirely differently internally, but perfectly mimics 
    the outward-facing public API dictated by the base class.
    """
    def __init__(self, client_email: str) -> None:
        self._client_email = client_email

    def authenticate(self) -> bool:
        # Specialized authentication logic for PayPal
        return "@" in self._client_email

    def process_payment(self, amount: float) -> str:
        if not self.authenticate():
            raise PermissionError("PayPal verification failed: Invalid merchant email.")
        
        # Simulate processing...
        return f"PAYPAL_PAYMENT_REF_{abs(hash(self._client_email))}"

# ==============================================================================
# OrderForge Test Suite - Polymorphism Verification (Milestone 05)
# ==============================================================================

import pytest
from orderforge.domain.gateways import StripeGateway, PayPalGateway


class TestPolymorphicGateways:
    """Unit tests asserting both adapters fulfill the abstract contract."""

    def test_stripe_gateway_successful_processing(self):
        stripe = StripeGateway(secret_key="sk_live_12345")
        assert stripe.authenticate() is True
        
        receipt = stripe.process_payment(50.50)
        assert receipt == "STRIPE_TXN_5050_SUCCESS"

    def test_stripe_gateway_authentication_failure(self):
        stripe = StripeGateway(secret_key="sk_test_12345")  # Invalid for production!
        
        with pytest.raises(PermissionError, match=r"Invalid live API key"):
            stripe.process_payment(100.0)

    def test_paypal_gateway_successful_processing(self):
        paypal = PayPalGateway(client_email="shop@orderforge.com")
        assert paypal.authenticate() is True
        
        receipt = paypal.process_payment(25.0)
        assert receipt.startswith("PAYPAL_PAYMENT_REF_")

    def test_dynamic_dispatch_execution(self):
        """Proves that a single function can accept either class transparently."""
        
        def charge_order(gateway, amount):
            # The magic of polymorphism: we don't know or care what type 'gateway' is!
            return gateway.process_payment(amount)

        stripe = StripeGateway("sk_live_999")
        paypal = PayPalGateway("hello@world.com")

        # Dynamic dispatch routes the call perfectly to the distinct implementations
        assert charge_order(stripe, 10.0) == "STRIPE_TXN_1000_SUCCESS"
        assert charge_order(paypal, 20.0).startswith("PAYPAL_")
Warning Track

Beginner Pitfalls & Architectural Anti-Patterns

❌ The `isinstance()` Type Ladder

Writing if isinstance(obj, StripeGateway): ... elif isinstance(obj, PayPalGateway): ... inside your core checkout logic.

Why this destroys architecture: This completely defeats the purpose of OOP! It violates the Open/Closed Principle because every time you add a new payment provider (e.g., Apple Pay), you have to hunt down this if/elif block and modify it. Just call obj.process_payment() and let Python figure it out.

❌ Violating the Liskov Substitution Principle (LSP)

If the base class PaymentGateway says `process_payment(amount)` returns a string, but your new CryptoGateway returns a Dictionary or a Boolean.

Why it crashes systems: The caller expects a string receipt. If you substitute the object and it suddenly returns a Dictionary, the calling code will crash when it tries to run receipt.startswith(). A subclass must always honor the signature and return types of its parent.
